## Executive Summary

**EARLIEST MISSING EVENT FOUND.** At log line 8315 of `exp118_run.log`, the Unity IL2CPP runtime calls NID `XAKDgxcra6k` which resolves to **`arch_init_gc`** — the IL2CPP Garbage Collector architecture initializer. SharpEmu has **NO IMPLEMENTATION** for this NID anywhere in `src/`. It returns `0x80020002` (NOT_FOUND), causing the IL2CPP runtime to immediately invoke `arch_raise_user` (NID `J3edELK4FvM`, also unimplemented) — the IL2CPP abort/exception mechanism. The system then appears to continue (GC scavenger thread gets scheduled, workers spin), but the actual Unity Job System bootstrap path is silently aborted. The bootstrap job that would have signaled semaphore `0x81` is **never submitted**.

**This is the answer to the question every EXP from EXP-127 through EXP-135 has been circling: "Why is the bootstrap job never submitted?"** Answer: because the IL2CPP GC architecture initialization failed silently and aborted the bootstrap path before it reached the job-submission call.

**Root cause ranking:**
1. **Missing HLE primitive `arch_init_gc` (NID `XAKDgxcra6k`)** — **70% confidence**
2. Missing HLE primitive `arch_raise_user` (NID `J3edELK4FvM`) — contributes to #1
3. Missing HLE primitive `powf` (NID `1D0H2KNjshE`) — 5% (only matters if gameplay uses it)
4. Missing HLE primitive `log2f` (NID `hsi9drzHR2k`) — 5%
5. Other unknown — 20%

## Why This Finding Was Missed for 20 EXPs

The trajectory concern raised in EXP-113 ("EXP-089 ≈ EXP-112 — same conclusion with new function names") was correct in spirit but had a subtle effect: after EXP-113, the investigation pivoted AWAY from "missing HLE primitive" hypothesis toward "callback dispatch" / "metadata registration" / "RELA relocation" hypotheses. EXP-115 (consolidated maintainer summary) explicitly framed the problem as "callback-dispatch trigger missing" — which is correct in the abstract but missed the specific primitive (`arch_init_gc`).

EXP-126 confirmed the "no dotnet SDK, cannot rebuild SharpEmu" constraint, which led to static-analysis-only investigations (EXP-127..EXP-135). Static analysis is excellent at finding unreachable code, missing relocations, and coverage gaps — but it CANNOT discover that an unimplemented NID was called at runtime and returned an error code. That information is only in the runtime log.

The runtime log evidence (`arch_init_gc` returning NOT_FOUND at line 8315) was always there. It was missed because:
1. The line is in a `[LOADER][WARN]` block, not an `[ERROR]` block — easy to skim past
2. The NID `XAKDgxcra6k` is opaque — no human-readable name unless you reverse-resolve it via the aerolib names database
3. The diagnostic message at line 8316 (`[DIAG-VERIFY] Import #39000 OK: ?::XAKDgxcra6k`) misleadingly says "OK" — but the OK refers to the diagnostic verification completing, not to the NID resolving successfully. The actual return value is `0xFFFFFFFF80020002` (NOT_FOUND)
4. The 244-line gap between `arch_init_gc` failing (line 8315) and the stall being detected (line 8559) is filled with NID-COUNTS / PIPELINE-COUNTS snapshots that all read zero, creating a wall of noise

**Lesson for future EXPs:** When auditing a runtime log, never trust `[DIAG-VERIFY]` "OK" messages — always cross-check the actual return value. And always reverse-resolve NIDs to human-readable names; the cost is small (one SHA1 computation per NID) and the payoff is large.
