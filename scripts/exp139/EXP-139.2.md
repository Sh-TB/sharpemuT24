## 1. Why Nested CallNativeEntry Fails

.NET 10 throws "Invalid Program: attempted to call a UnmanagedCallersOnly method from managed code" when `CallNativeEntry` (which invokes `delegate* unmanaged[Cdecl]<int>`) is called from a managed context that has already crossed the managed→native boundary.

The chain:
```
CLR Thread: ExecuteEntry → CallNativeEntry (managed→native crossing 1)
  → Guest runs → Import dispatch (native→managed crossing 2)
    → TryCallGuestFunction → ExecuteGuestThreadEntry (managed)
      → RunGuestEntryStub → worker.Run() (managed, signals worker thread)
        → Worker Thread: runs guest stub via native code (no CLR frames)
        → Worker returns to CLR Thread
      → RunGuestEntryStub returns
    → ExecuteGuestThreadEntry returns
  → Import dispatch returns (managed→native crossing 3)
  → Guest continues → next import dispatch (native→managed crossing 4)
    → ... eventually reaches ExecuteEntry → CallNativeEntry again
      → *** CRASH: .NET 10 detects too many managed/native crossings ***
```

The `delegate* unmanaged[Cdecl]<int>` invocation in `CallNativeEntry` is treated as `UnmanagedCallersOnly` by .NET 10. After multiple managed/native transitions (even with the worker thread handling the nested call), the runtime's state tracking breaks.

## 2. Linux vs Windows Execution Path

### Windows Path (working)
```
CLR Thread → ExecuteEntry → CallNativeEntry → guest runs
  → Import dispatch → TryCallGuestFunction → ExecuteGuestThreadEntry
    → RunGuestEntryStub → RentNativeGuestExecutor (returns non-null on Windows)
      → worker.Run() → signals Windows worker thread
      → Worker Thread (raw OS thread, no CLR frames): runs guest stub
      → Worker returns result to CLR Thread
    → RunGuestEntryStub returns
  → Import dispatch returns to guest
  → Guest continues → next import → CallNativeEntry
  → WORKS: Windows CLR handles nested transitions differently
```

### Linux Path (EXP-139.2 attempt)
```
CLR Thread → ExecuteEntry → CallNativeEntry → guest runs
  → Import dispatch → TryCallGuestFunction → ExecuteGuestThreadEntry
    → RunGuestEntryStub → RentNativeGuestExecutor (NOW returns non-null on Linux)
      → worker.Run() → signals POSIX worker thread (sem_post)
      → Worker Thread (pthread, no CLR frames): runs guest stub
      → Worker returns result to CLR Thread (sem_wait)
    → RunGuestEntryStub returns
  → Import dispatch returns to guest
  → Guest continues → next import → CallNativeEntry
  → *** CRASH: .NET 10 on Linux still detects the transition issue ***
```

**Difference:** The Windows CLR (.NET 10 on Windows) tolerates the nested `CallNativeEntry` call after the worker thread returns. The Linux CLR (.NET 10 on Linux) does NOT — it throws "Invalid Program" regardless of whether the nested call used a worker thread.

### Files Changed

| `DirectExecutionBackend.Imports.cs` | Reverted EXP-139.1 skip (re-enabled nested resolver call) |

### POSIX Threading Implementation

- **Thread creation:** `pthread_create` (replaces `CreateThread`)
- **Work synchronization:** `sem_wait`/`sem_post` (replaces `WaitForSingleObject`/`SetEvent`)
- **Thread exit:** `pthread_exit` (replaces `ExitThread`)
- **ABI conversion:** `PosixHostStubs.CreateWin64ToSysVThunk` (replaces direct kernel32 calls)
- **Prologue/epilogue:** Already had POSIX thunk support (Win64→SysV conversion)

### Worker Thread Architecture

```
CLR Thread:
  1. RentNativeGuestExecutor() → returns NativeGuestExecutor
  2. worker.Run(context, ...) → sets _runContext etc.
  3. SignalWorkAvailable() → sem_post(_workSemaphore)
  4. WaitWorkCompleted() → sem_wait(_doneSemaphore) [blocks CLR thread]

Worker Thread (pthread, no CLR frames):
  Loop:
    1. sem_wait(_workSemaphore) [blocks until work available]
    2. Check stop flag → if set, pthread_exit
    3. RunPrologue(executorHandle) → binds ambient, returns entry stub
    4. Call entry stub → guest runs
    5. RunEpilogue(executorHandle, result) → captures result
    6. sem_post(_doneSemaphore) → signal CLR thread
    7. Goto Loop
```

**Evidence:**
```
[THREADMODE] worker_created native_tid=24539 loop=0x00007F36EC014000 tid=24539 managed=4
Fatal error.
Invalid Program: attempted to call a UnmanagedCallersOnly method from managed code.
```

The native worker thread IS created and used. But the .NET 10 runtime on Linux still throws "Invalid Program" when `CallNativeEntry` is called from the outer `ExecuteEntry` after the nested `TryCallGuestFunction` → `RunGuestEntryStub` → `worker.Run()` chain returns.

**Root cause:** The .NET 10 runtime on Linux tracks managed/native transitions differently than Windows. Even though the nested guest execution happens on a separate worker thread (no CLR frames), the CLR thread's transition counter is incremented by the `TryCallGuestFunction` → `ExecuteGuestThreadEntry` → `RunGuestEntryStub` → `worker.Run()` managed call chain. When the outer `ExecuteEntry` → `CallNativeEntry` runs after this chain returns, the runtime detects an invalid state.

## 7. Final Status

# **BLOCKED**

- ✅ Linux NativeGuestExecutor implemented (pthread + semaphores + Win64→SysV thunks)
- ✅ Worker thread created and used (`worker_created native_tid=24539`)
- ✅ Dreaming Sarah Golden Gate: PASS (23/23/260 colors)
- ❌ Yatzi still crashes with "Invalid Program" (.NET 10 Linux limitation)
- ❌ EXP-138 RAX propagation fix: STILL NOT VALIDATED

### What was proven
1. The POSIX infrastructure (`PosixHostStubs`) works correctly for semaphore-based synchronization
2. `pthread_create` successfully creates a worker thread on Linux
3. The worker thread can run guest entry stubs (Dreaming Sarah uses it without issues)
4. The .NET 10 "Invalid Program" crash is NOT caused by `CallNativeEntry` running on the CLR thread — it's caused by the .NET 10 runtime's transition tracking after the managed call chain returns

### What is still blocked
The .NET 10 runtime on Linux throws "Invalid Program" even when the nested call uses a separate worker thread. The issue is in the .NET 10 runtime's managed/native transition state machine, not in the actual native execution.

### Possible next experiments
1. **EXP-139.3:** Move `TryCallGuestFunction` entirely to a separate managed thread (not just the native execution)
2. **EXP-139.4:** Use `ThreadPool.QueueUserWorkItem` to run `TryCallGuestFunction` on a thread pool thread
3. **EXP-139.5:** Restructure `DispatchIl2CppApiLookupSymbol` to defer the resolver call to the main execution loop (avoiding the nested managed call chain)
