## P1: Native il2cpp_resolve_icall Trace Result

### Instrumentation
- INT3 patch installed at `0x804ED8780` (il2cpp_resolve_icall address from old EXP-118 log)
- Original byte: `0xE9` (JMP instruction — this is a JMP thunk, not a function entry)
- Patch installed after `Il2cppUserAssemblies.prx` module_start completes

### Result
```
[ICALL-TRACE] INT3 patch installed at 0x0000000804ED8780 (original byte=0xE9)
```

**0 icall trace entries.** `il2cpp_resolve_icall` was **NEVER CALLED** by the guest.

### Analysis
1. The address `0x804ED8780` starts with `0xE9` (JMP) — it's a thunk, not a function entry
2. The guest never calls this address
3. This means either:
   - (A) The guest uses a different address for `il2cpp_resolve_icall` (the BST resolver returned a different address in the native path)
   - (B) The guest doesn't use `il2cpp_resolve_icall` at all — it uses a different icall resolution mechanism
   - (C) The icall table is pre-linked at compile time (no runtime resolution needed)

### Most likely: (B) or (C)
In Unity IL2CPP, icalls can be resolved in two ways:
1. **Runtime resolution:** `il2cpp_resolve_icall(name)` — looks up icall in a hash table
2. **Compile-time linking:** icall function pointers are embedded directly in the IL2CPP code

If the PS5 IL2CPP build uses compile-time linking (which is common for console builds), `il2cpp_resolve_icall` is never called. The icall function pointers are already in the code — no runtime lookup needed.

**This means the icall resolution hypothesis (EXP-142) is WRONG.** The icalls are NOT resolved at runtime — they're pre-linked. The deadlock is NOT caused by NULL icall resolution.

## P2: Revised Hypothesis

### Previous hypothesis (REJECTED):
```
il2cpp_resolve_icall returns NULL for Job System icalls
→ Schedule_Injected silently fails
→ Bootstrap job never submitted
→ WaitSema(0x81) deadlock
```

### New hypothesis:
The bootstrap job submission code IS in the binary and IS linked correctly. But it's **never executed** because the code path that calls it is skipped or blocked by a different issue.

### Possible causes:
1. **A conditional branch before the bootstrap job submission evaluates wrong** — some earlier HLE call returns a value that causes the guest to skip the bootstrap
2. **An exception or error during Unity initialization** causes the init code to abort early, before reaching the bootstrap job submission
3. **The dispatch loop is entered too early** — the main thread enters the dispatch loop before the bootstrap job submission code runs

### Evidence for hypothesis 3:
From the timeline (EXP-141):
```
Line 2964: sema.create 0x81 (main thread's job queue)
Line 2980: Thread-XXX (GC) scheduled
Line 2981: Main thread IMMEDIATELY blocks on WaitSema(0x81)
```

The main thread creates semaphore 0x81 and IMMEDIATELY blocks on it. There is NO code between semaphore creation and WaitSema(0x81) that could submit a bootstrap job.

This means the bootstrap job submission should happen **BEFORE** the dispatch loop is entered — but it doesn't.

## P3: First Divergence Point

### Expected execution path:
```
Unity Init
  → PlayerLoop setup
    → Register Job System icalls (if runtime resolution)
    → Create worker threads
    → Create semaphores (0x81-0x90)
    → Submit bootstrap job ← THIS IS MISSING
    → Enter dispatch loop
    → WaitSema(0x81)
```

### Actual execution path:
```
Unity Init
  → Create worker threads
  → Create semaphores (0x81-0x90)
  → Enter dispatch loop
  → WaitSema(0x81) ← BLOCKS HERE
```

### First divergence:
The bootstrap job submission step is MISSING between semaphore creation and dispatch loop entry.

### Who should submit the bootstrap job?
The bootstrap job is submitted by the Unity C# code that runs during `PlayerLoop.EarlyUpdate`. This code calls `Schedule_Injected` or `ScheduleBatchedJobs` via the pre-linked icall function pointer.

### Why is it missing?
The C# code that submits the bootstrap job runs inside the IL2CPP runtime. Since `il2cpp_resolve_icall` is never called, the icalls are pre-linked. The pre-linked icall function pointers should work — unless:

1. The function pointers point to the wrong addresses (relocation issue)
2. The C# code that calls them is never reached (initialization abort)
3. The dispatch loop entry happens before the C# code runs (timing issue)
