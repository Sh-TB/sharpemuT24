## 5. Full Exception Stack

### Crash sequence (from log):
```
[RESOLVER-TRACE] Entry #1: rdi=0x0000000801B5A62C name='il2cpp_init' ret=0x0000000000000000
[LOADER][TRACE] posix-signal#1: sig=11 rip=0x0000000804ED9B90 fault=0x0000000804ED9B90 access=8 rsp=0x00006FFFE01FFFC8
Fatal error.
Invalid Program: attempted to call a UnmanagedCallersOnly method from managed code.
```

### Analysis:
1. IL2CPP resolver called for `il2cpp_init`
2. `TryCallGuestFunction` → `ExecuteGuestThreadEntry` → `RunGuestEntryStub` → worker thread
3. Worker thread tries to execute code at `0x804ED9B90` (resolver address)
4. **SIGSEGV** (signal 11) at `rip=0x804ED9B90`, `access=8` (EXECUTE fault)
5. Signal handler tries to re-enter managed code → **"Invalid Program"** error

### Transition point:
- The crash is NOT in `CallNativeEntry` or `delegate* unmanaged` invocation
- The crash is a **SIGSEGV** when the worker thread tries to execute guest code at `0x804ED9B90`
- The "Invalid Program" is a SECONDARY error from the signal handler

## 6. ROOT CAUSE DISCOVERY

### The REAL root cause: PRX files not loaded

**The "Invalid Program" error is NOT the primary crash.** The primary crash is a **SIGSEGV** at the IL2CPP resolver address `0x804ED9B90`, which is inside `Il2cppUserAssemblies.prx`.

**`Il2cppUserAssemblies.prx` was NEVER loaded into guest memory.**

### Evidence:

1. The PRX files are in `/tmp/exp125_games/yatzi/` (root directory):
   - `Il2cppUserAssemblies.prx` (74.7 MB)
   - `libc.prx`, `PS5Util.prx`, etc.

2. SharpEmu expects PRXs in subdirectories:
   - `sce_module/libc.prx`
   - `Media/Modules/Il2cppUserAssemblies.prx`

3. The boot dependency report shows:
   - `sce_module/libc.prx`: MISSING
   - `sce_module/libSceNpCppWebApi.prx`: MISSING
   - `Il2cppUserAssemblies.prx`: not even listed (not expected at root)

4. No PRX loading occurs in the log:
   - No "Starting module" lines for PRXs
   - No "dt_init" lines for PRXs
   - Only eboot.bin is loaded

5. The resolver address `0x804ED9B90` is inside `Il2cppUserAssemblies.prx` (PRX base `0x804CD5000` + offset `0x204B90`). Since the PRX was never loaded, this address is unmapped → SIGSEGV on execute.

### The "Invalid Program" is a red herring:
- The SIGSEGV happens FIRST (worker thread tries to execute unmapped code)
- The signal handler tries to call back into managed code to report the fault
- The signal handler's managed callback triggers the "Invalid Program" error
- The "Invalid Program" masks the real SIGSEGV

### Why EXP-139.1 (skip nested) "worked":
- When nested calls are skipped, the resolver returns 0 immediately
- The guest never tries to execute code at `0x804ED9B90`
- No SIGSEGV → no signal handler → no "Invalid Program"
- But the resolver returns 0 for all symbols → guest crashes later with SIGSEGV from NULL pointer

---

## 7. Decision

### The .NET 10 "Invalid Program" issue is REAL but SECONDARY.

**Primary issue:** PRX files not loaded because they're in the wrong directory path.

**Fix needed:** Create proper directory structure for Yatzi game dump:
```
/tmp/exp125_games/yatzi/
├── eboot.bin
├── sce_module/
│   └── libc.prx
└── Media/
    └── Modules/
        ├── Il2cppUserAssemblies.prx
        ├── PS5Util.prx
        └── ...
```

### Architecture change (EXP-139.3 separate thread): NOT NEEDED

The .NET 10 "Invalid Program" error is caused by the SIGSEGV signal handler, not by the nested `CallNativeEntry` itself. If the PRX is properly loaded and the resolver address is executable, the SIGSEGV won't happen, and the "Invalid Program" won't be triggered.

### Next step:
1. Create proper directory structure for Yatzi
2. Re-run Yatzi with properly loaded PRXs
3. Verify the SIGSEGV at `0x804ED9B90` is resolved
4. If resolved, the "Invalid Program" should also disappear
5. Then validate EXP-138 RAX propagation fix
