### Why the resolver is not called:

When PRXs are NOT loaded (old run):
1. Guest calls `cJ2Y4E-t258` (il2cpp_api_register_symbols) as an import
2. SharpEmu's `DispatchIl2CppApiLookupSymbol` handler intercepts
3. Handler calls `TryCallGuestFunction` to run the real BST resolver
4. Resolver returns function pointers for each `il2cpp_*` API

When PRXs ARE loaded (new run):
1. `Il2cppUserAssemblies.prx` is loaded and `module_start` runs
2. The IL2CPP init path changes — the guest uses a **different initialization mechanism**
3. `cJ2Y4E-t258` is never called as an import
4. The resolver at `0x804ED9B90` is never executed via `TryCallGuestFunction`
5. `il2cpp_*` API function pointers are **NEVER populated**
6. Guest tries to use NULL function pointers → SIGSEGV

## 4. Root Cause Classification

**[x] Missing HLE export** — The IL2CPP API symbols are not being resolved because the resolver dispatch mechanism (`cJ2Y4E-t258` / `r8mvOaWdi28`) is not triggered when PRXs are properly loaded.

**[ ] Resolver incomplete** — The resolver itself works (confirmed in old run: 232 entries, all non-zero returns). But it's not being called.

**[ ] Return value propagation** — EXP-138 RAX propagation is present but cannot be validated because the resolver is never called.

**[ ] IL2CPP initialization state** — The IL2CPP init state is incomplete because the resolver never runs, not because of a state management bug.

**[ ] Other** — N/A

### Hypothesis A: CONFIRMED
NULL dereference caused by unresolved IL2CPP symbol. The resolver is not called → `il2cpp_*` APIs return NULL → guest dereferences NULL+0x98 → SIGSEGV.

### Hypothesis B: REJECTED
Resolver is working but IL2CPP init state is incomplete. The resolver is NOT working — it's never called.

## 5. Next Steps

The key question: **Why is `cJ2Y4E-t258` (il2cpp_api_register_symbols) not called when PRXs are loaded?**

Possible explanations:
1. **The PRX's module_start initializes IL2CPP differently** — when `Il2cppUserAssemblies.prx` is loaded, its `module_start` may call `il2cpp_init` directly (via a function pointer in the PRX), bypassing the import dispatch mechanism.
2. **The eboot's IL2CPP init code detects the PRX is loaded** — and takes a different code path that doesn't call `cJ2Y4E-t258`.
3. **The import dispatch for `cJ2Y4E-t258` is patched differently** — when the PRX is loaded, the import table may be modified to point to the PRX's own implementation instead of SharpEmu's HLE handler.

### Required investigation:
1. Check if `cJ2Y4E-t258` is in the import table but resolved to a PRX address instead of SharpEmu's HLE handler
2. Check if the PRX's `module_start` calls `il2cpp_init` directly
3. Check if the guest's IL2CPP init code path changes when the PRX is loaded
