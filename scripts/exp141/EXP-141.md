| 0x5F | 0x5F (briefly) | 0x5F (signaled once) |
| ... (pattern repeats for 13 worker pairs) | | |
| 0x80 | (never waited) | (never signaled) |
| 0x81 | 0x81 (main thread, blocks forever) | 0x81 (NEVER signaled) |
| 0x82 | (never waited) | (never signaled) |
| 0x83 | 0x83 (Thread-X, blocks forever) | 0x83 (NEVER signaled) |
| 0x84 | (never waited) | 0x84 (NEVER signaled — THIS IS THE MISSING SIGNAL) |

**Critical observation:** Handle 0x84 (ResumeSemaphore) is the missing signal. It should be signaled by Unity's PlayerLoop to resume Thread-X from SuspendSemaphore (0x83). Once Thread-X runs, it would signal 0x81 to wake the main thread.

### 141.7 Count overflow — ⏸ PENDING (low priority)
Test: `SignalSema(id, count)` where `count > maxCount`. Should return error.

SharpEmu's implementation at `KernelSemaphoreCompatExports.cs:377-398` does `semaphore.Count += signalCount` without checking `Count > MaxCount`. This is a latent bug but not the current deadlock cause (no signal calls are being made at all).

### 141.8 Priority wait (FIFO vs priority queue) — ✅ STATIC-COMPLETE
SharpEmu's semaphore implementation uses `Monitor.PulseAll(semaphore.Gate)` which wakes ALL waiters in unspecified order (effectively FIFO on .NET runtime). PS5's `sceKernelWaitSema` is documented as FIFO. SharpEmu's behavior is consistent.

Priority-based semaphore wait is not a PS5 feature (PS5 uses priority for thread scheduling, not for semaphore wakeup order).

## My Additional Considerations (Beyond User's List)

### 141.9 Thread-X is the GC scavenger, not a Job.worker
Per EXP-123, thread 0x804F88AA0 (entry of Thread-X) was identified as the IL2CPP GC scavenger thread, not a Unity Job.worker. This means:
- Thread-X is NOT supposed to dispatch jobs
- Thread-X is supposed to wait for GC suspend/resume signals
- The 0x83 SuspendSemaphore + 0x84 ResumeSemaphore pair is the GC suspend/resume mechanism
- The 0x81 Baselib_SystemSemaphore might be the GC's own work-completion signal

**Implication:** The deadlock may be GC-related, not Job-System-related. If the GC never gets resumed (0x84 never signaled), it never signals 0x81, main thread blocks forever.

### 141.10 Worker entry address 0x800BB06A0 — what does it do?
All 13 AssetGarbageCollectorHelper workers share the same entry address `0x800BB06A0`. Static disassembly of this function would reveal what workers do on entry.

**Hypothesis:** Workers enter, signal their ODD kickoff semaphore (0x5D, 0x5F, etc.) to indicate readiness, then wait on their EVEN work semaphore (0x5C, 0x5E, etc.) for dispatched work.

### 141.11 Thread-X entry address 0x804F88AA0 — what does it do?
Static disassembly would reveal whether this is GC scavenger or Job.worker. EXP-123 claims GC scavenger — needs verification.
