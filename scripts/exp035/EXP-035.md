# EXP-035 — IL2CPP Runtime Dependency Trace & Fix Plan

## Date: 2026-07-30
## Status: COMPLETE — Root cause REVISED (fake heap is NOT the issue)

---

## Executive Summary

The user's hypothesis was that IL2CPP fake heap stubs return 0, causing NULL
execute faults and crashing the game. **This hypothesis is DISPROVEN by evidence.**

The actual root cause is:
- The fake heap is **NEVER INITIALIZED** (zero INT3 stubs hit)
- All 12,000+ NULL executes come from **one specific call site**: `call [rbx+0xf8]` at 0x800AA01CE
- The object at `rbx` is a **native worker-thread task descriptor** (not an IL2CPP managed object)
- The task handler field `[obj+0xf8]` is **0 (never set)** because the C# initialization code hasn't run
- `il2cpp_init` appears to **not have been called yet** when worker threads start spinning

## Task 1 — IL2CPP Runtime Call Tracing

### Implementation
- Created `_Exp035Il2CppCallTracer.cs` (partial class on `DirectExecutionBackend`)
- Replaced fake heap stubs (`mov rax, imm64; ret`) with INT3-only stubs (1 byte)
- Added INT3 handler in `VectoredHandler` that logs: function name, stub address, caller RIP, thread, return value
- Added vtable tracer stub (all 512 vtable slots point to INT3 stub)
- Added return-fake-object INT3 stub

### Result
```
EXP035-CALL count: 0
EXP035 vtable_calls: 0
EXP035 return_fake_object_calls: 0
```

**The fake heap is NEVER USED.** Zero INT3 stubs were hit across the entire run.
The `[IL2CPP][INFO] Fake runtime heap at 0x...` message never appears in the log.

### Why fake heap is not used
During `SetupImportStubs`, all 3,652 imports are resolved via **direct bridge** to real
PRX symbols (`lle_redirects=2516`). The `TryResolveIl2CppApiAddress` fallback to
`GetIl2CppStubForFunction` is never reached because:
1. il2cpp_* symbols are found as runtime symbols in `Il2cppUserAssemblies.prx`
2. OR they go through the HLE resolver path (NID r8mvOaWdi28)
3. The resolver populates the global function table at 0x801ED6320+

The game calls il2cpp_* functions **through the global table**, not through import stubs.

**Category A** fields ([obj+0xf8] and [obj+0x68]) are the boot blockers.

## Task 4 — Source of Bad Return

The NULL at [obj+0xf8] is **NOT** from:
- ❌ A) Fake heap stub (fake heap never initialized)
- ❌ B) Existing HLE implementation returning wrong value
- ❌ C) Missing HLE export
- ❌ D) Real implementation exists but dispatch is broken

The NULL is from **incomplete object initialization**:
- The task descriptor object was allocated (on guest heap at 0x6006D0FF0+)
- Native fields were set: [obj+0x28] = work function (0x800AA0170)
- Managed/C# fields were NOT set: [obj+0xf8], [obj+0x100], [obj+0x68]
- The flag [obj+0x108] was set to 1 (prematurely?)

**The C# initialization code has not run** because `il2cpp_init` has not been called
(or has not completed) when the worker threads start spinning.

Evidence:
- No file I/O for `global-metadata.dat` in the log
- No IL2CPP runtime activity between resolver completion and thread scheduling
- Worker threads are scheduled immediately after resolver completes (line 7665 → 8443)
- The main thread continues scheduling threads but never calls il2cpp_init

## Task 6 — Minimum Required Runtime Support

**No code fix was applied** because the root cause is NOT in the fake heap.

The evidence points to a **synchronization/init-order issue**:
1. Worker threads start before `il2cpp_init` completes
2. The "wait" function (PLT 0x801937720) returns immediately instead of blocking
3. Worker threads spin on uninitialized task descriptors

### Recommended fix (NOT YET IMPLEMENTED):
The PLT entry at 0x801937720 needs to be investigated:
- It's called with args `(wait_object, 1, 0)` — consistent with `scePthreadCondTimedwait`
- But import #268 resolves to `libc:__cxa_atexit` (NID `tsvEmnenz48`)
- This may be an import resolution error (wrong NID mapping)

**Next investigation**: verify that PLT 0x801937720 resolves to the correct function.
If the game expects `scePthreadCondTimedwait` but gets `__cxa_atexit`, the wait
won't block, causing the spin loop.

## Task 10 — Final Deliverable

### 1. First bad "IL2CPP API" found
**There is NO bad IL2CPP API.** The fake heap is never used. The NULL comes from
a native task descriptor field `[obj+0xf8]` that was never initialized.

### 2. Evidence trace
```
Game main thread
    ↓
Resolver (232/232) → populates global IL2CPP function table
    ↓
[NO il2cpp_init call observed]
    ↓
Game schedules 13+ AssetGarbageCollectorHelper threads
    ↓
Each thread enters work function at 0x800AA0170
    ↓
Dispatch loop: decrement refcount → 0 → wait path
    ↓
Wait: call PLT 0x801937720 (resolves to __cxa_atexit — returns immediately)
    ↓
Check flag [obj+0x108] = 1 → call [obj+0xf8] = 0 → NULL execute
    ↓
Recovery → loop (12,000+ times → crash)
```

### 3. Why return value was invalid
`[obj+0xf8]` is 0 because the task handler was never set. The task handler is
likely a C# method pointer that requires `il2cpp_init` to have run. Since
`il2cpp_init` hasn't been called (or hasn't completed), the handler is 0.

### 4. Implementation/fix
**No code fix applied.** The root cause is in the game's initialization sequence,
not in the emulator's fake heap.

### 5. Before/after boot progress
- Before: BOOT_STAGE_4 blocked, 100,000+ NULL executes
- After: BOOT_STAGE_4 blocked, 12,000+ NULL executes (same crash, better traced)

### 6. Next blocker
The next investigation should focus on:
1. **Why is `il2cpp_init` not being called?** Trace calls through the global
   function table at 0x801ED6320+. The game should call `global[0]` (= 0x804ED85D0)
   to invoke `il2cpp_init`.

2. **Why does the wait function return immediately?** Verify that PLT 0x801937720
   resolves to the correct function. If it resolves to `__cxa_atexit` instead of
   `scePthreadCondTimedwait`, that's the bug.

3. **Is the main thread blocked?** Check if the main thread is stuck waiting for
   something (e.g., a semaphore that's never signaled by HLE).
