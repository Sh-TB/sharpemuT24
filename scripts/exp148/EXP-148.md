## Required Debug Thinking Model

### For the dispatch loop function (0x804F6E510):

1. **Who calls this?** — 5 callers, all inside Il2cppUserAssemblies.prx:
   - 0x804F455B0 (called by 0x804ECC640)
   - 0x804F45650 (called by 0x804ECAA80)
   - 0x804FA1D60 (called by 0x804F06070)
   - 0x804FA2130 (called by 0x804F527C0)
   - 0x804FA2160 (called by 0x804F6F520, 0x804F76F90, 0x804F78E30)

2. **Why is it called?** — To process jobs from the worker queue. The dispatch loop atomically decrements work counters and calls WaitSema when no work is available.

3. **When should it be called?** — After PlayerLoop registration submits the first bootstrap job. The dispatch loop should ONLY be entered after work has been submitted.

4. **What executes before it?** — IL2CPP type initialization (38000+ mutex calls), worker queue creation (semaphores 0x7C-0x90), GC thread scheduling.

5. **What executes after it?** — Nothing. The dispatch loop blocks on WaitSema(0x81) and never returns.

6. **What happens if it never executes?** — The main thread would continue past the dispatch loop call site. But it DOES execute, and blocks.

7. **Which register, memory value, branch, or state transition controls reaching it?** — The dispatch loop is reached because the IL2CPP init sequence calls it directly. The MISSING step is the PlayerLoop registration that should happen BEFORE the dispatch loop is entered.

### For the producer function (0x80015DCD0):

1. **Who calls this?** — NOBODY. Zero direct CALL, zero LEA, zero 64-bit data references, zero 32-bit data references (that aren't IL2CPP metadata), zero indirect CALL/JMP through GOT slots.
2. **Why is it called?** — It should increment the work counter [r14+0x90] and signal semaphore 0x81. But it's never called.
3. **When should it be called?** — During PlayerLoop registration, when the first bootstrap job is submitted.
4. **What executes before it?** — Nothing, because it's never reached.
5. **What executes after it?** — Nothing, because it's never reached.
6. **What happens if it never executes?** — The work counter stays at 0, the dispatch loop blocks on WaitSema(0x81) forever. THIS IS EXACTLY WHAT HAPPENS.
7. **Which register, memory value, branch, or state transition controls reaching it?** — The function containing the producer caller (0x8001ED430) has ZERO references. It is dead code or called via a mechanism that doesn't exist in the binary.

**Runtime evidence:**
- The ICALL-TRACE was installed on `il2cpp_resolve_icall` at 0x804ED8780 — ZERO HITS (confirms EXP-143: PS5 uses compile-time linked icalls, il2cpp_resolve_icall is NEVER called)
- No INT3 was placed on `il2cpp_runtime_invoke` itself (we don't know its actual function address from the BST node alone)
- Between mkdir (log line 2927) and dispatch loop entry (log line 2985), ONLY 38000+ scePthreadMutexLock calls occur — NO other HLE imports

### Classification: **hits == 0 (indirect evidence)**

### Conclusion
Managed C# execution likely NEVER STARTS through `il2cpp_runtime_invoke`. However, C# static constructors (.cctor) DO run (evidenced by 38000+ mutex calls during IL2CPP type initialization). This means:
- IL2CPP type initialization runs (.cctor methods are called directly via compile-time linked function pointers)
- But `il2cpp_runtime_invoke` (which invokes arbitrary C# methods at runtime) is NOT called
- The PlayerLoop registration (a specific C# method) is NOT invoked

### Why il2cpp_runtime_invoke is not called
On PS5, `il2cpp_runtime_invoke` is used for reflective invocation (e.g., `MethodInfo.Invoke()`). Unity's bootstrap does NOT use reflection — it calls C# methods directly through compile-time linked function pointers. So `il2cpp_runtime_invoke` being unused is EXPECTED behavior, not a bug.

The REAL question is: which compile-time linked function pointer should call PlayerLoop registration, and why is it not called?

## Step 3: Runtime Dispatch Investigation

### Method
Since static XREF showed zero references to the producer function, I investigated ALL possible runtime dispatch mechanisms:

1. **64-bit little-endian search** for producer function address (0x80015DCD0) in ALL segments of both binaries
2. **32-bit lower-half search** for 0x15DCD0 in data sections
3. **LEA rip-relative** instruction search (48 8D / 4C 8D with mod=0, rm=5)
4. **Indirect CALL/JMP** through GOT-like slots (FF 15 / FF 25 with RIP-relative addressing)
5. **Function pointer table** pattern search (arrays of 64-bit code pointers)
6. **RELA relocation table** entry search (r_addend matching the function address)

### Findings

**Producer function 0x80015DCD0:**
| Search Type | Eboot | PRX |
|-------------|-------|-----|
| 64-bit LE direct | 0 matches | 0 matches |
| 32-bit lower half | 1 match (0x801971DD8) | 0 matches |
| LEA rip-relative | 0 matches | 0 matches |
| Indirect CALL/JMP | 0 matches | 0 matches |

The 32-bit match at 0x801971DD8 is **NOT a function pointer**. The 64-bit value at that address is `0xFF67F5900015DCD0`. Analysis of the surrounding data shows this is an IL2CPP metadata hash table entry:
```
0x801971D98: 0xFF67D6300015DB98
0x801971DA0: 0xFF67DC500015DBB8
0x801971DA8: 0xFF67F0900015DBE0
...
0x801971DD8: 0xFF67F5900015DCD0  ← "match" (lower 32 bits = 0x15DCD0)
0x801971DE0: 0xFF67F6F00015DD00
```
The lower 32 bits are incrementing offsets (0x15DB98, 0x15DBB8, 0x15DBE0, ..., 0x15DCD0, 0x15DD00) — these are IL2CPP metadata token offsets, NOT function pointers. The upper 32 bits are hash/type identifiers.

**Producer caller parent 0x8001ED514:**
| Search Type | Eboot | PRX |
|-------------|-------|-----|
| 64-bit LE direct | 0 matches | 0 matches |
| 32-bit lower half | 0 matches | 1 match (0x807C90914) |
| LEA rip-relative | 0 matches | 0 matches |
| Indirect CALL/JMP | 0 matches | 0 matches |

The 32-bit match at 0x807C90914 is also **NOT a function pointer**. The 64-bit value is `0xFD07DA88001ED514`. Analysis of surrounding data:
```
0x807C9090C: 0x0000003400000000
0x807C90914: 0xFD07DA88001ED514  ← "match" (lower 32 bits = 0x1ED514)
0x807C9091C: 0x100E4100000000F2
0x807C90944: 0x0000002400000000
0x807C9094C: 0xFD07DB50001ED54C  ← next entry (lower 32 = 0x1ED54C)
0x807C90974: 0xFD07DB78001ED574  ← next entry (lower 32 = 0x1ED574)
```
The lower 32 bits increment by 0x38 each entry (0x1ED4DC → 0x1ED514 → 0x1ED54C → 0x1ED574). This is an IL2CPP metadata method definition table, where each entry is a method descriptor. The lower 32 bits are method token offsets, NOT function addresses.

### Conclusion
The producer function (0x80015DCD0) and its entire caller chain (0x8001EDB28, 0x8001ED514, 0x8001ED430) have **ZERO references via ANY dispatch mechanism**:
- No direct CALL
- No LEA
- No GOT slot
- No function pointer table
- No vtable
- No delegate
- The only "matches" are IL2CPP metadata structures that happen to contain the same numeric values as lower 32 bits

**The producer function is DEAD CODE.** It is never called by any mechanism that exists in the binary. The bootstrap job submission uses a DIFFERENT code path that we haven't identified.

## Step 5: Dispatch Loop rax=0xFFFFFFFF Analysis

### Method
- Disassembled the dispatch loop function at 0x804F6E510 (PRX file offset 0x29D510)
- Traced the source of rax=0xFFFFFFFF
- Analyzed the loop structure and counter logic

### Findings

**Dispatch loop function prologue (0x804F6E510):**
```asm
0x804F6E510: push rbp
0x804F6E511: mov rbp, rsp
0x804F6E514: push r15
0x804F6E516: push r14
0x804F6E518: push r13
0x804F6E51A: push r12
0x804F6E51C: push rbx
0x804F6E51D: push rax
0x804F6E51E: mov [rbp-0x2C], rdx
0x804F6E522: mov r13, rsi
0x804F6E525: mov rbx, rdi        ; rbx = first argument (queue structure)
0x804F6E528: call 0x804F88F30    ; get worker state -> rax
0x804F6E52D: mov r14, rax        ; r14 = worker state
```

**First counter check (0x804F6E540):**
```asm
0x804F6E540: mov eax, 0xFFFFFFFF   ; sentinel value for atomic decrement
0x804F6E545: lock xadd [rbx+0x10], eax  ; atomically: old=[rbx+0x10], [rbx+0x10]=old+eax(=-1), eax=old
0x804F6E549: test eax, eax
0x804F6E54B: jle <wait_path>       ; if old value <= 0, no work available
```

**Second counter check (0x804F6E96D — the loop restart):**
```asm
0x804F6E96D: mov eax, 0xFFFFFFFF   ; sentinel for atomic decrement
0x804F6E972: mov r15d, 0xFFFFFFFF  ; backup sentinel
0x804F6E978: lock xadd [r14+0x90], eax  ; atomically decrement [r14+0x90]
0x804F6E980: test eax, eax
0x804F6E982: jle <wait_path_2>     ; if old value <= 0, no work
```

**WaitSema(0x81) call site (0x804F6E9E6):**
```asm
0x804F6E9E6: call 0x804FC1C60      ; WaitSema(0x81) — blocks here
0x804F6E9EB: lock xadd [rbx+0x10], ...  ; after wake, re-check counter
```

### What rax=0xFFFFFFFF means

**rax=0xFFFFFFFF is NOT a return value.** It is the SENTINEL VALUE used by the `lock xadd` instruction to atomically decrement the work counter.

The `lock xadd [mem], reg` instruction:
1. Reads the old value of [mem] into `reg`
2. Writes (old_value + reg) back to [mem]
3. Returns the old value in `reg`

With `eax = 0xFFFFFFFF` (which is -1 in signed 32-bit):
1. Old value of [rbx+0x10] or [r14+0x90] is read into eax
2. Counter is decremented by 1
3. eax now holds the OLD counter value

**The INT3 trace showed:**
- Hit 1: rax=0x0 — This is the value of rax BEFORE the `mov eax, 0xFFFFFFFF` at 0x804F6E96D. The INT3 is at 0x804F6E9E6 (the WaitSema call), which is AFTER the second counter check. The rax=0 means the previous call (to 0x804FC1C60 or similar) returned 0.
- Hit 2: rax=0xFFFFFFFF — This is the value AFTER `mov eax, 0xFFFFFFFF` but BEFORE the WaitSema call. Wait — the INT3 is at the WaitSema call site. The rax value at the INT3 would be the value BEFORE the WaitSema call executes.

Actually, the rax=0xFFFFFFFF in hit 2 is the **sentinel value from `mov eax, 0xFFFFFFFF` at 0x804F6E96D**. This means the INT3 is hit AFTER the sentinel is loaded but BEFORE the WaitSema call. The loop executed the sentinel load, then jumped to the WaitSema call site.

### Is the queue empty because the producer never runs?

**YES.** Both work counters ([rbx+0x10] and [r14+0x90]) are 0 because:
1. The producer function (0x80015DCD0) that increments [r14+0x90] has ZERO callers (confirmed in Step 3)
2. No other code increments [rbx+0x10] (would need separate search, but the dispatch loop blocks on the FIRST check)

### Is an initialization flag missing?

The dispatch loop does NOT check any initialization flag. It simply:
1. Atomically decrements the work counter
2. If counter was <= 0, calls WaitSema to block
3. When woken, re-checks the counter

The loop is CORRECT. The problem is that NO WORK IS EVER SUBMITTED to the queue.

## BONUS: INT3 Handler Bug Discovered

### The SIGILL crash at 0x804F6EA21 is an INT3 handler artifact

**File bytes at 0x804F6EA21:** `FF FF CC CC CC CC CC CC CC CC CC CC CC CC CC 55`

This matches the log exactly: `Code at RIP: FF FF CC CC CC CC CC CC CC CC CC CC CC CC CC 55`

**But the `FF FF` is NOT at the crash address in normal execution.** The crash address 0x804F6EA21 is byte 3 of a `JMP rel32` instruction at 0x804F6EA1E:
```
0x804F6EA1E: E9 4A FF FF FF    ; JMP 0x804F6E96D (5 bytes)
0x804F6EA23: CC CC CC CC...    ; INT3 padding
0x804F6EA30: 55 48 89 E5...    ; next function (push rbp; mov rbp, rsp)
```

The CPU cannot crash at byte 3 of a JMP instruction in normal execution. The crash happens because the INT3 handler corrupts RIP:

1. INT3 is installed at 0x804F6E9E6 (WaitSema call site)
2. Original byte at 0x804F6E9E6 is `E8` (CALL opcode, 5-byte instruction)
3. INT3 replaces `E8` with `CC` (1-byte INT3)
4. When INT3 hits, handler advances RIP to `0x804F6E9E6 + 1 = 0x804F6E9E7`
5. **BUG:** 0x804F6E9E7 is byte 2 of the original CALL instruction (the rel32 displacement)
6. CPU tries to decode from 0x804F6E9E7: `75 32 05 00 F0 44 0F C1...`
7. `75 32` = JNE +0x32 → jumps to 0x804F6EA19
8. At 0x804F6EA19: `E8 C2 32 05 00` = CALL 0x804FC1CE0
9. After CALL returns, executes `E9 4A FF FF FF` = JMP 0x804F6E96D
10. But due to corrupted state, eventually crashes at 0x804F6EA21

**The INT3 handler (DirectExecutionBackend.Exceptions.cs line 209) advances RIP by only 1 byte:**
```csharp
WriteCtxU64Icall(contextRecord, 248, _ripTraceAddress3 + 1);
```

This is correct for 1-byte instructions but **WRONG for multi-byte instructions like CALL (5 bytes)**. The handler should either:
1. Restore the original byte and single-step
2. Or advance RIP by the original instruction length

**Impact:** The yatzi-rip-trace.log crash is an INT3 handler bug, NOT a real game crash. The other logs (without INT3) show the actual behavior: hang at `sema.wait-block handle=0x83`.

2. **Dispatch loop has 5 callers** — All inside Il2cppUserAssemblies.prx, none from eboot.bin
3. **Work counters are both 0** — [rbx+0x10] and [r14+0x90] are never incremented
4. **Producer function is dead code** — ZERO references via any dispatch mechanism (direct, LEA, GOT, vtable, delegate, fp table, metadata)

7. **PlayerLoop registration is skipped** — Between IL2CPP type init and dispatch loop entry, NO HLE imports are called
8. **INT3 handler has a critical bug** — Advances RIP by only 1 byte on multi-byte CALL instructions, causing SIGILL crash
9. **PS5 IL2CPP uses compile-time linked icalls** — il2cpp_resolve_icall is NEVER called (confirms EXP-143)

## Root Cause Status

**Root cause is NOT yet isolated.** The investigation has narrowed it to:

The IL2CPP initialization sequence inside Il2cppUserAssemblies.prx skips the PlayerLoop registration step. This causes:
1. No PlayerLoop callbacks registered
2. No bootstrap job submitted to the worker queue
3. Work counters remain at 0
4. Dispatch loop blocks on WaitSema(0x81) forever
5. GC thread blocks on WaitSema(0x83) forever
6. Complete deadlock

**The specific missing function call** is a C# method (likely `PlayerLoop.Initialization()` or similar) that should be called through a compile-time linked function pointer during IL2CPP init. This function pointer is either:
- NULL (due to the EXP-138 RAX propagation bug — but the fix is applied and needs build verification)
- Pointing to the wrong function (due to incorrect resolver return value)
- Never reached (due to a conditional check failing earlier in the init sequence)

**Confidence ranking:**
1. **EXP-138 RAX propagation bug not yet built/validated** — 40% confidence. The fix is in source (commit 9cef960) but hasn't been built and tested. If the fix resolves the issue, all nested guest callbacks (including the function pointer call to PlayerLoop registration) would work correctly.
2. **IL2CPP init conditional check fails silently** — 30% confidence. Some initialization step returns failure, causing the init sequence to skip PlayerLoop registration and go directly to the dispatch loop.
