# EXP-134 — Find the REAL Producer of Semaphore 0x81

**Date:** 2026-08-04
**Status:** COMPLETE

## Finding

**458 out of 459 SignalSema call sites in eboot.bin were NEVER executed at runtime.** Only 1 SignalSema caller (the worker completion signal at `0x800AA024C`) has its return address in the runtime log. No SignalSema caller that could signal handle 0x81 was ever reached.

**The dispatch loop at `0x804F6E510` is a DIRECT call (not indirect), so there's no function pointer issue.** The main thread enters the dispatch loop as part of normal Unity initialization, which is the expected behavior.

**The dispatch loop has TWO WaitSema calls:**
1. `WaitSema([rbx+8])` at `0x804F6E64F` — the caller's queue semaphore
2. `WaitSema([r14+0x88])` = `WaitSema(0x81)` at `0x804F6E9E6` — the worker queue semaphore

The main thread blocks at the SECOND wait (return address `0x804F6E9EB` in the stall snapshot). The first wait was either satisfied or skipped.

**The root issue is that the 458 SignalSema callers in eboot.bin are never reached because the main thread blocks inside the PRX dispatch loop before returning to eboot code.** This is the same conclusion as EXP-127, now confirmed with runtime RIP coverage data.

```asm

```

### Dispatch loop structure (0x804F6E510)

The function has two WaitSema paths:
1. `0x804F6E64F: call 0x804FC1C60` — WaitSema(`[rbx+8]`) — caller's queue
2. `0x804F6E6B8: call 0x804F6E880` → `0x804F6E9E6: call WaitSema` — WaitSema(`[r14+0x88]` = 0x81) — worker queue

The stall is at path 2 (return address `0x804F6E9EB`).
