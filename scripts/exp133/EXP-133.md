# EXP-133 — Multi-Hypothesis Root Cause Investigation

**Date:** 2026-08-04
**Status:** COMPLETE

## Finding

**The producer function at `0x801028d80` is UNREACHABLE CODE.** It has:
- 0 direct callers (no `call` instructions targeting it)
- 0 LEA references (no code computes its address)
- 0 reads from `0x801cfccb0` (the RELA relocation target — nobody reads this address as a function pointer)

**The RELA entry at `r_offset=0x1cfccb0` patches a DATA location that no code ever reads.** It's a data relocation, not a function pointer table entry. EXP-130's identification of this as "the producer's function pointer" was incorrect.

**The runtime value at `0x801cfccb0` is UNKNOWN** (cannot dump guest memory without dotnet SDK), but it doesn't matter — nobody reads it.

## Next Experiment

**EXP-134 (proposed):**

The investigation needs to shift from "find the producer" to "understand the control flow." The main thread blocks on WaitSema(0x81) inside the PRX dispatch loop at `0x804F6E880`. The 459 SignalSema callers in eboot.bin are never reached because the main thread never returns from the PRX.

**New approach:** Instead of searching for who signals 0x81, investigate WHY the main thread enters the dispatch loop at all. The dispatch loop is called from `0x804F4560E` inside real_init. On real PS5, does real_init enter the dispatch loop, or does it return to the caller which then enters the main loop separately?

**Hypothesis:** real_init should NOT enter the dispatch loop directly. The dispatch loop entry at `0x804F4560E` might be an indirect call through a function pointer that should point to a DIFFERENT function (not the dispatch loop), but due to a missing relocation or incorrect initialization, it points to the dispatch loop instead.
