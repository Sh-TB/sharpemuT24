# EXP-039 — Find PS5 DT_INIT Callback

## Date: 2026-07-30
## Status: COMPLETE — EXP-038 hypothesis REVISED

---

## Executive Summary

EXP-038 hypothesized that SharpEmu passes `rdx=0` to DT_INIT, missing
the module's initialization callback. EXP-039 **DISPROVES** this hypothesis:

1. The PRX's DT_INIT callback (`rdx`) is `base+0` which is **INT3 padding**
2. The PS5 does NOT have a separate module_start callback in metadata
3. The hash table IS allocated and the pointer IS stored correctly
4. The real issue is a **circular dependency**: il2cpp_init needs the hash
   table filled, but the hash table is filled BY il2cpp_init — and il2cpp_init
   crashes before reaching the filling code

---

## Task 1 — PT_SCE_DYNAMIC / ORBI Metadata

### ORBI structure (eboot.bin and PRX)

```
eboot ORBI (0x60 bytes):
  +0x00: 0x60 (size)
  +0x08: "ORBI" magic, version 5
  +0x10: 0x0700003810590001 (packed flags)
  +0x58: 0x311

PRX ORBI (0x20 bytes):
  +0x00: 0x20 (size)
  +0x08: "ORBI" magic, version 5
  +0x10: 0x0700003810590001 (same packed flags)
  +0x18: 0x311
```

**No entry callback field found** in the ORBI structure. The packed value
`0x0700003810590001` appears in both modules but does not resolve to a
valid code address.

### DT_SCE entries
- No `DT_SCE_MODULE_INFO` (0x61000002) in any module
- No `PT_SCE_MODULEPARAM` (0x61000004) in the PRX
- No `PT_SCE_PROCPARAM` (0x61000003) in the PRX
- Both modules have only `PT_SCE_DYNLIBDATA` (0x61000002) with the ORBI struct

### Conclusion
The PS5 does NOT use a separate metadata-specified callback address.
The DT_INIT callback (`rdx`) IS the module's `e_entry` (base + e_entry).
For the PRX, `e_entry=0` → callback = `base+0` = INT3 padding.

## Task 2 — Full ELF Dump

### All three modules

| Module | e_entry | DT_INIT | DT_INIT_ARRAY | DT_SCE_INIT_ARRAY |
|--------|---------|---------|---------------|-------------------|
| eboot.bin | 0x70 | 0x10 | 0x0 (empty) | 0x0 (empty) |
| Il2cppUserAssemblies.prx | 0x0 | 0x10 | 0x0 (empty) | 0x0 (empty) |
| libc.prx | 0x0 | 0x10 | 0x0 (empty) | 0x0 (empty) |

### PRX DT_INIT behavior with rdx

```asm
; PRX DT_INIT at base+0x10
mov r13, rdx          ; save callback
; ... iterate init_array (empty) ...
; ... iterate fini_array ...
test r13, r13         ; if callback != 0
je check_flag
mov rax, r13          ; rax = callback
mov rdi, r15          ; rdi = argc
mov rsi, r14          ; rsi = argv
jmp rax               ; TAIL CALL callback(argc, argv)

check_flag:
cmp [global_flag], 0  ; if flag set
je return_zero
jmp base+0            ; jump to entry (INT3!)

return_zero:
xor eax, eax
ret
```

When `rdx=0` (SharpEmu's current behavior):
- Skips callback path
- Checks global_flag (also 0)
- Returns 0 — **no initialization runs**

When `rdx=base+0` (INT3):
- Tail-calls base+0 → SIGTRAP → crash

**Neither path performs initialization.** The PRX genuinely has no
module_start function.

## Task 3 — Registration Function Table

### List head at 0x801E9DF28

The registration functions (895 of them) each write to the global at
`0x801E9DF28`, building a **linked list** of registration entries.

Each entry has:
- `+0x08`: argument (string pointer)
- `+0x10`: function pointer (the registration function)
- `+0x20`: done flag
- `+0x28`: next pointer

### Iterator at 0x800B8D530

The iterator reads the list head, builds an array, then calls each entry's
function pointer:

```asm
0x800B8D60C: mov rax, [r14 + rbx*8]     ; load entry
0x800B8D610: mov rcx, [rax + 0x10]      ; function pointer
0x800B8D614: test rcx, rcx              ; NULL check
0x800B8D617: je skip
0x800B8D619: cmp byte [rax + 0x20], 0   ; done flag
0x800B8D61D: jne skip
0x800B8D61F: mov rdi, [rax + 8]         ; argument
0x800B8D623: call rcx                   ; CALL registration function
```

### Caller of iterator

The iterator is called from `0x8013EBDF5` — inside the init function
`0x8013EB6B0` (which also calls `il2cpp_init`).

### Registration function behavior

Each registration function (e.g., `0x800454530`):
1. Checks a "done" flag
2. Builds a registration struct
3. Adds itself to the linked list at `0x801E9DF28`
4. Calls `__cxa_atexit` (PLT `tsvEmnenz48`) to register a destructor
5. Returns

**The registration functions do NOT fill the hash table.** They register
destructors and build a linked list.

## Task 4 — Hash Table Write Tracing

### Hash table pointer: 0x801EF7610

**CORRECTION from EXP-037/038**: The correct address is `0x801EF7610`,
not `0x801EE7610` (EXP-037 had a calculation error).

### Hash table writer: 0x8007F90A0

Found via static analysis: `MOV [0x801EF7610], rbx` at `0x8007F928C`.

The writer function:
1. Allocates a hash table structure (call `0x8007e2190` — allocator)
2. Allocates an entries array of 0x7FFF8 bytes (65535 entries)
3. Initializes entries with `0xFFFFFFFF` sentinel
4. Stores the table pointer at `0x801EF7610`

### INT3 tracing result

```
[EXP039-HASH_WRITER-ENTER] #1 caller=0x800B8D625 tid=4 hash_table_before=0x0
```

The writer IS called from the iterator (`0x800B8D625` = return address
after `call rcx` at `0x800B8D623`).

### Hash table state at crash time

```
[EXP038-CRASH_FUNC-STATE] hash_table=0x600103DB0 global=0x0
```

The hash table IS populated (non-zero pointer) but the global at
`0x801E51240` is still NULL.

### Hash table contents

  +0x00: 0x60053E990 (entries array pointer)
  +0x08: 0x7FFF8 (mask/size)

**The hash table is allocated but EMPTY.** All entries are `0xFFFFFFFF`.

## Task 5 — Who Should Fill the Hash Table?

### il2cpp_add_internal_call

The 995 `il2cpp_add_internal_call` calls (from the 949 registration functions)
fill a **DIFFERENT** table — the PRX's internal icall map at `0x8088B4BA8`:

```asm
; il2cpp_add_internal_call at 0x804F677A0
lea rdi, [rip + 0x3bed39c]  ; -> 0x8088B4BA8 (PRX internal map)
mov rsi, r15                 ; string key
call 0x804f67890             ; insert into map
mov [rax], r14               ; store function pointer
```

This is NOT the hash table at `0x801EF7610`.

### Hash table at 0x801EF7610

This table is for **metadata type/method lookup**. It should be filled
by `il2cpp_init`'s internal code (specifically, the metadata registration
step inside `0x804f04ba0` — the real init function).

### The circular dependency

```
il2cpp_init (0x804ED85D0)
  → real_init (0x804f04ba0)
    → ... sets [0x801EA49D8] = callback function ...
    → ... calls callback via [0x801EA49D8] ...
      → returns object with vtable
      → call [rax] = 0x80135DDD0 (crash function)
        → reads [0x801E51240] = 0 ← CRASH (table not filled yet)
    → ... SHOULD fill hash table entries here (never reached) ...
```

il2cpp_init calls the callback **BEFORE** filling the hash table entries.
On a real PS5, this works because the hash table is pre-filled. But with
SharpEmu, the table is empty, causing the crash.

## Task 6 — Evidence Report

### Real callback address
There is **no separate DT_INIT callback address** in the PS5 metadata.
The callback is `e_entry` (base + e_entry). For the PRX, this is `base+0`
which is INT3 padding — meaning "no module_start function."

### How PS5 invokes it
On PS5, `sceKernelLoadStartModule` calls `DT_INIT(argc, argv, module_start)`.
If `module_start` is INT3/0, the DT_INIT returns without calling it.
The real initialization happens via `il2cpp_init` called from the game's
entry point.

### Why SharpEmu misses it
SharpEmu's `rdx=0` is **correct** for this PRX (no module_start).
The issue is NOT the DT_INIT callback.

### Exact issue
The hash table at `0x801EF7610` is allocated but its entries are never
filled. The entries should be filled by `il2cpp_init`'s internal metadata
registration code, but `il2cpp_init` crashes before reaching that code
because it calls a callback that reads an uninitialized global.

### Root cause (revised)
The crash is caused by `il2cpp_init` calling a callback (`0x80135DDD0`)
that requires a metadata global (`0x801E51240`) to be set. The global
is set by a hash lookup that fails because the hash table entries are
empty. The entries are empty because `il2cpp_init` hasn't filled them yet.

This is a **circular dependency within il2cpp_init**:
- il2cpp_init needs the hash table filled to set the global
- The hash table is filled by il2cpp_init itself
- il2cpp_init crashes before filling the table

On a real PS5, this works because the execution order within il2cpp_init
is different, OR because the hash table is pre-filled by a mechanism
that SharpEmu doesn't implement.

## Next Blocker

The circular dependency within `il2cpp_init` must be resolved. Possible
approaches for EXP-040:

1. **Trace il2cpp_init's internal execution**: Add INT3 at key points
   inside `0x804f04ba0` (real init) to find where the hash table should
   be filled and why the callback fires before that.

2. **Check signal recovery interference**: SharpEmu's SIGSEGV recovery
   (setting dest=0 and skipping instruction) might alter the execution
   flow within il2cpp_init, causing the callback to fire at the wrong time.

3. **Compare with real PS5**: The hash table filling might require a
   specific HLE function (like `il2cpp_codegen_register`) that SharpEmu
   doesn't implement. Check if `il2cpp_init` calls an HLE function that
   should populate the table but returns 0 instead.

4. **Pre-fill the hash table**: As a workaround, manually populate the
   hash table entries from the metadata table at `0x1CC0080` before
   il2cpp_init runs.
