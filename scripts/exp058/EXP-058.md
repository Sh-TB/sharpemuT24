# EXP-058 — Runtime Trace Call #7 Consumer Candidate

## Date: 2026-07-31
## Status: COMPLETE — Call #7 entered but returns early; guard function fails due to missing metadata load

---

## Executive Summary

Instrumented call #7 (`0x804F23320`), its loop body (`0x804F238F0`), and array
processor (`0x804F2B4D0`) with INT3 tracers. Ran baseline Yatzi (no EXP-048 stub).

**Key findings:**

1. **Call #7 WAS entered** (`hit#1 caller=0x804F04C63`) with `RDI = 0x8086E9010`
   (CodeReg + 0x10). This confirms real_init calls `0x804F23320`.

2. **Loop body and array processor were NEVER reached** (0 hits each). Call #7
   returned early before executing its main processing loops.

3. **Guard function `0x804F713A0` causes early return**: Call #7 calls
   `0x804F713A0` which calls `0x804F04750`. If `0x804F04750` returns NULL,
   the guard returns 0, and call #7 jumps to `0x804F237CC` (near end, skipping
   all loops).

4. **`0x804F04750` uses the string "Metadata"** and reads the context global
   at `0x808923D88`. This is a **metadata loading function** that tries to
   load IL2CPP metadata from a file or resource.

5. **No `global-metadata.dat` file exists** in the game directory. The metadata
   is likely embedded or loaded from a path that SharpEmu doesn't serve.

6. **Context global `[0x808923D88]` = `0x7F82F4E53840`** — this is a HOST
   address (SharpEmu internal context), not a guest struct. The context
   contains `0xC0DEC0DECAFEBA00` canary values and host pointers.

7. **Hash table remained empty** (0 populated entries) before and after call #7.

**ROOT CAUSE IDENTIFIED**: The metadata loading function `0x804F04750` fails
because SharpEmu doesn't provide the metadata file/resource that the PRX
expects. This causes the guard to return 0, causing call #7 to skip its
hash-table-population loops, leaving all metadata uninitialized.

## Group 2: Context Global and Guard Function

### G2-T9: Context global [0x808923D88]

```
[0x808923D88] = 0x7F82F4E53840  (HOST address, not guest)
```

This is a HOST address (SharpEmu internal context), not a guest struct.
The context contains `0xC0DEC0DECAFEBA00` canary values and host pointers.
This is SharpEmu's internal thread/context state, not an IL2CPP struct.

### G2-T11/12: Guard function chain

Call #7's early return is caused by this chain:

```
call #7 (0x804F23320)
  → calls 0x804F713A0 (guard function)
    → calls 0x804F04750 (metadata loader)
      → uses string "Metadata"
      → reads [0x808923D88] (context global)
      → tries to load metadata
      → RETURNS NULL (metadata not found)
    → test rax, rax; je 0x804F71509  (if NULL, jump to early return)
    → returns 0
  → test al, al; je 0x804F237CC  (if 0, skip all loops)
  → returns without populating hash table
```

### G2-T13: What the metadata loader needs

The function `0x804F04750`:
1. Reads context global `[0x808923D88]`
2. Uses the string `"Metadata"` (at `0x80824FFBE` in PRX rodata)
3. Calls `0x804F86250` (likely file/path resolution)
4. Calls `0x804ECC2F0` (likely file open/read)
5. Returns NULL if the metadata can't be loaded

**The metadata is likely `global-metadata.dat`** — the standard IL2CPP metadata
file. This file does NOT exist in the game directory:

```
/tmp/games/yatzi/
  eboot.bin
  sce_module/libc.prx
  Media/Modules/Il2cppUserAssemblies.prx
  Media/Modules/PS5Util.prx
  (NO global-metadata.dat)
```

### G2-T14: The real gate

The **real single-point fix** is: provide the metadata that `0x804F04750`
expects. This could be:
1. A `global-metadata.dat` file in the game directory
2. An embedded metadata resource that SharpEmu's filesystem HLE doesn't serve
3. An HLE function that returns the metadata from memory

## Group 3: Hash Table Linkage

### G3-T15: Array processor never reached

Since the array processor (`0x804F2B4D0`) was never called, we can't verify
whether it writes to the hash table. But the static analysis from EXP-057
showed it uses 0x38-byte stride (matching hash table entry size).

### G3-T18: Crash function lookup path

The crash function `0x80135DDD0` reads `[0x801E51240]` which is set by the
init function's hash lookup at `0x8013EEFE7`. Since the hash table is empty
(call #7 didn't populate it), the lookup returns NULL, and `[0x801E51240]`
stays NULL, causing the crash.

**The circular dependency is CONFIRMED at a new level:**
1. Call #7 needs metadata file → fails → skips loops → hash table empty
2. Hash table empty → lookup returns NULL → `[0x801E51240]` = NULL
3. Crash function reads NULL → SIGSEGV

## Group 6: Object 0x801EC0C78

### G6: BSS object holding 0x80135DDD0

`[0x801EC0C78] = 0x80135DDD0` (the crash function address). This is in BSS
(no relocations target it). The value is written at runtime by unknown code.

This is a secondary issue — the primary crash is at `[0x801E51240]` = NULL.
The `0x801EC0C78` object is what the metadata lookup returns when the hash
table has a specific (wrong) entry. Since the hash table is empty, the
lookup returns NULL, not `0x801EC0C78`.

## Confirmed Findings

1. **Call #7 (`0x804F23320`) IS entered** during real_init execution
2. **Call #7 returns early** without executing its loops (loop body 0 hits)
3. **Guard function `0x804F713A0`** causes the early return
4. **Metadata loader `0x804F04750`** returns NULL — the guard fails
5. **Metadata loader uses string "Metadata"** — likely loads `global-metadata.dat`
6. **No `global-metadata.dat` file exists** in the game directory
7. **Context global `[0x808923D88]`** is a HOST address (SharpEmu internal)
8. **Hash table remains empty** (0 populated entries) after call #7
9. **No SIGSEGV during call #7** — it returns cleanly (just skips work)
10. **RDI = CodeReg + 0x10** — call #7 receives CodeReg pointer as arg0

## Disproven Hypotheses

1. ❌ Call #7 directly populates the hash table — it skips its loops due to guard
2. ❌ The hash table is populated by a different consumer — no other consumer found
3. ❌ The context global `[0x808923D88]` holds CodeReg/MetaReg pointers — it's a HOST address
4. ❌ The consumer is never called — call #7 IS called, but returns early

## Remaining Unknowns

1. **What exact file/path does `0x804F04750` try to load?** — Need to trace
   `0x804F86250` and `0x804ECC2F0` to find the file path
2. **Is the metadata embedded in eboot.bin or the PRX?** — PS5 may embed it
   differently than standard Unity
3. **Does SharpEmu's filesystem HLE return failure for the metadata file?** —
   Need to trace file I/O calls during `0x804F04750`
4. **Can we provide the metadata manually?** — If we find the expected format,
   we might be able to serve it via HLE
