# EXP-041 — IL2CPP Metadata Registration Debug

## Date: 2026-07-30
## Status: COMPLETE — Root cause refined: initialization ORDER issue

---

## Executive Summary

The crash at `0x80135DE83` is caused by an **initialization order issue**:
`il2cpp_init` (at `0x8013ED057`) is called BEFORE the hash lookup that
sets `0x801E51240` (at `0x8013EEFE7`). The address `0x8013EEFE7` is
**after** `0x8013ED057` in the init function's code.

il2cpp_init's callback (call #7 in real_init) reads `0x801E51240` which
is still NULL because the hash lookup hasn't run yet. On a real PS5, this
works because the callback takes a different code path that doesn't need
`0x801E51240` on the first invocation.

---

## Key Discovery: Initialization Order

```
Init function (0x8013EB6B0):
  0x8013EBDF5: call iterator (allocates hash table)
  ...
  0x8013ED057: call il2cpp_init  ← CALLED FIRST
  ...
  0x8013EEFE0: call hash function  ← CALLED AFTER il2cpp_init
  0x8013EEFE7: call hash lookup
  0x8013EF019: write 0x801E51240  ← SET AFTER il2cpp_init
```

The hash lookup that sets `0x801E51240` is at address `0x8013EEFE7`,
which is **0x1F90 bytes after** the `il2cpp_init` call at `0x8013ED057`.

il2cpp_init crashes before reaching `0x8013EEFE7`, so `0x801E51240`
is never set.

## Task 5 — Callback Global Already Set

```
[EXP041-CALLBACK-GLOBAL] [0x801EA49D8]=0x800C66B40 at hash_writer entry
```

The callback global `[0x801EA49D8]` is **already set** to `0x800C66B40`
before the hash writer runs. This means the callback registration
function (`0x800C66670`) runs early in the boot process, before the
registration iterator.

## Root Cause (Refined)

The crash is NOT caused by the hash table being empty. It's caused by
**initialization order**: il2cpp_init is called before the hash lookup
that sets `0x801E51240`.

On a real PS5, il2cpp_init's callback (call #7) does NOT read
`0x801E51240` on the first invocation. The callback likely checks
a "ready" flag or takes a different path when the metadata isn't
loaded yet. SharpEmu's execution may alter this behavior through:

1. **Signal recovery interference**: SharpEmu's SIGSEGV recovery
   (setting dest=0, skipping instruction) may change the control flow
   within the callback, causing it to reach the `0x801E51240` read
   when it shouldn't

2. **Different callback target**: The function at `[0x808958220]`
   might be different on a real PS5 (set by calls #1-6 which might
   behave differently under SharpEmu)

3. **Missing HLE function**: One of calls #1-6 might call an HLE
   function that should return a specific value, changing the
   callback registration

## Validation

### State at call #7
```
[0x801EA49D8] = 0x800C66B40 (set ✓)
hash_table = 0x600103DB0 (allocated ✓)
hash_entries = all 0xFFFFFFFF (empty — but expected at this point)
global 0x801E51240 = 0x0 (NOT SET — hash lookup is after il2cpp_init)
```

### Key insight
The hash table being empty is EXPECTED at this point — the hash lookups
run AFTER il2cpp_init. The crash is because il2cpp_init's callback
reads a global that hasn't been set yet.

On a real PS5, the callback doesn't read this global on the first call.
SharpEmu's execution path differs, causing the callback to reach the
global read prematurely.

## Next Step (EXP-042)

Investigate why the callback at call #7 reads `0x801E51240` under
SharpEmu but not on a real PS5:

1. **Trace the callback path in detail**: Add INT3 at `0x80134FA00`
   (the eboot.bin callback) and trace which branch it takes

2. **Check signal recovery**: The first SIGSEGV in the callback might
   alter the control flow. Check if the callback would take a different
   path without SIGSEGV recovery

3. **Compare call #7 target**: Check if `0x804D9C620` (the PRX function)
   takes a different branch under SharpEmu vs real PS5

4. **Check "ready" flag**: The callback might check a flag before
   reading `0x801E51240`. If the flag is set prematurely, the callback
   reads the global too early
