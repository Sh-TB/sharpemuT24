# EXP-038 — IL2CPP Static Initialization Investigation

## Date: 2026-07-30
## Status: COMPLETE — Root cause identified, fix proposed

---

## Executive Summary

The crash at `0x80135DE83` is caused by uninitialized IL2CPP metadata globals.
The root cause is that **SharpEmu passes `rdx=0` to the PRX's DT_INIT function**,
but the PS5 DT_INIT expects `rdx` to be a **callback function pointer** that
performs the real module initialization (including IL2CPP metadata registration).

Without the callback, the DT_INIT only iterates the (empty) init_array and returns
without running any registration code. The hash table at `0x801EE7610` stays NULL,
the global at `0x801E51240` stays 0, and il2cpp_init crashes when it calls back
into eboot.bin and reads the NULL global.

---

## Task 1 — PS5 Static Initialization Mechanism

### Finding: DT_INIT callback mechanism

The PS5 DT_INIT function (at `base+0x10` for all modules) has three execution paths:

```asm
; DT_INIT at 0x804CD5010 (Il2cppUserAssemblies.prx)
mov r13, rdx          ; r13 = callback (3rd argument)
mov r14, rsi          ; r14 = argv
mov r15, rdi          ; r15 = argc

; Path A: Iterate init_array (empty for all modules)
lea rbx, [init_array_start]
cmp rbx, [init_array_end]
jae skip_init_array
... call each init_array entry ...

skip_init_array:
; Path B: Iterate fini_array backwards
...

; Path C: Check callback (rdx)
test r13, r13
je path_d             ; if rdx == 0, skip to path D
mov rax, r13
mov rdi, r15           ; pass argc
mov rsi, r14           ; pass argv
jmp rax                ; TAIL CALL to callback(argc, argv)

path_d:
; Path D: Check global flag, potentially jump to entry point
cmp [global_flag], 0
je return_zero
jmp entry_point        ; jump to base+0 (INT3 padding!)

return_zero:
xor eax, eax
ret
```

### SharpEmu's behavior
```csharp
// CpuDispatcher.cs, InitializeModuleInitializerFrame:
context[CpuRegister.Rdi] = 0;  // argc
context[CpuRegister.Rsi] = 0;  // argv
context[CpuRegister.Rdx] = 0;  // callback — SHOULD BE NON-ZERO!
```

SharpEmu passes `rdx=0`, so:
- Path C is skipped (callback never called)
- Path D checks global_flag (also 0) → returns 0
- **No initialization runs**

### What should happen
On a real PS5, `sceKernelLoadStartModule` passes the module's entry callback as `rdx`.
The DT_INIT runs init_array, then tail-calls the callback. The callback performs the
real initialization (IL2CPP metadata registration, hash table population, etc.).

## Task 2 — Full ELF Analysis

### All three modules have identical init structure:

| Module | DT_INIT | DT_INIT_ARRAY | DT_SCE_INIT_ARRAY | Init_array entries |
|--------|---------|---------------|-------------------|--------------------|
| eboot.bin | 0x10 | 0x0 (empty) | 0x0 (empty) | 0 |
| Il2cppUserAssemblies.prx | 0x10 | 0x0 (empty) | 0x0 (empty) | 0 |
| libc.prx | 0x10 | 0x0 (empty) | 0x0 (empty) | 0 |

### PS5-specific segments
- `PT_SCE_DYNAMIC`: Present for eboot.bin (vaddr 0x1D1C3F0, size 0x60)
  - Contains "ORBI" magic + version 5
  - SharpEmu does NOT parse this segment
- `PT_SCE_DYNLIBDATA`: Present for PRXs (size 0x20)
- No `DT_SCE_INIT_ARRAY` entries in any module

### Conclusion
Init_array IS genuinely empty for all modules. The initialization relies on
the DT_INIT callback mechanism (rdx argument), not init_array.

## Task 3 — Registration Function Table

### Metadata table found
- Address: `0x1CC0080`..`0x1CE0000` (128KB, 13,905 RELATIVE relocations)
- Contains function pointers in two categories:
  - Code addresses (`0x8003C6xxx`, `0x80045Bxxx`-`0x80047xxx`) — registration functions
  - Read-only data addresses (`0x801B9xxxx`-`0x801BExxxx`) — string names

### No direct references
- **Zero code references** to the table (no LEA/MOV instructions target it)
- **Zero global pointers** pointing into the table (no relocations outside table)
- The table is accessed **indirectly** at runtime via a callback function

### 995 il2cpp_add_internal_call sites
- Found 949 unique registration functions containing these calls
- All have **zero direct callers**
- They are NOT dead code — they are called by the DT_INIT callback

## Task 4 — Crash Function Caller Traced

### INT3 tracing result
```
[EXP038-CRASH_FUNC-ENTER] #1 caller=0x80134FA7F tid=4
```

### Call chain
```
0x80134FA69: call [0x801EA49D8]     ; indirect call through global
0x80134FA7D: call [rax]             ; virtual method call through returned object
0x80134FA7F: (return address)       ; ← caller of crash function
```

The crash function `0x80135DDD0` is called via **virtual method dispatch**:
1. `call [0x801EA49D8]` calls an IL2CPP API function (set at runtime by il2cpp_init)
2. The API returns an object pointer in `rax`
3. `call [rax]` calls `vtable[0]` = `0x80135DDD0`

### Runtime state at crash
```
hash_table_ptr at 0x801EE7610 = 0x0   (NULL — never populated)
global_ptr at 0x801E51240 = 0x0       (NULL — hash lookup failed)
[0x801EA49D8] = valid function pointer (set by il2cpp_init)
```

il2cpp_init sets SOME globals (like `[0x801EA49D8]`) but NOT the hash table.
The hash table should be populated by the DT_INIT callback, which never runs.

## Task 5 — il2cpp_codegen_register

### Not found
- `il2cpp_codegen_register` is NOT in the PRX's string table (PS5 uses NIDs)
- Not in SharpEmu's Aerolib database
- The PRX has 592 exported symbols, all NID-based

### IL2CPP registration mechanism
The registration is performed by the DT_INIT callback function, which:
1. Creates `Il2CppCodeRegistration` struct (pointing to metadata table at 0x1CC0080)
2. Creates `Il2CppMetadataRegistration` struct
3. Calls an internal PRX function to register them
4. Populates the hash table at `0x801EE7610`

## Task 6 — Proposed Fix

### Root cause
`InitializeModuleInitializerFrame` in `CpuDispatcher.cs` passes `rdx=0`:
```csharp
private static bool InitializeModuleInitializerFrame(CpuContext context)
{
    context[CpuRegister.Rdi] = 0;
    context[CpuRegister.Rsi] = 0;
    context[CpuRegister.Rdx] = 0;  // ← BUG: should be callback function
    ...
}
```

### Fix
Pass the module's entry point as `rdx`. The PS5 `sceKernelLoadStartModule` passes
the module's real entry as the callback. For PRXs with `e_entry=0`, the entry is
`base+0` (which has INT3 padding in the file, but may be overwritten at runtime).

**However**: The PRX entry at `base+0` is INT3 padding. The real callback might be:
1. A function specified by `PT_SCE_DYNAMIC` or Sony module metadata
2. The module's first exported function
3. A function discovered by analyzing the PRX's code

### Validation plan
Before fix:
```
0x801EE7610 = 0x0 (NULL)
0x801E51240 = 0x0 (NULL)
```

After fix:
```
0x801EE7610 = non-zero (hash table populated)
0x801E51240 = valid pointer (metadata global set)
```

## Next Blocker

The fix requires determining what function to pass as `rdx` to DT_INIT.
The PRX's `e_entry=0` and `base+0` has INT3 padding. Options:

1. **Analyze PT_SCE_DYNAMIC**: The "ORBI" structure at `0x1D1C3F0` may contain
   the real entry callback address. SharpEmu doesn't parse this.

2. **Check Sony module metadata**: The `DT_SCE_MODULE_INFO` entry may specify
   the entry function.

3. **Runtime experiment**: Patch `InitializeModuleInitializerFrame` to pass
   `rdx=entryPoint` (base+0) and see if the INT3 is overwritten by a relocation
   before DT_INIT runs.

4. **Skip INT3**: If `base+0` is INT3, pass `base+0x10` (DT_INIT itself) —
   this would cause recursive init but might work if init_array guard prevents
   re-entry.
