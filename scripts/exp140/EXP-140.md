## My Additional Considerations (Beyond User's List)

### 140.5 The "chicken-and-egg" deadlock structure
Per EXP-137 Phase 2B section E:
- Main thread → WaitSema(0x81) — waiting for Thread-X
- Thread-X → WaitSema(0x83 SuspendSemaphore) — waiting for someone to signal 0x84
- Workers → WaitSema(0x5C..0x74) — waiting for main thread to dispatch

**Question:** What code path SHOULD signal `0x84` (ResumeSemaphore) to wake Thread-X? Without 0x84 being signaled, Thread-X never wakes, never signals 0x81, deadlock is permanent.

**Hypothesis:** The `0x84` signal should come from Unity's PlayerLoop `EarlyUpdate` phase, which runs `JobsUtility::ResetJobWorkerCount` → spawns Thread-X → signals `0x84` → Thread-X starts its main loop.

If `ResetJobWorkerCount` is a no-op (because the icall returned NULL due to RAX bug), Thread-X gets spawned but never resumed.

### 140.6 Job queue memory (`[r14+0x90]`) — ✅ STATIC-COMPLETE (from EXP-137 Phase 2C)
**Producer:** `eboot.bin @ 0x159d52`: `inc dword [r14+0x90]` in function `func@0x159cd0` (queue-push operation)

**Consumer:** `Il2cppUserAssemblies.prx @ 0x299978`: `lock xadd dword [r14+0x90], eax` (eax = -1) — atomic decrement in dispatch loop

**Question:** Is the queue actually empty at the moment of WaitSema?
- Static analysis: producer exists but is never called (per EXP-134 RIP coverage, 458/459 SignalSema callers never execute, and the producer is one of them)
- Runtime: counter `[r14+0x90]` is 0 at the moment of WaitSema → queue IS empty → WaitSema correctly blocks
