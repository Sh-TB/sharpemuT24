**Date:** 2026-08-04

## Executive Summary

**Static analysis is exhausted.** After 17 experiments (EXP-118..135), we have conclusively mapped the deadlock chain but cannot identify the specific missing HLE primitive without runtime instrumentation or maintainer expertise.

The deadlock chain is:
```
Main thread enters Unity Job System dispatch loop (0x804F6E510) during real_init
  → Processes existing work items (counter [rbx+0x10] > 0)
  → Calls enqueue function (0x804F6E880) to submit to worker queue
  → Worker queue counter [r14+0x90] = 0 → WaitSema(0x81) → BLOCKS
  → 458 SignalSema callers in eboot never reached
  → Workers block on WaitSema(0x5C-0x74)
  → No GPU init, no frame
```

## Confirmed Facts

1. Semaphore 0x81 created with init=0 (confirmed from log)
2. HLE CreateSema honors initialCount correctly (`Count = initialCount`)
3. First WaitSema ([rbx+8] at 0x804F6E64F) was NEVER called — counter [rbx+0x10] was > 0
4. Main thread processes existing work items, then blocks on WaitSema(0x81) at 0x804F6E9E6
5. 458/459 SignalSema callers in eboot never executed (confirmed by RIP coverage)
6. Zero atomic increments of [reg+0x90] in ANY binary (eboot + all 8 PRX modules)
7. Zero non-atomic writes to [reg+0x90] in eboot's code segment
8. Dispatch loop call is DIRECT (not indirect) — no function pointer issue
9. HLE semaphore implementation is correct
10. RELA table loaded successfully (50,450 relocations)
11. RELATIVE relocation code is correct
12. Producer at 0x801028d80 is unreachable (0 callers, 0 reads from 0x801cfccb0)

### ACTION #3: First WaitSema ([rbx+8])
- **NEVER called** — zero sema.wait events with return address 0x804F6E654
- This means counter [rbx+0x10] was > 0 (the main thread had work items to process)
- The main thread processed existing work, then reached the worker queue wait

### Non-atomic [reg+0x90] writes
- 33 non-atomic writes found, but ALL at addresses 0x100004xxxx+ (outside eboot's code segment)
- These are in other modules (libc.prx etc.), not in eboot
- Zero non-atomic writes to [reg+0x90] in eboot's code segment (0x800000000-0x801938c2c)

## Knowledge Transfer Section

### For maintainers / next investigator:

**The deadlock chain (fully mapped):**
1. Main thread enters Unity Job System dispatch loop during real_init
2. Dispatch loop processes existing work items (counter [rbx+0x10] > 0)
3. Dispatch loop calls enqueue function (0x804F6E880) to submit to worker queue
4. Worker queue counter [r14+0x90] = 0 → main thread blocks on WaitSema(0x81)
5. 458 SignalSema callers in eboot.bin are never reached (main thread doesn't return from PRX)
6. Workers block on WaitSema(0x5C-0x74) — no tasks dispatched
7. No GPU init, no VideoOut, no frame

**What's NOT the bug (exhaustively verified):**
- NOT a vblank/event issue (no vblank imports)
- NOT an HLE semaphore bug (implementation correct)
- NOT a RELA/relocation failure (table loaded, code correct)
- NOT a function pointer corruption (direct call)
- NOT an initial count issue (HLE honors init=0 correctly)
- NOT an unreachable producer function (0x801028d80 is dead code, irrelevant)

**What IS the bug:**
- The worker queue counter [r14+0x90] is NEVER incremented by ANY code in ANY binary
- The main thread blocks on WaitSema(0x81) waiting for work that never arrives
- This is either: (a) a missing HLE primitive that should trigger job submission, (b) a Unity Baselib internal mechanism that doesn't go through PS5 syscalls, or (c) an initialization ordering issue where the job submitter hasn't been created/started yet

**What's needed to proceed:**
1. Runtime instrumentation: log ALL SignalSema calls with handle, caller RIP, thread ID
2. OR: Maintainer expertise on what HLE primitive should trigger Unity's job system
3. OR: Binary patching to inject SignalSema(0x81) and observe if the system progresses
