# EXP-169 RESULT

## Confirmed Execution Chain

```
PS5 loader (SharpEmu) → sets up entry params structure
  ↓
eboot main (0x800000070) → reads [rdi] = argc
  ↓
r14d = argc
  ↓
rdi = r14 (passes argc as first arg to 0x8013FCE40)
  ↓
0x8013FCE40: mov ebx, edi → ebx = argc
  ↓
mov r13d, ebx → r13d = argc
  ↓
cmp r13d, 2; jl → if argc < 2, SKIP init
```

## Meaning of RDI=1

**RDI=1 is argc (argument count).**

SharpEmu's CpuDispatcher.cs sets up an entry parameter structure:
```csharp
// +0x00: uint32 argc = arguments.Count (default: 1, just "eboot.bin")
// +0x04: uint32 padding = 0
// +0x08: uint64 argv[0] = pointer to "eboot.bin" string
```

The eboot main reads `[rdi]` which is `argc`. With default settings, `argc = 1` (only the program name). The function 0x8013FCE40 checks `argc >= 2` to decide whether to perform initialization.

## Root Cause Classification

**Loader parameter mismatch.**

SharpEmu passes `argc = 1` by default. The game's function 0x8013FCE40 expects `argc >= 2` to perform the initialization that sets `[0x801E518C8]`.

With `SHARPEMU_GUEST_ARGS="dummy_arg"`, `argc = 2`, the initialization IS performed, and `[0x801E518C8]` becomes non-NULL.

However, the deadlock at WaitSema(0x81) still occurs even with argc=2, indicating there are additional issues downstream.

## TEST 2: All Callers of 0x8013FCE40

**1 caller:** 0x8000000AA (in function 0x800000010, which is DT_INIT that calls eboot main)

The function has only one caller. There is no alternate path that could pass a different argument.

## TEST 4: Can Init Be Reached Naturally?

**YES** — with `SHARPEMU_GUEST_ARGS="dummy_arg"` (argc=2):
- The `jl` branch at +0x91 is NOT taken
- `[0x801E518C8]` is initialized to 0x00000020000259C0
- But the init write at 0x8013FD08E was STILL NOT HIT — the initialization happened through a DIFFERENT code path (likely 0x80080455E: `mov [0x801E518C8], r15`)

## TEST 5: Downstream Effect

With argc=2:
- Consumer 0x8013EB6B0 entered with `[0x801E518C8] = 0x00000020000259C0` (non-NULL)
- Consumer did NOT early-exit (rbx=0x70, not 0x801E518C8)
- But WaitSema(0x81) deadlock still occurred
- 0 VideoOut calls — PlayerLoop still not reached

This confirms that fixing the argc=1 issue is necessary but NOT sufficient. There are additional blockers downstream.
