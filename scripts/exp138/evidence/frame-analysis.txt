=== Root Cause: Why draws=0 ===
The draws=0 counter is OWNED by VulkanVideoPresenter._perfDrawCount
(VideoOutExports.cs:1484-1488), NOT by HeadlessVideoPresenter.

In headless mode:
1. VideoOutManager.HasGpuSupport() returns false (no /dev/dri, /sys/class/drm, NVIDIA)
2. HeadlessVideoPresenter is selected (no Vulkan render thread starts)
3. AGC DCB parser runs and identifies draw packets (sceAgcDcbDrawIndexOffset, etc.)
4. Parser routes draws to GuestGpu.Current (= VulkanGuestGpuBackend)
5. VulkanGuestGpuBackend has no render thread → draws silently dropped
6. _perfDrawCount never increments → draws=0

The DCB parser DOES run (sceAgcDriverSubmitDcb unconditionally calls ParseSubmittedDcb).
But its output goes only to VulkanVideoPresenter, which is not active in headless mode.
HeadlessVideoPresenter.DrawCall() exists but is NEVER called from anywhere.

=== Is this a regression from EXP-138? ===
NO.

EXP-138 only modified 2 files:
- src/SharpEmu.Core/Cpu/Native/DirectExecutionBackend.cs
- src/SharpEmu.Core/Cpu/Native/DirectExecutionBackend.NativeWorker.cs

EXP-138 did NOT touch any GPU/AGC/VideoOut/HeadlessVideoPresenter files.
The draws=0 and empty framebuffer are pre-existing architectural limitations
of headless mode without a GPU backend.

=== What would be needed to render in this sandbox? ===
1. A Vulkan-capable GPU + working GLFW windowing init (not available)
2. OR a software IGuestGpuBackend implementation (does not exist in codebase)
3. OR wire HeadlessVideoPresenter.AgcDraw() into the AGC DCB parser
   (would make draws= non-zero but still no pixel output)
