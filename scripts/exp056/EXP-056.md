# EXP-056 — IL2CPP Registration Chain Investigation (Hypothesis-Group Test)

## Date: 2026-07-31
## Status: COMPLETE — Major pivot: structs already populated; root cause is missing CONSUMER

---

## Executive Summary

Executed Groups 1, 3, 4, 5 of the EXP-056 master plan. The investigation
**pivoted significantly** based on new evidence:

**Key breakthroughs:**

1. **Both CodeReg and MetaReg are ALREADY FULLY POPULATED via relocations.**
   All pointer fields have R_X86_64_RELATIVE relocations. The structs don't
   need a "registration" function to fill them — they're populated at load
   time. (G5-T38)

2. **The root cause is NOT "structs unfilled" but "CONSUMER function never
   invoked."** The hash table at `0x801EF7610` is supposed to be filled by
   a consumer function that reads CodeReg/MetaReg and inserts entries. This
   consumer is never called. (G5-T39)

3. **The crash function reads a DIFFERENT struct** — `[0x801E51240]` points
   to a runtime metadata object (not CodeReg/MetaReg). The object has fields
   at +0x90 (array ptr), +0x98 (count), +0xA0 (stride). Neither CodeReg nor
   MetaReg has this layout. The hash table lookup is supposed to RETURN
   pointers to these runtime objects. (G5-T41)

4. **MetaReg has 3 CODE pointers at +0x00, +0x08, +0x10** (to `0x805380680`,
   `0x8053806F0`, `0x805380770`). These are likely reverse P/Invoke wrappers
   or icall registration functions — a new finding not in EXP-055. (G1-T6)

5. **PRX DT_INIT execution is MASKED** — SharpEmu calls `0x804CD5010` (ELF
   header bytes), the CPU executes garbage, exception handler recovers with
   RAX=0, and the runtime treats it as "module init succeeded." This masks
   the missing real init. (G2-T11/12)

6. **Wrapper `0x800805AE0` handles BOTH P/Invoke and metadata** — the
   `#dllimport:` prefix is a special case, not the only path. The wrapper
   is the metadata inserter. (G4-T34/35)

## Group 4: Wrapper Verification

### G4-T34/35: Wrapper 0x800805AE0 — metadata-insert or P/Invoke-only?

**CONFIRMED: The wrapper handles BOTH P/Invoke and metadata.**

- The `#dllimport:` prefix check is a SPECIAL CASE for P/Invoke
- Strings WITHOUT the prefix go through the GENERIC metadata insertion path
- The wrapper calls `hash_insert 0x800806940` which writes to the hash table
  at `[0x801EF7610]`
- The hash table is read by `lookup 0x8004BD620` (286 callers — too many for
  P/Invoke only)

**The wrapper IS the metadata inserter.** It's never called because the
missing walker/consumer function that should call it is never invoked.

## Group 5: Runtime Cross-Validation

### G5-T38: Are structs already populated via relocations?

**YES — FULLY POPULATED.** Both CodeReg and MetaReg have all pointer fields
populated via R_X86_64_RELATIVE relocations. SharpEmu's loader applies these
correctly during PRX load. The structs contain valid pointers at runtime.

### G5-T39: PIVOT — Root cause is missing CONSUMER

Since the structs are already populated, the root cause is NOT "structs
unfilled." The root cause is:

**A CONSUMER function that reads CodeReg/MetaReg and populates the hash
table is NEVER INVOKED.**

This consumer function would:
1. Iterate the `types[]` array (13,082 entries at `0x80893E950`)
2. For each `Il2CppType`, get the type name string
3. Call the wrapper `0x800805AE0` with the name string
4. The wrapper inserts the name→type mapping into the hash table

The consumer function exists somewhere in the PRX code (it must, since the
hash table IS populated on real PS5). But it's called indirectly and cannot
be found via static analysis alone.

### G5-T40: Is the hash table a red herring?

**NO — the hash table IS the correct path.** The crash function reads
`[0x801E51240]` which is set by the init function's hash lookup. If the
hash table were populated, the lookup would return a valid pointer, and
`0x801E51240` would be non-NULL.

### G5-T41: What does the crash function actually need?

The crash function `0x80135DDD0` reads:
```asm
mov rax, [rip + 0xaf33cc]    ; rax = [0x801E51240] (metadata global, currently NULL)
mov ecx, [rax + 0x98]         ; count
mov rsi, [rax + 0x90]         ; array pointer
mov rax, [rax + 0xA0]         ; stride
```

So `[0x801E51240]` should point to a struct with:
- `+0x90`: array pointer
- `+0x98`: count
- `+0xA0`: stride

**Neither CodeReg nor MetaReg has this exact layout.** The struct at
`[0x801E51240]` is a RUNTIME METADATA OBJECT — created by the consumer
function when it processes a type. The hash table maps type names to these
runtime objects.

### G5-T42: Hash-table investigation is NOT a red herring

The hash table investigation (EXP-039 through EXP-053) is VALID. The hash
table IS the mechanism for runtime metadata lookup. The issue is that the
hash table is never filled because the consumer function is never called.

## Group 2: Init-Order and Mechanism

### G2-T11/12: PRX DT_INIT execution is MASKED

From the baseline log:
```
[RUNTIME] Starting module Il2cppUserAssemblies.prx: dt_init=0x0000000804CD5010
[DISPATCHER] DispatchEntryCore STARTING...
[LOADER][INFO] ExecuteEntry starting at 0x0000000804CD5010
[LOADER][INFO] Calling guest entry...
[LOADER][INFO] Guest returned: 0
[LOADER][INFO] === Execute END (LastError: null) ===
```

**The PRX DT_INIT at `0x804CD5010` (ELF header bytes) executed and
"returned" 0.** SharpEmu's exception handler recovered from the invalid
execution, and the runtime treated it as a successful module init.

This MASKS the missing real init — SharpEmu proceeds as if the PRX was
properly initialized, but no IL2CPP registration actually happened.

### G2-T15: Eboot entry point

Not yet traced in this experiment. The eboot entry point (`e_entry = 0x70`)
calls the standard libc startup which eventually calls `il2cpp_init`. The
registration consumer should be called BETWEEN PRX load and `il2cpp_init`.

## Confirmed Findings

1. **Il2CppCodeRegistration** at `0x8086E9000` — fully populated via relocations
2. **Il2CppMetadataRegistration** at `0x80885C580` — fully populated via relocations
3. **MetaReg has 3 code pointers** at +0x00, +0x08, +0x10 (new finding)
4. **types[] array** at `0x80893E950` (13,082 entries) — populated
5. **methodPointers[]** at `0x808791958` (103,816 entries) — populated
6. **metadataUsages[]** at `0x8088944F0` (40,310 entries) — populated
7. **Wrapper `0x800805AE0`** handles both P/Invoke and metadata insertion
8. **Hash table at `0x801EF7610`** is the correct runtime metadata lookup mechanism
9. **PRX DT_INIT is invalid** (ELF header bytes) — execution is masked by exception handler
10. **Root cause: missing CONSUMER function** that reads CodeReg/MetaReg and populates hash table

## Disproven Hypotheses

1. ❌ "The structs need a registration function to fill them" — they're already filled via relocations
2. ❌ "The wrapper is P/Invoke-only" — it handles both P/Invoke and metadata
3. ❌ "The hash table is a red herring" — it IS the correct mechanism
4. ❌ "0x801E51240 points to CodeReg or MetaReg" — it points to a runtime metadata object
5. ❌ "PRX DT_INIT crashes visibly" — it's silently recovered (masked)
6. ❌ "EXP-044 found 11 PRX fini_array entries" — PRX has no fini_array (confirmed in EXP-055)
7. ❌ "codeGenModules[] array exists with adjacent CodeReg+MetaReg pointers" — not found

## Remaining Hypotheses

1. **The consumer function is inside `il2cpp_init`** — `il2cpp_init` crashes before reaching it
   (circular dependency: hash table needed before callback, callback needed before hash table fill)
2. **The consumer function is called via an indirect call** — resolved at runtime
3. **The consumer function is in a different module** (libc.prx, PS5Util.prx) — not yet checked
4. **The PS5 loader has a special IL2CPP init mechanism** not implemented by SharpEmu
5. **The consumer function is `il2cpp_codegen_register`** which takes (CodeReg*, MetaReg*) and
   is called explicitly by eboot or by the PRX's real entry point (not DT_INIT)

## Pre-Diagnosis for EXP-057

### Next investigation target: Find the CONSUMER function

The consumer function reads CodeReg/MetaReg and populates the hash table.
Approaches:

1. **Runtime trace `il2cpp_init`'s early code** — Set INT3 at `il2cpp_init`
   entry (`0x804ED85D0`) and single-step the first 200 instructions. Look
   for a call that takes CodeReg (`0x8086E9000`) as an argument.

2. **Search for functions that LEA both CodeReg AND MetaReg** — The consumer
   must access both structs. Search for functions that load both addresses
   (even via different registers).

3. **Check the 3 code pointers in MetaReg** (+0x00, +0x08, +0x10) — These
   might be the consumer function or its dispatchers. Disassemble
   `0x805380680`, `0x8053806F0`, `0x805380770`.

4. **Check PS5Util.prx** — This module might contain the IL2CPP bootstrap
   that calls the consumer. Its DT_INIT is also `imageBase+0x10` (invalid).

5. **Manually call the consumer** — If found, call it from SharpEmu after
   PRX load, before `il2cpp_init`. This would populate the hash table and
   allow `il2cpp_init` to progress.

### Expected outcome

Once the consumer function is identified and called:
- Hash table gets populated with 13,082+ type entries
- Init function's lookups return non-NULL
- `0x801E51240` gets set to a valid runtime metadata object
- Crash function reads valid data at +0x90, +0x98, +0xA0
- `il2cpp_init` progresses past the callback
- BOOT_STAGE_5 reached
