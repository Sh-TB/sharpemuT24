# EXP-042 — IL2CPP Initialization Order / Callback Path Investigation

## Date: 2026-07-30
## Status: COMPLETE — Root cause identified, fix requires PS5 pre-init mechanism

---

## Executive Summary

The crash at `0x80135DE83` is caused by `0x801E51240` being NULL when
il2cpp_init's callback reads it. The hash lookup that sets `0x801E51240`
(at `0x8013EEFE7`) runs AFTER `il2cpp_init` (at `0x8013ED057`).

On a real PS5, `0x801E51240` is set by a **pre-init mechanism** that
runs before the init function. SharpEmu doesn't implement this mechanism.

The metadata lookup at `0x800C66B40` (called via `[0x801EA49D8]`) returns
a valid object because the metadata list IS populated (by registration
functions that run before il2cpp_init). The object's vtable[0] =
`0x80135DDD0` reads `0x801E51240` = 0 → crash.

Setting `0x801E51240` to a non-zero value clears the original crash but
causes new crashes because the dummy value is not the correct metadata struct.

## Task 1 — Full Callback Chain Analysis

### 0x80134FA00 (callback entry, called from PRX real_init)
```
0x80134FA69: call [0x801EA49D8] = 0x800C66B40  ; metadata lookup
0x80134FA7D: call [rax]                         ; call vtable[0] of returned object
0x80134FA7F: (continue — no rax check!)
0x80134FAAE: call 0x801352760                   ; reads more globals → crash
```
**No NULL check on rax before call [rax].** The callback assumes the
metadata lookup always returns a valid object.

### 0x800C66B40 (metadata lookup)
```
mov rax, [0x801EA4E80]  ; lazyInitPtr
mov rcx, [rax+8]        ; linked list head
mov rdx, [rcx+8]        ; first entry
cmp byte [rdx+0x19], 0  ; initialized flag
je search_path           ; flag=0 → search (finds entry)
xor eax, eax            ; flag≠0 → return 0
ret
```
**Runtime trace:** `[rdx+0x19] = 0x00` (NOT initialized) → search path runs →
returns valid object with vtable[0] = `0x80135DDD0`.

### 0x80135DDD0 (crash function)
```
0x80135DE07: cmp byte [rbp+0x10], 0  ; check argument
0x80135DE0B: je skip                  ; if 0, skip (NOT taken — arg="None")
... string processing ...
0x80135DE6D: mov rax, [0x801E51240]   ; READ GLOBAL = 0
0x80135DE83: mov ecx, [rax+0x98]      ; CRASH (rax=0)
```
**No NULL check on rax after loading `0x801E51240`.** The function assumes
the global is always valid.

- **Value:** `0x00` (NOT initialized)
- **Set by:** `0x800C66670` (creates the metadata list with flag=1 at [node+0x18])
- **Current value:** 0 because a registration function inserted a NEW node
  with flag=0, replacing the original node

### Global 0x801E51240
- **Address:** `0x801E51240` (BSS, zero-initialized)
- **Value:** `0x0` (NULL)
- **Set by:** Hash lookup at `0x8013EF019` (AFTER il2cpp_init — never reached)
- **Expected:** Non-zero metadata pointer (set by PS5 pre-init mechanism)

## Task 4 — Callback Object Creation

### 0x800C66670 (sets up [0x801EA49D8])
```
Allocates structure (rbx) → zero-initialized
Allocates linked list node (rax) → self-referencing, [rax+0x18]=0x101
Stores node in [rbx+8]
Stores rbx in [0x801EA4E80] (lazyInitPtr)
Stores 0x800C66B40 in [0x801EA49D8] (metadata lookup function)
```

### Runtime state
```
[0x801EA4E80] = 0x600103EB0 (lazyInitPtr, set early)
[0x801EA49D8] = 0x800C66B40 (metadata lookup, set early)
```

Both are set BEFORE the hash writer runs (confirmed by EXP-041).

### Metadata list populated
The linked list initially has ONE node (self-referencing, flag=1).
Registration functions insert NEW nodes with flag=0.
By the time il2cpp_init runs, the list has entries with flag=0.
The search path finds these entries and returns their function pointers.

On a real PS5, the list should also be populated (same code).
But `0x801E51240` should be non-zero (set by pre-init).

## Task 5 — real_init Ordering

### Call sequence (confirmed)
```
#1-6: Setup, allocation, string operations
#7: call [rax] = 0x804D9C620 (indirect callback → CRASHES)
#8: 0x804F23320 (metadata registration — NEVER REACHED)
#9-17: Various init (NEVER REACHED)
#18-85: 0x804f21d70 x68 (metadata — NEVER REACHED)
```

### Fix attempts

1. **Set flag [rdx+0x19] = 1:** Metadata lookup returns 0. Call [0] →
   SIGSEGV → recovered → callback continues with garbage → crash at
   0x801352760 (reads more NULL globals).

2. **NOP call #7:** Skips one callback path. But 0x80134FA00 is called
   via OTHER indirect paths → crash function still fires 3 times.

3. **Set 0x801E51240 = metadata table entry:** Clears original crash
   but new crash at different location (wrong metadata struct).

## Root Cause

On a real PS5, `0x801E51240` is set by a **pre-init mechanism** that
runs before the init function (`0x8013EB6B0`). This mechanism is likely:

1. **PS5 dynamic linker:** Resolves metadata symbols during module loading
2. **PS5 SDK runtime:** Initializes IL2CPP metadata before user code runs
3. **PRX DT_INIT callback:** Sets up metadata during module initialization

SharpEmu doesn't implement this pre-init mechanism. The hash lookup at
`0x8013EEFE7` would set `0x801E51240`, but it runs AFTER `il2cpp_init`
which crashes first.

### Why the crash doesn't happen on real PS5
- `0x801E51240` is non-zero (set by pre-init)
- The metadata lookup returns a valid object
- The object's vtable[0] (`0x80135DDD0`) reads `0x801E51240` → non-zero
- Function continues normally

### Why it crashes on SharpEmu
- `0x801E51240` is zero (pre-init not implemented)
- The metadata lookup returns a valid object (list is populated)
- The object's vtable[0] reads `0x801E51240` = 0 → SIGSEGV

## Next Step (EXP-043)

Find and implement the PS5 pre-init mechanism that sets `0x801E51240`:

1. **Trace what writes to 0x801E51240:** The hash lookup at `0x8013EF019`
   writes it, but that's AFTER il2cpp_init. Find any OTHER writes.

2. **Check PS5 SDK initialization:** The PS5 SDK might have a runtime
   initialization step that sets metadata globals before user code.

3. **Check PRX DT_INIT:** The PRX's DT_INIT (with rdx callback) might
   set up metadata. Even though rdx=0, the DT_INIT might still do
   something useful.

4. **Pre-populate hash table:** Instead of setting `0x801E51240` directly,
   fill the hash table entries so the hash lookup at `0x8013EEFE7` succeeds.
   This requires understanding the hash table entry format.
