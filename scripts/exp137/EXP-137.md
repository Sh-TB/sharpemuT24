## Summary

1. **NEW CRITICAL BUG (Phase 5):** `TryCallGuestFunction` reads the inner `CpuContext.Rax` as the return value, but the direct-execution thunk never writes host RAX back into `CpuContext.Rax`. This bug affects every nested guest callback that returns a value, not just the IL2CPP resolver.

These three findings **do not invalidate** EXP-136's `arch_init_gc` hypothesis — they reveal that the deadlock has multiple compounding causes, with `TryCallGuestFunction` return-value bug being the deepest and most universal.

## New Findings

### Finding 1 (CRITICAL): `TryCallGuestFunction` return-value propagation bug

**File:** `/home/z/my-project/github-push/sharpemuT24/work/sharpemuT24/src/SharpEmu.Core/Cpu/Native/DirectExecutionBackend.cs`

**Bug location:** Line 3500: `returnValue = context[CpuRegister.Rax];`

**Mechanism:**
- `TryCallGuestFunction` creates a brand-new `CpuContext` for the inner guest function call (Backend.cs:3459-3472). The inner context's `Rax` is initialized to 0 (default from `new ulong[16]` in CpuContext.cs:12).
- The inner context's `Rflags` is hardcoded to `0x202` (Backend.cs:3462) and never updated.
- The native thunk (`ExecuteGuestThreadEntry`, Backend.cs:4866-5071) saves host callee-saved GPRs (RBX/RBP/R12-R15) and non-volatile XMM, but **does NOT push RFLAGS** and **does NOT write host RAX back into `context.Rax`** after the guest returns.
- The thunk's sentinel (Backend.cs:4983-5007) does `add rsp,8; mov rsp,[r10]; restore XMM; pop r15...rbx; ret` — no store to `context[Rax]`.
- When `strcmp` is dispatched as a native intrinsic (Backend.cs:1328-1340), the HLE dispatcher is bypassed entirely, so no side-channel write to `ctx[Rax]` occurs.
- Result: `TryCallGuestFunction` reads `context[Rax]` = 0 (the construction-time default), regardless of what the guest function actually returned.

**Effect on Yatzi:**
- The IL2CPP API lookup (`DispatchIl2CppApiLookupSymbol`, Imports.cs:2252-2426) calls Yatzi's own resolver at `0x804ED9B90` via `TryCallGuestFunction`.
- Yatzi's resolver correctly finds the BST match, executes `mov rax, [r12+0x28]` to load the function pointer, and `ret`s.
- SharpEmu throws away that RAX, returning 0 to the outer guest instead.
- This is the **EXP-026 "232 NULL returns" root cause** that has been unresolved since EXP-026.

**Why this matters for the deadlock:**
- If `il2cpp_resolve_icall` had returned a real function pointer, Yatzi could have used it to register Unity Job System icalls (`Schedule_Injected`, `ScheduleBatchedJobs`, etc.).
- Without those icalls, the C# bootstrap code's `JobHandle.Schedule()` call silently no-ops.
- The bootstrap job that should signal semaphore 0x81 is never submitted.
- Deadlock.

### Finding 3: EXP-135 overturned — producer `inc [r14+0x90]` EXISTS in eboot.bin

**Previous conclusion (EXP-135):** "`[r14+0x90]` is never incremented by any binary code; either missing HLE primitive, Unity Baselib internal mechanism, or init ordering."

**New evidence (EXP-137 Phase 2C):**
- `eboot.bin @ 0x159d52`: `inc dword [r14+0x90]` — **producer increment exists**, in function `func@0x159cd0`.
- The containing function performs a queue-push operation:
  ```asm
  mov  ecx, 0x7fffffff
  and  ecx, dword ptr [r14 + 0x94]     ; capacity (masked to 31 bits)
  mov  eax, dword ptr [r14 + 0x90]     ; current count
  cmp  ecx, eax                         ; if count < capacity
  jbe  .full
  mov  rcx, qword ptr [r14 + 0x88]     ; buffer pointer
  mov  qword ptr [rcx + rax*8], rbx    ; store element (8 bytes each)
  inc  dword ptr [r14 + 0x90]          ; ← PRODUCER INCREMENT (NON-ATOMIC)
  ```
- Structure layout (`+0x88`=buffer, `+0x90`=count dword, `+0x94`=capacity dword) matches what a worker-queue would use.
- EXP-135 most likely only scanned the 8 PRX modules and missed eboot.bin.

**Additional finding (atomicity mismatch):**
- Consumer (Il2cppUserAssemblies.prx @ 0x299978): `lock xadd dword [r14+0x90], eax` with `eax = -1` (atomic decrement).
- Producer (eboot.bin @ 0x159d52): `inc dword [r14+0x90]` (non-atomic increment).
- On real PS5 this works because the producer runs single-threaded and x86 TSO ensures visibility. Under SharpEmu's emulation, this *may* be a memory-ordering issue — but more likely the producer is simply never called because the C# `JobHandle.Schedule()` call that should invoke it is a no-op (due to Finding 1).

## Updated Investigation Status

**Combined EXP-136 + EXP-137 root-cause picture:**

The Yatzi deadlock has **multiple compounding causes**, in order of depth:

1. **Deepest bug:** `TryCallGuestFunction` return-value propagation (EXP-137 Phase 5). Affects every nested guest callback. Causes the EXP-026 "232 NULL returns" symptom. If fixed, may cascade-fix many downstream issues.

2. **Missing HLE primitive:** `arch_init_gc` (EXP-136). Returns NOT_FOUND, triggers IL2CPP abort cascade via `arch_raise_user`. Independent of #1 — needs its own fix even if #1 is fixed.

3. **Missing Unity Job System icalls:** `Schedule_Injected`, `ScheduleBatchedJobs`, `ResetJobWorkerCount` (EXP-137 Phase 4). Downstream of #1 (icalls would be registered if `il2cpp_add_internal_call` worked, which depends on #1) but may also need direct HLE implementation if Yatzi's own init code doesn't register them.

4. **Producer unreachable:** `inc [r14+0x90]` at `eboot.bin @ 0x159d52` exists but is never called (EXP-137 Phase 2C, EXP-134). Downstream of #1, #2, #3 — if the C# `JobHandle.Schedule()` call worked, it would invoke this producer.
