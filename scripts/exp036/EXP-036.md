# EXP-036 — IL2CPP Initialization Order & Threading Import Investigation

## Date: 2026-07-30
## Status: COMPLETE — Root cause FOUND and FIX VERIFIED

---

## Executive Summary

EXP-035 suspected the IL2CPP fake heap or uninitialized task descriptors.
EXP-036 DISPROVED that and found the **actual root cause**:

**`SHARPEMU_SEMA_FAST_PATH=1` causes `sceKernelWaitSema` to return immediately
instead of blocking, which makes worker threads spin in a tight loop calling
NULL function pointers before `il2cpp_init` has a chance to run.**

With `SHARPEMU_SEMA_FAST_PATH=0`, `il2cpp_init` IS called, the NULL execute
loop is **completely eliminated** (0 vs 12,000+), and the game progresses
to a new crash deeper inside il2cpp_init's metadata loading.

---

## Task 1 — Verify il2cpp_init execution

### Implementation
- Patched the first byte of `il2cpp_init` at `0x804ED85D0` with INT3
- Added `Exp036TryHandleIl2cppInitInt3` handler in `VectoredHandler`
- On ENTER: log caller RIP, thread, arguments; restore original byte; re-execute

### Result

**With `SHARPEMU_SEMA_FAST_PATH=1` (EXP-035 config):**
```
[EXP036-PATCH] il2cpp_init at 0x804ED85D0 patched with INT3 (original byte=0x55)
```
**il2cpp_init was NEVER called.** Zero ENTER traces. The INT3 was placed but
never triggered because the main thread was stuck scheduling workers and
the workers were spinning.

**With `SHARPEMU_SEMA_FAST_PATH=0` (EXP-036 fix):**
```
[EXP036-IL2CPP_INIT-ENTER] #1 caller=0x00000008013ED05D tid=4
    rdi=0x0000000801BBD6A7 rsi=0x0000000801B1BBB5 rdx=0x0000000000000001
    rsp=0x00006FFFF01FBA98
```
**il2cpp_init WAS called** from `0x8013ED05D` on the main thread (tid=4).

### Answer
**Yes, real `il2cpp_init` executes** — but ONLY when `SHARPEMU_SEMA_FAST_PATH=0`.

## Task 2 — Verify initialization order

### Timeline (with `SHARPEMU_SEMA_FAST_PATH=0`):

```
1. Resolver completed (232/232)                              [line 7664]
2. Global IL2CPP function table populated                   [line 7666]
3. il2cpp_init patched with INT3                             [line 7675]
4. AssetGarbageCollectorHelper threads scheduled (13)       [line 8443]
5. il2cpp_init CALLED from 0x8013ED05D                      [line ~8500]
6. Job.worker 0-12 threads scheduled                         [line ~8505]
7. Background Job.worker 0-1 threads scheduled               [line ~8520]
8. Crash inside il2cpp_init at 0x80135DE83                  [line ~8500]
```

### Where [obj+0xf8] should be written

The task descriptor's `[obj+0xf8]` (task handler) is set by the code that
**submits a task** to the worker pool. In the disassembly:

- Worker pool init at `0x800A9FA20` creates task descriptors
- `0x800A9FAED: mov byte [rbx+0x108], 1` — sets "ready" flag
- `0x800A9FBD4: mov [rbx+0x28], rcx` — sets work function (0x800AA0170)
- `[rbx+0xf8]` is set LATER by task submission code (not in the init path)

With `SHARPEMU_SEMA_FAST_PATH=1`, the workers spin before any tasks are
submitted, so `[obj+0xf8]` is still 0 when they call it.

With `SHARPEMU_SEMA_FAST_PATH=0`, the workers block on `sceKernelWaitSema`,
allowing the main thread to call `il2cpp_init` and submit real tasks.

## Task 3 — Audit PLT 0x801937720

### Finding: The log was MISLEADING

The EXP-035 log showed:
```
[LOADER][TRACE] Import#268: libc:__cxa_atexit (tsvEmnenz48)
```

This made it look like PLT 0x801937720 resolved to `__cxa_atexit`. But this
was import #268 of **libc.prx**, NOT eboot.bin.

### Actual resolution

The PLT at `0x801937720` has `push 0x10c` (import index 268 in eboot.bin's
JmpRel table). By reading the ELF symbol table directly:

```
JmpRel[268] → symbol #273
symbol #273 → st_name=4353 → string "Zxa0VhQVTsk#k#N"
ExtractNid() strips "#k#N" → NID = "Zxa0VhQVTsk"
```

NID `Zxa0VhQVTsk` maps to **`sceKernelWaitSema`** (in
`KernelSemaphoreCompatExports.cs` line 94-95).

### Verification

The EXP-036 sync trace confirmed:
```
[EXP036-SYNC] #1 func='sceKernelWaitSema' caller=0x0000000800A9FC25 tid=4
    a1=0x000000000000005D a2=0x0000000000000001 a3=0x0000000000000000 ret=0
```

The call signature `sceKernelWaitSema(handle, needCount=1, timeout=0)` matches
the disassembly at `0x800AA0202: call 0x801937720`.

### Conclusion

**The import mapping is CORRECT.** PLT 0x801937720 → `sceKernelWaitSema`.
The EXP-035 log entry for "Import#268" was from a different module (libc.prx).

## Task 4 — Audit synchronization HLE

### Implementation
- Added `_Exp036SyncTrace` static class in SharpEmu.Libs
- Added `Exp036RecordSyncCall` in DirectExecutionBackend (sets callback via
  `_Exp036SyncTrace.SetRecorder`)
- Patched `KernelWaitSema` to record every call (function, caller, tid, args, ret)

### Result (with `SHARPEMU_SEMA_FAST_PATH=1`)

```
[EXP036-SYNC] #1  sceKernelWaitSema caller=0x800A9FC25 tid=4 a1=0x5D ... ret=0
[EXP036-SYNC] #2  sceKernelWaitSema caller=0x800A9FC25 tid=4 a1=0x5F ... ret=0
[EXP036-SYNC] #3  sceKernelWaitSema caller=0x800AA0207 tid=26 a1=0x5C ... ret=0
[EXP036-SYNC] #4  sceKernelWaitSema caller=0x800AA0207 tid=26 a1=0x5C ... ret=0
... (thousands of calls, all returning 0 immediately)
```

### Root cause identified

The `SHARPEMU_SEMA_FAST_PATH=1` environment variable makes `sceKernelWaitSema`
return `ORBIS_GEN2_OK` (0) immediately without blocking:

```csharp
// KernelSemaphoreCompatExports.cs, KernelWaitSema method:
if (string.Equals(Environment.GetEnvironmentVariable("SHARPEMU_SEMA_FAST_PATH"), "1", ...))
{
    return SetReturn(ctx, OrbisGen2Result.ORBIS_GEN2_OK);  // ← returns immediately!
}
```

This was intended as an "emergency bypass" for games stuck in semaphore waits,
but for Yatzi it **prevents** the game from initializing properly:

1. Main thread creates worker threads and per-worker semaphores
2. Workers call `sceKernelWaitSema` to wait for tasks
3. With FAST_PATH=1, WaitSema returns immediately (no task available)
4. Workers check `[obj+0x108]` flag (set to 1) → call `[obj+0xf8]` (NULL) → crash
5. Main thread never gets to call `il2cpp_init` because it's also spinning
   on its own semaphores

### Fix

**Set `SHARPEMU_SEMA_FAST_PATH=0`** (or unset it) to enable real semaphore
blocking. This allows workers to sleep while the main thread runs `il2cpp_init`.

## Task 5 — Trace skipped il2cpp_init path

### Finding

`il2cpp_init` was **NOT skipped** — it was **starved**.

With `SHARPEMU_SEMA_FAST_PATH=1`, the main thread (tid=4) was caught in a
loop of:
- Create semaphore
- Schedule worker thread
- Wait on semaphore (returns immediately)
- Create next semaphore
- ...

The main thread never reached the `call il2cpp_init` instruction because it
was busy spinning on its own semaphores alongside the workers.

With `SHARPEMU_SEMA_FAST_PATH=0`, the main thread's `sceKernelWaitSema` calls
block properly, the scheduler switches to the main thread's `il2cpp_init`
call, and the game progresses.

### Who calls il2cpp_init?

The caller is at `0x8013ED05D`. This is in eboot.bin's C# runtime startup
code that:
1. Resolves all IL2CPP API symbols (via the resolver at 0x804ED9B90)
2. Calls `il2cpp_init` (global[0] = 0x804ED85D0)
3. Calls `il2cpp_set_config_dir`, `il2cpp_set_data_dir`, etc.

## Task 6 — Validate task descriptor fix

### N/A

The task descriptor was **not broken**. The fields `[obj+0xf8]` and `[obj+0x68]`
are intentionally NULL at initialization time — they get populated when a task
is submitted to the worker. The crash occurred because workers were spinning
before any tasks were submitted, due to the FAST_PATH semaphore bug.

With `SHARPEMU_SEMA_FAST_PATH=0`, workers block properly and the task
descriptors are populated by the main thread before workers wake up.

## Remaining Blocker

The new crash is at `0x80135DE83: mov ecx, [rax+0x98]` where `rax=0`.

This is inside a function at `0x80135DDD0` that:
1. Loads a global pointer from `[rip + 0xaf33cc]` (address 0x80135DE6D)
2. The global pointer is NULL
3. Tries to read `[rax+0x98]` → SIGSEGV

This is likely an IL2CPP metadata global that hasn't been initialized.
The function appears to be part of IL2CPP's string/metadata handling
(it builds a string-like object from the global state).

### Next investigation (EXP-037)
1. Identify what global variable is at `[rip + 0xaf33cc]` (address ~0x802331C40)
2. Determine which IL2CPP API should initialize it
3. Check if `il2cpp_init` is supposed to set it, or if an earlier API call
   (like `il2cpp_set_data_dir` or `il2cpp_domain_get`) should have run first
4. The crash happens AFTER `il2cpp_init` ENTER but the function hasn't
   returned yet — so `il2cpp_init` itself calls this code path
