# EXP-045 — Find Missing IL2CPP Pre-Initialization Path

## Date: 2026-07-30
## Status: COMPLETE — eboot fini_array found (20 entries), but not the root cause

---

## Executive Summary

Discovered eboot.bin has a **fini_array with 20+ entries** (RELATIVE
relocations, all non-zero at runtime). These entries include registration
functions (e.g., `0x800454530`). The eboot DT_INIT (`0x800000010`) runs
BOTH init_array AND fini_array at startup.

However, **skipping the fini_array did NOT fix the crash** — the
registration list `[0x801E9DF28]` is still populated (non-zero =
`0x801EF3150`) even without the fini_array. The list is populated by
an **unknown mechanism** within the init function's first-time path
(29 calls between `0x8013EB6E7` and `0x8013EBDFA`).

The circular dependency remains unresolved.

---

## Task 1 — eboot.bin Fini_array

### Discovery
eboot DT_INIT (`0x800000010`) iterates a fini_array at `0x801D1C3D0`
backwards. Found **20+ entries** with RELATIVE relocations:

```
[1] 0x800454430    [2] 0x800454470    [3] 0x8004544B0
[4] 0x8004544F0    [5] 0x800454530 (registration function!)
[6] 0x8007F1880    [7] 0x800969BD0    [8] 0x8009C27B0
... (20 total)
```

### Test: Skip fini_array
Patched eboot DT_INIT to JMP past fini_array iteration (at `0x800000045`).
**Result:** Registration list `[0x801E9DF28]` still non-zero (`0x801EF3150`).
The crash still occurs (3 crash function calls, 226 SIGSEGVs).

### Conclusion
The fini_array is NOT the (sole) mechanism that populates the registration
list. Another mechanism within the init function's first-time path also
populates it.

## Task 3 — Init Function First-Time Path

### Range
`0x8013EB6E7` to `0x8013EBDFA` (1811 bytes, 29 calls)

### Key calls
```
0x8013EB6E7: call 0x801937500  (PLT)
0x8013EB6FA: call 0x8007e3ba0  (allocator)
0x8013EB87F: call 0x8007e91c0
0x8013EBB2D: call 0x800ba4ff0
0x8013EBD7E: call 0x800b8d3b0  (once-init, calls 0x8007EB180)
0x8013EBDE5: call 0x800ba8ce0
0x8013EBDF5: call 0x800b8d530  (iterator)
```

### Writes to target globals
**0 writes** to `[0x801E9DF28]`, `[0x801E51240]`, or `[0x801EF7610]`
in the first-time path. The writes are indirect (through called functions).

### Once-init callback (0x8007EB180)
- Initializes a 0x3878-byte structure at `[0x801E50E40]`
- `[0x801E51240]` = `[0x801E50E40 + 0x400]` — a FIELD within this structure
- The once-init ZEROS this field (that's why `0x801E51240` is 0)
- The hash lookup at `0x8013EF019` writes to this field AFTER il2cpp_init

### Registration list population
The list `[0x801E9DF28]` is populated by registration functions called
INDIRECTLY from the first-time path. None of the 29 calls directly write
to `[0x801E9DF28]`. The registration functions have zero direct callers
and are called via function pointer tables or iterators.

## Task 4 — List Head State

### With fini_array skipped
```
[EXP045-LIST_HEAD] [0x801E9DF28] = 0x801EF3150 at hash_writer entry
```
The list is **still populated** despite skipping the fini_array.

### Implication
The registration list is populated by a mechanism that does NOT depend
on the fini_array. The most likely candidate is one of the 29 calls in
the first-time path, which calls an initialization function that
indirectly triggers registration functions.

---

## Key Findings

1. **eboot has 20 fini_array entries** (RELATIVE relocations, all non-zero)
2. **fini_array includes registration functions** (e.g., `0x800454530`)
3. **Skipping fini_array doesn't fix the crash** — list still populated
4. **`0x801E51240` is a field at offset 0x400** within a 0x3878-byte
   structure at `[0x801E50E40]`, initialized by the once-init callback
5. **The once-init zeros `0x801E51240`** — it starts as 0 on BOTH platforms
6. **The hash lookup at `0x8013EF019` sets `0x801E51240`** AFTER il2cpp_init
7. **On real PS5, `0x801E51240` is ALSO 0** during il2cpp_init — the callback
   must take a different path on real PS5

---

## Root Cause (Revised)

The crash is NOT caused by 0x801E51240 being NULL (it's NULL on both
platforms). The crash is caused by the **callback taking the wrong path**
on SharpEmu. On a real PS5, the callback at call #7 doesn't reach
`0x80135DDD0` (which reads `0x801E51240`). On SharpEmu, it does.

The difference is likely in:
1. **The metadata lookup (`0x800C66B40`)** returning different results
2. **The metadata list contents** being different
3. **Signal recovery** changing the control flow after a NULL call
