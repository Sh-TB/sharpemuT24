## Unknown

1. **What mechanism does the game use to signal the job queue?** Since the game doesn't use vblank events, event flags, or condition variables for this purpose, the signal must come from a different source. Possibilities:
   - A **timer callback** (sceKernelSetTimer or similar) — but no timer imports were found
   - An **internal IL2CPP/Unity mechanism** that doesn't go through PS5 syscalls — the producer might be entirely within IL2CPP's managed code, using a different code path that SharpEmu doesn't execute
   - A **thread that should be created but isn't** — the job submitter thread may not be created because an earlier initialization step failed silently
   - The **main thread itself** should submit the first job BEFORE entering the dispatch loop — but the dispatch loop blocks immediately, suggesting the "first job" submission code was never reached

2. **Would artificial SignalSema(0x81) allow the main thread to progress?** Cannot test without rebuilding SharpEmu. This remains the most promising next experiment if a build environment is available.

3. **Is the job queue producer in the IL2CPP managed code (C#) rather than native code?** If the producer is a C# method compiled by IL2CPP, it would be in Il2cppUserAssemblies.prx but might use a different calling convention or code pattern that my static search didn't find. The search for `lock xadd/inc/add [reg+0x90]` only found the consumer decrement — but the producer might use a different instruction pattern (e.g., `lock xadd` with a positive value loaded from a variable, or a non-locked `mov` followed by a SignalSema call).

4. **Is there a Baselib/Unity internal mechanism that doesn't use PS5 semaphores?** Unity's Baselib might use a different synchronization primitive internally (e.g., futex, spinlock, or a custom event mechanism) that doesn't go through `sceKernelSignalSema`. If so, the producer might exist in the PRX but use a different signaling path.
