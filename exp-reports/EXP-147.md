## Step 1: il2cpp_runtime_invoke

### Old run evidence (EXP-118, no PRXs):
- BST node #64 found: `il2cpp_runtime_invoke` at `0x2000028720`
- Resolver Entry #168: `il2cpp_runtime_invoke` → `ret=0x0` (NULL — RAX propagation bug)
- The function WAS in the BST, but the resolver returned 0

### New run (EXP-139.4+, with PRXs):
- The resolver is direct-bridged — runs natively
- Cannot trace return values
- But: the BST node exists (confirmed in BST-WALK)
- The resolver SHOULD return the correct function pointer

### Key question:
Is `il2cpp_runtime_invoke` actually CALLED by the guest after being resolved?

### Evidence:
- `il2cpp_runtime_invoke` is a C API function that the IL2CPP runtime calls to invoke C# methods
- It's resolved via the BST resolver (like all il2cpp_* APIs)
- The guest stores the function pointer in a GOT slot
- When the guest needs to call a C# method, it calls through the GOT slot

### If the resolver returns the correct address:
- The GOT slot has the correct function pointer
- `il2cpp_runtime_invoke` runs when called
- C# methods execute

### If the resolver returns 0 (RAX propagation bug):
- The GOT slot has NULL
- Calling through the GOT slot → NULL execute → crash or silent skip
- C# methods never execute

### We cannot verify which case applies because the resolver is direct-bridged.

## Step 3: Dispatch Loop Analysis

### Key discovery:
- `0x804F6E9E6` in the FILE is `add rdi, 0x10` (3 bytes)
- `0x804F6E9E6` in LOADED code is `CALL` (5 bytes, original byte = `0xE8`)
- SharpEmu patches import call sites with CALL to HLE stubs
- This is CORRECT — PS5 uses inline import call sites

### The stall stack:
```
rip = 0x00006FFFFD001150 (WaitSema import stub)
rdi = 0x00006FFF00000081 (handle 0x81)
[rsp] = 0x0000000804F6E9EB (return address from CALL at 0x804F6E9E6)
```

### The WaitSema(0x81) call comes from inside the PRX
The dispatch loop function is inside Il2cppUserAssemblies.prx, not eboot.bin.

### The producer (inc [r14+0x90]) is in eboot.bin
The consumer (lock xadd [r14+0x90]) is in the PRX.
They use the SAME r14 base register — the queue structure is shared.

### But the producer function has ZERO callers
The eboot producer may be for a DIFFERENT queue (not the Unity Job System queue).

### The `rax=0xFFFFFFFF` confirms:

### Missing transition: STATE 3 → STATE 4 (or STATE 4 → STATE 5)

The key question: **Does `il2cpp_runtime_invoke` ever execute?**

If NO → C# managed code never runs → PlayerLoop never registers → deadlock
If YES → C# runs but PlayerLoop registration fails for another reason

## Root Cause Hypothesis (Updated)

### Most likely:
The IL2CPP resolver runs natively and resolves all 232 symbols correctly. The function pointers are stored in GOT slots. But `il2cpp_runtime_invoke` (which calls C# methods) is **never called** by the IL2CPP runtime because:

1. The IL2CPP runtime's initialization path doesn't reach the point where `il2cpp_runtime_invoke` is called
2. OR: `il2cpp_runtime_invoke` is called but fails because the GC is not initialized
3. OR: The IL2CPP runtime's main loop is the dispatch loop itself — it enters the dispatch loop BEFORE calling any C# methods

### The dispatch loop IS the IL2CPP runtime's main loop:
The dispatch loop at 0x804F6E9E6 is inside Il2cppUserAssemblies.prx. It's the IL2CPP runtime's job dispatch loop. The runtime enters this loop and waits for work.

### On real PS5:
- The IL2CPP runtime registers PlayerLoop callbacks BEFORE entering the dispatch loop
- The PlayerLoop callbacks submit jobs to the queue
- The dispatch loop processes jobs

### On SharpEmu:
- The IL2CPP runtime enters the dispatch loop WITHOUT registering PlayerLoop callbacks
- No jobs are submitted → WaitSema(0x81) blocks forever

### Why PlayerLoop registration is skipped:
The PlayerLoop registration is done by C# code (via `il2cpp_runtime_invoke`). If `il2cpp_runtime_invoke` is never called, the C# PlayerLoop registration code never runs.

### Why `il2cpp_runtime_invoke` is never called:
This is the deepest unknown. The IL2CPP runtime should call `il2cpp_runtime_invoke` during its initialization sequence. If it doesn't, something in the IL2CPP runtime's init path failed or was skipped.
