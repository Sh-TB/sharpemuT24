## Goal

Determine how far SharpEmuT24 executes after IL2CPP bootstrap (EXP-198 fix), and what exactly prevents the first visible PS5 boot screen.

## Method

3. Analyzed runtime log for: GPU activity, VideoOut, thread states, semaphore operations, import resolution
4. Compared with Prosper's implementation of `sceKernelRaiseException` and GC stop-the-world

## Findings

### Finding 1: IL2CPP Bootstrap Fully Functional

The EXP-198 fix (commenting out `cJ2Y4E-t258` HLE stub) is confirmed working:
- `cJ2Y4E-t258` is direct-bridged to `0x804ED3AE0` (PRX function)
- BST is populated with 232+ IL2CPP function name→address mappings
- API table at `0x801ED6320` is populated (resolver returns valid function pointers)
- Old crash at `0x80080684D` is eliminated (0 occurrences)
- `1D0H2KNjshE`/`hsi9drzHR2k` are no longer called (0 calls)

### Finding 2: Semaphore Deadlock Prevents GPU Initialization

The game reaches the point where:
1. EBOOT's EXECUTE_ONCE callback runs successfully
2. Unity worker threads (AssetGarbageCollectorHelper) are scheduled (13 threads)
3. IL2CPP GC thread is scheduled (entry `0x804F88AA0` in PRX)
4. All threads immediately block on `sceKernelWaitSema`
5. No thread can make progress → stall watchdog triggers after 20s

### Finding 3: No Graphics API Calls Attempted

Zero GPU activity:
- `VideoOutOpen` = 0
- `AgcInit` = 0
- `AgcCreateShader` = 0
- `AgcDriverSubmitDcb` = 0
- `VideoOutSubmitFlip` = 0
- `VideoOutRegisterBuffers` = 0

The game never reaches any graphics initialization code. It's stuck in the IL2CPP/Unity runtime initialization phase, before the rendering pipeline starts.

### Finding 4: sceKernelRaiseException Not Called

In this run, `sceKernelRaiseException` was called **0 times**. In the EXP-198 run (with `SHARPEMU_LOG_ALL_IMPORTS=1`), it was called 7 times. The difference may be timing-related (the verbose logging in EXP-198 slowed execution enough for the GC to fire).

However, even when `sceKernelRaiseException` IS called (EXP-198), the HLE implementation in `KernelExceptionCompatExports.cs` calls `scheduler.TryRaiseGuestException()` which attempts to deliver the exception to the target thread. If this delivery fails (returns `ORBIS_GEN2_ERROR_BUSY`), the GC stop-the-world mechanism breaks, causing the deadlock.

### Finding 5: Prosper's Warning About RaiseException

Prosper's source (`hle_kernel.cpp:3080`) explicitly warns:
> "A stubbed RaiseException left every thread un-acked -> deadlock."

This is exactly the symptom we observe: all threads blocked on semaphores because the GC stop-the-world acknowledgment never arrives.

## Root Cause

### Primary Blocker: IL2CPP GC Semaphore Deadlock

The game stalls because the IL2CPP Garbage Collector's stop-the-world mechanism deadlocks:

1. The IL2CPP GC thread (entry `0x804F88AA0`) needs to stop all worker threads for garbage collection
2. It calls `sceKernelRaiseException(targetThread, 0x1E)` to asynchronously interrupt each worker thread
3. The interrupted thread should run its exception handler (installed via `sceKernelInstallExceptionHandler`), which captures register state and acknowledges the GC
4. The GC thread then waits on semaphore `0x83` for acknowledgments from all worker threads
5. If `sceKernelRaiseException` doesn't actually interrupt the target thread (delivery fails), the worker threads never acknowledge, and the GC thread blocks forever on semaphore `0x83`
6. The worker threads are also blocked on their own semaphores (waiting for the GC to complete)
7. **Result: Classic deadlock — all threads waiting for each other**

### Secondary Issue: Semaphore Handle Corruption

The semaphore handles seen at stall time (`0x0D0000005C`, `0x00006FFF00000081`) are corrupted versions of the original handles (`0x5C`, `0x81`). This suggests either:
- A struct layout mismatch in IL2CPP runtime structures
- Memory corruption from incorrect HLE behavior
- Or the handles are being read from wrong offsets due to alignment differences

This corruption may be a symptom of the GC deadlock (threads reading stale/corrupted data from partially initialized structures) rather than a root cause.

## Current Blocker

### Exact Blocker

```
Stopped at:
  IL2CPP initialized ✅
  Worker threads scheduled ✅
  IL2CPP GC thread started ✅
  GC stop-the-world attempted → sceKernelRaiseException delivery fails
  All threads deadlock on semaphores
  GPU initialization NOT reached
  First frame NOT reached
```

### Root Cause

`sceKernelRaiseException` (NID `il03nluKfMk`) does not properly deliver async exceptions to target guest threads. The HLE implementation calls `scheduler.TryRaiseGuestException()` but this likely fails because:
1. The target thread is executing native guest code (not at a safe point)
2. The exception delivery mechanism doesn't actually interrupt the target thread's execution
3. Without the exception handler running on the target thread, the GC acknowledgment semaphore is never signaled

### What Prosper Does Differently

Prosper implements `sceKernelRaiseException` with **real async exception delivery**:
- On Linux: uses targeted POSIX signals (SIGUSR1) to interrupt the target thread
- On Windows: suspends the target thread, redirects its CONTEXT through a thunk, and restores after the handler returns
- Both paths synthesize a FreeBSD amd64 mcontext and run the real guest handler on the target thread

SharpEmu's `TryRaiseGuestException` likely doesn't implement the actual thread interruption — it may just queue the exception or return an error.

## Next Experiment

### EXP-200: Implement sceKernelRaiseException Async Delivery

**Goal**: Make `sceKernelRaiseException` actually interrupt the target guest thread and run the installed exception handler on that thread.

**Approach**:
1. Study Prosper's `hle_kernel.cpp:3072-3198` implementation in detail
2. Implement targeted POSIX signal delivery (SIGUSR1) on Linux
3. In the signal handler, save the target thread's register state
4. Redirect the target thread's RIP to the installed exception handler
5. After the handler returns, restore the original register state
6. This allows the GC stop-the-world to work: the handler runs on the target thread, acknowledges the GC, and the semaphore gets signaled

**Success criteria**: 
- `sceKernelRaiseException` calls succeed (no `ORBIS_GEN2_ERROR_BUSY`)
- Worker threads acknowledge the GC (semaphore `0x83` gets signaled)
- The deadlock is broken
- The game progresses past the GC initialization phase
- GPU/VideoOut initialization is attempted (pipeline counters > 0)
