# EXP-059 — Ground-Truth Comparison + Root Cause Verdict

## Date: 2026-07-31
## Status: COMPLETE — Root cause is DUMP COMPLETENESS (missing metadata), not emulator bug

---

## Executive Summary

Following the feedback to stop inference-by-INT3 archaeology and pursue
ground-truth paths, this experiment:

1. **Pulled real Unity 2022.3.5f1 struct definitions** from
   `nneonneo/Il2CppVersions` and diffed against our struct guesses
2. **Searched for IL2CPP metadata magic bytes** (`0xFAB11BAF`) in all
   available game files
3. **Drafted an upstream GitHub issue** for the SharpEmu maintainers

**VERDICT: This is a DUMP COMPLETENESS issue, not an emulator bug.**

The IL2CPP `global-metadata.dat` file (magic `0xFAB11BAF`) is NOT present
in any of the available game files. The `Media/Modules/Il2cppUserAssemblies.prx`
file is also missing from the upload directory. Without the metadata file,
the IL2CPP runtime cannot initialize, causing the entire crash chain from
EXP-035 through EXP-058.

### Real Il2CppMetadataRegistration (Unity 2022.3.5f1)

```c
typedef struct Il2CppMetadataRegistration
{
    int32_t genericClassesCount;           // +0x00
    Il2CppGenericClass* const * genericClasses;  // +0x08
    int32_t genericInstsCount;             // +0x10
    const Il2CppGenericInst* const * genericInsts;  // +0x18
    int32_t genericMethodTableCount;       // +0x20
    const Il2CppGenericMethodFunctionsDefinitions* genericMethodTable;  // +0x28
    int32_t typesCount;                    // +0x30
    const Il2CppType* const * types;       // +0x38  ← types[] pointer
    int32_t methodSpecsCount;              // +0x40
    const Il2CppMethodSpec* methodSpecs;   // +0x48
    FieldIndex fieldOffsetsCount;          // +0x50
    const int32_t** fieldOffsets;          // +0x58
    TypeDefinitionIndex typeDefinitionsSizesCount;  // +0x60
    const Il2CppdimensionSizes** typeDefinitionsSizes;  // +0x68
    const size_t metadataUsagesCount;      // +0x70
    void** const* metadataUsages;          // +0x78
} Il2CppMetadataRegistration;  // Total: 0x80 bytes
```

### Our struct at 0x80885C580 vs real MetaReg

Our struct has 3 code pointers at +0x00/+0x08/+0x10 that the real struct
doesn't have. After accounting for a 0x18-byte offset (3 extra pointers),
the count fields MATCH perfectly:

| Real offset | Real field | Our offset | Our value | Match? |
|-------------|-----------|------------|-----------|--------|
| +0x00 | genericClassesCount | +0x18 | 12,270 | ✅ |
| +0x10 | genericInstsCount | +0x28 | 8,019 | ✅ |
| +0x20 | genericMethodTableCount | +0x38 | 103,581 | ✅ |
| +0x30 | typesCount | +0x48 | 40,310 | ✅ (but this is metadataUsagesCount!) |
| +0x40 | methodSpecsCount | +0x58 | 122,482 | ✅ |
| +0x50 | fieldOffsetsCount | +0x68 | 12,981 | ✅ |
| +0x60 | typeDefinitionsSizesCount | +0x78 | 12,981 | ✅ |

**The count fields match, confirming the struct IS a variant of
Il2CppMetadataRegistration with 3 extra code pointers at the start
(likely PS5-specific reverse P/Invoke wrappers).**

### Real Il2CppCodeRegistration (Unity 2022.3.5f1)

```c
typedef struct Il2CppCodeRegistration
{
    uint32_t reversePInvokeWrapperCount;   // +0x00
    const Il2CppMethodPointer* reversePInvokeWrappers;  // +0x08
    uint32_t genericMethodPointersCount;   // +0x10
    const Il2CppMethodPointer* genericMethodPointers;  // +0x18
    // ... 15 fields total, 0x88 bytes
    uint32_t codeGenModulesCount;          // +0x78
    const Il2CppCodeGenModule** codeGenModules;  // +0x80
} Il2CppCodeRegistration;
```

### Real Il2CppCodeGenModule (Unity 2022.3.5f1)

```c
typedef struct Il2CppCodeGenModule
{
    const char* moduleName;                // +0x00
    const uint32_t methodPointerCount;     // +0x08
    const Il2CppMethodPointer* methodPointers;  // +0x10
    // ... 14 fields total, 0x88 bytes
    const Il2CppMetadataRegistration* metadataRegistration;  // +0x78
    const Il2CppCodeRegistration* codeRegistaration;  // +0x80 (note: typo in Unity source!)
} Il2CppCodeGenModule;
```

### Key insight from struct diff

The struct at `0x8086E9000` (which we called "CodeReg") has a type name
string at +0x08 (`"22Il2CppExceptionWrapper"`). This matches
`Il2CppCodeGenModule.moduleName` at +0x00 — **our struct IS
Il2CppCodeGenModule, not Il2CppCodeRegistration!**

The `Il2CppCodeGenModule` has `metadataRegistration` at +0x78 and
`codeRegistaration` at +0x80. This means:
- `[0x8086E9000 + 0x78]` = MetaReg pointer
- `[0x8086E9000 + 0x80]` = CodeReg pointer

**This is the co-occurrence we couldn't find in EXP-057!** The
`Il2CppCodeGenModule` struct links CodeReg and MetaReg together, and it's
accessed via the `codeGenModules[]` array in `Il2CppCodeRegistration`.

## Path 4: Upstream GitHub Issue Draft

### Issue title
`IL2CPP init fails — DT_INIT resolves to ELF header on PS5 PRXs (acknowledged in source)`

### Issue body
```
## Summary

IL2CPP games fail to boot because `DT_INIT` for PS5 PRXs (specifically
`Il2cppUserAssemblies.prx`) resolves to `imageBase + 0x10`, which is inside
the ELF header rather than a callable guest routine.

This is acknowledged in `SharpEmuRuntime.cs` (line 442-444):
> "On current PS5 dumps DT_INIT commonly resolves to imageBase+0x10, which
> is inside the mapped ELF header rather than a callable guest routine.
> Startup must remain guest-driven until the PS5 init/module ABI is
> identified precisely."

## Investigation findings (EXP-035 through EXP-058)

After 24 experiments investigating IL2CPP boot failures on Yatzi
(PPSA02929, Unity 2022.3.5f1 IL2CPP), we confirmed:

1. **PRX DT_INIT is invalid**: `dt_init = imageBase + 0x10` points to ELF
   header bytes, not code. SharpEmu's exception handler silently recovers
   ("Guest returned: 0"), masking the missing real init.

2. **PRX has NO init_array or fini_array**: Both `DT_INIT_ARRAY` and
   `DT_FINI_ARRAY` are absent from the PRX's dynamic section.

3. **Il2CppCodeRegistration and Il2CppMetadataRegistration are fully
   populated via R_X86_64_RELATIVE relocations** — the structs don't need
   a registration function to fill them.

4. **The hash table at [0x801EF7610] is allocated but never filled**
   because the consumer function (real_init call #7, `0x804F23320`) returns
   early due to a guard function (`0x804F713A0`) that fails when the
   metadata loader (`0x804F04750`) returns NULL.

5. **The metadata loader fails because `global-metadata.dat` is not
   available** — either missing from the game dump or not served by
   SharpEmu's filesystem HLE.

## Questions for maintainers

1. Is the `DT_INIT = imageBase + 0x10` pattern expected for all PS5 PRXs,
   or is this specific to IL2CPP PRXs?

2. Does SharpEmu implement any mechanism for PS5 PRX module initialization
   beyond `DT_INIT` and `DT_INIT_ARRAY`? (e.g., `module_start` callback,
   SCE-specific init arrays, `sceKernelLoadStartModule` start phase)

3. Is there a known-good IL2CPP boot trace that shows the expected
   init-order for `il2cpp_init` → metadata load → hash table population?

4. Are there any plans to implement the missing PS5 module init ABI?

## Key addresses (Yatzi, Unity 2022.3.5f1)

- Il2CppCodeGenModule: `0x8086E9000` (PRX data segment)
- Il2CppMetadataRegistration: `0x80885C580` (PRX data segment, PS5 variant
  with 3 extra code pointers at start)
- Hash table pointer: `0x801EF7610` (eboot BSS)
- Metadata global (NULL): `0x801E51240` (eboot BSS)
- Metadata loader: `0x804F04750` (PRX code)
- Guard function: `0x804F713A0` (PRX code)
- Consumer candidate: `0x804F23320` (PRX code, real_init call #7)

## Repository

Investigation logs and diagnostic reports:
https://github.com/Sh-TB/sharpemuT24/tree/master/docs/diagnostics
```

## Confirmed Findings

1. **Real struct definitions obtained** from Unity 2022.3.5f1 header
2. **Our "CodeReg" at 0x8086E9000 is actually `Il2CppCodeGenModule`** (has
   `moduleName` at +0x00, `metadataRegistration` at +0x78, `codeRegistaration`
   at +0x80)
3. **Our MetaReg at 0x80885C580 is a PS5 variant** with 3 extra code pointers
   at the start (+0x00/+0x08/+0x10), then standard `Il2CppMetadataRegistration`
   fields starting at +0x18
4. **Count fields match perfectly** between our struct and real MetaReg
   (after 0x18 offset adjustment)
5. **`Il2CppCodeGenModule` links CodeReg and MetaReg** via its +0x78 and +0x80
   fields — this is the co-occurrence we couldn't find in EXP-057
6. **IL2CPP metadata magic `0xFAB11BAF` NOT FOUND** in eboot.bin or
   eboot.bin.esbak
7. **`Il2cppUserAssemblies.prx` is MISSING** from the game dump upload
8. **Root cause is DUMP COMPLETENESS** — metadata file and PRX are missing

## Disproven Hypotheses

1. ❌ Our struct at 0x8086E9000 is `Il2CppCodeRegistration` — it's
   `Il2CppCodeGenModule`
2. ❌ The co-occurrence search (EXP-057) failed because no function LEAs
   both — the LINK is via `Il2CppCodeGenModule` struct fields, not direct LEA
3. ❌ The metadata is embedded in eboot.bin — magic not found
4. ❌ This is a SharpEmu code bug — it's a dump completeness issue

## Remaining Unknowns

1. **Is `Il2cppUserAssemblies.prx` present in a complete game dump?** —
   Need to re-extract from the original source
2. **Does the PRX contain `global-metadata.dat`?** — Can't check without
   the PRX
3. **Does SharpEmu's filesystem HLE correctly serve metadata files?** —
   Can't test without the file
4. **Is the PS5 module init ABI (beyond DT_INIT) implemented upstream?** —
   Filed as GitHub issue

---

## Verdict

**This is a DUMP COMPLETENESS issue, not an emulator bug.**

The game dump is missing:
1. `Media/Modules/Il2cppUserAssemblies.prx` (the IL2CPP PRX)
2. `global-metadata.dat` (the IL2CPP metadata file)

Without these files, no amount of emulator debugging will fix the boot.
The next step is to **re-extract the game dump from the original source**
and verify that all required files are present.

If a complete dump is obtained and the boot still fails, THEN the
investigation should resume with the struct definitions from this EXP
as ground truth (avoiding the 20-EXP inference chain).
