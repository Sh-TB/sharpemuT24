## Root Cause Analysis

### Thread Handle Mismatch

The IL2CPP GC thread calls `sceKernelRaiseException` with target handle `0x00007FB61CD7EC30`. This handle was obtained by the GC thread from somewhere (likely `scePthreadSelf()` called by the target thread, or stored during thread creation). However, this handle does not match any thread registered in SharpEmu's `_guestThreads` or `_externalGuestThreads` dictionaries.

**Why the handles don't match:**

1. `KernelPthreadState.CreateThreadHandle()` returns `Marshal.AllocHGlobal(ThreadObjectSize)` — a **host-side heap pointer**
2. This host pointer is written to the guest's `[threadIdAddress]` and returned to the guest as the thread ID
3. When the guest later calls `sceKernelRaiseException(targetThreadHandle)`, it passes this host pointer
4. `TryRaiseGuestException` looks up `_guestThreads[threadHandle]` — but the handle may have been obtained from `scePthreadSelf()` on a different code path
5. `scePthreadSelf()` calls `GetCurrentThreadHandle()` which checks `GuestThreadExecution.CurrentGuestThreadHandle` first, then falls back to `EnsureCurrentThreadRegistered()` which allocates a NEW handle
6. If the main thread calls `scePthreadSelf()` before `RegisterGuestThreadContext` is called, it gets a different handle than what `TryStartThread` registered

**The target `0x7FB61CD7EC30` is likely the main EBOOT thread's self-handle** (obtained via `scePthreadSelf()` → `EnsureCurrentThreadRegistered()` → `AllocateThreadHandle()`), which was never registered in `_guestThreads` because the main thread wasn't started via `TryStartThread`.

```

  ↓

  ↓

```

3. **Fix approach (EXP-202)**: Either:
   - Register the main thread in `_externalGuestThreads` when `EnsureCurrentThreadRegistered()` is called
   - OR: Make `TryRaiseGuestException` fall back to looking up the thread by its `KernelPthreadState` handle instead of just `_guestThreads`/`_externalGuestThreads`
   - OR: Ensure `RegisterGuestThreadContext` is called for the main thread with the correct handle

## Comparison: SharpEmu vs shadPS4

### SharpEmu

```
RaiseException(targetHandle, type)
  ↓
TryRaiseGuestException(targetHandle, handler, type)
  ↓
Look up targetHandle in _guestThreads / _externalGuestThreads
  ↓
If not found → queue in _pendingGuestExceptions[targetHandle]
  ↓
Wait for target to reach HLE safe point
  ↓
DeliverPendingGuestExceptionAtSafePoint checks CurrentGuestThreadHandle
  ↓
If CurrentGuestThreadHandle != queued targetHandle → exception never delivered
  ↓
WaitSema → deadlock
```

### shadPS4 (reference)

```
Exception request (sceKernelRaiseException)
  ↓
Signal/thread interruption (POSIX signal to target host thread)
  ↓
Signal handler saves guest register state
  ↓
Redirect guest RIP to installed exception handler
  ↓
Handler runs, captures registers for GC root scanning
  ↓
Handler signals acknowledgment semaphore
  ↓
Original execution resumed
```

### Key Difference

SharpEmu uses **cooperative** exception delivery (waits for safe point) while shadPS4/Prosper use **preemptive** delivery (POSIX signal interrupts the target thread). The cooperative approach fails when the target thread's handle doesn't match the queued exception's target handle.
