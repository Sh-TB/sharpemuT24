# EXP-123 — Investigate IL2CPP Dispatch Thread and Missing Work Submission

**Date:** 2026-08-03
**Status:** COMPLETE
**Goal:** Determine whether the IL2CPP thread at `0x804F88AA0` is responsible for task dispatch (writing `[rbx+0xF8]`, `[rbx+0x100]`, and signaling work semaphores).

---

## Finding

**The IL2CPP thread at `0x804F88AA0` is NOT the task dispatcher.** It is a generic IL2CPP thread wrapper that calls `[rbx+0x10]` (a function pointer in a struct). The function it calls (at `0x804FB5B70`) is a GC/scavenger scheduler that walks an object array and checks `[rbx+0xF8]` as a FLAG (bit test), not as a function pointer. This thread blocks on a "SuspendSemaphore" (handle 0x83) when there's nothing to scavenge.

**The IL2CPP thread is NEVER CREATED under FAST_PATH=1.** In Test A (FAST_PATH=0), it's created at line 8511 and blocks on SuspendSemaphore 0x83. In Test B (FAST_PATH=1), it's never created — the main thread crashes the workers (NULL pointer) before reaching the thread creation point.

**The missing dispatch is NOT this thread.** The dispatch should come from elsewhere — likely the main thread, which is stuck in a busy loop (per CHECKPOINT section 15) and never reaches the dispatch code.

0x804f88aa1: mov rbp, rsp
0x804f88aa4: push rbx
0x804f88aa5: push rax
0x804f88aa6: mov rbx, rdi              ; rbx = struct pointer (arg)
0x804f88aa9: call 0x804fc33f0           ; PLT stub (once-init related)
0x804f88aae: xchg [rbx], rax           ; exchange value at [rbx]
0x804f88ab1: mov rdi, [rbx]            ; rdi = new value at [rbx]
0x804f88ab4: call 0x804fc3400           ; PLT stub
0x804f88ab9: mov rdi, [rbx + 0x18]     ; rdi = arg from struct field +0x18
0x804f88abd: call [rbx + 0x10]         ; INDIRECT CALL to function pointer at [rbx+0x10]

0x804f88ac6: pop rbx

This is a **generic thread wrapper** — it takes a struct, does some once-init, then calls `[rbx+0x10]` with `rdi = [rbx+0x18]`. The actual function depends on what's in the struct at runtime.

### Task 2 — Thread presence comparison

| Mode | IL2CPP thread created? | Line number | Status |
|------|----------------------|-------------|--------|
| Test A (FAST_PATH=0) | YES | Line 8511 | Blocked on SuspendSemaphore 0x83 |
| Test B (FAST_PATH=1) | **NO** | Never | Thread never created |

**Why missing in Test B:** Under FAST_PATH=1, workers bypass WaitSema and immediately crash (NULL pointer at `[rbx+0xF8]`). The crash happens BEFORE the main thread reaches the point where it would create the IL2CPP GC thread. The main thread's execution is interrupted by the worker crashes, preventing the IL2CPP thread from being created.

**In Test A (FAST_PATH=0):** Workers block at WaitSema (don't crash), allowing the main thread to continue and create the IL2CPP GC thread. But the main thread then gets stuck in a busy loop (per CHECKPOINT section 15), so the IL2CPP thread is created but never receives work.

### Task 3 — Semaphore 0x83 lifecycle

| Event | Count | Details |
|-------|-------|---------|
| Create | 1 | `sema.create handle=0x83 name='SuspendSemaphore' attr=0x0 init=0 max=256` |
| Wait | 1 | `sema.wait-block handle=0x83 name='SuspendSemaphore' need=1 count=0 timeout=infinite waiters=1 guest=Thread-7F6A70B592E0 ret=0x804FB5BAF` |
| Signal | **0** | Nobody signals the SuspendSemaphore |

**Handle 0x83 is a "SuspendSemaphore"** — the IL2CPP GC thread suspends itself when there's nothing to scavenge. It should be signaled when there's GC work to do. Nobody signals it, so the GC thread sleeps forever.

This is NOT a work dispatch semaphore — it's a GC suspend/resume semaphore. The GC thread is idle, waiting for GC work, not waiting to dispatch tasks to workers.

### Task 4 — PRX task submission patterns

The function at `0x804fc1590` (called by the IL2CPP thread) is a **scavenger loop** that:

```asm
0x804fc15ec: mov rbx, [r15 + r14*8]    ; load object from array (up to 256)
0x804fc1611: test byte [rbx + 0xF8], 1  ; check flag bit at +0xF8
0x804fc161a: mov rax, [rbx + 0x10]      ; read [rbx+0x10]
0x804fc1627: cmp byte [rbx + 0xF9], 0   ; check flag at +0xF9
0x804fc1630: call 0x804fc38c0           ; process matching object
```

**This tests `[rbx+0xF8]` as a FLAG (bit test), not as a function pointer.** The `[rbx+0xF8]` here is on a DIFFERENT object type (GC-managed objects), not the worker objects. The worker objects also have a field at +0xF8, but it's a different struct type. This is a coincidence of offset, not a shared structure.

## Thread Analysis

### IL2CPP thread (0x804F88AA0)

- **Type:** Generic IL2CPP thread wrapper
- **Entry:** Calls `[rbx+0x10]` with `rdi = [rbx+0x18]` (function pointer + arg from struct)
- **Actual function called:** `0x804FB5B70` (GC/scavenger scheduler)
- **Behavior:** Walks object array (up to 256 entries), checks `[obj+0xF8]` as a flag, processes matching objects, then suspends on SuspendSemaphore 0x83
- **NOT a task dispatcher:** Does not write `[worker+0xF8]`, does not signal work semaphores

### Worker threads (0x800BB06A0 → 0x800AA0170)

- **Type:** AssetGarbageCollectorHelper
- **Behavior:** Wait on EVEN work semaphores (0x5C-0x74), call `[worker+0xF8]` when signaled, signal ODD completion semaphores (0x5D-0x75)
- **Current state:** Blocked on WaitSema (Test A) or crash on NULL call (Test B)

## Dispatch Path

**The dispatch path has NOT been found.** The IL2CPP thread at `0x804F88AA0` is NOT the dispatcher — it's a GC scavenger. The actual task dispatch (writing `[worker+0xF8]` and signaling work semaphores) should come from:

1. **The main thread** — which is stuck in a busy loop (per CHECKPOINT section 15: calling `1D0H2KNjshE`, `hsi9drzHR2k`, `scePthreadMutexLock`, `sceKernelClockGettime`, `sceAudioOutOutput`). The main thread never reaches the dispatch code.

2. **Some other thread** — not yet identified. No other non-worker thread exists in the logs.

3. **A callback or event handler** — possibly the registered callback `0x804FA1FE0` (never invoked, per EXP-106), but this has NOT been proven.

## Confirmed

1. **The IL2CPP thread (0x804F88AA0) is a generic thread wrapper** that calls `[rbx+0x10]` — CONFIRMED by disassembly.

2. **The function called by the IL2CPP thread (0x804FB5B70) is a GC/scavenger scheduler** — CONFIRMED by disassembly showing object array iteration with `[rbx+0xF8]` bit tests.

3. **Semaphore 0x83 is a "SuspendSemaphore"** — CONFIRMED by `sema.create handle=0x83 name='SuspendSemaphore'`.

4. **The IL2CPP thread is NEVER CREATED under FAST_PATH=1** — CONFIRMED by log comparison (Test A: created at line 8511; Test B: never created).

5. **Nobody signals the SuspendSemaphore (0x83)** — CONFIRMED (0 SignalSema on handle 0x83).

6. **The IL2CPP GC thread is NOT the task dispatcher** — CONFIRMED. It does not write `[worker+0xF8]`, does not signal work semaphores. It's a scavenger that checks `[obj+0xF8]` as a flag on GC-managed objects (different struct type from worker objects).

## Rejected

1. **"The IL2CPP thread (0x804F88AA0) is the missing dispatcher"** — REJECTED. It's a GC scavenger, not a task dispatcher. It doesn't touch worker objects or work semaphores.

2. **"The IL2CPP thread is missing in FAST_PATH=1 because FAST_PATH prevents its creation"** — PARTIALLY REJECTED. FAST_PATH doesn't directly prevent creation; the worker crashes (caused by FAST_PATH=1 letting workers reach the NULL call) interrupt the main thread before it reaches the thread creation point.

3. **"Semaphore 0x83 is a work/scheduler semaphore"** — REJECTED. It's a "SuspendSemaphore" for the GC thread — a suspend/resume mechanism, not a work dispatch mechanism.

## Unknown

1. **What code should dispatch tasks to workers?** The dispatch path has not been found. The main thread is the most likely candidate (it creates the workers and should submit work to them), but it's stuck in a busy loop.

2. **Why is the main thread stuck in a busy loop?** Per CHECKPOINT section 15: "calling 1D0H2KNjshE, hsi9drzHR2k, scePthreadMutexLock, sceKernelClockGettime, sceAudioOutOutput." These are NID stubs and real HLE functions in a loop. Why doesn't the loop exit?

3. **Is the missing dispatch caused by:**
   - A) Dispatcher thread never created — PARTIALLY (the IL2CPP GC thread IS created in Test A, but it's not the dispatcher)
   - B) Dispatcher thread created but blocked — YES for the GC thread (blocked on SuspendSemaphore), but it's not the dispatcher
   - C) Main thread never submits first job — LIKELY (main thread stuck in busy loop)
   - D) IL2CPP initialization incomplete — UNKNOWN
   - E) Emulator HLE missing an event/callback — UNKNOWN (this is the question for maintainers from EXP-115)

4. **What is the main thread's busy loop waiting for?** The `1D0H2KNjshE` and `hsi9drzHR2k` NID stubs were investigated in CHECKPOINT section 17 — they were found to be a finite loop (80,311 calls in ~2 seconds), not an infinite busy-wait. But the main thread is still stuck AFTER that loop completes.
