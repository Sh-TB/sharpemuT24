## Evidence

### Step 1: Writer Function Deep Analysis

**Writer Function 1: 0x804FB1B90** (contains writer at 0x804FB1C1B)

Full decoded logic:
```
0x804FB1B90: push rbp; mov rbp, rsp
0x804FB1B94: cmp byte [0x808D67BB8], 0    ← FIRST GUARD (different flag!)
0x804FB1B9B: je +2 → ret                   ← if 0, return early
... (initialization code) ...
0x804FB1C05: cmp byte [0x808D67B98], 0    ← SECOND GUARD (target flag)
0x804FB1C0C: je +0x17 → 0x804FB1C25       ← if 0, SKIP write
0x804FB1C0E: cmp byte [0x808B55690], 2    ← THIRD GUARD
0x804FB1C15: je +0xDA → 0x804FB1CF5       ← if == 2, skip
0x804FB1C1B: mov dword [0x808D67B98], 1   ← WRITE TARGET FLAG
... (more code) ...
0x804FB1C93: mov dword [0x808D67BB8], 1   ← SET FIRST GUARD FLAG
```

**Key insight:** The FIRST guard checks 0x808D67BB8, NOT 0x808D67B98. The function returns early if 0x808D67BB8 is 0. But 0x808D67BB8 is only set to 1 INSIDE the function (at 0x804FB1C93). This is a chicken-and-egg problem.

| Flag Address | Writers | Notes |
|-------------|---------|-------|
| 0x808D67B98 | 3 | All write value 1, all guarded by 0x808D67BB8 |

**No unconditional writer exists for 0x808D67BB8.** The flag is only set to 1 inside the writer function, which can only run if the flag is already non-zero.

### Step 4: Second Gate (0x808B55690)

- **0 write instructions found** — flag is NEVER set by code
- **In BSS** — value is always 0 at runtime
- The THIRD guard checks `cmp byte [0x808B55690], 2` → since it's always 0, the comparison is 0 != 2, so the guard does NOT skip
- This gate does NOT block initialization

### Step 5: IL2CPP Class Initialization — SMOKING GUN

From EXP-118 runtime log, Entry #170:

```
[RESOLVER-TRACE] Entry #170: name='il2cpp_runtime_class_init' ret=0x0000000000000000
[EXP032-ABI-AFTER] nativeReturn=0x0000000804ED9590 contextRax=0x0000000804ED9590
[EXP032-RETURN] innerRax=0x0000000804ED9590 returnValue=0x0000000804ED9590 match=True
[EXP028-T13-CASE-B] *** RETURN CORRUPTION *** call=170
  Resolver returned 0x804ed9590 but cpuContext.Rax = 0x7fd670094000
  → Bug is in RETURN PROPAGATION (TryCallGuestFunction reads back RAX incorrectly)
[RESOLVER-TRACE] Exit #170: RAX=0x0000000804ED9590 (non-zero)
```

**The resolver correctly returns 0x804ED9590** (the `il2cpp_runtime_class_init` function address inside the PRX), **but `cpuContext.Rax` contains 0x7fd670094000** (garbage).

This is EXACTLY the EXP-138 RAX propagation bug:
- The resolver function executes natively and returns the correct address in RAX
- `TryCallGuestFunction` captures the return value correctly (`innerRax=0x804ED9590`)
- But `cpuContext.Rax` is NOT updated — it contains a stale/garbage value
- The caller reads `cpuContext.Rax` and gets the garbage value
- The garbage value is stored in the GOT slot for `il2cpp_runtime_class_init`
- Subsequent calls to `il2cpp_runtime_class_init` jump to the garbage address
- Type initialization NEVER runs
- Type initialized flags are NEVER set

### Step 6: BST Confirmation

From BST-WALK:
```
Node #65 @0x200002b240: name='il2cpp_runtime_class_init' left=0x2000003f20 right=0x2000003f20 flag[0x19]=0
```

`il2cpp_runtime_class_init` IS in the BST and IS found by the resolver. The function exists at 0x804ED9590 inside the PRX. The issue is purely the RAX propagation bug.
