## Why Previous Test Was Wrong

The previous "RENDERING BLOCKED" result was caused by **incorrect test environment setup**, NOT by EXP-138.

**The mistake:**
```
SHARPEMU_HEADLESS=1
    ↓
HeadlessVideoPresenter selected (instead of VulkanVideoPresenter)
    ↓
HeadlessVideoPresenter is a STUB — allocates framebuffer but never executes draw commands
    ↓
colors = 0, draws = 0, framebuffer = all zeros
    ↓
False "RENDERING BLOCKED" conclusion
```

**Why HeadlessVideoPresenter doesn't render:**
- `DrawCall()` method exists but is NEVER called from anywhere in the codebase
- The `draws=` counter is owned by `VulkanVideoPresenter._perfDrawCount`, not HeadlessVideoPresenter
- AGC DCB parser routes draws to `GuestGpu.Current` (hardcoded to `VulkanGuestGpuBackend`)
- In headless mode, no Vulkan render thread runs → draws silently dropped

**EXP-138 did NOT touch any GPU/AGC/VideoOut files** — it only modified CPU backend files. The rendering block was purely an environment setup error.

## How Rendering Was Restored

### Required Environment

| Component | Source | Purpose |
|-----------|--------|---------|
| Xvfb | System package | Virtual X11 display on `:99` |
| Lavapipe | `mesa-vulkan-drivers` .deb (extracted) | Software Vulkan ICD |
| GLFW | `libglfw3` .deb (extracted) | X11 windowing backend |
| VulkanVideoPresenter | SharpEmu built-in | Real GPU rendering pipeline |

### Critical Environment Variable

```bash
unset SHARPEMU_HEADLESS    # CRITICAL — must NOT be set
```

When `SHARPEMU_HEADLESS` is unset and Xvfb + Lavapipe + GLFW are available:
1. `VideoOutManager.HasGpuSupport()` returns true (Lavapipe detected)
2. `VulkanVideoPresenter` is selected (not HeadlessVideoPresenter)
3. GLFW X11 backend initializes (connects to Xvfb :99)
4. Vulkan device created (Lavapipe software renderer)
5. AGC draw commands execute via Vulkan render thread
6. Framebuffer populated with real pixel data
7. Frame captures contain non-zero content
