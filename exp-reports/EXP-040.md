# EXP-040 — IL2CPP Initialization Order / Hash Population Failure Investigation

## Date: 2026-07-30
## Status: COMPLETE — Root cause confirmed, workaround tested

---

## Executive Summary

The IL2CPP metadata hash table at `0x801EF7610` is **allocated but never
filled with entries**. All entries remain `0xFFFFFFFF` (empty sentinel).
This causes 1689 hash lookups to fail, leaving global `0x801E51240` at NULL.
il2cpp_init's callback reads this NULL global and crashes.

**Setting `0x801E51240` to a non-zero value clears the original crash**,
proving the NULL global is the sole cause of the crash at `0x80135DE83`.
A new crash appears at `0x8007E1965` because the dummy value is not the
correct metadata pointer.

The hash table fill function is **never called** during the entire boot
process. It should be called inside il2cpp_init, but il2cpp_init crashes
before reaching the fill code.

---

## Problem

The hash table at `0x801EF7610` is allocated by `0x8007F90A0` (called
from the registration iterator `0x800B8D530`). The writer allocates the
table structure and entries array, initializes entries with `0xFFFFFFFF`
sentinels, but **never inserts actual metadata entries**.

The hash lookup function at `0x8004BD620` probes the entries array,
finds only `0xFFFFFFFF` sentinels, and returns 0 for every lookup.

The global `0x801E51240` should be set by a hash lookup at `0x8013EF019`
(in the init function `0x8013EB6B0`). Since the lookup returns 0, the
global stays NULL.

il2cpp_init (via real_init `0x804F04BA0`) calls a callback into eboot.bin
at call #7 (`call [rax]` at `0x804F04C5C`). This callback eventually calls
`0x80135DDD0` which reads `0x801E51240` = 0 → SIGSEGV.

## Actual Initialization Order

```
1. Entry → 0x8013FCE40 (main)
2. Main → 0x8013EB6B0 (init function)
3. Init → 0x800B8D530 (registration iterator)
4. Iterator → calls 895 registration functions
   - Each adds to linked list at 0x801E9DF28
   - Each calls __cxa_atexit (registers destructor)
   - One (0x8007F90A0) allocates hash table at 0x801EF7610
   - NONE fill the hash table entries
5. Init → hash lookup at 0x8013EEFE7 (FAILS — table empty)
6. Init → global 0x801E51240 stays 0
7. Init → call il2cpp_init at 0x8013ED057
8. il2cpp_init → real_init 0x804F04BA0
9. real_init → call #7: call [rax] (indirect callback into eboot.bin)
10. Callback → 0x80134FA69: call [0x801EA49D8] = 0x800C66B40
11. 0x800C66B40 → returns metadata object (vtable[0] = 0x80135DDD0)
12. Callback → 0x80134FA7D: call [rax] = 0x80135DDD0
13. 0x80135DDD0 → reads 0x801E51240 = 0 → CRASH at 0x80135DE83
```

### Where hash table fill SHOULD happen
Between step 4 (iterator) and step 5 (hash lookup), the hash table entries
should be filled. But **no code fills them**. The fill function is never
called.

The fill function is likely inside il2cpp_init (real_init), but real_init
crashes at call #7 before reaching the fill code (which would be at calls
#8+).

---

## Broken Function

The hash table **insert/fill function** is never called. Static analysis
found:
- 1689 hash table READS (lookups) in eboot.bin
- 1 hash table WRITE (the allocator at `0x8007F928C`)
- **0 hash table entry fills** (no code writes actual entries to the
  dynamically allocated entries array)

The PRX (Il2cppUserAssemblies.prx) has **0 references** to `0x801EF7610`.
The hash table is entirely managed by eboot.bin, but eboot.bin never fills it.

---

## Missing Call/Data

The hash table entries should contain metadata type/method pointers.
The metadata is in the table at `0x1CC0080` (13,905 RELATIVE relocations,
found in EXP-037). This metadata should be inserted into the hash table
by a registration function.

On a real PS5, this registration is performed by:
1. The PS5 dynamic linker (during symbol resolution), OR
2. A PS5-specific runtime initialization callback, OR
3. il2cpp_init's internal metadata registration (calls #8+ in real_init)

SharpEmu doesn't implement options 1 or 2. Option 3 crashes before
reaching the registration code.

---

## Minimal Fix

### Workaround (tested, partial)
Set `0x801E51240` to a non-zero value before il2cpp_init runs. This
clears the original crash but causes a new crash because the dummy
value is not the correct metadata pointer.

### Proper fix (not yet implemented)
Fill the hash table entries with actual metadata before il2cpp_init runs.
This requires:
1. Finding the hash table INSERT function (not found in static analysis)
2. OR: Manually populating the hash table from the metadata table at
   `0x1CC0080`
3. OR: Implementing the PS5 dynamic linker's symbol resolution that
   fills the hash table

### Recommended approach for EXP-041
1. Trace il2cpp_init's real_init (`0x804F04BA0`) call-by-call to find
   which call fills the hash table
2. The fill likely happens at calls #8-80 (the 63+ calls to `0x804EEE8D0`)
3. These calls might be metadata registration functions that insert
   into the hash table
4. If call #7 crashes before calls #8+ run, the fix is to make call #7
   not crash (by pre-filling the hash table or setting the global)
