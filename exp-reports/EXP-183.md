## Evidence

### Task 1: ALL Writers to 0x801E51240

**Static analysis (eboot executable segment):**

| Address | Instruction | Type | Path |
|---------|-------------|------|------|
| 0x8007FD8F9 | `mov qword [0x801E51240], 0x0` | Clear (writes NULL) | Executed early |
| 0x8013EF019 | `mov [0x801E51240], rax` | Init writer | **NEVER reached** (error path only) |

**LEA instructions loading address 0x801E51240:**

| Address | Instruction | Purpose |
|---------|-------------|---------|
| 0x8013EEFF1 | `lea rdx, [0x801E51240]` | Load address for indirect use (near init writer) |

**Relocation analysis:**
- DT_RELA: 49,850 entries — **NONE** target 0x801E51240
- DT_JMPREL: 600 entries — **NONE** target 0x801E51240
- No GLOB_DAT, no JUMP_SLOT, no RELATIVE relocation

**PRX analysis:**
- Target `0x801E51240` is in EBOOT's BSS (segment vaddr=0x1D20000)
- PRX base `0x804CD5000` — target is at negative offset from PRX
- PRX **cannot** write to this address via RIP-relative addressing

**Conclusion:** The ONLY code that writes a non-NULL value to `[0x801E51240]` is at `0x8013EF019`, which is on the ERROR path of the consumer function. There are no relocations and no other writers.

### Task 2: IL2CPP Initialization Flow Analysis

**Real IL2CPP init flow (from reverse engineering references):**

```
il2cpp_init():
  1. Load global-metadata.dat into memory
  2. Parse metadata header
  3. Register metadata with IL2CPP runtime
  4. Set up internal global pointers
  5. Initialize codegen registration
  6. Create default domain
  7. Return 0 (success)
```

**Key insight from il2cpp reverse engineering guide:**
> "When the IL2CPP runtime starts (il2cpp_init), this file [global-metadata.dat] is loaded into memory. IL2CPP API functions (e.g., il2cpp_class_from_name) map the C++ structures in memory to the names in this metadata file."

**SharpEmu's il2cpp_init handling:**

The real `il2cpp_init` at `0x804ED85D0` (inside Il2cppUserAssemblies.prx) IS called and returns 0. However:

1. The real `il2cpp_init` initializes PRX-internal globals (IL2CPP runtime state inside the PRX)
2. It does NOT initialize EBOOT globals like `[0x801E51240]`
3. EBOOT's `[0x801E51240]` is supposed to be set by EBOOT code, not by the PRX

### Task 3: PS4 vs PS5 IL2CPP Comparison

**Architecture pattern (same on PS4 and PS5):**

```
EBOOT (game executable):
  - Contains Unity player code
  - Contains consumer function that calls il2cpp_init
  - Contains global pointers like [0x801E51240]
  - These globals bridge EBOOT ↔ IL2CPP runtime

PRX (Il2cppUserAssemblies.prx):
  - Contains IL2CPP compiled C++ code
  - Contains il2cpp_init, il2cpp_domain_get, etc.
  - Has its own internal globals
  - Does NOT know about EBOOT's globals
```

**shadPS4 approach:**
- shadPS4 uses a generic stub system — returns 0 for all unresolved NIDs
- This means il2cpp_init "succeeds" but does nothing
- Games that depend on il2cpp_init setting up metadata will crash later
- shadPS4 relies on the PRX's native il2cpp_init running correctly

**SharpEmu's approach:**
- When PRXs are loaded, il2cpp_init runs natively at `0x804ED85D0`
- The native il2cpp_init initializes PRX-internal state
- But EBOOT globals like `[0x801E51240]` are NOT set by the PRX
- These globals must be set by EBOOT code that runs AFTER il2cpp_init

### Task 4: Is SharpEmu's il2cpp HLE Too Minimal?

**HLE stub for il2cpp_init (line 2607 of DirectExecutionBackend.Imports.cs):**
```csharp
if (name == "il2cpp_init" || name == "il2cpp_shutdown") return 0;
```

This HLE stub is ONLY used when PRXs are NOT loaded. When PRXs ARE loaded (correct directory structure), the real `il2cpp_init` at `0x804ED85D0` runs natively. So the HLE stub is NOT the issue.

**The real issue:** The native `il2cpp_init` at `0x804ED85D0` returns 0 (success), but the consumer function's success path does NOT initialize `[0x801E51240]`. The init writer is only on the ERROR path.

## Root Cause

### Why [0x801E51240] is NULL:

```
1. EBOOT clear writer (0x8007FD8F9) sets [0x801E51240] = 0 early in boot
2. il2cpp_init (0x804ED85D0) runs and returns 0 (success)
3. Consumer function (0x8013EB6B0) is called
4. Consumer calls il2cpp_init at +0x19A7 → returns 0
5. Consumer takes je at +0x19B1 (success path, eax=0)
6. Success path does NOT reach init writer at +0x3969
7. [0x801E51240] stays NULL
8. Later code calls 0x80135DDD0 which reads [0x801E51240] → NULL
9. Crash at 0x80135DE83: mov ecx, [rax+0x98] (fault=0x98)
```

### The design:

The init writer at `+0x3969` (`0x8013EF019`) is part of a code block starting at `+0x3941` (`0x8013EEFF1`) that:
1. Loads the address of `[0x801E51240]` into `rdx`
2. Tests if `rax` (the value to store) is non-NULL
3. Performs a range check on `rax`
4. Only writes if both checks pass

This code is ONLY reachable via the ERROR path — when `il2cpp_init` returns non-zero. The SUCCESS path skips it entirely.

### What this means:

`[0x801E51240]` is NOT supposed to be initialized by the consumer's success path. It should be initialized by:

1. **A different EBOOT function** that runs BEFORE the consumer, OR
2. **The consumer's ERROR path** — but only when il2cpp_init fails (which it doesn't)

The most likely explanation is that `[0x801E51240]` should be initialized by an EBOOT function that runs between `il2cpp_init` returning and the crash function `0x80135DDD0` being called. The consumer's success path at `+0x19CC` leads to code that should call this initializer, but something goes wrong.

### Alternative hypothesis:

The consumer's success path may be supposed to reach `+0x3969` via a different route — not through the `je` at `+0x19B1`, but through a later branch that loops back. The `je` at `+0x19B1` may not be the only path to `+0x3969`.

## No Fixes. No Speculative Initialization.

The exact initializer of `[0x801E51240]` is the code at `0x8013EF019` (consumer +0x3969), but this code is on the ERROR path and is never reached when `il2cpp_init` returns 0 (success). The success path does not initialize `[0x801E51240]`, and no relocations or other writers exist. The next step is to trace the success path to find if it should reach `+0x3969` via a different route or if another function should initialize the global.
