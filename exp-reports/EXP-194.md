# EXP-194 — IL2CPP Registration Chain: Evidence-First Cross-Validation

**Date:** 2026-08-10
**Status:** COMPLETED — Root cause identified, fix direction validated
**Predecessor:** EXP-193 (DT_INIT completes; `[0x801E51240]=NULL`; crash at `0x80080684D`)

---

## Executive Summary

EXP-194 definitively maps the IL2CPP registration architecture in Yatzi's PRX and disproves two long-standing assumptions:

1. **`0x801E51240` is NOT an `Il2CppClass*` global.** It is a lazy cache for the return value of EBOOT function `0x4BD620`. The cache stays NULL because the function returns NULL (or fails bounds checks), not because IL2CPP registration failed.

2. **The crash at `0x80080684D` is a hash-table lookup with a NULL base pointer (r15=0).** It is causally downstream of missing registration but occurs in EBOOT code, not PRX code.

The actual IL2CPP registration chain is fully identified:

```
il2cpp_init (EBOOT calls via API table)
  → Runtime::Init @ 0x804F04BA0 (PRX)
    → guard checks (NID aI+OeCz8xrQ)
    → 0x804F04C55: lea rax, [0x808958220]  (s_Il2CppCodegenRegistration struct)
    → 0x804F04C5C: call [rax]              (indirect call to Il2CppCodegenRegistration)
      → Il2CppCodegenRegistration @ 0x804D9C620
        → lea rdi, [0x8086E9010]  (CodeRegistration)
        → lea rsi, [0x80885C598]  (MetadataRegistration)
        → lea rdx, [0x8082AE0C0]  (codeGenOptions)
        → jmp 0x804FA60C0          (thunk)
          → MetadataCache::Register @ 0x804F23280
            → mov [0x808B542E8], rdi  (s_Il2CppCodeRegistration)
            → mov [0x808B542F0], rsi  (s_Il2CppMetadataRegistration)
            → mov [0x808B542F8], rdx  (s_Il2CodegenOptions)
```

The registration call site is guarded by a `pthread_once`-like pattern at `0x804F04BE2`/`0x804F04BF7`. If the guard PLT function (NID `aI+OeCz8xrQ`) returns an incorrect value, the registration call at `0x804F04C5C` is skipped, leaving the registration globals NULL and causing the downstream crash.

```

### Runtime Execution Status

**NOT VERIFIED.** Static analysis confirms the call chain EXISTS and is REACHABLE, but whether SharpEmu actually executes `0x804F04C5C` at runtime was not verified (would require runtime instrumentation in SharpEmu source, which is not present in this environment).

### Caller of `Runtime::Init`

`Runtime::Init @ 0x804F04BA0` has **0 direct E8 callers** in the PRX text segment. This is expected because `Runtime::Init` is called from `il2cpp_init`, which is an EXPORTED function (called from EBOOT via the IL2CPP API table). The EBOOT's call to `il2cpp_init` is an indirect call through `[0x801ED6320]` (the API table), not a direct E8.

### Table 2 Membership

`Il2CppCodegenRegistration @ 0x804D9C620` is **NOT in Table 2** (Table 2 entries are at `0x8089246F8..0x8089247D8`, containing function pointers in the range `0x804EC1240..0x804FC2470`). The registration is invoked via the `s_Il2CppCodegenRegistration` function-pointer struct at `0x808958220`, which is called from `Runtime::Init`.

This means: **registration is NOT triggered by DT_INIT directly.** It is triggered by `il2cpp_init` → `Runtime::Init` → `call [s_Il2CppCodegenRegistration]`.

## 7. `0x801E51240` Validation

### CONFIRMED: NOT an `Il2CppClass*` global

| Attribute | Value |
|-----------|-------|
| Address | `0x801E51240` (runtime), `0x1E51240` (EBOOT vaddr) |
| Segment | `PT_LOAD[7] RW-` BSS (zero-initialized at runtime) |

### Cross-Reference Analysis

**Writes (1 found):**
- `0x8013EF019`: `mov [rip + 0xA62220], rax` → writes `rax` to `0x801E51240`
- Context:
  ```
  0x8013EEFE7: call 0x4BD620              ← returns rax
  0x8013EEFF1: lea rdx, [0x801E51240]     ← address of the cache
  0x8013EEFF8: test rax, rax              ← check if return is NULL
  0x8013EEFFB: je 0x13EF3C4               ← if NULL, SKIP the write
  0x8013EF001: mov esi, [rax + 0xC]       ← bounds check setup
  0x8013EF004: shr esi, 0x15
  0x8013EF007: sub esi, [rip + 0xA012CB]
  0x8013EF00D: cmp esi, [rip + 0xA012C9]
  0x8013EF013: jae 0x13EF3C4              ← if out of bounds, SKIP the write
  0x8013EF019: mov [0x801E51240], rax     ← **WRITE (only if non-NULL + in bounds)**
  ```

**Reads (1 LEA found):**
- `0x8013EEFF1`: `lea rdx, [rip + 0xA62248]` → `0x801E51240` (loads address, likely for passing to another function)

### Conclusion

`0x801E51240` is a **lazy cache** for the return value of EBOOT function `0x4BD620`. The cache:
1. Is BSS (zero-initialized)
2. Is only written if `0x4BD620` returns non-NULL **AND** passes bounds checks
3. Stays NULL if `0x4BD620` returns NULL or fails bounds checks

**The NULL value is caused by `0x4BD620` returning NULL (or failing bounds checks), NOT by missing IL2CPP registration.**

The past EXPs' assumption that `[0x801E51240] == Il2CppClass*` was **WRONG**. While it MAY cache an `Il2CppClass*` (if `0x4BD620` is `il2cpp_class_from_name` or similar), the NULL value does not directly indicate registration failure.

## 8. Crash `0x80080684D` Root-Cause Analysis

### Crash Instruction

```
0x80080684D:  mov r8d, [r15 + rcx]    ← fault address = 0x0
```

### Register State (inferred from static analysis)

| Register | Value | Source |
|----------|-------|--------|
| `r15` | `0x0` (NULL) | Hash-table base pointer — never initialized |
| `rcx` | `(hash & mask) * 7` | Computed at `0x800806842-0x80080684A` |
| Effective address | `r15 + rcx = 0 + rcx = rcx` | Small value, in zero-page → fault |

### Crash Context (hash-table lookup)

```
0x800806830: add esi, 8                ← stride = 8 (linear probe)
0x800806833: cmp r8d, -1               ← check for empty slot (-1 sentinel)
0x800806837: je 0x80690C               ← if empty, exit loop
0x80080683D: add eax, esi              ← hash += stride
0x80080683F: and eax, r14d             ← hash &= mask
0x800806842: lea rcx, [rax*8]          ← rcx = hash * 8
0x80080684A: sub rcx, rax              ← rcx = hash * 7 (entry size = 28 bytes)
0x80080684D: mov r8d, [r15 + rcx]      ← **CRASH** — r15 (table base) is NULL
0x800806851: cmp r8d, r9d              ← compare entry key with search key
0x800806854: jne 0x806830              ← if no match, continue probe
0x800806856: add rcx, r15              ← rcx = &entry (if match found)
0x800806859: movzx edx, byte [rcx+0x28] ← entry->field_at_0x28
...
```

### Hash-Table Structure

| Field | Offset | Type | Purpose |
|-------|--------|------|---------|
| key | `+0x00` | `int32` | Hash key (compared with `r9d`) |
| ? | `+0x04..+0x17` | `byte[20]` | Unknown |
| pointer | `+0x18` | `void*` | Data pointer |
| flag | `+0x20` | `byte` | Type flag (compared with 1) |
| ? | `+0x21..+0x27` | `byte[7]` | Padding |
| type | `+0x28` | `byte` | Type field |

Entry size = `0x1C` (28 bytes), matching `rcx = hash * 7` (7 × 4 bytes = 28).

### NULL Source

`r15` (the hash-table base) is loaded earlier in the function (not shown in the crash-context window). Based on the entry structure (key + pointer + type), this is likely an **IL2CPP internal type/method lookup table** — possibly:
- `s_TypeInfoTable` (allocated in `MetadataCache::Initialize` from `s_Il2CppMetadataRegistration->typesCount`)
- `s_GenericClassTable`
- `s_MethodTable`

If `MetadataCache::Register` never ran, `s_Il2CppMetadataRegistration = NULL`, so `MetadataCache::Initialize` cannot compute `typesCount` → allocates a zero-size table → `s_TypeInfoTable = NULL` (or a dangling minimal allocation).

### First Initialization Failure

The NULL in `r15` traces back to:
1. `MetadataCache::Register` not being called (registration globals stay NULL)
2. `MetadataCache::Initialize` allocating a NULL/zero-size table
3. EBOOT code looking up a type/method in the NULL table → crash

**The crash is causally downstream of missing registration, but occurs in EBOOT code (not PRX code).**

## 9. Hypothesis A — IL2CPP Registration Never Occurs

### Status: **PARTIALLY CONFIRMED (static evidence); NOT VERIFIED (runtime evidence)**

### Evidence FOR

1. `[0x801E51240] = NULL` — but this is a lazy cache, not a registration global (see §7)
2. Crash at `0x80080684D` with NULL hash-table base — consistent with missing registration
3. The registration call site at `0x804F04C5C` is guarded by `pthread_once`-like checks — if the guard fails, registration is skipped

### Evidence AGAINST

1. `il2cpp_init` returns 0 (success) — if `Runtime::Init` failed, `il2cpp_init` should return non-zero
2. All 4 DT_INIT modules return 0 — no abort/failure detected
3. The registration structs (CodeRegistration, MetadataRegistration) are valid and populated
4. The `s_Il2CppCodegenRegistration` function-pointer struct at `0x808958220` is correctly populated by RELA (`[0x808958220] = 0x804D9C620`)

### Conclusion

The registration chain EXISTS and is REACHABLE. The most likely failure mode is:

**The guard at `0x804F04BE2` (`je 0x230C6E`) or `0x804F04BF7` (`jle 0x230C7B`) is incorrectly taken, causing the registration call at `0x804F04C5C` to be skipped.**

The guard calls NID `aI+OeCz8xrQ` (PLT `0x804FC1970`). If SharpEmu's HLE for this NID returns an incorrect value (e.g., always 0, or a thread ID that matches the stored global `[0x808B53D24]`), the guard would think initialization already happened and skip registration.

**This requires runtime verification.** Recommended instrumentation:
- Log entry to `0x804F04BA0` (Runtime::Init)
- Log the guard branch decisions at `0x804F04BE2` and `0x804F04BF7`
- Log entry to `0x804F04C5C` (the `call [rax]` instruction)
- Log entry to `0x804D9C620` (Il2CppCodegenRegistration)
- Log entry to `0x804F23280` (MetadataCache::Register)
- After `il2cpp_init` returns, read `[0x808B542E8]`, `[0x808B542F0]`, `[0x808B542F8]` — should be non-NULL if registration ran

## 10. Hypothesis B — `0x801E51240` is Misidentified

### Status: **CONFIRMED**

### Proof

`0x801E51240` is a **lazy cache** for the return value of EBOOT function `0x4BD620`:

1. **Location:** EBOOT vaddr `0x1E51240`, in `PT_LOAD[7]` BSS (zero-initialized)
2. **Single writer:** `0x8013EF019` (`mov [0x801E51240], rax`), only executed if:
   - `0x4BD620` returns non-NULL (`test rax, rax; je skip`)
   - Bounds check passes (`cmp esi, [global]; jae skip`)
3. **Single LEA reader:** `0x8013EEFF1` (`lea rdx, [0x801E51240]`)

The NULL value is caused by `0x4BD620` returning NULL (or failing bounds checks), **not** by missing IL2CPP registration. While `0x4BD620` MAY be an IL2CPP API function (e.g., `il2cpp_class_from_name`) that depends on registration, the NULL at `0x801E51240` is a **symptom** of upstream failure, not a direct indicator of registration status.

### Corrected State Model

```

## 11. Prosper Comparison

### Architecture

| Aspect | Prosper | SharpEmu |
|--------|---------|----------|
| Type | User-space compatibility layer (Wine-shaped) | Direct-execution emulator |
| CPU | Native x86_64 (no emulation) | Native x86_64 (direct execution) |
| IL2CPP HLE | **NONE** — relies entirely on guest binary's IL2CPP runtime | Partial HLE (IL2CPP API table, C++ ABI) |

### Module Initialization Flow (Prosper)

1. **Preload modules** in fixed order at fixed bases (`boot_program.cpp:124-169`):
   - `eboot.bin` @ `0x410000000`
   - `Il2cppUserAssemblies.prx` @ `0x440000000`
   - `libc.prx` loaded LAST (deepest dependency, init_array runs first)
2. **3-pass link** (`linker.cpp:32-186`):
   - Pass 1: Parse SELF, build relocatable image
   - Pass 2: Resolve imports (cross-module exports)
   - Pass 3: **Apply relocations** (AFTER imports resolved)
3. **Collect init functions** (`linker.cpp:158-184`):
   - Module 0 (eboot) EXCLUDED (runs own ctors via `_start`)
   - For each dependent module (reverse load order):
     - Add `DT_INIT` to init_fns
     - Add each `DT_INIT_ARRAY` entry to init_fns
   - **init_array entries read from RELOCATED image** (after Pass 3)
4. **Execute inits** (`exec_image_linux.cpp:3582-3636`):
   - Each init called as `module_start(argc, argp)` with `(0, NULL)` by default
   - `sigsetjmp` recovery — faulting init is logged + skipped (best-effort)

### Sony DT Tag Handling (Confirmed)

`0x61000017 = DT_SCE_EXPORT_LIB_ATTR` (NOT init_array). Prosper's loader does NOT switch on `0x61000017` at all. Prosper uses standard `DT_INIT` (`0xc`) / `DT_INIT_ARRAY` (`0x19`) / `DT_INIT_ARRAYSZ` (`0x1b`) only.

**EXP-190's finding is confirmed.** EXP-187/188/189's hypothesis that `0x61000017` is `DT_SCE_INIT_ARRAY` was correctly revised.

### Prosper's Unity-Specific Quirk (PT_DYNAMIC mis-based offset)

Prosper has a workaround in `module.cpp:131-158` for `Il2cppUserAssemblies.prx` where the `PT_DYNAMIC` program header's `p_offset` is "mis-based" — `elf_base + p_offset` points at garbage, causing the DYNAMIC table to read as junk → 0 exports / 0 init → IL2CPP never bootstraps.

**This does NOT apply to Yatzi's PRX.** Static analysis (Step 1) confirmed that `PT_DYNAMIC p_offset` is SANE for all of Yatzi's modules (eboot, Il2cppUserAssemblies.prx, libc.prx, etc.). The Prosper workaround is for a different Unity build/version.

### Prosper's HLE Relevant to IL2CPP

| HLE | NID | Prosper Behavior | SharpEmu Status |
|-----|-----|------------------|-----------------|
| `__cxa_guard_acquire` | — | **REAL** — mutex+condvar, recursive-init detection | UNKNOWN — needs verification |

### Key Differences from SharpEmu

1. **Prosper does NOT HLE `il2cpp_init`** — it lets the PRX's own `il2cpp_init` run natively. If SharpEmu HLEs `il2cpp_init` to just return 0, `Runtime::Init` never runs.
2. **Prosper applies relocations BEFORE reading init_array** — if SharpEmu reads init_array before RELA, entries are raw addends/NULL.
3. **Prosper implements `__cxa_guard_acquire` atomically** — if SharpEmu's version is non-atomic, the `pthread_once`-like guard in `Runtime::Init` may behave incorrectly.
