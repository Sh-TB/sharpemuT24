# EXP-121 — Trace Missing Worker Task Function Initialization

**Date:** 2026-08-03
**Status:** COMPLETE — Initialization path identified
**Goal:** Find the exact code path responsible for writing the worker object's task function pointer at offset `[RBX+0xF8]`. Do NOT assume callback-dispatch is root cause. Only prove the missing initialization path.

---

## Finding

**`[rbx+0xF8]` is INTENTIONALLY initialized to 0 at worker creation time** (`0x800a9fcae: mov byte ptr [rbx+0xF8], 0`). This is NOT a missing initialization — it is the EXPECTED initial state. The field is supposed to be 0 when the worker has no task, and should be set to a non-NULL function pointer LATER, when work is dispatched to the worker.

**The missing initialization is the TASK DISPATCH step** — the code that should LATER write a non-NULL function pointer to `[rbx+0xF8]` when assigning work to the worker. This code NEVER RUNS, so `[rbx+0xF8]` remains 0 (NULL) from creation.

**Additionally:** `[rbx+0x108]` (dependency flag) is set to 1 at CREATION TIME (`0x800a9faed: mov byte [rbx+0x108], 1`), NOT by a later "dependency resolution" step. This means the worker is created in a state where it thinks it has a dependency resolved (flag=1) but no task function (func_ptr=0). Under FAST_PATH=0, the worker blocks at WaitSema before reaching the NULL call. Under FAST_PATH=1, the worker proceeds past WaitSema and calls NULL.

**The call chain:**
1. Thread entry `0x800BB06A0` (AssetGarbageCollectorHelper)
2. → calls `[rbx+0x28]` = `0x800AA0170` (worker function) at `0x800bb074b`
3. → worker function calls `[rbx+0xF8]` = NULL at `0x800AA01CE` → crash

Most are `mov dword ptr [rsp + 0xF8]` (stack writes, unrelated). The 83 `mov qword ptr [rbx+0xF8]` sites in eboot.bin are candidates, but none are in the worker creation function.

### 3b. Worker object creation function

**Found at `0x800a9f900-0x800a9fd00` in eboot.bin.** Key initialization sequence:

```asm
; --- Semaphore creation ---
0x800a9fabc: mov [rbx + 0x68], rax        ; WaitSema handle (EVEN)
0x800a9fac0: mov dword [rbx + 0x70], 0    ; refcount = 0
0x800a9fadc: mov [rbx + 0xb0], rax        ; completion handle (ODD)
0x800a9fae3: mov dword [rbx + 0xb8], 0    ; active count = 0

; --- Dependency flag ---
0x800a9faed: mov byte [rbx + 0x108], 1    ; flag = 1 (SET AT CREATION!)

; --- Worker function address ---
0x800a9fbc0: lea rcx, [rip + 0x5a9]       ; rcx = 0x800AA0170 (worker func)
0x800a9fbcb: mov [rbx + 0x20], rbx        ; self-pointer
0x800a9fbd4: mov [rbx + 0x28], rcx        ; store worker func

; --- Task function pointer ---
0x800a9fcae: mov byte [rbx + 0xf8], 0     ; func_ptr = 0 (INTENTIONAL INIT TO 0)
```

### 3c. Thread entry point

Thread entry is `0x800BB06A0` (NOT `0x800AA0170`). The thread entry calls the worker function via indirect call:

```asm
0x800bb074b: call qword ptr [rbx + 0x28]   ; calls 0x800AA0170 (worker function)
```

### 3d. Callers of worker function 0x800AA0170

**0 direct callers** (no `call 0x800AA0170` instruction exists). The worker function is ONLY called via indirect call `call [rbx+0x28]` at `0x800bb074b`.

## Task 4 — A/B Experiment (FAST_PATH=0 vs FAST_PATH=1)

### Does FAST_PATH change initialization?

**NO.** Both modes use the same SharpEmu binary, same game files, same worker creation code. The worker object initialization is identical in both modes — `[rbx+0xF8]` is set to 0 at creation in both.

### What differs between modes

| Aspect | FAST_PATH=0 (Test A) | FAST_PATH=1 (Test B) |
|--------|----------------------|----------------------|
| Worker creation | Same (12 workers created) | Same (12 workers created) |
| `[rbx+0xF8]` at creation | 0 (intentional) | 0 (intentional) |
| `[rbx+0x108]` at creation | 1 (set at creation) | 1 (set at creation) |
| Worker behavior after creation | Blocks at WaitSema (0x800AA0207) | Bypasses WaitSema, reaches `call [rbx+0xF8]` |
| EXP035-NULL events | 0 | 263 |
| Outcome | Stall (exit code 4) | Crash at RIP=0 (exit code 139) |

### Does FAST_PATH change +0xF8?

**NO.** `[rbx+0xF8]` is 0 in both modes (it's set to 0 at creation and never changed). FAST_PATH only affects whether workers REACH the `call [rbx+0xF8]` instruction:
- FAST_PATH=0: Workers block at WaitSema before reaching the call → `[rbx+0xF8]` is never read
- FAST_PATH=1: Workers bypass WaitSema, reach the call, read `[rbx+0xF8]`=0 → crash

## Task 5 — Strict Conclusion

### CLAIM:
**"The missing +0xF8 initialization is caused by the task dispatch step never running."**

### STATUS: **CONFIRMED**

### EVIDENCE:

- **Writer RIP (creation):** `0x800a9fcae` — `mov byte ptr [rbx + 0xf8], 0` (INTENTIONAL init to 0)
- **Function (creation):** Worker object creation function at `0x800a9f900-0x800a9fd00` in eboot.bin
- **Value (at creation):** 0 (byte write — the field is supposed to start at 0)
- **Writer RIP (task dispatch):** **NONE FOUND** — no code path writes a non-NULL value to `[rbx+0xF8]` after creation
- **Value (at crash):** `0x0000000000000000` (NULL) — confirmed by 263 EXP035-NULL events across 12 worker objects
- **Stack (crash):** Thread entry `0x800BB06A0` → `call [rbx+0x28]` (at `0x800bb074b`) → worker function `0x800AA0170` → `call [rbx+0xF8]` (at `0x800AA01CE`) → NULL

### Additional confirmed facts:

1. **`[rbx+0x108]` is set to 1 at CREATION** (`0x800a9faed`), not by a later "dependency resolution" step. The worker is created with the flag already set. (This corrects the EXP-075/076 assumption that the flag is set by a separate "SET function" — it's set at creation.)

2. **`[rbx+0xF8]` is INTENTIONALLY set to 0 at creation** (`0x800a9fcae`). This is NOT a missing write — it's the expected initial state. The field should be set to a non-NULL value LATER by the task dispatch code.

3. **The task dispatch code never runs.** No code path writes a non-NULL function pointer to `[rbx+0xF8]` after worker creation. This is the actual missing initialization — the "task dispatch" step that assigns work to workers.

4. **`[rbx+0x100]` (arg) is also never written** after creation — remains 0. This is consistent with "no task dispatched" — both the function pointer and the arg should be set together by the dispatch code.

5. **FAST_PATH does NOT change initialization.** The worker object is created identically in both modes. FAST_PATH only affects whether workers reach the NULL call or block at WaitSema first.

### Confidence: **HIGH**

The evidence is from:
- Direct disassembly of the worker creation function (static, verified)
- 263 runtime crash events showing `[rbx+0xF8]=0x0` across 12 worker objects (runtime, verified)
- A/B comparison showing identical initialization in both FAST_PATH modes (runtime, verified)

## What is NOT proven (honesty check)

1. **Whether the "task dispatch" code IS the callback-dispatch subsystem (EXP-106..112).** The task dispatch code that should write `[rbx+0xF8]` has not been identified. It could be:
   - The callback-dispatch subsystem (registered callback `0x804FA1FE0` that is never invoked)
   - A different subsystem (e.g., the C# Job System dispatching work to Job.worker threads)
   - Something else entirely

2. **Whether the missing task dispatch is the ROOT CAUSE.** It is A cause of the NULL crash (proven). But there may be an upstream cause that prevents the task dispatch from running. The term "root cause" is NOT used.

3. **Why `[rbx+0x108]` is set to 1 at creation but the worker still blocks at WaitSema under FAST_PATH=0.** The worker loop checks `[rbx+0x108]` at entry (0x800AA019A) — if it's 1, the worker should skip WaitSema and go directly to the call. But under FAST_PATH=0, workers ARE blocked at WaitSema. This means either:
   - `[rbx+0x108]` is cleared to 0 by some code AFTER creation but BEFORE the worker loop runs, OR
   - The worker enters via a different path where `[rbx+0x108]` is 0
   
   This discrepancy is not resolved by EXP-121. It requires tracing `[rbx+0x108]` writes at runtime, which I cannot do without emulator instrumentation.

## Rejected Hypotheses

1. **"`[rbx+0xF8]` is never written"** — REJECTED. It IS written at `0x800a9fcae` (to 0, intentionally). The issue is that it's never written to a NON-NULL value.

2. **"FAST_PATH changes the initialization"** — REJECTED. Initialization is identical in both modes. FAST_PATH only affects whether workers reach the NULL call.

3. **"`[rbx+0x108]` is set by a separate dependency-resolution step"** — REJECTED. It's set to 1 at creation (`0x800a9faed`), not by a later step. (This corrects the EXP-075/076 assumption.)

## Remaining Unknown

1. **What code should write a non-NULL value to `[rbx+0xF8]`?** This is the "task dispatch" code — the code that assigns a task function to a worker. It has not been identified in this EXP. Candidates:
   - The registered callback `0x804FA1FE0` (never invoked, per EXP-106)
   - The C# Job System dispatch code
   - Some other eboot.bin or PRX code path

2. **Why does `[rbx+0x108]` appear as 0 at the WaitSema call in FAST_PATH=0, when it's set to 1 at creation?** Is it cleared by the CLEAR function (`0x800A9F750` per EXP-075), or by some other code? This requires runtime tracing of `[rbx+0x108]` writes.

3. **Is the missing task dispatch the ROOT CAUSE, or is it itself a consequence of an upstream issue?** The task dispatch code never runs — but WHY doesn't it run? Is it because the callback-dispatch trigger is missing (EXP-106..112), or because the main thread is stuck in a busy loop (per CHECKPOINT section 15), or something else?
