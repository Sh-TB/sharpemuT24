## Step 2: Analyze Conditional Gates

### Gate at 0x804FB8E60

**Instruction decode:**
```
0x804FB8E60: 83 3D 31 ED DA 03 00   cmp byte [rip+0x03DAED31], 0
0x804FB8E67: 74 28                   je +0x28
```

**Byte address calculation:**
- Gate address: 0x804FB8E60
- Instruction length: 7 bytes (cmp byte [rip+disp32], imm8)
- Displacement: 0x03DAED31
- Byte address: 0x804FB8E60 + 7 + 0x03DAED31 = **0x808D67B98**

**Byte location analysis:**
- PRX load base: 0x804CD5000
- Byte vaddr in PRX: 0x808D67B98 - 0x804CD5000 = 0x404EB98
- PRX segment layout:
  - Seg 3: vaddr=0x3C50000, filesz=0x21CBC8, memsz>filesz (BSS)
  - File-backed range: 0x3C50000 to 0x3E6CBC8
  - Byte vaddr 0x404EB98 > 0x3E6CBC8
  - **Byte is in BSS (beyond file-backed region)**
  - **Byte value at runtime = 0x00** (BSS is zero-initialized)

**Branch analysis:**
- `cmp byte [0x808D67B98], 0` → compares 0 with 0 → ZF=1 (equal)
- `je +0x28` → ZF=1, so **JUMP IS TAKEN**
- Jump target: 0x804FB8E60 + 7 + 2 + 0x28 = **0x804FB8E91**

**Not-taken path (byte != 0, initialization runs):**
```
0x804FB8E69: B8 12 0F 00 00    mov eax, 0x0F12
0x804FB8E6E: BA 01 00 00 00    mov edx, 1
0x804FB8E73: 48 8D 0D 1E C8 B9 03  lea rcx, [rip+0x3B9C81E]
0x804FB8E7A: C4 E2 F8 F7 C7    ... (some instruction)
0x804FB8E7F: 48 ...
```
This looks like initialization code with specific parameters (eax=0x0F12, edx=1).

**Write search:**
- Searched for `C6 05` (mov byte [rip+disp32], imm8) instructions targeting 0x808D67B98
- Searched for `48 89 05` / `4C 89 05` (mov [rip+disp32], reg) targeting 0x808D67B98
- **Result: ZERO writes found** — the byte is NEVER set by any code in the PRX

### Root Cause Thinking Model Answers

1. **Who called it?** dt_init (0x804CD5010) via JMP thunk at 0x804FA6030
2. **Why was it called?** One-time initialization guard — checks if init has already run
3. **What should happen before it?** The byte should be set to non-zero by RELA relocation or prior init step
4. **What should happen after it?** PlayerLoop registration, then dispatch loop
5. **Did it fail?** YES — the byte is in BSS (always 0), and no code ever writes to it. The je is ALWAYS taken.
6. **Real or artifact?** REAL — the byte address is confirmed in BSS, zero-initialized
7. **Part of final execution path?** YES — called directly from dt_init at offset 0x804CD517F

### Interpretation

The gate logic is:
- `byte == 0` → `je` TAKEN → jump to 0x804FB8E91 (skip initialization)
- `byte != 0` → fall through → run initialization code (mov eax, 0x0F12; ...)

Since the byte is ALWAYS 0 (BSS, never written), the initialization code is ALWAYS SKIPPED.

**However**, there's an alternative interpretation: the `je +0x28` might jump TO the initialization code (not past it). In that case, `byte == 0` means "not yet initialized, jump to init code". Without seeing the code at 0x804FB8E91, we cannot definitively determine which interpretation is correct.

**The single-step trace (Step 1) will resolve this ambiguity.**

### Who sets this byte?

**No code in the PRX writes to this byte address.** Possible sources:
1. **RELA relocation** — R_X86_64_RELATIVE with r_offset targeting the byte address. Need to check PRX RELA table.
2. **IL2CPP API function** — An IL2CPP function called before the gate that sets the byte. The gate is called at dt_init offset 0x804CD517F. Functions called before this offset (0x804CD50E5, 0x804CD50F6, 0x804CD5141, 0x804CD5160, 0x804CD5174) might set it.
3. **HLE function** — A SharpEmu HLE implementation that should set the byte but doesn't.

### Key Correction

**The previous understanding was WRONG.** The 38000+ mutex calls do NOT happen during dt_init. They happen during **eboot execution** (after dt_init returns).

The correct flow is:
1. dt_init (0x804CD5010) runs and RETURNS SUCCESSFULLY (line 933)
2. During dt_init, the gate at 0x804FB8E60 is checked (at offset 0x804CD517F)
3. If the gate skips initialization, PlayerLoop registration is skipped during dt_init
4. dt_init returns, and eboot entry point (0x800000070) runs
5. Eboot calls IL2CPP API functions, triggering 38000+ mutex calls (type init)
6. Eboot creates worker threads and enters the dispatch loop
7. Dispatch loop blocks on WaitSema(0x81) because no bootstrap job was submitted

### Main Thread Only

The main thread's exact RIP timeline:
1. **0x800000070** (eboot entry) — starts execution
2. Calls into IL2CPP API (via thunks in eboot that redirect to PRX)
3. IL2CPP type initialization runs (38000+ mutex calls)
4. Worker queue setup (semaphores 0x7C-0x90 created)
5. 13 AGC threads created
6. GC thread created
7. Dispatch loop entered (0x804F6E510)
8. WaitSema(0x81) → DEADLOCK

**No PlayerLoop registration HLE imports are called between steps 3 and 7.**

## New Facts Discovered

1. **dt_init RETURNS SUCCESSFULLY** — The IL2CPP module_start (dt_init at 0x804CD5010) runs and returns 0 at EXP-118 log line 933. The 38000+ mutex calls happen AFTER dt_init returns, during eboot execution.

2. **Gate byte is in BSS** — The byte checked by the gate at 0x804FB8E60 is at address 0x808D67B98, which is in the PRX's BSS segment (beyond file-backed region). Its runtime value is ALWAYS 0.

3. **No code writes to the gate byte** — Exhaustive search for `C6 05` (mov byte [rip+disp32], imm8) and `48/4C 89 05` (mov [rip+disp32], reg) instructions targeting 0x808D67B98 found ZERO writes.

4. **arch_raise_user IS called in OLD log** — In EXP-118 (without PRXs), `arch_raise_user` (J3edELK4FvM) is called at line 8319, but the game doesn't abort — it continues to the deadlock. This suggests arch_raise_user is handled or non-fatal.

5. **Gate not-taken path has init parameters** — The code after the je (not-taken, byte != 0) loads `eax=0x0F12`, `edx=1`, `lea rcx, [rip+0x3B9C81E]`, which looks like initialization parameters. This suggests the not-taken path IS the initialization path.

6. **Timeline correction** — The 38000+ mutex calls happen during eboot execution (after dt_init returns), NOT during dt_init. The gate is checked during dt_init (before return).
