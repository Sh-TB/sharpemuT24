## Confirmed Facts (NEW, runtime-verified in EXP-118)

1. **Placing real `unity_builtin_extra` (820KB) and `unity default resources` (859KB) in `Media/Resources/` eliminates the `rip=0x800B28A0D` abort.** Runtime-verified: 0 occurrences of the abort address, 0 occurrences of `Internal-ErrorShader`, 0 UNMAPPED faults. (EXP-118)

2. **Under `FAST_PATH=0` (clean run, no bypass), the game stalls on `WaitSema` deadlock, NOT on the shader abort.** 13 `AssetGarbageCollectorHelper` workers blocked on handles 0x5C-0x74 (EVEN handles), 1 additional thread blocked on handle 0x83. (EXP-118)

3. **The worker return address `0x800AA0207` is the same as EXP-078** — confirming this is the same worker spin/wait pattern, now observed under clean `FAST_PATH=0` semantics (not the contaminated `FAST_PATH=1` data from EXP-078). (EXP-118)

4. **The callback-dispatch/semaphore deadlock is REAL under `FAST_PATH=0`** — it is NOT an artifact of the `FAST_PATH=1` bypass. The deadlock reproduces with clean semaphore semantics. (EXP-118)

5. **The "missing shader" theory and the "callback-dispatch" theory are SEPARATE issues**, now both confirmed:
   - Missing shader: RESOLVED by placing real Unity resource files (EXP-118)
   - Callback-dispatch/semaphore deadlock: STILL PRESENT under clean `FAST_PATH=0` (EXP-118)

## Remaining Unknowns

1. **Why did the 2026-07-24 checkpoint run reach `VideoOutOpen`/`SubmitFlip` but EXP-118 did not?** The 2026-07-24 run used a different SharpEmu build (likely the `exp107` build or earlier) that may have had different code paths or environment variables. The clean build used in EXP-118 stalled earlier (on `WaitSema`) before reaching GPU init. This could be because:
   - The 2026-07-24 run had `FAST_PATH=1` enabled (masking the `WaitSema` deadlock, allowing the game to progress past it to GPU init, where the shader abort then fired)
   - OR: different SharpEmu build versions have different behavior
   - This requires investigation (potentially re-running with the exp107 build + real resources)

2. **What HLE primitive should fire to release the worker semaphores (0x5C-0x74)?** The 13 workers are correctly waiting on their personal semaphores (EVEN handles). Nobody signals them. The main thread is stuck somewhere (not directly visible in the stall snapshot). This is the same question from EXP-115's maintainer summary.

3. **What is `Thread-7FD674F612D0` (entry `0x804F88AA0`) blocked on handle 0x83?** This is a 14th thread, not one of the 13 `AssetGarbageCollectorHelper` workers. Handle 0x83 is in the "deadlocked" range (0x81-0x8D) per CHECKPOINT section 14. This may be a `Job.worker` thread (the C# Job System worker) that's idle waiting for work dispatch.

4. **Would the game progress further with `FAST_PATH=1` + real resources?** This would test whether the shader abort was the only thing preventing GPU init, or whether the `WaitSema` deadlock also blocks GPU init. (Requires another run — not done in EXP-118 per user instruction to use the same config that produced `rip=0x800B28A0D`.)
