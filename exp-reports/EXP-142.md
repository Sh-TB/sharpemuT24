## P1: Native il2cpp_resolve_icall Trace

### Challenge
`il2cpp_resolve_icall` (at `0x804ED8780`) is **direct-bridged** — it runs natively in guest code. We cannot intercept it via HLE dispatch. No `RESOLVER-TRACE` entries appear in the log because the resolver doesn't go through `TryCallGuestFunction`.

### Approach
Since we cannot trace `il2cpp_resolve_icall` at runtime, we verified:
1. Whether icall name strings exist in the binaries (they should, as static data)
2. Whether `il2cpp_init` runs (confirmed by `unity_mono_set_user_malloc_mutex` being called after it)
3. Whether the icall table could be empty (timing hypothesis)

## il2cpp_init Execution Confirmation

### Evidence that il2cpp_init runs:
1. `Import#2084: unity_mono_set_user_malloc_mutex` is called — this happens AFTER `il2cpp_init`
2. BST-WALK finds `il2cpp_init` at node #117 — the symbol exists in the BST
3. The resolver is direct-bridged — `il2cpp_init` is called natively via function pointer
4. Worker threads are created (13 `AssetGarbageCollectorHelper` + 1 GC scavenger) — this requires IL2CPP runtime to be initialized

### Conclusion:
`il2cpp_init` IS called and returns. The IL2CPP runtime initializes. The question is whether it SUCCEEDS completely.

## Remaining Hypothesis: Icall Registration Timing

### Unity registers icalls in phases:
1. **Phase 1 (during il2cpp_init):** Core IL2CPP API icalls (`il2cpp_class_*`, `il2cpp_method_*`, etc.)
2. **Phase 2 (during Unity runtime init):** Engine icalls (`UnityEngine.*`)
3. **Phase 3 (during PlayerLoop setup):** Job System icalls (`Unity.Jobs.*`)

### The timing issue:
From the execution timeline:
```
Line 2020: unity_mono_set_user_malloc_mutex (after il2cpp_init)
Line 2640: BST-WALK (resolver snapshot)
Line 2804: Worker threads created
Line 2964: Semaphore 0x81 created
Line 2980: GC thread scheduled
Line 2981: Main thread blocks on WaitSema(0x81)
```

The main thread blocks on `WaitSema(0x81)` at line 2981. If Job System icalls are registered in Phase 3 (PlayerLoop setup), and the dispatch loop starts BEFORE Phase 3 completes, the icall resolution would fail.

### On real PS5:
- The CPU is faster, so Phase 3 completes before the dispatch loop starts
- Or: the dispatch loop and Phase 3 run on different threads, and the timing works out

### On SharpEmu:
- The scheduling may be different, causing the dispatch loop to start before Phase 3
- Or: a missing HLE export causes Phase 3 to fail silently, preventing icall registration

## P3: Producer Verification

### Producer at eboot.bin @ 0x159d52:
- Address: `0x800159D52` (eboot base + 0x159D52)
- Instruction: `inc dword [r14+0x90]`
- This is the queue-push operation that increments the job counter

### Verification:
- The dispatch loop IS reached (return address `0x804F6E9EB` on stall stack)
- The dispatch loop performs `lock xadd [r14+0x90], -1` (consumer decrement)
- But the producer `inc [r14+0x90]` at `0x800159D52` is **never reached** (the job counter stays at 0)

### Conclusion:
The producer is NOT reached because the code that calls it (the bootstrap job submission via `Schedule_Injected` or `ScheduleBatchedJobs`) either:
1. Resolves to NULL via `il2cpp_resolve_icall` and silently skips
2. Is never called because an earlier initialization step failed

## Root Cause Classification

**[ ] Missing HLE export** — All critical HLE exports are implemented
**[ ] Resolver incomplete** — Native resolver works (BST-WALK finds all symbols)
**[ ] Return value propagation** — EXP-138 not needed (native path doesn't use TryCallGuestFunction)
**[x] IL2CPP initialization state** — Icall table may not be fully populated when dispatch loop starts
**[x] Timing/scheduling issue** — Dispatch loop may start before Job System icalls are registered
