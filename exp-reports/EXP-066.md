## Task 1: NULL Execute Source Analysis

### Finding

All 1,004 NULL execute faults come from the **same caller**: `0x800AA01D4` (worker thread task processing). The NULL is at `[rbx+0xf8]` — a function pointer in a task descriptor that was never set.

### Root Cause Chain

```
EXP-034 re-patching fails (0/232 import stubs patched)
↓
IL2CPP import stubs remain as fake heap stubs (return 0)
↓
Game calls IL2CPP API through fake stub → gets NULL
↓
Game stores NULL as task function pointer [rbx+0xf8]
↓
Worker thread calls [rbx+0xf8] → RIP=0
↓
TryRecoverNullExecuteFault recovers (1,004 times)
↓
Host stack corrupted (glibc stack canary mismatch)
↓
*** stack smashing detected ***: terminated
```

### Why EXP-034 Re-patching Fails

The re-patching code:
1. Iterates `_importEntries` (eboot's import stubs)
2. Looks up each entry's NID in Aerolib to get the function name
3. If the name starts with `il2cpp_`, looks up the real func_impl in `_resolverResults`
4. Patches the import stub with the real address

**The issue:** The NID-to-name lookup fails for most import entries. The eboot uses obfuscated PS5 NIDs that don't map to `il2cpp_*` names in Aerolib. So `funcName` is null for most entries, and they're skipped.

### Evidence

- `_resolverResults.Count` = 232 (all IL2CPP functions resolved with real addresses)
- `patched` = 0 (no import stubs were re-patched)
- The resolver DID find real func_impl addresses (e.g., `il2cpp_init` → `0x804ED85D0`)
- But the import stubs still point to fake heap stubs

## Task 3: IL2CPP Stub Fix Attempt

### Change Applied

Modified `DecideIl2CppReturnValue` to return fake object pointer for ALL il2cpp functions (instead of NULL for most). Integer-returning functions still return 0.

### Result

**No improvement** — still 1,004 NULL execute recoveries and stack smashing. The fix didn't help because the fake stubs use EXP-035 INT3-based tracing which bypasses `DecideIl2CppReturnValue` for most calls. The actual return value is set by the INT3 handler, not by `DecideIl2CppReturnValue`.

## Confirmed Findings

1. **Stack corruption is HOST-SIDE** (glibc `__fortify_fail`, not guest `__stack_chk_fail`)
2. **All 1,004 NULL executes come from `0x800AA01D4`** (worker task processing)
3. **EXP-034 re-patching fails** (0/232) because NID-to-name lookup fails for most imports
4. **The resolver DID find real func_impl addresses** (232 entries in `_resolverResults`)
5. **`DecideIl2CppReturnValue` fix had no effect** (stubs use INT3 handler, not this function)
6. **The real fix is to make EXP-034 re-patching work** — patch import stubs with real PRX func_impl addresses

## Disproven Hypotheses

1. ❌ Stack corruption is guest-side — it's HOST-SIDE (glibc)
2. ❌ `DecideIl2CppReturnValue` fix would reduce NULL executes — stubs use INT3 handler
3. ❌ The fake stubs call `DecideIl2CppReturnValue` — they use EXP-035 INT3 tracing

## Next Step (EXP-067)

### Fix EXP-034 re-patching

The re-patching fails because NID-to-name lookup fails. Two approaches:

**A) Match by address, not by name:** Instead of looking up NID → name → func_impl, directly match import stub addresses to resolver results by matching the symbol name the resolver was called with.

**B) Patch ALL import stubs that point to the fake heap:** Instead of matching by name, check if an import stub points to the fake heap region (`_il2cppHeap`). If so, replace it with the corresponding real func_impl from `_resolverResults`.

**C) Make the INT3 handler use `DecideIl2CppReturnValue`:** The EXP-035 INT3 handler currently sets RAX to a pre-computed value. Make it call `DecideIl2CppReturnValue` at runtime so the improved return values take effect.

Approach B is simplest and most robust.
