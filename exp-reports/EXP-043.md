# EXP-043 — Find Missing IL2CPP Pre-Initialization Path

## Date: 2026-07-30
## Status: COMPLETE — Multiple findings, pre-init mechanism still elusive

---

## Executive Summary

Exhaustive analysis of writes to `0x801E51240` found only ONE write site
(`0x8013EF019`), which runs AFTER `il2cpp_init`. No relocations target
this address. No TLS, no Sony-specific relocation, no constructor mechanism
sets it before `il2cpp_init`.

**Key discovery:** The PRX DT_INIT has a flag at `[0x808923E90]` that is
set to non-zero by a RELATIVE relocation (addend `0xA212F0`). This causes
the DT_INIT to ALWAYS jump to `base+0` (INT3), which never runs on SharpEmu.
On a real PS5, this jump might trigger the module start function, which
could be the missing pre-init mechanism.

---

## Task 1 — Exhaustive Write Tracing

### Results
- **RIP-relative MOV writes:** 1 (at `0x8013EF019` — after il2cpp_init)
- **LEA targeting 0x801E51240:** 1 (at `0x8013EEFF1` — argument, not write)
- **PRX writes:** 0 (PRX has 0 references to `0x801E51240`)
- **Relocation targeting 0x801E51240:** 0 (no RELATIVE, GLOB_DAT, or JUMP_SLOT)
- **Nearby relocations (±256 bytes):** 0
- **Struct initialization candidates:** 0

### Conclusion
`0x801E51240` is in pure BSS with no loader initialization. It can only
be set by runtime code. The only runtime write is at `0x8013EF019` which
runs after `il2cpp_init`.

## Task 3 — Sony Relocation Analysis

### Standard relocations
- `DT_RELA`: 49,850 entries — **0 target 0x801E51240**
- `DT_JMPREL`: 768 entries — **0 target 0x801E51240**

### Sony-specific relocations
- No `DT_SCE_INIT_ARRAY` in any module
- `PT_SCE_DYNAMIC` (ORBI) doesn't contain init callback address
- No relocation targets 0x801E51240 or nearby addresses

### PRX DT_INIT flag discovery
The PRX DT_INIT checks a flag at `[0x808923E90]`:
```asm
cmp [0x808923E90], 0   ; flag check
je return_zero          ; if 0, return 0
jmp 0x804CD5000         ; if non-zero, jump to base+0 (INT3!)
```

**The flag has a RELATIVE relocation** (addend `0xA212F0`), making it
non-zero at load time. This means the DT_INIT ALWAYS jumps to `base+0`.

On SharpEmu, `base+0` is INT3 (0xCC), causing SIGTRAP → recovered →
DT_INIT returns 0 without running the module start.

On a real PS5, this jump to `base+0` might be handled by the kernel
as a "module start" signal, triggering the real initialization.

### `__cxa_atexit` / `__cxa_finalize`
- Registration functions call `__cxa_atexit` to register destructors
- `__cxa_finalize` is NOT called during init (only at exit)
- Neither sets `0x801E51240`

### Registration list population
- List head at `[0x801E9DF28]` starts as NULL (no relocation)
- 871 registration functions write to this list
- But the list must be populated BEFORE the iterator runs
- The iterator (0x800B8D530) checks for NULL and skips if empty
- **Unknown mechanism populates the list before the iterator**

## Task 6 — Registration Table Analysis

### real_init (0x804F04BA0) calls
- Calls #1-6: Setup (allocator, string ops, PLT calls)
- **Call #7: CRASHES** (indirect callback via `[0x808958220]` = `0x804D9C620`)
- Calls #8-85: **NEVER REACHED** (metadata registration at `0x804F23320`,
  repeated calls to `0x804F21D70`)

### 0x804F21D70 (calls #18-85)
- This is a JMP stub to `0x804EEE8D0`
- `0x804EEE8D0` is a metadata initialization function
- It reads from `[0x808923D88]` and processes metadata entries
- **Never reached** because call #7 crashes first

## Task 7 — Controlled Reorder (not implemented)

### Challenge
The hash lookup at `0x8013EEFE7` requires:
1. A string key (built on stack, 11 bytes)
2. The hash function (`0x800ce3aa0`)
3. The hash lookup function (`0x8004bd620`)
4. A populated hash table (currently empty)

Running the hash lookup before il2cpp_init would fail because the hash
table has no entries. The entries are filled by calls #8-85 in real_init,
which run AFTER the callback at call #7.

### Circular dependency (confirmed)
```
il2cpp_init (call #7) → needs 0x801E51240 → set by hash lookup
hash lookup → needs hash table entries → filled by calls #8-85
calls #8-85 → run AFTER call #7 → never reached (call #7 crashes)
```

On a real PS5, this circular dependency is broken by a pre-init mechanism
that sets `0x801E51240` before `il2cpp_init` runs.

## Root Cause Summary

### What's missing
A **PS5 pre-init mechanism** that sets `0x801E51240` (and possibly other
metadata globals) before `il2cpp_init` runs. This mechanism is not
implemented in SharpEmu.

### Most likely candidate
The PRX DT_INIT's jump to `base+0` (INT3) might trigger the module start
function on a real PS5. The module start function would:
1. Call IL2CPP registration functions
2. Populate the metadata list
3. Fill the hash table entries
4. Set metadata globals like `0x801E51240`

On SharpEmu, the INT3 at `base+0` is recovered as SIGTRAP, and the
module start never runs.

### Alternative candidate
The registration list at `[0x801E9DF28]` is populated by an unknown
mechanism before the init function's iterator runs. This mechanism
might also set `0x801E51240`.

## Next Step (EXP-044)

1. **Investigate the PRX base+0 INT3:** On a real PS5, the INT3 at PRX
   base+0 might be handled by the kernel as a module start signal.
   Check if the PS5 SDK has a documented "module start" mechanism that
   replaces the INT3 with real code.

2. **Trace registration list population:** Add a write-watchpoint on
   `[0x801E9DF28]` to find what populates the list before the iterator.

3. **Check SharpEmu's PRX loader:** Verify if SharpEmu patches PRX base+0
   with real code or handles the INT3 differently.

4. **Pre-fill hash table:** As a workaround, manually populate the hash
   table entries from the metadata table at `0x1CC0080` before
   `il2cpp_init` runs. This requires understanding the entry format
   (12-byte entries: hash, key, value).
