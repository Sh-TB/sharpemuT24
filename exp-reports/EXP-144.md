## P1: sceKernelMkdir Analysis

The guest calls `sceKernelMkdir("/devlog")` — a PS5 system directory.

- HLE caught the exception and returned `PERMISSION_DENIED`

### After fix
- Added special case: `/devlog` → return `ALREADY_EXISTS`
- `PERMISSION_DENIED` is now 0 (eliminated)
- **Deadlock unchanged**: 13 signals, 0 on 0x81, 0 on 0x84

### Verdict: mkdir is NOT the blocker

## P3: Execution Timeline

### Complete timeline from mkdir to deadlock:

```
Line 2926: mkdir("/devlog") → ALREADY_EXISTS
Line 2927: sema.create 0x7D (Baselib_SystemSemaphore)
Line 2928-2965: 38000+ scePthreadMutexLock calls (massive loop)
Line 2966: sema.create 0x80 (Baselib_SystemSemaphore)
Line 2967: sema.create 0x81 (Baselib_SystemSemaphore — main thread's wait)
Line 2968: sema.create 0x82 (Baselib_SystemSemaphore)
Line 2969: sema.create 0x83 (SuspendSemaphore — GC thread)
Line 2970: sema.create 0x84 (ResumeSemaphore — GC thread resume)
Line 2971-2984: sema.create 0x85-0x90 (more Baselib_SystemSemaphore)
Line 2985: Thread-XXX (GC scavenger) scheduled
Line 2986: Main thread blocks on WaitSema(0x81)
Line 2999: Stall detected
```

### Key observations:

1. **38000+ mutex lock calls** between mkdir and semaphore creation
   - This is a massive loop doing `scePthreadMutexLock` + `scePthreadMutexUnlock`
   - Likely IL2CPP type initialization or metadata processing
   - This is probably NORMAL — IL2CPP processes thousands of types during init

2. **Semaphore creation burst**: 0x80 through 0x90 created in immediate succession
   - 0x81 (main wait), 0x83 (Suspend), 0x84 (Resume) all created together
   - This is the Unity Job System setup

3. **Main thread goes directly from semaphore creation to WaitSema(0x81)**
   - NO code between sema.create(0x81) and sema.wait(0x81) that could submit a job
   - The bootstrap job submission is MISSING from this sequence

4. **GC thread (Thread-XXX) is scheduled AFTER all semaphores are created**
   - GC thread immediately blocks on 0x83 (SuspendSemaphore)
   - GC thread never runs any work code

### First divergence point:

```
Expected:
  Create semaphores (0x80-0x90)
  → Submit bootstrap job (increment [r14+0x90], signal worker)
  → Schedule GC thread
  → Enter dispatch loop
  → WaitSema(0x81)

Actual:
  Create semaphores (0x80-0x90)
  → Schedule GC thread
  → Enter dispatch loop
  → WaitSema(0x81)
```

The bootstrap job submission step is **MISSING** between semaphore creation and GC thread scheduling.

## Decision Tree

### Case A: mkdir PERMISSION_DENIED causes skip → REJECTED
- mkdir now returns ALREADY_EXISTS
- Deadlock unchanged
- mkdir is NOT the cause

### Case B: Missing producer thread → REJECTED
- Only 14 threads created (13 workers + 1 GC)
- No separate bootstrap producer thread exists
- The main thread should submit the bootstrap job

### Case C: Dispatch loop entered too early → CURRENT HYPOTHESIS
- The main thread enters the dispatch loop immediately after creating semaphores
- The bootstrap job submission should happen BEFORE entering the dispatch loop
- But it doesn't — the main thread goes directly to WaitSema(0x81)

### Case D: 38000+ mutex calls are a problem → UNKNOWN
- The massive mutex loop may be normal IL2CPP type initialization
- Or it may be a spin loop waiting for something that never happens
- Need to investigate what the mutex loop is doing
