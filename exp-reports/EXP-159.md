## Task 1: Verify if MOV [0x801E51240], RAX Executes

### Static Analysis

Found **2 unique write instructions** to 0x801E51240 in eboot.bin:

1. **0x8007FD8F9** in function 0x8007FD320: `mov qword [0x801E51240], 0` — writes ZERO (clears)
2. **0x8013EF019** in function 0x8013EB6B0: `mov [0x801E51240], rax` — writes RAX (initialization)

The second write (0x8013EF019) is the **decoder's claimed store** — it IS inside function 0x8013EB6B0, matching the decoder hypothesis.

### Runtime Evidence

**Cannot verify execution at runtime.** The write instruction is in eboot native code, which runs without HLE interception. The runtime log only records HLE import dispatches, not native code execution.

### Decoder Call Chain Verification

The decoder claimed: `DT_INIT → 0x13FCE40 → 0x13EB6B0 → MOV [0x801E51240], RAX`

- 0x8013FCE40 IS a valid function (starts with push rbp)
- 0x8013EB6B0 IS a valid function (starts with push rbp)
- **BUT: 0x8013FCE40 does NOT directly call 0x8013EB6B0** — no direct CALL instruction found
- DT_INIT at 0x800000010 starts with push rbp (valid function prologue)

The decoder's call chain is **partially confirmed** — the functions exist and the store instruction exists, but the direct call from 0x13FCE40 to 0x13EB6B0 is NOT found.

## Task 5: If NULL, Why?

### Possible Reasons

1. **Store never executed** — function 0x8013EB6B0 might not be called
2. **Store executed with RAX==0** — the function might return 0
3. **Store overwritten** — the write at 0x8007FD8F9 writes 0 (clears)
4. **Relocation mismatch** — not applicable (address is in BSS, no relocation needed)
5. **Wrong image base** — NOT applicable (0x801E51240 is correctly mapped via ELF headers)

### Most Likely

**Cannot determine** without runtime instrumentation. The store instruction exists and is in a valid function, but we cannot verify if the function is called or what RAX contains when it executes.

## Task 6: Correlate with PlayerLoop and WaitSema(0x81)

### Runtime Evidence

The WaitSema(0x81) deadlock occurs at:
- RIP: 0x00006FFFFD001150 (WaitSema import stub)
- Semaphore: 0x81 (rdi=0x00006FFF00000081)
- Return address: 0x804F6E9EB (dispatch loop in PRX)

### Correlation

The 84 reads from 0x801E51240 suggest it's a critical runtime object. If it's NULL (never initialized), functions that read it would get NULL and likely skip critical initialization — potentially including PlayerLoop registration.

However, **we cannot prove** that 0x801E51240 being NULL is the cause of the PlayerLoop skip. The correlation is plausible but unverified.

### Is Missing Initialization Sufficient to Explain the Deadlock?

**Possibly, but unproven.** If 0x801E51240 is a runtime context object that PlayerLoop registration depends on, and it's NULL because the store never executes, that could explain the deadlock. But this requires runtime verification.

## Classification

### A. Store never executed
**Confidence: 30%**

The store instruction exists in function 0x8013EB6B0. We cannot verify if this function is called during Yatzi startup. The decoder's call chain (DT_INIT → 0x13FCE40 → 0x13EB6B0) is partially confirmed — the functions exist, but the direct call from 0x13FCE40 to 0x13EB6B0 is NOT found. The function might be called through a different path.

### B. Store executed with NULL
**Confidence: 20%**

If the function IS called, RAX might be 0 at the point of the store. The function has many CALLs before the store (100+ calls visible in the disassembly), and any of them could leave RAX as 0.

### C. Store executed correctly but later lost
**Confidence: 15%**

The write at 0x8007FD8F9 writes 0 to the same address. If this executes AFTER the initialization write, it would clear the value. But 0x8007FD8F9 is in a different function (0x8007FD320) and might execute at a different time.

### D. Store unrelated to WaitSema
**Confidence: 35%**

The 84 reads suggest this global is widely used, but we cannot prove it's directly related to the WaitSema(0x81) deadlock. The deadlock is in the PRX's dispatch loop, not in eboot code. The global might be unrelated to the PRX's PlayerLoop registration.

### Conclusion

**D. Unknown — more instrumentation required**

We cannot definitively classify the status of 0x801E51240 because:
1. The store instruction exists in eboot code
2. We cannot verify if it executes at runtime
3. We cannot dump the runtime value (no memory watch for non-exception paths)
4. The decoder's call chain is partially correct but not fully verified

**To resolve this, we need:**
1. INT3 at 0x8013EF019 (the store instruction) to verify execution
2. Memory watch on 0x801E51240 that triggers on every access (not just exceptions)
3. Single-step trace through function 0x8013EB6B0 to verify it's called
