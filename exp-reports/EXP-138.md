## Bug Confirmed (Static Analysis)

### Location
- **File:** `src/SharpEmu.Core/Cpu/Native/DirectExecutionBackend.cs`
- **Line 3500:** `returnValue = context[CpuRegister.Rax];` (in `TryCallGuestFunction`)
- **Line 874-878:** `CallNativeEntry` returns `int` (32-bit) — truncates 64-bit guest function pointers
- **Lines 4866-5071:** `ExecuteGuestThreadEntry` thunk — never writes host RAX back into `context.Rax`

### Asymmetry (proof that fix is feasible)
- **Continuation path** (`ExecuteGuestContinuationEntry`, line 5176): explicitly emits `EmitMovR64Imm(0x48, 0xB8, context[CpuRegister.Rax])` to write Rax back. **This path is correct.**
- **Bare callback path** (`ExecuteGuestThreadEntry`, line 4866-5071): **does NOT have this write-back**. Sentinel at lines 4983-5007 only restores R15/R14/R13/R12/RBP/RBX, not RAX.

### Mechanism
1. `TryCallGuestFunction` (line 3459) creates a brand-new `CpuContext`. The constructor at `CpuContext.cs:12` allocates `new ulong[16]` for registers — all zeroed. So inner `Rax = 0`.
2. `ExecuteGuestThreadEntry` (line 4875) allocates a 512-byte native thunk.
3. Thunk saves host RBX/RBP/RDI/RSI/R12/R13/R14/R15 (lines 4913-4924) and non-volatile XMM (line 4925), but **does NOT push RAX**.
4. Thunk loads context's Rsp/Rbp/Rdi/Rsi/Rdx/Rcx into host registers (lines 4933-4975), then `call rax` (line 4980-4981) jumps to guest entry.
5. Guest executes; on return, control hits the sentinel (line 4983+).
6. Sentinel (lines 4983-5007): `add rsp,8; mov rsp,[r10]; restore XMM; pop r15/r14/r13/r12/rbp/rbx; ret`. **No store of host RAX into `context[Rax]`.**
7. `CallNativeEntry` (line 877) returns `int nativeEntry()` — captures host EAX (low 32 bits) only.
8. `ExecuteGuestThreadEntry` line 5043 uses `nativeReturn` only for the log string.
9. `TryCallGuestFunction` line 3500: `returnValue = context[CpuRegister.Rax]` — reads inner context's Rax, which is still 0.

### Two-Bug-in-One
- **Bug A:** Inner `context.Rax` is never written back by the thunk.
- **Bug B:** Even if we used `nativeReturn`, `CallNativeEntry` returns `int` (32-bit), so 64-bit function pointers like `0x804ED9B90` would be truncated to `0xF4ED9B90` (sign-extended wrong on Linux/x86-64).

Both must be fixed.

## Fix Patch (Proposed)

### Change 1: `CallNativeEntry` signature (DirectExecutionBackend.cs:874-878)

```diff
- private unsafe static int CallNativeEntry(void* entry)
- {
-     var nativeEntry = (delegate* unmanaged[Cdecl]<int>)entry;
-     return nativeEntry();
- }
+ private unsafe static ulong CallNativeEntry(void* entry)
+ {
+     var nativeEntry = (delegate* unmanaged[Cdecl]<ulong>)entry;
+     return nativeEntry();
+ }
```

### Change 2: `ExecuteGuestThreadEntry` capture (DirectExecutionBackend.cs:5032-5044)

```diff
- var nativeReturn = CallNativeEntry(ptr);
+ var nativeReturn64 = CallNativeEntry(ptr);
  if (ActiveGuestThreadYieldRequested)
  {
      reason = ActiveGuestThreadYieldReason ?? "guest thread blocked";
      return GuestNativeCallExitReason.Blocked;
  }
  if (ActiveForcedGuestExit)
  {
      reason = LastError ?? "guest thread forced exit";
      return GuestNativeCallExitReason.ForcedExit;
  }
- reason = $"returned 0x{nativeReturn:X8}";
+ reason = $"returned 0x{nativeReturn64:X16}";
+ // Capture host RAX into context so TryCallGuestFunction can read it.
+ context[CpuRegister.Rax] = nativeReturn64;
  return GuestNativeCallExitReason.Returned;
```

### Change 3: Same fix in `ExecuteGuestContinuationEntry` (line 5200)
Same pattern — change `nativeReturn` to `nativeReturn64`, write back to `context[CpuRegister.Rax]`. Note: continuation path already has the manual `EmitMovR64Imm(0x48, 0xB8, ...)` at line 5176 to set Rax going IN; this change captures it going OUT.

### Change 4: Same fix at line 5482 and 5491 (`CallNativeEntry` callers)
Two more call sites need their `nativeReturn` variable type changed from `int` to `ulong`.

### Change 5: Audit `TryCallGuestFunction` line 3500
No change needed — once `context.Rax` is populated by Change 2, line 3500 will correctly read the real return value.

## My Additional Considerations (Beyond User's List)

### 138.16 Test the `Blocking` resume path
`TryCallGuestFunction` line 3488-3493 handles the case where the inner guest callback blocks (calls an HLE import that blocks). The `ResumeBlockedNestedGuestCallback` resumes it. After resume, does `context.Rax` get populated correctly?

The blocking path goes through `ExecuteGuestContinuationEntry` (line 5073+) which DOES have the `EmitMovR64Imm(0x48, 0xB8, ...)` Rax write-back at line 5176. So blocking resume should be correct — but verify with a test.

### 138.17 Test multi-threaded scenarios
`TryCallGuestFunction` runs synchronously on the calling host thread. But what if the calling host thread is itself a guest worker thread? Verify the host-RSP storage (TLS-indexed via `_hostRspSlotTlsIndex`) correctly isolates between threads.

### 138.18 Audit other `CallNativeEntry` callers
Lines 5482 and 5491 also call `CallNativeEntry`. Verify these paths also need the `ulong` return type change.

### 138.19 Verify `delegate* unmanaged[Cdecl]<ulong>` ABI
On Linux x86-64, `ulong` return is in RAX (full 64 bits). Cdecl on x86-64 is identical to SysV ABI (caller-cleans-stack is irrelevant since x86-64 passes args in registers). This should work without issue.

### 138.20 Test with a synthetic guest function that returns a known 64-bit value
Before testing Yatzi, write a minimal C program that SharpEmu can load as a "guest" which:
1. Calls a SharpEmu HLE export that uses `TryCallGuestFunction`
2. The HLE export invokes a guest function that returns 0xDEADBEEFCAFEBABE
3. Verify the HLE export sees 0xDEADBEEFCAFEBABE, not 0

This is a unit-test-style validation that doesn't depend on Yatzi or Dreaming Sarah.
