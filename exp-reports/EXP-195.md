# EXP-195 — Autonomous IL2CPP + NULL-Crash Investigation Campaign

## Executive Result

**ROOT CAUSE IDENTIFIED** ✅ — SharpEmu stubs `il2cpp_init` to return 0, bypassing the PRX's actual `il2cpp_init` → `Runtime::Init` → `Il2CppCodegenRegistration` → `MetadataCache::Register` call chain. This leaves all IL2CPP registration globals (`s_Il2CppCodeRegistration`, `s_Il2CppMetadataRegistration`, `s_Il2CodegenOptions`) at NULL, `s_TypeInfoTable` never gets allocated, and EBOOT's hash-table lookups crash with NULL base (`r15=0`) at `0x80080684D: mov r8d, [r15+rcx]`.

**FIX APPLIED** (source-level): Removed the `il2cpp_init`/`il2cpp_shutdown` stub in `DirectExecutionBackend.Imports.cs` line 2411 (so it falls through to runtime symbol resolution → PRX's actual `il2cpp_init`), and removed the `1D0H2KNjshE`/`hsi9drzHR2k` stubs in `GameCompatExports.cs` (which the source comment explicitly warned corrupt Yatzi's IL2CPP state — these were observed being called 80,000+ times in the EXP-195 baseline run).

**FIX VALIDATION**: ⚠️ BLOCKED by package compatibility — SharpEmu cannot be rebuilt locally because Avalonia 11.3.18, Silk.NET 2.23.0, HarfBuzzSharp 8.3.1.1, SkiaSharp 2.88.9, and Microsoft.DotNet.PlatformAbstractions 3.1.6 all report `NU1202: does not support any target frameworks` for net10.0. Both .NET 9 and .NET 10 SDKs were attempted. The pre-built `SharpEmu.bin` was built with an older environment that is no longer reproducible.

**CAMPAIGN STATUS**: STOPPED at hard external blocker (cannot rebuild SharpEmu to validate fix). All static analysis is complete; runtime validation requires either:
1. Upstream Avalonia/Silk.NET package updates to support net10.0
2. A pre-cached NuGet package store from a working build environment
3. A different build approach (e.g., downgrading to net8.0)

## IL2CPP Reference Matrix

See above table. **Conclusion**: All major IL2CPP analysis tools (Il2CppInspector, Il2CppDumper, kp7742 reference runtime) agree on:
1. Registration is called from a C++ static initializer (NOT from `il2cpp_init` directly)
2. The signature is `il2cpp_codegen_register(CodeRegistration*, MetadataRegistration*, CodegenOptions*)`
3. `MetadataCache::Register` stores the 3 args to file-scope statics
4. `Runtime::Init` calls `ExecuteInitializations` then `MetadataCache::Initialize` (which allocates `s_TypeInfoTable` from `s_Il2CppMetadataRegistration->typesCount`)
5. PS5 uses `e_entry`/`DT_INIT` (the two-table walker), not standard `DT_INIT_ARRAY`

This matches what we see statically in Yatzi's PRX (EXP-194 confirmed all of this).

### Guard pattern (pthreads_once-like)

The registration call at `0x804F04C5C` is preceded by guard checks:
- `0x804F04BD0`: `call NID aI+OeCz8xrQ` (PLT `0x804FC1970` → GOT `0x8089245E0`) — likely `pthread_self` or thread ID lookup
- `0x804F04BE2`: `je 0x230C6E` (skip if thread matches stored value — recursive init)
- `0x804F04BED`: `lock xadd [0x808B53CF8], eax` (atomic counter decrement)
- `0x804F04BF7`: `jle 0x230C7B` (skip if counter ≤ 0 — another thread is initializing)

If `il2cpp_init` is stubbed to return 0, **`Runtime::Init` is never entered** because the call chain `il2cpp_init → Runtime::Init` is severed at the stub.

## 0x801E51240 Identity

### CONFIRMED: NOT an `Il2CppClass*` global

`0x801E51240` is a **lazy cache** for the return value of EBOOT function `0x4BD620`:

| Attribute | Value |
|-----------|-------|
| Address | `0x801E51240` (runtime), `0x1E51240` (EBOOT vaddr) |
| Segment | EBOOT PT_LOAD[7] RW- BSS (zero-initialized) |
| Current value (after RELA) | `0x0` (NULL) |

### Writes (1 found)

| Address | Instruction | Source | Guard |
|---------|-------------|--------|-------|
| `0x8013EF019` | `mov [rip + 0xA62220], rax` | `RAX` (return of `0x4BD620` called at `0x8013EEFE7`) | Skip if `test rax, rax; je` (NULL return); Skip if `cmp esi, [global]; jae` (bounds check fails) |

### Reads (1 LEA found)

| Address | Instruction | Register |
|---------|-------------|----------|
| `0x8013EEFF1` | `lea rdx, [rip + 0xA62248]` | `RDX` (loaded with address of cache, likely passed to another function) |

### Interpretation

The NULL value at `0x801E51240` is a **symptom** of the upstream registration failure, not the cause. The cache stays NULL because:
1. `0x4BD620` (likely `il2cpp_class_from_name` or similar) returns NULL when IL2CPP runtime is not initialized
2. The bounds check fails because the type index extracted from `rax+0xC` is meaningless when `rax` is NULL

**The EXP-193 assumption that `[0x801E51240] == Il2CppClass*` was a reasonable inference but turned out to be wrong**. While `0x4BD620` MAY be an IL2CPP API function that returns an `Il2CppClass*`, the cache mechanism is the load-bearing observation — fixing the cache directly (e.g., forcing it non-NULL) would NOT fix the crash, because the underlying hash-table base (`r15`) is still NULL.

## NULL Origin

### Trace Backwards from NULL

```
NULL (r15 = 0x0)
  ↑
  r15 was loaded from a global (not yet identified — likely s_TypeInfoTable or s_GenericClassTable)
  ↑
  s_TypeInfoTable is allocated in MetadataCache::Initialize (per kp7742 source) using:
    IL2CPP_CALLOC(s_Il2CppMetadataRegistration->typesCount, sizeof(Il2CppClass*))
  ↑
  s_Il2CppMetadataRegistration is NULL (BSS at 0x808B542F0)
  ↑
  MetadataCache::Register @ 0x804F23280 never ran
  ↑
  Il2CppCodegenRegistration @ 0x804D9C620 never called (no callers reached it)
  ↑
  Runtime::Init @ 0x804F04BA0 never entered
  ↑
  il2cpp_init was stubbed by SharpEmu to return 0
    (DirectExecutionBackend.Imports.cs line 2411:
     if (name == "il2cpp_init" || name == "il2cpp_shutdown") return 0;)
  ↑
  ROOT CAUSE: SharpEmu stubs il2cpp_init to return 0 instead of calling the PRX's actual il2cpp_init
```

### Secondary Contributor

The `1D0H2KNjshE` and `hsi9drzHR2k` stubs (Harvest Days-specific NIDs, but Yatzi Windows had 0 calls) were observed being called 80,000+ times in the EXP-195 baseline run. The source comment in `GameCompatExports.cs` lines 9-19 explicitly warned:

> "Yatzi Windows had 0 calls, our fork has 59+21 calls due to false stubs, which corrupted the IL2CPP runtime state and caused the bootstrap deadlock."

These stubs were ADDED BACK to the source (despite the warning), contributing to the bootstrap failure.

## Root Cause

### Primary Root Cause: `il2cpp_init` Stub

**Location**: `/tmp/my-project/work/sharpemuT24-broken/src/SharpEmu.Core/Cpu/Native/DirectExecutionBackend.Imports.cs` line 2411

```csharp
if (name == "il2cpp_init" || name == "il2cpp_shutdown") return 0;
```

**Effect**: When EBOOT calls `dlsym`/`il2cpp_api_register_symbols` to look up `il2cpp_init`, SharpEmu's `TryResolveIl2CppApiAddress` returns a stub function (`mov rax, 0; ret`) instead of the PRX's actual `il2cpp_init` address. The stub returns 0 (success), so EBOOT thinks IL2CPP initialized successfully and proceeds to use IL2CPP APIs — but the actual `Runtime::Init` → `Il2CppCodegenRegistration` → `MetadataCache::Register` call chain never executed.

**Result**: All registration globals stay NULL:
- `s_Il2CppCodeRegistration @ 0x808B542E8` = NULL
- `s_Il2CppMetadataRegistration @ 0x808B542F0` = NULL
- `s_Il2CodegenOptions @ 0x808B542F8` = NULL

`MetadataCache::Initialize` cannot allocate `s_TypeInfoTable` (needs `typesCount` from `s_Il2CppMetadataRegistration`). When EBOOT later tries to look up a type by name (e.g., "FXExpressionValuesProxy"), the hash-table base pointer `r15` is NULL → crash at `0x80080684D: mov r8d, [r15+rcx]`.

### Secondary Contributor: `1D0H2KNjshE` / `hsi9drzHR2k` Stubs

**Location**: `/tmp/my-project/work/sharpemuT24-broken/src/SharpEmu.Libs/Kernel/GameCompatExports.cs` lines 138-186

**Source comment warning** (lines 9-19):
> "1D0H2KNjshE and hsi9drzHR2k are Harvest Days only — they had 0 calls on Yatzi Windows but 59+21 calls on our fork due to false stubs, which corrupted the IL2CPP runtime state and caused the bootstrap deadlock."

**EXP-195 baseline observation**: 80,000+ calls to these stubs in a single run. The stubs were ADDED BACK to the source despite the warning, contributing to (or accelerating) the bootstrap failure.
