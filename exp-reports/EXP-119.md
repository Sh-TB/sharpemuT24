# EXP-119 RESULT

**Date:** 2026-08-03
**Status:** COMPLETE — Controlled A/B experiment
**Goal:** Determine whether `FAST_PATH=1` actually allows YATZI to progress past the `WaitSema` stall and reach the GPU/VideoOut path.

---

## Finding

**FAST_PATH=1 does bypass the `WaitSema` stall, but execution does NOT progress to GPU/VideoOut.** Instead, workers proceed past `WaitSema` (which returns OK immediately) and then crash by **calling a NULL function pointer** (RIP=0x0000000000000000, 12 occurrences). Neither mode reaches `AgcInit`, `VideoOutOpen`, `SubmitFlip`, or any GPU activity. Pipeline counts remain ALL ZERO in both modes.

**The failure mode changes, but the outcome is the same: no GPU initialization, no frame.**

The NULL pointer crash in FAST_PATH=1 is consistent with the callback-dispatch issue identified in EXP-106..112: workers proceed past the semaphore wait but then try to call a function pointer that was never initialized (because the registered callback `0x804FA1FE0` is never invoked, so whatever it should have set up remains NULL).

## Runtime Evidence

### Q1: Does FAST_PATH=1 bypass the exact WaitSema stall observed in EXP-118?

**CONFIRMED.** FAST_PATH=1 bypasses the WaitSema stall. Under FAST_PATH=0, 14 threads are `state=Blocked` on `sceKernelWaitSema`. Under FAST_PATH=1, 0 threads are blocked — all are `state=Running`. WaitSema returns OK immediately (rax=0) without blocking, as documented in the source code (EXP-114, line 108 of `KernelSemaphoreCompatExports.cs`).

### Q2: If yes, does execution actually progress farther?

**PARTIALLY CONFIRMED.** Execution progresses farther in terms of:
- Import count: 100,000+ (vs 83,492 in Test A)
- Log lines: 10,703 (vs 8,559)
- WaitSema call count: 145 (vs 35 — workers loop more times)

But execution does NOT progress farther in terms of GPU/VideoOut activity:
- `AgcInit` = 0 in both
- `VideoOutOpen` = 0 in both
- `SubmitFlip` = 0 in both
- `DCB submits` = 0 in both
- `drawCalls` = 0 in both
- `Render targets` = 0 in both
- `Framebuffer writes` = 0 in both
- `CreateWorkload` = 0 in both

### Q3: Does it reach AgcInit? VideoOutOpen? SubmitFlip? DCB submission?

**REJECTED.** None of these are reached in either mode. All pipeline counters remain at 0 in both Test A and Test B.

### Q4: If FAST_PATH=1 progresses farther, what exact event/path is bypassed?

**CONFIRMED (the bypass mechanism is identified).** FAST_PATH=1 bypasses the `sceKernelWaitSema` blocking call. Under FAST_PATH=0, workers block forever waiting for a signal that never comes (SignalSema=0 in both modes). Under FAST_PATH=1, `WaitSema` returns OK immediately without blocking or decrementing count, so workers proceed past the wait.

However, after proceeding past the wait, workers call a NULL function pointer (RIP=0) and crash. This is NOT a fix — it's a different failure mode. The NULL pointer call suggests that whatever the workers expected to find after the wait (likely a function pointer set up by the callback dispatch subsystem) was never initialized.

**This is NOT called a fix.** FAST_PATH=1 changes the failure mode from "stall" to "crash (NULL pointer execution)" but does NOT enable GPU initialization or frame production.

### Q5: If both modes stall at the same location, FAST_PATH is NOT the immediate cause.

**N/A — the modes do NOT stall at the same location.** Test A stalls on WaitSema; Test B crashes on NULL pointer execution. But both fail to reach GPU init, so FAST_PATH is not the FIX either — it's a bypass that changes the symptom without addressing the root cause.

### Q6: If FAST_PATH=1 reaches GPU while FAST_PATH=0 does not, record this as a runtime A/B fact only.

**N/A — FAST_PATH=1 does NOT reach GPU.** Both modes have all-zero pipeline counts. This fact is recorded as: "FAST_PATH=1 does NOT reach GPU/VideoOut even though it bypasses the WaitSema stall."

## Accepted Hypothesis

1. **FAST_PATH=1 bypasses the WaitSema stall** — CONFIRMED. Workers proceed past WaitSema (returns OK immediately, rax=0). 0 threads blocked vs 14 in FAST_PATH=0.

2. **The callback-dispatch issue is the real blocker, manifesting differently depending on FAST_PATH** — CONFIRMED as a runtime A/B fact:
   - FAST_PATH=0: Workers block forever on WaitSema (handles 0x5C-0x74 never signaled) → stall
   - FAST_PATH=1: Workers proceed past WaitSema but call a NULL function pointer → SIGSEGV at RIP=0
   - Both modes: SignalSema=0 (nobody signals anything), pipeline counts all zero, no GPU init

3. **The NULL pointer crash in FAST_PATH=1 is consistent with the callback-dispatch issue** — The registered callback `0x804FA1FE0` is never invoked (EXP-106), so whatever function pointer it should have set up remains NULL. When workers proceed past WaitSema (under FAST_PATH=1), they attempt to call that NULL pointer.

---

## Rejected Hypothesis

1. **"FAST_PATH=1 would allow the game to reach GPU init / VideoOut / Flip"** — REJECTED. Pipeline counts are ALL ZERO in both modes. FAST_PATH=1 does not reach any GPU activity.

2. **"FAST_PATH=1 is a fix (or partial fix)"** — REJECTED. FAST_PATH=1 changes the failure mode from stall to crash (SIGSEGV at RIP=0). It does not fix anything.

3. **"The WaitSema stall is the sole blocker"** — REJECTED. Even when the WaitSema stall is bypassed (FAST_PATH=1), the game still doesn't progress to GPU init — it crashes on a NULL pointer call instead.

4. **"FAST_PATH=0 and FAST_PATH=1 stall at the same location"** — REJECTED. They fail at different points: Test A stalls on WaitSema (rip=0x00006FFFFD001150); Test B crashes on NULL pointer execution (RIP=0x0000000000000000).

5. **"SignalSema is being called but on wrong handles" (EXP-078's claim)** — REJECTED (again). SignalSema=0 in BOTH modes. Nobody signals anything. The "workers signal wrong handles" claim from EXP-078 was already corrected by checkpoint section 14 (paired semaphores by design) and is now further refuted: there are zero signals in either mode.

## Remaining Unknown

1. **What is the NULL function pointer that workers call after WaitSema returns OK (under FAST_PATH=1)?** The crash is at RIP=0x0000000000000000 (execute access). The workers' last import was `sceKernelWaitSema` (returned 0). The function pointer they tried to call is at address 0 — it was never set. What was supposed to set it? Likely the callback dispatch subsystem (the registered callback `0x804FA1FE0` that is never invoked, per EXP-106).

2. **Why does SignalSema=0 in both modes?** Nobody signals any semaphore. The main thread is presumably stuck somewhere (not visible in the stall/crash snapshots). The callback-dispatch trigger that should signal the worker semaphores (0x5C-0x74) is missing. This is the same question from EXP-115's maintainer summary.

3. **Would the game reach GPU init if the NULL pointer issue were resolved?** Unknown — the NULL pointer crash happens before any GPU activity. Resolving it (by implementing the callback dispatch trigger) might reveal a further blocker, or might allow GPU init to proceed. Cannot determine without resolving the callback-dispatch issue first.

4. **Why did the 2026-07-24 checkpoint reach VideoOutOpen/SubmitFlip but EXP-119 Test B does not?** The 2026-07-24 checkpoint used a different SharpEmu build (likely `exp107` or earlier) that may have had different code paths, patches, or environment variables. The clean build used in EXP-119 crashes (under FAST_PATH=1) or stalls (under FAST_PATH=0) before reaching GPU init. This discrepancy requires investigation but is beyond EXP-119's scope.
