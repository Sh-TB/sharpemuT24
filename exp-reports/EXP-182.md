## Root Cause

### Why [0x801E51240] is NULL:

The consumer function `0x8013EB6B0` has an init writer for `[0x801E51240]` at offset `+0x3969` (`0x8013EF019`). However, after `il2cpp_init` returns 0 (success), the consumer takes a `je` branch at `+0x19B1` that redirects execution to `+0x19CC`. From there, the consumer follows a series of conditional checks that NEVER lead to `+0x3969`.

The init writer at `+0x3969` is only reached via a DIFFERENT code path — one that is taken when `il2cpp_init` returns a NON-ZERO value (error). Since `il2cpp_init` returns 0 (success), the consumer takes the "success" path, which skips the init writer entirely.

### The design issue:

The init writer at `+0x3969` appears to be in an ERROR HANDLING path, not the success path. The consumer's logic is:
```
if (il2cpp_init() == 0) {
    // success path — skips [0x801E51240] initialization
    // continues to other initialization
} else {
    // error path — reaches +0x3969, writes [0x801E51240]
    // (this seems backwards — error path shouldn't initialize)
}
```

This suggests that `[0x801E51240]` is NOT meant to be initialized by the consumer at all — it should be initialized by a DIFFERENT function that runs BEFORE the consumer.

### What calls 0x80135DDD0:

The crash function `0x80135DDD0` is called from `0x800C854CE` (return address on stack). This is in a different part of eboot — likely Unity IL2CPP type metadata processing that runs after il2cpp_init. It reads `[0x801E51240]` expecting it to contain a valid IL2CPP metadata pointer, but the pointer was never set.

## Next Investigation Point

### The real question: What should initialize [0x801E51240]?

The consumer's init writer at `+0x3969` is NOT the correct initialization path — it's in an error handling branch. `[0x801E51240]` should be initialized by:

1. **il2cpp_init itself** — il2cpp_init may be supposed to set `[0x801E51240]` as part of IL2CPP runtime initialization. The fact that it returns 0 (success) but doesn't set `[0x801E51240]` suggests il2cpp_init's HLE implementation is incomplete.

2. **Another IL2CPP API function** — One of the 232 IL2CPP API functions resolved by the GOT writer may be responsible for setting `[0x801E51240]`. Need to check which function writes to this address.

3. **A GLOB_DAT relocation** — Like `__stack_chk_guard`, `[0x801E51240]` might need a GLOB_DAT relocation that SharpEmu isn't resolving.
