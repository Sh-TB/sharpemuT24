**Root cause chain:**
```
0x80135DE6D: mov rax, [rip+0xAF33CC] → mov rax, [0x801E51240]
  ↓ [0x801E51240] = NULL (never initialized)
0x80135DE83: mov ecx, [rax+0x98] → mov ecx, [0+0x98] → CRASH (fault=0x98)
```

- **Previous blocker:** il2cpp_init at consumer +0x19A7 didn't return (EXP-177)

## 4. Root Cause

### The crash at 0x80135DE83 is caused by [0x801E51240] = NULL

This is NOT a new issue — it's the SAME `[0x801E51240]` global from EXP-159 through EXP-177. The consumer function `0x8013EB6B0` has an init writer at offset +0x3969 (`0x8013EF019`) that is NEVER reached.

**Why the consumer doesn't reach +0x3969 even after EXP-179:**
- EXP-179 fixed the `_ZdlPv` blocking import (NID `z+P+xCnWLBk`)
- il2cpp_init now returns successfully
- BUT the consumer function `0x8013EB6B0` calls il2cpp_init at +0x19A7
- After il2cpp_init returns, the consumer should continue to +0x3969
- The crash at `0x80135DE83` happens BEFORE the consumer can reach +0x3969
- This means `0x80135DE83` is called from a DIFFERENT path (not the consumer)

**Call chain to crash:**
```
Some function calls 0x80135DDD0 (containing function)
  ↓ 0x80135DE6D: mov rax, [0x801E51240]  ← rax = NULL
  ↓ 0x80135DE83: mov ecx, [rax+0x98]     ← CRASH (fault=0x98)
```

The function at `0x80135DDD0` is called with `[0x801E51240]` still NULL. This function runs BEFORE the consumer can initialize `[0x801E51240]`.

## 5. Fix Implemented

### Fix 1: `__stack_chk_guard` GLOB_DAT resolution (EXP-181)

**File:** `src/SharpEmu.Core/Loader/SelfLoader.cs`
**Change:** Added `HleDataSymbols.TryGetAddress()` check for GLOB_DAT relocations

This fix is correct and necessary — `__stack_chk_guard` is a DATA symbol that needs its address resolved during relocation, not a function stub. However, this alone doesn't fix the crash because the crash is caused by a DIFFERENT NULL global (`0x801E51240`).

### Fix 2: NOT YET IMPLEMENTED

The crash at `0x80135DE83` requires `[0x801E51240]` to be initialized. The init writer at `0x8013EF019` is inside the consumer function that runs after il2cpp_init returns. The function at `0x80135DDD0` runs BEFORE the consumer can initialize `[0x801E51240]`.

**Possible solutions (not yet implemented):**
1. Initialize `[0x801E51240]` to a dummy non-NULL value before the game starts
2. Find what should call the consumer function earlier in the boot sequence
3. Trace the caller of `0x80135DDD0` to understand the execution order
