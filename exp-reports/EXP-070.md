## The Single Question

**"What specific conditional branch between WaitSema and SignalSema decides whether SignalSema is reached?"**

## Answer

**`cmp byte ptr [rbx+0x108], 0` at `0x800AA0207`, followed by `jne` at `0x800AA020E`**

If `[rbx+0x108]` (low byte) is non-zero, the `jne` jumps backward to `0x800AA01C7`, skipping the `call SignalSema` at `0x800AA021E` entirely.

## Evidence

### Disassembly (WaitSema return → SignalSema call)

```
0x800AA0202: call WaitSema           (E8 19 75 E9 00)
0x800AA0207: cmp byte [rbx+0x108], 0  (80 BB 08 01 00 00 00)  ← THE GATE
0x800AA020E: jne 0x800AA01C7         (75 B7)                   ← SKIPS SIGNAL IF [rbx+0x108]!=0
0x800AA0210: jmp 0x800AA0239         (EB 27)                   ← unconditional, also skips
0x800AA0212: mov rdi, [rbx+0xB0]     (48 8B BB B0 00 00 00)   ← load sema handle
0x800AA0219: mov esi, 1              (BE 01 00 00 00)          ← signal count = 1
0x800AA021E: call SignalSema         (E8 8D 75 E9 00)         ← THE SIGNAL CALL (never reached!)
```

### Runtime Value

From EXP035-NULL logs (object dump at `rbx=0x6006D1130`):
```
+0x108: 0x00000006006D1101
```

Low byte of `[rbx+0x108]` = `0x01` (non-zero).

### Gate Logic

```
WaitSema returns → check [rbx+0x108]
  ↓
[rbx+0x108] == 0?
  ├── YES → fall through to SignalSema call ✓
  └── NO  → jne skips back to 0x800AA01C7 (loop back to task check) ✗
```

**At runtime: `[rbx+0x108] = 0x01` → gate is CLOSED → SignalSema is NEVER reached.**

### FAST_PATH Independence

This gate is **FAST_PATH-independent** (confirming user feedback #2):
- The gate checks `[rbx+0x108]`, NOT the WaitSema return value
- FAST_PATH=0: WaitSema blocks → never reaches the gate → deadlock
- FAST_PATH=1: WaitSema returns → reaches gate → `[rbx+0x108]!=0` → skips SignalSema → loops back
- **Either way, SignalSema is never called** — the gate is the blocker, not FAST_PATH

### What is `[rbx+0x108]`?

From the object dump:
```
rbx = 0x6006D1130 (task descriptor)
[rbx+0x100] = 0x0000000000000000 (argument)
[rbx+0x108] = 0x00000006006D1101 (flag/state)
```

The value `0x6006D1101` looks like a pointer with the low bit set. `0x6006D1101` & ~1 = `0x6006D1100` — this could be a pointer to another object (with the low bit as a flag/tag).

The low byte `0x01` is likely a "task not ready" flag. It's set when the task descriptor is created but should be cleared when a task is assigned. Since no task is ever assigned (the main thread doesn't progress far enough), the flag stays set.

## Root Cause (Definitive)

The `jne` at `0x800AA020E` skips `sceKernelSignalSema` because `[rbx+0x108]` (low byte) is non-zero (`0x01`). This byte is a task-readiness flag that should be cleared when a task is assigned to the worker. Since the main thread never reaches the task-assignment code, the flag stays at `0x01`, and SignalSema is never called.

The chain:
```
Main thread doesn't reach task assignment code
↓
Task descriptor [rbx+0x108] stays = 0x01 (not ready)
↓
Worker checks [rbx+0x108] after WaitSema → non-zero → skips SignalSema
↓
Worker loops back to task check → [rbx+0xf8] still NULL → calls NULL
↓
1000+ NULL execute recoveries → stack corruption → SIGABRT
```

## Confirmed Findings

1. **SignalSema PLT entry at `0x8019377B0`** with 599 direct callers

3. **Gate is `cmp byte [rbx+0x108], 0` + `jne`** at `0x800AA0207-0x800AA020E`
4. **Runtime value `[rbx+0x108] = 0x01`** → gate is CLOSED → SignalSema skipped
5. **Gate is FAST_PATH-independent** — checks task flag, not WaitSema return
6. **`[rbx+0x108]` is a task-readiness flag** that should be cleared by task assignment

1. ❌ FAST_PATH setting determines whether SignalSema is reached — NO, the gate is `[rbx+0x108]`, not WaitSema return
2. ❌ A separate failed HLE call between WaitSema and SignalSema — NO, there's only a `cmp` + `jne` between them
3. ❌ SignalSema is called via indirect call — NO, it's a direct `call 0x8019377B0`
