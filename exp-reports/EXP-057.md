# EXP-057 — Find and Invoke the Consumer Function

## Date: 2026-07-31
## Status: COMPLETE — Consumer candidate identified (call #7 = 0x804F23320); MetaReg access via metadataUsages indirection

---

## Executive Summary

Executed Groups 1, 3, 4 of the EXP-057 master plan. Key findings:

1. **MetaReg access mechanism SOLVED**: MetaReg (`0x80885C580`) is accessed via
   the `metadataUsages[]` indirection table. 7 relocs point to MetaReg fields
   (+0x98, +0xA8, +0xB8...) from `0x8088AD3F8` onwards. The code reads
   `metadataUsages[index]` to get a pointer to a MetaReg field, then
   dereferences it. This is why no direct RIP-relative refs to MetaReg's base
   address exist.

2. **MetaReg's 3 code pointers are reverse P/Invoke wrappers** (Group 1
   DISPROVEN). All 3 (`0x805380680`, `0x8053806F0`, `0x805380770`) marshal
   arguments and call `0x807180CC0` (a common dispatcher). They are NOT the
   consumer function.

3. **No co-occurring CodeReg+MetaReg refs found** (Group 3 result). No
   function has RIP-relative refs to BOTH `0x8086E9000` AND `0x80885C580`.
   This is because MetaReg is accessed via metadataUsages indirection, not
   direct LEA.

4. **`il2cpp_init` is only 44 bytes** — a tiny thunk that calls `real_init`
   (`0x804F04BA0`). The actual init logic is in `real_init`.

5. **Call #7 (`0x804F23320`) is NOT a simple epilogue** — it's a large,
   complex function with loops that iterate over arrays with 0x38-byte
   stride entries. It reads from a context global at `0x808923D88`. This
   is a strong consumer candidate.

6. **CodeReg+0x08 is NOT a version string** — it's a length-prefixed IL2CPP
   string literal (`"22Il2CppExceptionWrapper"` where "22" is the length).
   This is a type name pointer, suggesting CodeReg's struct identity may
   need re-evaluation.

## Group 1: MetaReg's 3 Code Pointers (DISPROVEN)

### G1-T1/2/3: Disassembly of 0x805380680, 0x8053806F0, 0x805380770

All 3 functions have the same structure:
```asm
push rbp; mov rbp, rsp; push r15-r12, rbx
mov rax, [r8 + 0x38]          ; load context from arg3
test rax, rax; jne skip
call 0x804fa2770              ; lazy-init the context
mov rdi, [rax + 0x10]
call 0x805309430 / 0x8053096f0  ; get marshaling info
mov r8d, 0x2040 / 0x20         ; flags
mov rdi, r13; mov rsi, r12; mov rdx, r15; mov ecx, r14d; mov r9d, eax
call 0x807180cc0              ; COMMON DISPATCHER
ret
```

### G1-T5: P/Invoke thunk markers confirmed

- 5+ arguments (rdi, rsi, rdx, rcx, r8, r9)
- Calls `0x807180CC0` — a common marshaling dispatcher
- Reads `[r8 + 0x38]` — context pointer from arg3
- Uses `call [rdi]` pattern (indirect call through vtable)

**VERDICT: All 3 are reverse P/Invoke wrapper functions. NOT the consumer.**

## Group 3: Co-occurring Reference Search

### G3-T17: Co-occurrence scan results

```
PRX refs to 0x8086E9000 (CodeReg):     7,780
PRX refs to 0x80885C580 (MetaReg):     0
PRX refs to 0x80893E950 (types[]):     0
PRX refs to 0x808791958 (methodPtrs):  0

Functions with co-occurring CodeReg + MetaReg refs: NONE
```

**MetaReg has 0 direct RIP-relative refs.** This is because MetaReg is
accessed via the `metadataUsages[]` indirection table.

### MetaReg access mechanism (SOLVED)

7 relocs point to MetaReg FIELDS (not the base):
```
*[0x8088AD3F8] = 0x80885C618 (MetaReg+0x98)
*[0x8088AED98] = 0x80885C628 (MetaReg+0xA8)
*[0x8088AEDA0] = 0x80885C638 (MetaReg+0xB8)
*[0x8088AEDA8] = 0x80885C648 (MetaReg+0xC8)
*[0x8088AEDB0] = 0x80885C658 (MetaReg+0xD8)
*[0x8088AEDB8] = 0x80885C668 (MetaReg+0xE8)
*[0x8088AEDC0] = 0x80885C678 (MetaReg+0xF8)
```

These are entries in the `metadataUsages` indirection table. The code:
1. Reads `metadataUsages[index]` → gets pointer to a MetaReg field
2. Dereferences that pointer → gets the actual value

This two-level indirection explains why no direct LEA to MetaReg's base exists.

### G3-T19/20: No callers found for consumer

Since no co-occurring refs were found, the consumer function (if it exists)
doesn't access CodeReg and MetaReg via direct LEA. It likely:
- Reads them from the context global at `0x808923D88`
- Or receives them as arguments from a caller

## il2cpp_init and real_init Analysis

### il2cpp_init is a 44-byte thunk

```
0x804ED85D0 - 0x804ED85FC (44 bytes)
```

`il2cpp_init` just calls `real_init` (`0x804F04BA0`). All init logic is in
`real_init`.

### real_init call #7 (0x804F23320) — CONSUMER CANDIDATE

Call #7 is NOT the "epilogue" that EXP-041 reported. It's a large function
(0x500+ bytes) with:

1. **Reads context global**: `mov rbx, [rip + 0x3a00a49]` → `0x808923D88`
2. **Loads 2 rodata strings**: `lea rdi/rsi, [rip + ...]`
3. **Has loops**: iterates with counter, calls `0x804F238F0` each iteration
4. **Uses 0x38-byte stride**: `imul rsi, r14, 0x38` — matches hash table
   entry size!
5. **Calls `0x804F2B4D0`** with array pointer, count, and end pointer

The 0x38-byte stride is the same as the hash table entry size (confirmed
in EXP-052). This strongly suggests call #7 iterates over an array of
0x38-byte entries and processes each one — exactly what a consumer/registration
function would do.

### Context global at 0x808923D88

This global holds a pointer to a context struct that likely contains:
- Pointer to CodeReg
- Pointer to MetaReg
- Other init state

The consumer reads this context, not CodeReg/MetaReg directly. This explains
why no direct LEA refs to CodeReg/MetaReg were found in the consumer.

## CodeReg+0x08 String Analysis

### Length-prefixed IL2CPP string

CodeReg+0x08 points to `0x80828A7B1` which contains:
```
Raw bytes: 32 32 49 6c 32 43 70 70 45 78 63 65 70 74 69 6f 6e 57 72 61 70 70 65 72 00
ASCII:     "22Il2CppExceptionWrapper"
```

The "22" is the LENGTH (22 characters), followed by "Il2CppExceptionWrapper"
(the type name). This is a standard IL2CPP string literal format.

**This means CodeReg+0x08 is a type name pointer, not a version field.**
The struct at `0x8086E9000` may need re-evaluation — it could be a different
Unity struct that starts with a type name.

## Confirmed Findings

1. **MetaReg access mechanism**: via `metadataUsages[]` indirection table
   (7 relocs point to MetaReg fields from `0x8088AD3F8` onwards)
2. **MetaReg+0x00/08/10**: reverse P/Invoke wrappers (NOT consumer)
3. **No co-occurring CodeReg+MetaReg refs**: no function LEAs both directly
4. **No codeGenModules[] array**: single CodeReg/MetaReg pair
5. **`il2cpp_init` is a 44-byte thunk**: calls `real_init`
6. **Call #7 (`0x804F23320`) is a consumer candidate**: has loops with 0x38-byte
   stride (matching hash table entry size), reads context global at `0x808923D88`
7. **CodeReg+0x08 is a type name string**: "22Il2CppExceptionWrapper" (length-prefixed)
8. **Context global at `0x808923D88`**: likely holds pointers to CodeReg/MetaReg

## Disproven Hypotheses

1. ❌ MetaReg+0x00/08/10 are the consumer function — they're P/Invoke wrappers
2. ❌ A function exists with direct LEA refs to BOTH CodeReg and MetaReg — none found
3. ❌ codeGenModules[] array exists with adjacent CodeReg+MetaReg pairs — not found
4. ❌ Call #7 is a simple epilogue — it's a complex function with loops
5. ❌ CodeReg+0x08 is a version/magic field — it's a type name string literal
6. ❌ MetaReg is accessed via direct RIP-relative LEA — accessed via metadataUsages indirection

## Remaining Hypotheses

1. **Call #7 (`0x804F23320`) IS the consumer function** — needs runtime tracing
   to confirm it populates the hash table
2. **The context global at `0x808923D88` holds CodeReg/MetaReg pointers** —
   needs runtime dump to verify
3. **Call #7 fails silently** — it may be called but return early due to a
   guard flag or missing prerequisite
4. **Call #7 runs AFTER the crash point** — circular dependency at a new level
5. **The struct at `0x8086E9000` is NOT `Il2CppCodeRegistration`** but a
   different Unity struct (e.g., `Il2CppCodeGenModule`) — the type name at
   +0x08 suggests this
