## User Feedback #1: Exact Mismatch Confirmed

### Finding

**The eboot does NOT import `il2cpp_*` functions via static NID imports.** The eboot's import NIDs are PS5 obfuscated names for libKernel/libc functions:

| NID | Library |
|-----|---------|
| `188x57JYp0g` | libKernel (sceKernelCreateSema) |
| `1FGvU0i9saQ` | libKernel |
| `cmo1RIYva9o` | libKernel |
| `iMp8QpE+XO4` | libKernel |
| `smWEktiyyG0` | libKernel |
| `tsvEmnenz48` | libc (__cxa_atexit) |

**None of these are `il2cpp_*` NIDs.** The IL2CPP API functions are resolved at runtime via the PRX's resolver (`0x804ed9b90`), not via static import stubs.

### Why EXP-034 Re-patching Fails

The re-patching code iterates `_importEntries` (eboot's import stubs) and tries to match NIDs to `il2cpp_*` names. This fails because:
1. The import entries are for libKernel/libc, NOT for IL2CPP
2. The `il2cpp_*` functions are resolved via the PRX's resolver callback, not via import stubs
3. The re-patching approach is fundamentally wrong — it targets the wrong mechanism

### But the Resolver Already Works!

**The PRX's resolver returned ALL 232 real func_impl addresses:**
- 232/232 resolver calls returned non-zero (real PRX addresses like `0x804ED85D0`)
- 0/232 returned NULL
- All results were stored in `_resolverResults`

**The game IS receiving real func_impl addresses from the resolver.** The fake heap stubs are NOT being used for IL2CPP API calls — the real PRX functions are.

## User Feedback #3: Causal Chain Verification

### Finding

**The NULL execute at `[rbx+0xf8]=0` is NOT from an IL2CPP stub return value.** It is a **task-submission issue** — worker threads are spinning because no tasks are submitted to them.

### Evidence

1. **`last_il2cpp='<none>'`** in all 1,004 NULL execute logs — no IL2CPP function was called before the NULL
2. **All NULL executes from same caller** (`0x800AA01D4`) — worker thread task processing loop
3. **Multiple worker threads** (tid 26-35) all hit the same NULL
4. **`[rbx+0xf8]` is a task function pointer** in a task descriptor — it's NULL because no task was submitted
5. **The workers are spinning** — they check `[rbx+0xf8]`, find NULL, call NULL (recovered by TryRecoverNullExecuteFault), loop back, check again

### Causal Chain (Corrected)

```
il2cpp_init completes
↓
Unity runtime starts
↓
Worker threads created (AssetGarbageCollectorHelper)
↓
Workers enter task processing loop at 0x800AA01D4
↓
Workers check [rbx+0xf8] for task function pointer
↓
[rbx+0xf8] = NULL (no task submitted yet)
↓
Workers call NULL → RIP=0
↓
TryRecoverNullExecuteFault recovers (1,004 times)
↓
Workers loop back, check again, find NULL again
↓
Host stack corrupted by 1,004 signal handler invocations
↓
glibc __fortify_fail → SIGABRT
```

## Confirmed Findings

1. **Eboot does NOT import il2cpp_* via NID** — IL2CPP functions resolved via PRX resolver
2. **Resolver returns ALL 232 real func_impl addresses** — 232/232 non-zero, 0 NULL
3. **EXP-034 re-patching is unnecessary** — it targets the wrong mechanism
4. **NULL executes are NOT from IL2CPP stubs** — `last_il2cpp='<none>'` in all 1,004 cases
5. **NULL executes are from worker task spinning** — `[rbx+0xf8]` is NULL because no task submitted
6. **Stack corruption is from 1,004 signal handler invocations** — host-side glibc `__fortify_fail`
7. **The task submission issue is the same class as the semaphore issue** — workers wait for work that never arrives

## Disproven Hypotheses

1. ❌ EXP-034 re-patching failure causes NULL executes — re-patching is unnecessary, resolver already works
2. ❌ IL2CPP fake stubs return NULL causing the cascade — `last_il2cpp='<none>'` proves no IL2CPP call before NULL
3. ❌ `DecideIl2CppReturnValue` fix would help — IL2CPP stubs aren't the source of NULL
4. ❌ Address-based matching would fix the issue — the issue is task submission, not import matching

## Next Step (EXP-068)

### Investigate why tasks are never submitted to workers

The workers spin on `[rbx+0xf8]` (task function pointer) which is always NULL. This means the task submission code never runs or fails. Possible causes:

1. **The main thread doesn't progress far enough** to submit tasks (blocked on something else)
2. **A prerequisite for task submission is missing** (e.g., a Unity subsystem not initialized)
3. **The task submission function itself fails** (e.g., returns early due to an error)
4. **FAST_PATH=1 causes the main thread to skip task submission** (it returns from WaitSema too early, missing the submission step)

Approach:
1. Trace the main thread to see if it reaches the task submission code
2. Check if FAST_PATH=1 causes the main thread to skip an important step between WaitSema and task submission
3. Check if a required Unity subsystem (scene loading, asset loading) fails, preventing task submission
