# EXP-122 — Trace Worker Task Dispatch Path

**Date:** 2026-08-03
**Status:** COMPLETE — Dispatch path analyzed
**Goal:** Find the missing task dispatch path. What code should write `[rbx+0xF8]` and signal the work semaphores?

---

## Finding

**The task dispatch path does not exist in any code that runs.** No code writes a non-NULL function pointer to `[rbx+0xF8]` after worker creation, and no code signals the EVEN work semaphores (0x5C-0x74) that workers wait on. The dispatch step is entirely missing from the executed code path.

**The worker lifecycle is:**
1. ✅ Create Worker (at `0x800a9f900-0x800a9fd00`) — sets all fields including `[rbx+0xF8]=0`, `[rbx+0x108]=1`
2. ✅ Initialize fields — semaphores, self-pointer, worker func all set
3. ✅ Add Worker to pool — workers are scheduled as threads (13 × AssetGarbageCollectorHelper)
4. ❌ **Dispatch Task — MISSING** — no code writes `[rbx+0xF8]` to non-NULL, no code signals EVEN work semaphores
5. ❌ Worker executes — never happens (no task to execute)

**SignalSema calls DO exist** (13 in Test A, 12 in Test B) but ALL are on ODD handles (0x5D-0x75 = completion signals). These are workers signaling their own completion — but since they never receive work, this is likely a spurious "initial completion" signal during worker startup. **ZERO SignalSema calls on EVEN handles (0x5C-0x74 = work semaphores)** in either mode.

## Missing Step

**The missing step is "Dispatch Task."** This step should:
1. Write a non-NULL function pointer to `[rbx+0xF8]` (the task function)
2. Write the task argument to `[rbx+0x100]`
3. Signal the EVEN work semaphore (`[rbx+0x68]`) to wake the worker

**None of these three actions occur.** The dispatch code path either:
- Does not exist in the executed code (missing HLE primitive or missing game code path)
- Exists but is never reached (blocked by an upstream issue)

**The SignalSema calls that DO exist (13 in Test A, 12 in Test B) are workers signaling their OWN completion semaphores (ODD handles) at `0x800AA024C`** — this is the worker saying "I'm done" after the worker function's active-count check. But since no task was dispatched, this completion signal is spurious (the worker never actually did any work).

## Confirmed

1. **No code writes non-NULL to `[rbx+0xF8]` after worker creation** — CONFIRMED by static analysis (139 non-zero writes to `[reg+0xF8]` in eboot.bin, but none in the worker creation function or in a function that also writes `[rbx+0x100]` with the same base register)

2. **No SignalSema on EVEN work semaphores (0x5C-0x74)** — CONFIRMED by runtime log analysis (0 out of 13/12 SignalSema calls in either mode)

3. **SignalSema calls DO exist on ODD completion semaphores** — CONFIRMED (13 in Test A, 12 in Test B, all from return address `0x800AA0251` inside the worker function)

4. **The dispatch step (set func_ptr + signal work semaphore) is entirely missing from the executed code** — CONFIRMED

5. **Test A has an extra thread (Thread-7F6A70B592E0, entry 0x804F88AA0) that Test B does not** — CONFIRMED (this may be the IL2CPP runtime thread that should dispatch work)

## Rejected

1. **"SignalSema=0 in both modes" (from EXP-119)** — REJECTED. SignalSema=13 (Test A) and 12 (Test B). The previous count was wrong due to grep pattern differences. The correct statement is: "SignalSema on EVEN/work handles = 0; SignalSema on ODD/completion handles = 13/12."

2. **"The task dispatch writes `[rbx+0xF8]` and `[rbx+0x100]` together"** — PARTIALLY REJECTED. No code path was found that writes BOTH fields with non-zero values in the same function near the worker object. Either the dispatch uses a different mechanism, or it doesn't exist in the executed code.

3. **"FAST_PATH changes the dispatch behavior"** — REJECTED. No dispatch exists in either mode. FAST_PATH only affects whether workers reach the NULL call or block at WaitSema.

## Unknown

1. **What code should perform the dispatch?** The specific function that should write `[rbx+0xF8]` and signal the work semaphores has not been identified. Candidates:
   - The IL2CPP runtime thread (`Thread-7F6A70B592E0`, entry `0x804F88AA0` in Il2cppUserAssemblies.prx) — this thread exists in Test A (blocked on handle 0x83) but is absent in Test B
   - The registered callback `0x804FA1FE0` (never invoked, per EXP-106)
   - Some other code path in eboot.bin or PRX

2. **Why does Test A have an extra thread (0x804F88AA0) that Test B does not?** Is this thread the dispatch thread? Did it crash in Test B before being logged? Or does FAST_PATH=1 change the thread creation order?

3. **Is the missing dispatch the ROOT CAUSE, or is it a consequence of the main thread being stuck?** Per CHECKPOINT section 15, "the main thread is in a busy loop (calling 1D0H2KNjshE, hsi9drzHR2k, scePthreadMutexLock, sceKernelClockGettime, sceAudioOutOutput), NOT in a semaphore wait." If the main thread never reaches the dispatch code, that would explain why no dispatch happens.

4. **Why do workers signal their completion semaphores (ODD handles) if they never received work?** The worker function at `0x800AA0170` has a path that signals `[rbx+0xB0]` at `0x800AA0240-0x800AA0251` — this may be an "initialization complete" signal, not a "task complete" signal.
