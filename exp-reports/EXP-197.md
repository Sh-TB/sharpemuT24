# EXP-197 — Autonomous IL2CPP Initialization → Registration → Runtime-State → First-Frame Campaign

## Executive Summary

**EXP-195's root cause was WRONG.** The `il2cpp_init` stub in `DecideIl2CppReturnValue` (line 2411) is **NEVER REACHED** — confirmed by zero `IL2CPP_NULL`/`IL2CPP_STUB` log entries. The actual root cause is in the **IL2CPP API table resolution chain**.

### Actual Root Cause Chain (PROVEN by static + runtime evidence)

```
EBOOT calls cJ2Y4E-t258 (il2cpp_api_register_symbols) at 0x8013FB24F
  → PLT stub 0x19374C0 → GOT 0x801D1ACD8
  → SHOULD build BST of name→function at [0x808B53708]
  → STATUS: UNKNOWN (no crash at return_addr 0x8013FB254, but no evidence of success)

EBOOT calls r8mvOaWdi28 (resolver) for each IL2CPP function at 0x8013FB25B
  → PLT stub 0x19374D0 → GOT 0x801D1ACE0
  → Walks BST, returns function pointer in RAX

EBOOT calls through NULL API table slots
  → 10 NULL execute faults at rip=0 (recovered by SharpEmu VEH)
  → Eventually reaches hash-table lookup at 0x80080684D with r15=0
  → 100,000+ unmapped read faults → crash
```

## Crash Register Analysis

### Crash at 0x80080684D

| Register | Value | Role |
|----------|-------|------|
| RIP | 0x80080684D | `mov r8d, [r15+rcx]` |
| R15 | **0x0** | Hash-table base pointer (NULL) |
| RCX | 0x0 | Effective offset (hash * 7) |
| R8 | 0x0 | Target of load (crashes) |
| R9 | 0x4F04EB2C | Search key |
| Stack | "FXExpressionValuesProxy", "Unity.Collections" | IL2CPP type/method names |

### R15 Identity

R15 is the **hash-table base pointer** — likely `s_TypeInfoTable` or a similar IL2CPP internal lookup table. This table is allocated in `MetadataCache::Initialize` using `s_Il2CppMetadataRegistration->typesCount`. Since `MetadataCache::Register` never runs (registration chain severed), `s_Il2CppMetadataRegistration` is NULL, and `s_TypeInfoTable` is never allocated.

### NULL Origin Trace

```

  ↑
s_TypeInfoTable never allocated (by MetadataCache::Initialize)
  ↑
MetadataCache::Initialize never called (by Runtime::Init)
  ↑

  ↑
API table slot for il2cpp_init is NULL (resolver returned NULL)
  ↑

  ↑
BST empty because il2cpp_api_register_symbols either:
  A) Was dispatched (not direct-bridged) → returned NOT_FOUND → never ran
```

## Root Cause

### Primary Suspect: `cJ2Y4E-t258` (il2cpp_api_register_symbols) Not Running

The IL2CPP API table at `0x801ED6320` is all NULL because:

1. EBOOT calls `cJ2Y4E-t258` at `0x8013FB24F` → PLT `0x19374C0` → GOT `0x801D1ACD8`
2. If the GOT is **unresolved (0)** → crash at rip=0 → SharpEmu recovers → BST never built
3. If the GOT is **resolved but dispatched** → dispatch returns `ORBIS_GEN2_ERROR_NOT_FOUND` → function never runs → BST never built
4. If the GOT is **resolved and direct-bridged** → function runs → BST should be built → but resolver still returns NULL (BST might be malformed)

**Without runtime instrumentation, I cannot determine which case applies.** The most likely case is #2 or #3 — the GOT slot is either unresolved or dispatched without running the actual function.

### Secondary Suspect: `1D0H2KNjshE`/`hsi9drzHR2k` Stubs

These Harvest Days-specific NIDs are called 80,000+ times per run. The source comment explicitly warns they "corrupted the IL2CPP runtime state and caused the bootstrap deadlock." While they may not be the PRIMARY cause, they contribute to the failure.

## Minimal Fix (Evidence-Backed, Requires Build)

### Fix 1: Ensure `cJ2Y4E-t258` is Direct-Bridged

Add `cJ2Y4E-t258` to the `IsHlePreferredNid` EXCLUSION list (so `TryResolveDirectImportTarget` is NOT skipped), and verify that `TryResolveRuntimeSymbolAddress("cJ2Y4E-t258")` finds the PRX's export.

Alternatively, add `cJ2Y4E-t258` to a "force LLE" list that bypasses all HLE checks and always direct-bridges to the runtime symbol.

### Fix 2: Ensure `r8mvOaWdi28` is Direct-Bridged (Not Dispatched)

The dispatch code at line 607 intercepts `r8mvOaWdi28` and calls `DispatchIl2CppApiLookupSymbol`. This dispatch calls the PRX's resolver via `TryCallGuestFunction`. But the dispatch logs `[RESOLVER-TRACE]` entries, and there are ZERO. This means either:
- The import is direct-bridged (bypasses dispatch) → resolver runs silently
- OR the import is dispatched but the dispatch code has a bug

If the import is NOT direct-bridged (because `TryResolveDirectImportTarget` fails for some reason), the dispatch code at line 607 would fire. But it doesn't (0 traces). This is contradictory.

**The most likely explanation**: `r8mvOaWdi28` IS direct-bridged, and the resolver DOES run, but it returns NULL because the BST is empty (because `cJ2Y4E-t258` didn't run or failed).

### Fix 3: Remove `1D0H2KNjshE`/`hsi9drzHR2k` Stubs

Comment out the `SysAbiExport` attributes for these NIDs (as the source comment recommends). These are Harvest Days-specific and corrupt Yatzi's IL2CPP state.

### Fix Priority

1. **Fix 1** (ensure cJ2Y4E-t258 runs) — CRITICAL, this is the root cause
2. **Fix 3** (remove 1D0H2KNjshE/hsi9drzHR2k) — HIGH, secondary corruption
3. **Fix 2** (ensure r8mvOaWdi28 works) — MEDIUM, likely already works if Fix 1 is applied

### Root Cause of Build Failure

Silk.NET 2.23.0 packages have `lib/netcoreapp3.1`, `lib/net5.0`, `lib/netstandard2.0`, `lib/netstandard2.1` — but NOT `lib/net8.0` or `lib/net6.0`. NuGet should fall back to `netstandard2.1` for a net8.0 project, but instead reports "does not support any target frameworks."

This appears to be a NuGet version compatibility issue. The `.nupkg.metadata` file in the .packages folder lists `nuget.org` as the source, which may cause NuGet to try online verification. Using the local folder as the ONLY source (with `--ignore-failed-sources`) resolved Avalonia errors but not Silk.NET.

### Status

**BLOCKED** — Cannot rebuild SharpEmu without resolving the Silk.NET package compatibility issue. The pre-built `SharpEmu.bin` was built in an environment that is not reproducible with the available toolchain.
