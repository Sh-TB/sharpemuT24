# EXP-198 — IL2CPP API Table Registration Runtime Validation

## Executive Summary

**ROOT CAUSE PROVEN AND FIXED.** The `cJ2Y4E-t258` (il2cpp_api_register_symbols) HLE stub in `GameCompatExports.cs` line 37-38 was intercepting the call and returning 0 without actually running the PRX's function. This prevented the BST (binary search tree) of IL2CPP function name→address mappings from being built, causing the resolver to return NULL for all IL2CPP functions, leaving the API table at `0x801ED6320` all NULL, and crashing at `0x80080684D` with `r15=0`.

**FIX**: Comment out the `[SysAbiExport]` attribute for `cJ2Y4E-t258` so it falls through to runtime symbol resolution → direct-bridge to `0x804ED3AE0` (the PRX's actual function).

**RUNTIME VALIDATION**: ✅ **CONFIRMED** — Built SharpEmu from the backup source (which already has the fix), ran Yatzi, and verified:
- `cJ2Y4E-t258` is now **direct-bridged** to `0x804ED3AE0`
- BST is **populated** — `il2cpp_init` found at node `0x2000025AE0`
- API table is **populated** — resolver returns function pointers
- Old crash at `0x80080684D`: **0 occurrences** (ELIMINATED)
- Exit code: **124** (timeout — game ran 30 seconds without crashing)
- `1D0H2KNjshE`/`hsi9drzHR2k` calls: **0** (no longer triggered)
- `sceKernelRaiseException` called: **7 times** (IL2CPP GC stop-the-world active — IL2CPP runtime IS running)

## Root Cause

### The Bug

**File**: `src/SharpEmu.Libs/Kernel/GameCompatExports.cs` (in the "broken" source tree)

**Line 37-38**:
```csharp
[SysAbiExport(Nid = "cJ2Y4E-t258", ExportName = "il2cpp_api_register_symbols", Target = Generation.Gen4 | Generation.Gen5, LibraryName = "libil2cpp")]
public static int Il2cppApiRegisterSymbols(CpuContext ctx) => ctx.SetReturn(0);
```

### Why This Causes the Crash

1. The `[SysAbiExport]` attribute registers `cJ2Y4E-t258` in SharpEmu's HLE export table
2. When EBOOT's import for `cJ2Y4E-t258` is resolved, `TryResolveDirectImportTarget` finds it in the HLE table
3. Since the library is "libil2cpp" (not kernel/libc), `TryResolveDirectImportTarget` returns `false` → the import gets a **Trampoline** (dispatch stub) instead of a **Direct bridge**
4. At runtime, when EBOOT calls `cJ2Y4E-t258` at `0x8013FB24F`:
   - The Trampoline fires → SharpEmu dispatches to the HLE stub
   - The HLE stub does `ctx.SetReturn(0)` → returns 0 (success) **without running the PRX function**
5. The PRX's `il2cpp_api_register_symbols` at `0x804ED3AE0` is **NEVER CALLED**
6. The BST at `[0x808B53708]` is **NEVER BUILT** (remains empty)
7. When EBOOT then calls the resolver (`r8mvOaWdi28`, which IS direct-bridged) for each IL2CPP function name, the resolver walks the empty BST and returns NULL for all functions
8. The API table at `0x801ED6320` stays all NULL
9. When EBOOT later calls through the NULL API table slots, it crashes at `rip=0` (10 times, recovered by VEH), then eventually reaches `0x80080684D` (hash-table lookup with `r15=0`) → infinite crash loop

### The Fix

**Comment out the `[SysAbiExport]` attribute** (as the backup source already does):

```csharp
// REMOVED: [SysAbiExport] for cJ2Y4E-t258 — prevents HLE table registration.
// Without this attribute, TryGetExport won't find cJ2Y4E-t258 in HLE table.
// TryResolveDirectImportTarget will fall through to runtime symbol check
// and direct-bridge to the real PRX function at 0x804ED3AE0.
/*
[SysAbiExport(Nid = "cJ2Y4E-t258", ExportName = "il2cpp_api_register_symbols", Target = Generation.Gen4 | Generation.Gen5, LibraryName = "libil2cpp")]
public static int Il2cppApiRegisterSymbols(CpuContext ctx)
{
    Console.Error.WriteLine("[REGSYM-TRACE] WARNING: HLE stub called instead of direct bridge!");
    return ctx.SetReturn(0);
}
*/
```

### Why the Fix Works

1. Without the `[SysAbiExport]` attribute, `cJ2Y4E-t258` is NOT in the HLE export table
2. `TryResolveDirectImportTarget` checks HLE table → not found → falls through to `TryResolveRuntimeSymbolAddress("cJ2Y4E-t258")`
3. The runtime symbol dictionary has `cJ2Y4E-t258` (stripped NID) → `0x804ED3AE0` (PRX export)
4. `IsDirectImportTargetUsable(0x804ED3AE0)` → true (PRX text segment is executable)
5. Import is **direct-bridged**: GOT slot `0x801D1ACD8` = `0x804ED3AE0`
6. At runtime, EBOOT's call to `cJ2Y4E-t258` jumps directly to `0x804ED3AE0` (the PRX function)
7. The PRX function builds the BST with all IL2CPP function name→address pairs
8. The resolver (already direct-bridged) walks the populated BST and returns correct function pointers
9. The API table is populated with valid function pointers
10. EBOOT's subsequent calls through the API table succeed → IL2CPP runtime initializes → no crash

## Remaining Blockers (After Fix)

With the fix applied, the game runs 30 seconds without crashing. The next blockers are:

1. **`sceKernelRaiseException` (NID `il03nluKfMk`)**: Called 7 times — this is the IL2CPP GC stop-the-world mechanism. Prosper implements this with real async exception delivery. SharpEmu's HLE stub likely returns an error or does nothing, which may cause the GC to deadlock. This is the **next blocker** to investigate.

2. **GPU/Vulkan initialization**: No GPU activity observed in the log. The game may need `sceKernelGetModuleInfoForUnwind` (for C++ exception unwinding) before it can proceed to rendering.

3. **VideoOut**: Not reached in 30 seconds. The game may be stuck in the GC/worker thread phase.
