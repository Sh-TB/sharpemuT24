## External Reference Study

### 1. shadPS4 Emulator (https://github.com/shadps4-emu/shadPS4)

**Architecture studied:**
- `src/core/aerolib/stubs.cpp` — Generic stub system for unresolved NIDs
- `src/core/aerolib/aerolib.h` — NID-to-name lookup
- `src/core/libraries/libc_internal/` — libc internal implementations (memory, strings, threads, I/O, math)
- `src/core/linker.cpp` — Module loading and symbol resolution

**Key finding: shadPS4 uses a FUNDAMENTALLY DIFFERENT approach to unresolved NIDs:**
- shadPS4 has a `UnresolvedStub()` function that returns 0 for ALL unimplemented NIDs
- Uses `GetStub(nid)` to create pre-compiled stub slots (8192 max)
- Each stub logs "Returning zero to {caller}" and returns 0
- This means shadPS4 games can CALL missing functions and get 0 instead of blocking

**SharpEmu's approach (EXP-178/179):**
- SharpEmu returns `ORBIS_GEN2_ERROR_NOT_FOUND` (0x80020002) for missing NIDs
- This error code causes callers to enter error handling paths
- Error paths can lead to dispatch loop → WaitSema deadlock
- EXP-179 fixed this for `_ZdlPv` by implementing the actual function

**shadPS4's libc_internal_memory.cpp:**
- Implements `internal_memset`, `internal_memcpy`, `internal_memcpy_s`, `internal_memcmp`
- Does NOT implement `_ZdlPv`, `_Znwm`, etc. directly — relies on the stub system
- The stub system returns 0, which for `operator delete` is correct (void function)
- For `operator new`, returning 0 means "allocation failure" — PS4 games handle this

**shadPS4's __cxa_* handling:**
- Only `__cxa_guard_acquire`, `__cxa_guard_release`, `__cxa_guard_abort` are explicitly implemented
- All other `__cxa_*` functions go through the stub system (return 0)
- Exception handling (`__cxa_throw`, `__cxa_begin_catch`, etc.) is NOT implemented
- Games that use C++ exceptions will fail silently (exception is "caught" with 0)

### 2. PS4 Unity Native Projects (RetroGamer74)

**Studied:**
- RetroGamer74/PS4_UnjailPlugin_Unity_NativeCode — Unity native plugin for PS4
- RetroGamer74/PS4_Developing_Homebrew_Unity — Unity PS4 homebrew guide
- RetroGamer74/MediaPlayer_FileManager_Unjail — Unity PS4 media player

**Key findings:**
- Unity PS4 native plugins are compiled with the PS4 SDK (OpenOrbis or official)
- They link against `libc.prx` which provides all standard C functions
- C++ operator new/delete are part of `libc.prx` — NOT a separate library
- Unity IL2CPP generates C++ code that uses `operator new`/`operator delete` extensively
- The PS4 `libc.prx` implements these as wrappers around `malloc`/`free`

**Unity IL2CPP dependency chain:**
```
Unity IL2CPP generated code
  → operator new (C++ runtime, part of libc.prx)
  → operator delete (C++ runtime, part of libc.prx)
  → malloc/free (C runtime, part of libc.prx)
  → sceKernelMapDirectMemory (kernel, part of libKernel.prx)
```

**PS4 vs PS5:**
- PS4: `libc.prx` in `sce_module/` directory
- PS5: Same structure — `libc.prx` in `sce_module/`
- PS5 `libc.prx` includes the same C++ ABI functions as PS4
- NIDs are DIFFERENT between PS4 and PS5 (Sony changed NID hashing)

## Predicted Future Blockers

Based on the compatibility matrix, the following are likely to cause issues as the game progresses past the current NULL pointer crash at `0x80080684D`:

### HIGH RISK (likely to block soon):

1. **`__cxa_allocate_exception` (NID: cfAXurvfl5o)**
   - Called when C++ code throws an exception
   - Returning 0 (NULL) means exception allocation failure
   - Unity IL2CPP may use exceptions for error handling
   - **Prediction:** Will block if game throws any C++ exception

2. **`__cxa_throw` (NID: vkuuLfhnSZI)**
   - Actually throws the exception
   - Returning 0 means the throw "succeeded" but nothing happens
   - Game code expecting exception propagation will get incorrect behavior
   - **Prediction:** Will cause silent corruption if exceptions are thrown

3. **`__cxa_begin_catch` (NID: 3cUUypQzMiI)**
   - Called when entering a catch block
   - Returning 0 means no exception object
   - Catch block will operate on NULL pointer
   - **Prediction:** Will crash if game uses try/catch

4. **`__cxa_end_catch` (NID: lX+4FNUklF0)**
   - Called when exiting a catch block
   - Returning 0 is safe (no-op)
   - **Prediction:** Low risk, but needed for proper exception cleanup

### MEDIUM RISK:

5. **`__cxa_get_globals` / `__cxa_get_globals_fast`**
   - Returns pointer to C++ runtime globals structure
   - Returning 0 (NULL) means no runtime state
   - Some code checks this pointer before using it
   - **Prediction:** May cause NULL pointer checks to fail

6. **`__cxa_pure_virtual` (NID: zr094EQ39Ww)**
   - Called when a pure virtual function is invoked
   - Should abort/crash, but stub returns 0
   - **Prediction:** If hit, indicates a real bug in the game

7. **`__cxa_terminate_handler` (NID: 2uD7Mh6paO0)**
   - Sets the terminate handler function pointer
   - Returning 0 means no handler set
   - **Prediction:** Low impact unless std::terminate is called

8. **`__cxa_thread_atexit` (NID: BKSCW2bCACA)**
   - Registers thread-local destructors
   - Returning 0 means registration failed
   - **Prediction:** May cause thread-local variable leaks

### LOW RISK (unlikely to block):

9. Most other `__cxa_*` functions are for niche exception handling scenarios
10. `__cxa_demangle` — only called for debugging/error messages
11. `__cxa_bad_cast`, `__cxa_bad_typeid` — only called on RTTI failures

## Architecture Comparison

### shadPS4 Approach:
```
Unresolved NID → GetStub() → CommonStub() → return 0 + log error
```
- **Pros:** Simple, handles everything, no crashes from missing functions
- **Cons:** Silent corruption, hard to debug, incorrect behavior
- **Result:** Games "run" but may have subtle bugs

### SharpEmu Approach (current):
```
Unresolved NID → DispatchImport → return ORBIS_GEN2_ERROR_NOT_FOUND
```
- **Pros:** Explicit error, easy to identify missing functions
- **Cons:** Error code causes callers to enter error paths, may block
- **Result:** Games block on error handling (WaitSema deadlock)

### Recommended Hybrid Approach:
```
Unresolved NID → Check function category:
  - void functions (operator delete, __cxa_end_catch): return 0 (safe)
  - pointer functions (operator new, __cxa_allocate): return 0 (NULL = failure)
  - error code functions: return ORBIS_GEN2_ERROR_NOT_FOUND
  - bool functions (__cxa_uncaught_exception): return 0 (false)
```
This would prevent the WaitSema deadlock while still allowing detection of genuinely missing functions.

## Key Insights

1. **PS4/PS5 libc.prx includes C++ ABI functions** — they are NOT in a separate library. Both `malloc`/`free` and `operator new`/`operator delete` are in `libc.prx`.

2. **Unity IL2CPP depends heavily on C++ operators** — IL2CPP generates C++ code that uses `operator new`/`operator delete` for all managed object allocation. Missing these causes immediate failure.

3. **shadPS4's stub system is pragmatic but dangerous** — returning 0 for everything works for void functions but silently corrupts state for functions that should return valid pointers.

4. **C++ exception handling is likely the next blocker** — Unity IL2CPP uses C++ exceptions internally for some error paths. If the game hits an exception, `__cxa_allocate_exception` and `__cxa_throw` will fail.

5. **The NULL pointer crash at 0x80080684D (EXP-179)** may be caused by a function returning 0 where a valid pointer was expected. This could be:
   - A missing HLE function (not yet identified)
   - An incorrectly implemented HLE function returning 0 instead of a valid pointer
   - A timing/ordering issue where a structure hasn't been initialized yet
