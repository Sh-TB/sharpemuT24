# EXP-120 NULL CALL INVESTIGATION

**Date:** 2026-08-03
**Status:** COMPLETE — NULL call source identified and verified
**Goal:** Find the exact reason for NULL execution after FAST_PATH=1. Do NOT fix anything. Investigation only.

## Finding

**The NULL execution is caused by `call qword ptr [rbx + 0xF8]` at address `0x800AA01CE` in eboot.bin, where `[rbx+0xF8]` is NULL (0x0000000000000000).** This CONFIRMS the old hypothesis from EXP-075/076: "worker task function pointer `[rbx+0xF8]` is NULL."

The worker object at `rbx` has:
- `[rbx+0x108]` = `0x01` (dependency flag SET — worker thinks dependency is resolved)
- `[rbx+0xF8]` = `0x00` (function pointer NULL — never populated)
- `[rbx+0x100]` = `0x00` (arg NULL — never populated)

The worker loop logic: when `[rbx+0x108] != 0`, the worker decrements refcount, then calls `[rbx+0xF8]` with `rdi = [rbx+0x100]`. Since `[rbx+0xF8]` is NULL, this is a NULL pointer call → SIGSEGV at RIP=0.

**This is NOT callback-dispatch per se — it's a missing task function pointer in the worker object.** The worker thinks it has work (dependency resolved), but the work function was never set. Whoever was supposed to populate `[rbx+0xF8]` never did.

## Transfer Instruction

### Task 2 — The instruction that transfers control to NULL

**Instruction:** `call qword ptr [rbx + 0xF8]`

**Address:** `0x800AA01CE`

**Bytes:** `ff 93 f8 00 00 00`

**Encoding:** `FF /2` with ModR/M byte `0x93` = `mod=10 (disp32), reg=010 (CALL r/m), r/m=011 (rbx)`, displacement `0x000000F8`

**Operand type:** Memory indirect — `call [rbx + 0xF8]`

This is NOT:
- `call rax` (register direct) — would be `FF D0`
- `call rbx` — would be `FF D3`
- `jmp rax` — would be `FF E0`
- `ret` corruption — return address on stack is fine

It IS: **`call [rbx + 0xF8]`** — memory indirect call through a struct field at offset 0xF8 from the worker object pointer.

## NULL Pointer Source

### Task 4 — Trace NULL pointer origin

```
NULL target (RIP=0)
    ↑
call [rbx + 0xF8]   (instruction at 0x800AA01CE)
    ↑
[rbx + 0xF8] = 0x0000000000000000   (worker object field — func_ptr)
    ↑
Worker object at rbx=0x00000006006D1270
    ↑
Created by: (not directly observed in this EXP — worker creation logged in EXP-077)
    ↑
[rbx+0xF8] should have been populated by: ???
```

**The function pointer at `[rbx+0xF8]` was NEVER populated.** The worker object exists, has valid structure (self-pointer at +0x20, worker entry at +0x28, semaphore handles at +0x68 and +0xB0), but the task function pointer field at +0xF8 and the arg field at +0x100 remain NULL (0).

Per prior EXPs:
- EXP-075/076: "task function pointer `[rbx+0xf8]` is set by PRX — 170 write sites, never reached"
- The 170 PRX write sites for `[rbx+0xF8]` are in `Il2cppUserAssemblies.prx`, but none are reached at runtime (per EXP-077)
- The dependency at `[rbx+0x108]` is resolved by the CLEAR function (`0x800A9F750`), but CLEAR clears the flag to 0 — it does NOT write `[rbx+0xF8]`

**Initialization path missing:** The code that should write `[rbx+0xF8]` (the task function pointer) before the worker tries to call it is never executed. This is the same "missing trigger" identified in EXP-106..112, but now pinpointed to a specific struct field.

## Initialization Trace

### What we know about the worker object initialization

| Field | Offset | Value at crash | Expected | Initialized by |
|-------|--------|---------------|----------|----------------|
| Self-pointer | +0x20 | `0x00000006006D1270` | self | ✓ Set (worker creation) |
| Worker func entry | +0x28 | `0x0000000800AA0170` | worker function | ✓ Set (worker creation) |
| Wait semaphore | +0x68 | `0x0000000D00000060` | EVEN handle | ✓ Set (CreateSema) |
| Refcount | +0x70 | `0xFFFFFFFF` → decrementing | initial count | ✓ Set (init) |
| Completion semaphore | +0xB0 | `0x0000000D00000061` | ODD handle | ✓ Set (CreateSema) |
| Active count | +0xB8 | (lock xadd) | counter | ✓ Set (lock xadd) |
| **Task function ptr** | **+0xF8** | **`0x0000000000000000`** | **function pointer** | **✗ NEVER SET** |
| **Task arg** | **+0x100** | **`0x0000000000000000`** | **arg pointer** | **✗ NEVER SET** |
| Dependency flag | +0x108 | `0x00000006006D1201` (low byte=0x01) | 0 or 1 | ✓ Set (by some path — see below) |

### The critical question: why is [rbx+0x108] set (0x01) but [rbx+0xF8] is NULL?

The worker loop checks `[rbx+0x108]` before calling `[rbx+0xF8]`. If `[rbx+0x108] == 0`, the worker goes to WaitSema. If `[rbx+0x108] != 0`, the worker calls `[rbx+0xF8]`.

In Test B (FAST_PATH=1): `[rbx+0x108] = 0x01` (set), so the worker calls `[rbx+0xF8]` (NULL → crash).

In Test A (FAST_PATH=0): Workers are blocked at WaitSema, which means `[rbx+0x108]` was 0 when WaitSema was called. **But wait** — the worker loop at 0x800AA019A checks `[rbx+0x108]` FIRST, and only goes to WaitSema (0x800AA0239) if it's 0. Then after WaitSema returns (0x800AA0207), it checks `[rbx+0x108]` AGAIN at 0x800AA0207.

**Under FAST_PATH=0:** `[rbx+0x108] == 0` → WaitSema blocks forever (nobody signals) → stall.
**Under FAST_PATH=1:** WaitSema returns OK immediately (without blocking). Then at 0x800AA0207, `[rbx+0x108]` is checked again. If it's still 0, the worker exits (jmp 0x800AA0239). If it's non-zero, the worker goes to the call.

**But the crash log shows `[rbx+0x108] = 0x01` at crash time.** This means either:
1. `[rbx+0x108]` was set to 0x01 by some code path between the WaitSema call and the crash, OR
2. The worker entered via a different path (not through WaitSema) where `[rbx+0x108]` was already 0x01

Looking at the disassembly: the worker entry at 0x800AA0170 checks `[rbx+0x108]` at 0x800AA019A BEFORE going to WaitSema. If `[rbx+0x108] != 0` at entry, the worker goes directly to the inner loop (0x800AA01A7) and calls `[rbx+0xF8]` without ever calling WaitSema.

**So the crash path is:** Worker enters → `[rbx+0x108]` already 0x01 → skips WaitSema → calls `[rbx+0xF8]` (NULL) → crash.

This means `[rbx+0x108]` was set to 0x01 BEFORE the worker started, but `[rbx+0xF8]` was NOT set. The dependency flag says "go" but the task function is missing.

## FAST_PATH Comparison

### Task 6 — Does FAST_PATH=0 hide the same bug, or does FAST_PATH=1 create a new invalid path?

**CONFIRMED: FAST_PATH=0 hides the same bug behind WaitSema.**

The same NULL `[rbx+0xF8]` field exists in both modes. The difference is:

| Aspect | FAST_PATH=0 (Test A) | FAST_PATH=1 (Test B) |
|--------|----------------------|----------------------|
| `[rbx+0x108]` at worker entry | 0 (dependency NOT resolved) | 0x01 (dependency resolved) |
| Worker path | Goes to WaitSema → blocks forever | Goes to inner loop → calls `[rbx+0xF8]` |
| `[rbx+0xF8]` value | (not checked — worker never reaches the call) | 0x0 (NULL → crash) |
| Outcome | Stall (exit code 4) | SIGSEGV at RIP=0 (exit code 139) |

**Wait** — this comparison shows that `[rbx+0x108]` differs between the two modes (0 in Test A, 0x01 in Test B). This is suspicious. Why would FAST_PATH=1 cause `[rbx+0x108]` to be set?

**Hypothesis:** Under FAST_PATH=1, WaitSema returns OK immediately without blocking. This means workers cycle through the loop faster. Some other thread (perhaps the main thread or a dispatch thread) may set `[rbx+0x108]` as part of the dispatch process. Under FAST_PATH=0, workers block immediately and never reach the point where `[rbx+0x108]` would be checked again after a wake.

**Alternative hypothesis:** The `[rbx+0x108]` flag is set by the SAME code path that should set `[rbx+0xF8]`, but that code path only partially executes (sets the flag but not the function pointer). Under FAST_PATH=0, the partial execution is masked because workers block before checking the flag. Under FAST_PATH=1, workers proceed and hit the NULL function pointer.

**Cannot definitively determine which hypothesis is correct from the available data.** What IS confirmed:
1. The NULL `[rbx+0xF8]` is the crash cause in FAST_PATH=1
2. The same NULL `[rbx+0xF8]` likely exists in FAST_PATH=0 (workers just never reach the call)
3. FAST_PATH=1 does NOT create a new invalid path — it exposes the existing NULL pointer by letting workers proceed past WaitSema

**FAST_PATH=1 does NOT create a new bug. It exposes the same underlying bug (NULL task function pointer) that FAST_PATH=0 hides behind the WaitSema block.**

## Rejected Hypotheses

1. **"FAST_PATH=1 creates a new invalid execution path"** — REJECTED. FAST_PATH=1 exposes the same NULL `[rbx+0xF8]` that exists in both modes. The path (`call [rbx+0xF8]`) is the same; FAST_PATH=1 just lets workers reach it instead of blocking at WaitSema.

2. **"The NULL execution is a ret corruption"** — REJECTED. The crash is at `call [rbx+0xF8]` (memory indirect call), not a `ret` to a corrupted return address. The return address on the stack is fine (`0x800AA01D4`).

3. **"The NULL execution is a `call rax` or `call rbx`"** — REJECTED. The instruction is `call [rbx + 0xF8]` (memory indirect), not register-direct.

## Remaining Unknown

1. **What code should write `[rbx+0xF8]`?** The 170 PRX write sites (EXP-075/076) are never reached. Is there an eboot.bin path that should write it? Is it set by the callback dispatch subsystem (`0x804FA1FE0`)? This requires further investigation.

2. **Why is `[rbx+0x108]` (dependency flag) set to 0x01 in Test B but apparently 0 in Test A?** Is it set by a different code path under FAST_PATH=1, or is it set by the same (missing) initialization that should also set `[rbx+0xF8]`? This requires tracing `[rbx+0x108]` writes.

3. **Is the missing `[rbx+0xF8]` initialization the ROOT CAUSE, or is it itself a consequence of an earlier missing initialization?** The worker object is created and partially initialized (semaphores, self-pointer, etc.) — only the task function pointer and arg are missing. This suggests the init sequence got most of the way but stopped before populating the task fields. Why?
