## Task 2: Task Submission Path

### Finding

**`sceKernelSignalSema` is NEVER called** — 0 occurrences in the entire 11,181-line log.

The task submission code path (which should set `[rbx+0xf8]` to a real function pointer and call `sceKernelSignalSema` to wake workers) is **never reached**.

### Why tasks are never submitted

With `FAST_PATH=1`:
1. Main thread calls `sceKernelWaitSema` → returns immediately
2. Main thread creates workers
3. Workers call `sceKernelWaitSema` → returns immediately
4. Workers enter task loop, find NULL, spin
5. Main thread continues but never reaches task submission code

The main thread skips synchronization points that should gate task submission. It proceeds to create workers before the task dispatch infrastructure is ready.

## Task 4: FAST_PATH Mode Comparison

| Metric | FAST_PATH=0 (EXP-062) | FAST_PATH=1 (EXP-068) |
|--------|----------------------|----------------------|
| WaitSema behavior | Blocks properly | Returns immediately |

| Result | 20s stall → process exit | 1,005 NULL executes → stack corruption |
| il2cpp_init completed | N/A (stall before) | YES (line 1993) |

### Root Cause

**`sceKernelSignalSema` is never called in either mode.** The code that should signal semaphores (and submit tasks) is never reached. This is because:

1. With `FAST_PATH=0`: The main thread blocks on its own WaitSema before reaching the signaling code → deadlock
2. With `FAST_PATH=1`: The main thread skips the WaitSema but also skips the code between WaitSema and the next synchronization point → workers are created prematurely, spin on NULL tasks

The fundamental issue is that **SharpEmu's semaphore implementation doesn't properly handle the Unity job system's synchronization pattern**: the main thread needs to wait for a condition, then signal workers. SharpEmu either blocks forever (FAST_PATH=0) or skips the wait entirely (FAST_PATH=1).

## Root Cause (Unified)

The FAST_PATH=0 vs FAST_PATH=1 tension is the **same root cause** across EXP-036, EXP-062, and EXP-068:

- `sceKernelSignalSema` is never called by the game code
- With `FAST_PATH=0`: threads block forever waiting for a signal that never comes → deadlock
- With `FAST_PATH=1`: threads skip the wait, proceed prematurely, spin on uninitialized data → crash

The real fix is not choosing between FAST_PATH=0 or 1, but **implementing proper semaphore scheduling** so that:
1. Workers block on WaitSema (FAST_PATH=0 behavior)
2. The main thread progresses to the task submission code
3. The task submission code calls SignalSema to wake workers
4. Workers receive tasks and execute them

This requires understanding WHY the main thread can't progress to the task submission code with FAST_PATH=0. The main thread blocks on its own WaitSema (handle 0x5D) — something should signal that semaphore but doesn't.
