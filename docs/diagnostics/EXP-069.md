## User Feedback #3: AssetGarbageCollectorHelper Pattern

### Finding

The workers are `AssetGarbageCollectorHelper` threads — a Unity internal subsystem for garbage collection of assets. In Unity's job system:

1. Main thread creates worker pool
2. Workers wait on semaphores for task assignment
3. Main thread submits tasks (sets function pointer + signals semaphore)
4. Workers wake, execute task, return to wait

The signaling (step 3) **never happens** because the main thread's code path doesn't reach the task submission stage. With `FAST_PATH=1`, the main thread skips synchronization and creates workers prematurely, but never reaches the code that would submit tasks.

## Root Cause (Confirmed)

**The game code that calls `sceKernelSignalSema` is never reached.** This is a code path issue, not a missing HLE issue:

1. `sceKernelSignalSema` IS imported by the eboot (PLT relocation exists)
2. `sceKernelSignalSema` IS implemented by SharpEmu (HLE export registered)
3. But the game NEVER calls it (0 runtime occurrences)
4. The signaling code is gated behind something that hasn't completed

The FAST_PATH tension is a symptom:
- `FAST_PATH=0`: Main thread blocks on WaitSema before reaching signaling code → deadlock
- `FAST_PATH=1`: Main thread skips WaitSema but also skips code between wait and signal → workers spin

The real question: **what prerequisite must complete before the main thread reaches the SignalSema call?**
