### C) Who is signaling?

The 5.3M SignalSema calls come from **13 worker threads** (13 unique guest thread handles), each signaling ~440K times.

The return address is `0x800AA0223` — this is the instruction AFTER `call SignalSema` at `0x800AA021E` in the WORKER function (`0x800AA0170`).

**Workers are signaling the ODD handles (main thread's semaphores) in a tight loop.** They never signal the EVEN handles (their own worker semaphores).

### D) Is the process making progress?

**NO — tight spin loop.** Evidence:
- Same return address (`0x800AA0223`) for all 447,579 calls on handle 0x73
- Same 13 handles signaled repeatedly (~440K each)
- Worker handles (even) NEVER signaled
- No new imports after the initial burst (last import: #12,800,000, all SignalSema)
- Semaphore count keeps incrementing (0x73: count 1 → 447,579) — same semaphore signaled repeatedly

### E) Root cause classification

**CASE 1: 0x5C is NEVER signaled → Missing completion/signal path.**

The 11-byte NOP bypass allows workers to reach SignalSema, but they signal `[rbx+0xB0]` (task signal handle = odd) instead of the worker's personal handle (even). The correct handle (0x5C) would only be signaled through the CLEAR callback path, which requires the dependency at `[rbx+0x108]` to be properly resolved.

### F) CreateSema analysis

- **144 semaphores created** — all named `Baselib_SystemSemaphore`
- Handles assigned sequentially: 0x02 through 0x91
- Even handles = worker semaphores (never signaled)
- Odd handles = main thread semaphores (heavily signaled by workers)
- 144 is reasonable for Unity's Baselib threading model (13 workers × 2 semaphores each + overhead)

## Root Cause (Definitive)

The dependency at `[rbx+0x108]` (chain pointer to previous worker) is never resolved because:
1. The CLEAR function (`0x800A9F750`) never fires
2. CLEAR should fire when the previous worker completes its task
3. No worker completes because `[rbx+0xf8]=NULL` (no task function assigned)
4. The task function is assigned by PRX code (170 write sites) that's never reached
5. The PRX task dispatch is never reached because the main thread is stuck in its own initialization

The NOP bypass (11 bytes) allows SignalSema to fire but on the WRONG handle (task signal handle from `[rbx+0xB0]` instead of worker wait handle from `[rbx+0x068]`). This creates the appearance of activity (5.3M SignalSema calls) but no actual progress.

## Remaining Blocker

The dependency at `[rbx+0x108]` is never resolved. The CLEAR callback never fires because no worker completes its task (task function pointer `[rbx+0xf8]` is NULL — PRX task dispatch code never reached). The NOP bypass allows SignalSema to fire but on the wrong handle.

**The permanent fix requires implementing the dependency completion mechanism** — either:
1. Implement the async completion event that triggers the CLEAR callback
2. Or implement the PRX task dispatch path that assigns task functions
