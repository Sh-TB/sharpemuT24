# EXP-087 — Main Thread Blocked on WaitSema(0x81): All 15 Threads Deadlocked

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** `SHARPEMU_SEMA_FAST_PATH=0`, metadata at `Media/Metadata/`, EXP-085 flag patch active
**Path:** B (real metadata path)

**Question:** What is the main thread doing after `sceKernelAllocateDirectMemory`?

**Answer:** The main thread is **blocked on `sceKernelWaitSema(handle=0x81)`** — a `Baselib_SystemSemaphore` that is never signaled. The stall detector's snapshot already captured this: `rip=0x6FFFFD001150` (import stub for WaitSema), `rdi=0x6FFF00000081` (handle 0x81), `ret=0x804F6E9EB` (PRX caller). ALL 15 threads are blocked. This is a true deadlock.

**Classification:** **B) RIP repeats** — the main thread is blocked in the WaitSema import stub, waiting for a signal that never comes.

**Confidence:** PROVEN by the stall detector's snapshot output (no new diagnostics needed).

## Main Thread's WaitSema Caller

The main thread calls `sceKernelWaitSema(0x81, 1, 0)` from PRX address `0x804F6E9EB` (PRX vaddr `0x2999EB`).

This is in the PRX's IL2CPP runtime code. Handle 0x81 was created alongside 0x80 and 0x82, right before the GC semaphores (0x83, 0x84). These are likely part of the IL2CPP GC or thread pool initialization.

The main thread waits on handle 0x81 AFTER:
1. il2cpp_init completed
2. Workers created
3. GC thread created
4. `sceKernelAllocateDirectMemory` called (GPU memory allocated)
5. Some additional initialization in the PRX

Nobody signals handle 0x81. On real PS5, something in the IL2CPP runtime or the OS would signal it.

---

## Root Cause

**Handle 0x81 (Baselib_SystemSemaphore) is never signaled.** The main thread blocks on it, and all other threads are also blocked on their respective semaphores. This is a true all-threads-deadlocked state.

The question is: **what should signal handle 0x81?** This requires:
1. Disassembling the PRX code at 0x804F6E9EB to understand what the main thread is waiting for
2. Finding what code path should call `sceKernelSignalSema(0x81)` 
3. Determining if a missing SharpEmu HLE function prevents that code path from executing

## EXP-086 Correction

EXP-086 said "main thread is NOT blocked — it's running." This was **WRONG**.

The stall detector's `Stall snapshot` line shows the main thread IS blocked — it's stuck in the WaitSema import stub. The stall detector doesn't list it as a "Stall guest-thread" because the thread is in the import stub, not in the HLE handler's blocking path. But the thread IS effectively blocked.

**Corrected understanding:** ALL 15 threads are blocked. This is a true deadlock, not a "main thread running silently" situation.
