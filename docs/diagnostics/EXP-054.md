## Task 1: Baseline Run (No Patches)

### Setup
- Built SharpEmu with EXP-054 conditional stub (disabled by default)
- Ran with `SHARPEMU_SEMA_FAST_PATH=0`, `SHARPEMU_EXP048_STUB` unset
- Captured 10,238-line log at `/tmp/exp054_logs/baseline_run1.log`

### Crash Chain (no stub)

```
seq 1: EXP039-HASH_WRITER-ENTER #1 caller=0x800B8D625
        → Writer allocates hash table at 0x600103DB0 (entries all sentinel)

seq 2: EXP036-IL2CPP_INIT-ENTER #1 caller=0x8013ED05D
        → il2cpp_init called from init_func 0x8013EB6B0

seq 3: EXP040-REAL_INIT-ENTER caller=0x804ED85F2
        → real_init called from il2cpp_init
        → hash_table=0x600103DB0, global=0x0, entries all 0xFFFFFFFF

seq 4: EXP041-CALL7 rax=0x808958220 [rax]=0x804D9C620
        → Call #7 returns 0x804D9C620 (epilogue, returns immediately)

seq 5: EXP046-CRASH_PATH_LOOKUP tid=4 rax=0x801EC0C78
        → Call #8 invokes callback at 0x80134FA00 (NOT stubbed!)
        → Callback calls metadata lookup → returns 0x801EC0C78
        → [0x801EC0C78] = 0x80135DDD0 (crash function address)
        → call [rax] → jumps to 0x80135DDD0

seq 6: EXP038-CRASH_FUNC-ENTER #1 caller=0x80134FA7F
        → Crash function entered
        → Reads [rip+0xaf33cc] = [0x801E51240] = 0x0 (NULL metadata global)
        → mov ecx, [rax+0x98] where rax=0 → SIGSEGV

seq 7: UNMAPPED #1 READ rip=0x80135DE83 fault=0x98
        → SIGSEGV recovery (sets dest=0, advances RIP)
seq 8: UNMAPPED #2 READ rip=0x80135DEA2 fault=0x90
seq 9: UNMAPPED #3 READ rip=0x80135DEA9 fault=0xA0
        ... (cascade of 5 SIGSEGVs in crash function)

seq 10: EXP039-HASH_LOOKUP-ENTER #1 caller=0x8009739BC
        → UnityGfxDeviceWorker thread calls lookup
        → hash_input=0, hash_table=0x00FFF00000006090 (garbage - EXP-039 wrong addr)
        → Returns NULL

seq 11: SIGABRT (worker thread crashes, abort signaled)
```

### Key observations

1. **Callback `0x80134FA00` runs unmodified** and crashes at `call [rax]`
   because `rax` points to a fake "object" at `0x801EC0C78` (BSS) whose
   first qword happens to be `0x80135DDD0`.

2. **`0x801EC0C78` is in BSS** — no relocations target it. The value
   `0x80135DDD0` must be written there at runtime by some code we haven't
   traced yet.

3. **The crash function `0x80135DDD0` reads `[0x801E51240]`** (the metadata
   global that's been NULL since EXP-037). This confirms the same root cause:
   the hash table is empty, lookups return NULL, metadata globals stay NULL.

4. **Wrapper `0x800805AE0` was NEVER called** even in the baseline run.
   The stub doesn't affect whether the wrapper runs — it just masks the
   crash after the callback returns.

### Il2CppType struct layout (confirmed)

The `types[]` array at `0x80893E950` contains 13,082 pointers to
`Il2CppType` structs. Each struct is 16 bytes:

```
struct Il2CppType {
    union {
        void* dummy;                    // +0x00
        TypeDefinitionIndex klassIndex; // +0x00 (when type is VALUETYPE/CLASS)
        const Il2CppType* type;         // +0x00 (when type is PTR/ARRAY/etc)
    };
    uint8_t attrs;                      // +0x08
    uint8_t type;                       // +0x09 (Il2CppTypeEnum)
    uint8_t mod;                        // +0x0A
    uint8_t pinned;                     // +0x0B
    uint32_t padding;                   // +0x0C
};
```

First few entries:
```

types[1] -> 0x8082AB150: klassIndex=20, fieldIndex=4
types[2] -> 0x8082AB160: klassIndex=24, fieldIndex=8
types[3] -> 0x8082AB170: klassIndex=32, fieldIndex=16
```

## Task 2B: Il2CppCodeRegistration Struct Found

### Struct at `0x8086E9000`

Discovered via relocation search: a RELATIVE reloc at `0x8086E9030` writes
the address of the mixed array `0x808724730`. Expanding the search revealed
a structured layout at `0x8086E9000`:

```
Il2CppCodeRegistration @ 0x8086E9000:
  +0x00: 0x0                          (reserved/version?)
  +0x08: -> 0x80828A7B1 (rodata)      "22Il2CppExceptionWrapper" (type name?)
  +0x10: 0x11 (17)                    count for +0x18 array
  +0x18: -> 0x80870D940 (data1)       array of 17 entries
  +0x20: 0x19589 (103,561)            count for +0x28 array (methodPointers)
  +0x28: -> 0x808791950 (data1)       methodPointers[] (103,816 code ptrs)
  +0x30: -> 0x808724730 (data1)       mixed array (31,818 entries)
  +0x38: 0x4914 (18,708)              count for +0x40 array
  +0x40: -> 0x8086E90A0 (data1)       secondary method pointers (self-ref!)
  +0x48: 0xECB (3,787)                count for +0x50 array
  +0x50: -> 0x80870D9D0 (data1)
  +0x58: -> 0x808715030 (data1)
  +0x60: -> 0x80871C690 (data1)
  +0x68: 0x379 (889)                  count for +0x70 array
  +0x70: -> 0x808958230 (data2)
  +0x88: 0x68 (104)                   count for +0x90 array
  +0x90: -> 0x808957EE0 (data2)
  +0xA0: -> 0x804D9C640 (code)        inline methodPointers start
  +0xA8: -> 0x804D9C760 (code)
  ...  (continues for 18,725 code pointers)
```

This matches the `Il2CppCodeRegistration` struct from Unity's IL2CPP runtime:
```c
struct Il2CppCodeRegistration {
    uint32_t methodPointersCount;
    const Il2CppMethodPointer* methodPointers;
    uint32_t reversePInvokeWrapperCount;
    const Il2CppMethodPointer* reversePInvokeWrappers;
    uint32_t rgcxStartCount;
    ...
};
```

### Il2CppMetadataRegistration (still being located)

The `types[]` array at `0x80893E950` is part of `Il2CppMetadataRegistration`,
but no relocation points TO `0x80893E950` — it's accessed via RIP-relative
LEA. The `Il2CppMetadataRegistration` struct itself is likely nearby (in the
`0x8086E9xxx` or `0x80870xxxx` range) but hasn't been pinpointed yet.

## Task 7: Call #7 Re-verification

### Call #7 target: `0x804D9C620`

```
EXP041-CALL7: rax=0x808958220 [rax]=0x804D9C620
              rdi=0x2 rsi=0x200022E340
```

- `rax` = `0x808958220` (in PRX data segment 2)
- `[rax]` = `0x804D9C620` (in PRX code segment)
- `0x804D9C620` is the first entry of the inline methodPointers array at
  `Il2CppCodeRegistration + 0xA0`

**This confirms**: Call #7 reads `methodPointers[0]` from the
`Il2CppCodeRegistration` struct. The function at `0x804D9C620` is the first
method pointer — likely the IL2CPP runtime entry point.

`0x804D9C620` returns immediately (epilogue). This is correct behavior —
it's a "no-op" method that the runtime calls to verify the code registration
is valid.

## Next Step (EXP-055)

### Find the registration function

The `Il2CppCodeRegistration` struct at `0x8086E9000` must be passed to a
registration function (`il2cpp_codegen_register` or similar). This function:

1. Takes `Il2CppCodeRegistration*` and `Il2CppMetadataRegistration*` as args
2. Iterates the `types[]` array
3. For each type, calls the wrapper `0x800805AE0` with the type name
4. The wrapper inserts the name→type mapping into the hash table

### Specific tasks

1. **Search PRX code for LEA instructions loading `0x8086E9000`** — this
   will find the registration function that takes the struct as an argument.

2. **Search for `Il2CppMetadataRegistration`** — likely near
   `0x8086E9000` (similar struct layout with count+pointer pairs for
   `types[]`, `genericClasses[]`, `methodSpecs[]`, etc.)

3. **Trace real_init call #8 in detail** — the callback at `0x80134FA00`
   is invoked from call #8. Disassemble the PRX code around call #8 to
   see what arguments are passed and what metadata is accessed.

4. **Implement the manual walker** — once we know the registration
   function's signature, call it directly from SharpEmu after the PRX loads,
   before il2cpp_init runs.

### Target: BOOT_STAGE_5

Once the registration function runs:
- Hash table gets populated with real type metadata
- Lookups return non-NULL
- Init function's metadata globals are set
- il2cpp_init completes successfully
- Unity runtime starts
