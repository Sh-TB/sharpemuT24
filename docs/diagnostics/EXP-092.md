# EXP-092 — DT_INIT_ARRAY Fix: Progress Made (37 More Semaphores), Hash Table Still Empty

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** `SHARPEMU_SEMA_FAST_PATH=0`, metadata at `Media/Metadata/`, EXP-085 flag patch active, **DT_INIT_ARRAY fix applied**

**Question:** Does SharpEmu execute PRX DT_INIT during module loading?

**Answer:** SharpEmu's `RunPreloadedModuleInitializers` only called DT_INIT (which resolves to ELF header on PS5 PRXs) and **never called DT_INIT_ARRAY**. `RunImageInitializers` existed but was dead code. After fixing this, the PRX's module_start (`0x804CD5010`) was called, creating **37 more semaphores** (stall moved from handle `0x81` to `0xA6`). However, the hash table is still empty (`populated=0/100`).

**Confidence:** PROVEN by code analysis (dead code found and fixed) + runtime evidence (37 more semaphores created, different stall handle).

---

## Bug Found: RunImageInitializers Was Dead Code

`RunPreloadedModuleInitializers` (line 545) only called `InitFunctionEntryPoint` (DT_INIT). `RunImageInitializers` (line 600) — which calls `InitializerFunctions` (DT_INIT_ARRAY) — existed but was **never called by any code**.

Additionally, when `InitFunctionEntryPoint < 0x10000` (which happens on PS5 PRXs where DT_INIT = imageBase+0x10), the entire module was skipped via `continue`, preventing DT_INIT_ARRAY from running.

## Fix Applied

Modified `RunPreloadedModuleInitializers` to:
1. NOT skip the module when DT_INIT is invalid (< 0x10000) — only skip the DT_INIT call
2. Call `RunImageInitializers` for every module after DT_INIT (or skipping DT_INIT)

## Analysis

The DT_INIT_ARRAY fix caused the PRX's module_start to run, which initialized 37 more semaphores. This is real progress — the PRX's static initializers are now executing.

However, the hash table is **still empty**. The hash table population happens **during il2cpp_init** (in real_init → call#7), not during DT_INIT_ARRAY. The module_start runs BEFORE il2cpp_init and does different initialization (C++ static constructors, not IL2CPP metadata registration).

The remaining issue: `il2cpp_codegen_register` (which should populate the hash table) is called during il2cpp_init but doesn't insert entries. This is the same issue as EXP-040/EXP-091.

## Next Step

The hash table population mechanism needs to be traced inside il2cpp_init's execution. Specifically:
1. Find where `il2cpp_codegen_register` is called within real_init
2. Trace what it does with the metadata
3. Find why it doesn't insert entries into the hash table

The DT_INIT_ARRAY fix is **correct and necessary** but not sufficient to fix the hash table population. The population happens in a different code path (il2cpp_init, not DT_INIT).
