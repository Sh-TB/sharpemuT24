# EXP-088 — Semaphore 0x81 Owner: IL2CPP ThreadPool Work-Available Semaphore

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** `SHARPEMU_SEMA_FAST_PATH=0`, metadata at `Media/Metadata/`, EXP-085 flag patch active
**Path:** B (real metadata path)

**Question:** What PRX function calls `WaitSema(0x81)` at `0x804F6E9EB`, and what code should call `SignalSema(0x81)`?

**Answer:** Handle 0x81 is the **IL2CPP ThreadPool work-available semaphore**. The main thread enters the thread pool worker function at `0x804F6E510` and waits for work. `SignalSema(0x81)` exists at `0x804F6ECF9` in the **same function** — it's called when work is dispatched to a worker via atomic CAS. But no work is ever dispatched because the IL2CPP initialization hasn't queued any work items.

**Confidence:** PROVEN by static analysis (disassembly of WaitSema caller, SignalSema caller, and thread pool dispatch loop).

## SignalSema Caller (the ONLY one that uses [reg+0x88])

```
Same function: 0x804F6E510
  │
  ├── Loop: iterate worker entries in [r15+0x50] array
  │   └── For each entry:
  │       ├── Check [entry+0x90] (work count) vs [entry+0x94] (processed count)
  │       ├── If work pending: atomic CAS on [entry+0x90] to claim work
  │       ├── If CAS succeeds (je 0x804F6EC75):
  │       │   ├── 0x804F6EC75: test esi, esi     ← check work delta
  │       │   ├── 0x804F6EC77: js 0x804F6ECEB    ← if NEGATIVE (worker needs wake), signal!
  │       │   └── 0x804F6ECEB: mov rdi, [rcx+0x88] ← load semaphore handle
  │       │       0x804F6ECF9: call SignalSema     ← signal the worker
  │       └── Continue loop
  │
  └── 181 total callers of the SignalSema wrapper, but only 1 uses [reg+0x88]
```

## Thread Pool Entry Structure

```
struct ThreadPoolEntry {
    +0x00: ? (data pointer)
    +0x08: ? (thread pointer)
    +0x10: atomic counter (work claim)
    +0x50: array pointer (worker entries)
    +0x58: entry count
    +0x88: semaphore handle (Baselib_SystemSemaphore)
    +0x90: work count (atomic, CAS target)
    +0x94: processed count
}
```

## Why Handle 0x81 Is Never Signaled

The SignalSema(0x81) at `0x804F6ECF9` is called when:
1. The dispatch function iterates worker entries
2. Finds an entry where work count != processed count
3. Successfully claims work via atomic CAS
4. The work delta is negative (worker needs to be woken)

This never happens because:
- **No work is submitted to the thread pool**
- The main thread enters the pool as a worker (normal .NET behavior)
- But no other code path queues work items
- Without queued work, the CAS never succeeds
- Without CAS success, SignalSema is never called

## What Should Submit Work

Work would be submitted by:
1. **IL2CPP runtime initialization** — type registration, metadata processing
2. **GC system** — background collection tasks
3. **File I/O callbacks** — async file reads (fopen failed with NOT_FOUND!)
4. **Unity job system** — Job.worker threads (not created on Path B)

The most likely cause: an HLE function returns an error or is missing, preventing the IL2CPP runtime from reaching the work submission stage. The import errors found in EXP-086 are candidates:
- `sceKernelVirtualQuery` → NOT_FOUND
- `sceKernelDirectMemoryQuery` → NOT_FOUND
- `fopen` → NOT_FOUND
- Unknown NID `1-LFLmRFxxM` → PERMISSION_DENIED

## Fix Direction

**Do NOT force SignalSema(0x81).** This would wake the main thread without actual work, causing it to process garbage data.

The correct fix is to find what prevents work from being submitted to the thread pool. Candidates:
1. The failed `sceKernelVirtualQuery` / `sceKernelDirectMemoryQuery` calls may prevent memory mapping needed for work submission
2. The `fopen` NOT_FOUND error may prevent loading a required file
3. The `PERMISSION_DENIED` error for NID `1-LFLmRFxxM` may block a required operation

**Next EXP:** Trace what the main thread does between `sceKernelAllocateDirectMemory` and entering the thread pool, to find the exact point where work submission should occur but doesn't.
