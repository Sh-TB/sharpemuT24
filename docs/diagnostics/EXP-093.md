# EXP-093 — il2cpp_codegen_register Is a Stub: Saves Pointers to 3 Globals, Does NOT Populate Hash Table

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** `SHARPEMU_SEMA_FAST_PATH=0`, metadata at `Media/Metadata/`, EXP-085 flag patch active, DT_INIT_ARRAY fix (EXP-092) applied
**Path:** B (real metadata path)

**Question:** Why doesn't `il2cpp_codegen_register` insert entries into the hash table during `il2cpp_init`?

**Answer:** Because `il2cpp_codegen_register` (at `0x804F23280`) is a **STUB** that only saves its 3 arguments to 3 globals (`0x808B542E8`, `0x808B542F0`, `0x808B542F8`) and returns. It does NOT iterate types, does NOT compute hashes, does NOT insert anything into the hash table at `0x801EF7610`. This is by design — not a SharpEmu bug.

**Confidence:** PROVEN by static disassembly (full call chain from `real_init` → wrapper → trampoline → `il2cpp_codegen_register` body, all disassembled and verified).

## Hardcoded Arguments (Verified)

The wrapper `0x804D9C620` loads 3 hardcoded pointers (RIP-relative LEA):

| Register | Computed Address | Identity | Matches Prior EXP |
|----------|------------------|----------|-------------------|
| `rdi` | `0x8086E9010` | `Il2CppCodeRegistration @ 0x8086E9000 + 0x10` | EXP-054 ✓ |
| `rsi` | `0x80885C598` | `Il2CppMetadataRegistration @ 0x80885C580 + 0x18` | EXP-055 ✓ |
| `rdx` | `0x8082AE0C0` | method pointers / type index array | (new) |

The addresses match the registrations identified in EXP-054/055 (offset by struct field positions). The wrapper loads these as constants — it ignores whatever args were passed by `real_init` (`rdi=0x8`, `rsi=0x20231F60` per EXP-041 tracer).

## What il2cpp_codegen_register ACTUALLY Does

The body at `0x804F23280` is 55 bytes. It performs exactly 3 actions:

1. **Calls `0x804F71390`** — a once_init/lock helper (likely a pthread_once or std::once_flag implementation). This ensures the registration only runs once.

2. **Stores the 3 registration pointers to 3 globals:**
   - `[0x808B542E8] = rdi` (Il2CppCodeRegistration*)
   - `[0x808B542F0] = rsi` (Il2CppMetadataRegistration*)
   - `[0x808B542F8] = rdx` (method pointers array)

3. **Returns.** No iteration. No hash computation. No hash table insertion.

## Why the Hash Table Stays Empty

The hash table at `0x801EF7610` (created by EBOOT's `hash_table_writer` at `0x8007F90A0`) is **never written to** by:
- `il2cpp_codegen_register` (`0x804F23280`) — confirmed: stub only saves pointers
- `call#7` (`0x804F23320`) — confirmed: reads the 3 globals, processes them, but doesn't write to `0x801EF7610`
- `array_proc` (`0x804F2B4D0`) — confirmed: merge sort on the array at `0x808958230`, doesn't touch `0x801EF7610`
- Loop body `0x804F238F0` — confirmed: calls 5 functions, operates on a structure at `[0x808923D88]`, doesn't touch `0x801EF7610`

The PRX has 0 reads and 0 writes to `0x801EF7610` (confirmed by exhaustive static analysis in EXP-091). This is consistent with `il2cpp_codegen_register` being a stub — the PRX simply does not use the `0x801EF7610` hash table.

## Correction to EXP-091

EXP-091 said: *"Entries should be inserted by `il2cpp_codegen_register` during PRX DT_INIT. SharpEmu likely doesn't call the PRX's DT_INIT, so the registration never runs."*

**CORRECTED:** `il2cpp_codegen_register` is NOT called during DT_INIT. It IS called (from `real_init` at `0x804F04C5C`, via indirect call through `[0x808958220]`), and it DOES run (confirmed by EXP-041 tracer in the EXP-092 log). But it's a stub that only saves 3 pointers to globals — it does NOT insert anything into the hash table, by design.

The EXP-092 fix (DT_INIT_ARRAY) was correct and necessary (it enabled `module_start` to run, creating 37 more semaphores), but it was based on the wrong assumption that `il2cpp_codegen_register` runs during DT_INIT. In reality, `il2cpp_codegen_register` runs during `real_init`, and it's a stub.

## Correction to EXP-092

EXP-092 said: *"The hash table is NOT populated by DT_INIT_ARRAY. It's populated during `il2cpp_init` → `real_init` → `call#7`."*

**CORRECTED:** The hash table at `0x801EF7610` is NOT populated by `call#7` either. `call#7` (`0x804F23320`) reads the globals saved by `il2cpp_codegen_register` and processes them (sorting, per-entry registration into a DIFFERENT structure at `[0x808923D88]`), but does NOT write to `0x801EF7610`.

## Where the Metadata Actually Goes

The PRX's metadata registration uses a DIFFERENT structure than `0x801EF7610`:

1. **`il2cpp_codegen_register`** saves the 3 registration pointers to globals at `0x808B542E8/F0/F8`.
2. **`call#7`** reads those globals and processes them:
   - Loop 1 (0x804F233D0..0x804F233F4): calls `0x804F238F0` per iteration
   - `0x804F238F0` (loop body) calls `0x804F2AB80`, `0x804F2B160`, `0x804F2B330` — these operate on a structure accessed via `[0x808923D88]`, NOT via `0x801EF7610`
   - `array_proc` (`0x804F2B4D0`) sorts the type array by hash (merge sort)
3. The sorted array remains at `0x808958230` — it is NOT copied into `0x801EF7610`.

This means the **actual metadata lookup mechanism** uses the structure at `[0x808923D88]` (or the sorted array at `0x808958230`), NOT the hash table at `0x801EF7610`.
