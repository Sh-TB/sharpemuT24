# EXP-082 — Crash at 0x80080684D: NULL Per-Image Hash Table

**Identity:** Yatzi / PPSA17697 / verified (SHA256 `d17fba4a...` PASS)
**Configuration:** `SHARPEMU_SEMA_FAST_PATH=0` (proper blocking, no NOP bypass)

**Question:** Why does the game crash at `0x80080684D` (`mov r8d, [r15+rcx]` where `r15=NULL`)?

**Answer:** The crash is a NULL per-image hash table dereference. `r15` = `rdi` parameter = `[r12+0x278]`, where `r12` is an IL2CPP image object. The hash table at `[image+0x278]` was never initialized because the IL2CPP metadata registration process is incomplete. This is **downstream of the same issue identified in EXP-053**: the metadata registration wrapper is never properly invoked.

**Confidence:** PROVEN by static analysis (crash function disassembly + caller trace) + runtime evidence (EXP-053 wrapper 0 hits, hash_table global NULL at init).

---

## Hash Table Address Verification (per user request)

**This crash is NOT about the global hash table at `0x801EF7610` or `0x801EE7610`.**

The crash reads from `[r15+rcx]` where:
- `r15` = `rdi` = first parameter to the crash function (0x800806750)
- `r15` is set at `0x800806768: mov r15, rdi`
- `r15 = NULL` means the caller passed NULL as the first argument

The caller (`0x800C853C9`) sets `rdi = [r12+0x278]` where `r12` is an IL2CPP image object. This is a **per-image hash table** stored at offset `0x278` inside the image struct, NOT the global hash table at `0x801EF7610`.

The `0x801EF7610` vs `0x801EE7610` typo (standing gotcha) is NOT relevant to this crash.

## Task 1 — Relationship to EXP-053 (wrapper-never-called)

**CONFIRMED: This crash IS downstream of EXP-053's wrapper-never-called finding.**

Evidence:
1. **EXP-053 wrapper** (`0x800805AE0`): 0 hits in the FAST_PATH=0 validation run (confirmed never called)
2. **Crash function** (`0x800806750`): located at `0x800806750`, which is BETWEEN the EXP-053 wrapper (`0x800805AE0`) and EXP-053 insert (`0x800806940`) — same code region, same IL2CPP metadata module
3. **Per-image hash table** at `[image+0x278]` = NULL: this field should be initialized by the IL2CPP metadata registration process, which requires the wrapper to be called
4. **Global hash table** at `0x801EF7610` IS initialized (to `0x600103DB0` by hash_table_writer at `0x8007F90A0`), but per-image hash tables are NOT initialized

The user's suspicion was correct: "if the hash table is still empty because that wrapper never fires, this NULL `r15` might just be the next symptom of that same still-open mechanism, not a new independent bug."

The caller reads `[image+0x278]` as the hash table base. This field is **NULL** because the image object was never properly initialized.

## Task 3 — Which HLE/Metadata API Should Provide the Pointer?

The pointer at `[image+0x278]` is a **per-image type lookup hash table**. It should be initialized during IL2CPP metadata registration.

The initialization chain should be:
1. `il2cpp_init` (PRX `0x804ED85D0`) — called successfully ✓
2. `il2cpp_init` calls into EBOOT to register assemblies
3. EBOOT's IL2CPP registration code calls `il2cpp_codegen_register` (or equivalent)
4. `il2cpp_codegen_register` processes `Il2CppCodeRegistration` and `Il2CppMetadataRegistration`
5. For each image, it initializes the per-image type hash table at `[image+0x278]`

**Step 3 is failing.** The EBOOT's IL2CPP registration code (wrapper at `0x800805AE0`) is never called. This was first identified in EXP-052/053 and remains unresolved.

The wrapper at `0x800805AE0` was originally identified as `il2cpp_codegen_register`, but on closer inspection it appears to be a `#dllimport:` string parser (it checks for the bytes '#','d','l','l','i','m','p','o','r','t',':'). This means the actual `il2cpp_codegen_register` is a different function that calls this parser, and the registration chain is more complex than initially thought.

### Expected pointer source:
- `[image+0x278]` should be initialized by `il2cpp_codegen_register` or equivalent
- The registration function processes `Il2CppCodeRegistration` from the PRX
- It creates per-image type hash tables for fast `il2cpp_class_from_name` lookups
- Without registration, `[image+0x278]` stays NULL

### Hash table state:
- Global hash table at `0x801EF7610`: initialized to `0x600103DB0` ✓
- Per-image hash table at `[image+0x278]`: NULL ✗ (never initialized)

## Root Cause

**The IL2CPP metadata registration process does not complete.** Specifically:

1. `il2cpp_init` is called and runs successfully
2. The registration code that should initialize per-image type hash tables is **never reached**
3. The wrapper at `0x800805AE0` (identified in EXP-053) has 0 hits — it is never called
4. Without registration, `[image+0x278]` (per-image hash table) stays NULL
5. When Unity tries to look up a type by name (via `il2cpp_class_from_name` or similar), it calls the hash lookup function at `0x800806750` with the NULL hash table base → crash

This is the **same root cause** identified in EXP-053 ("wrapper never called") and EXP-056 ("missing consumer function"). The crash at `0x80080684D` is the **next symptom** of this still-open mechanism, not a new independent bug.

## Fix Location

**The fix must ensure the IL2CPP metadata registration chain completes.**

Specifically:
1. **Trace what should call the registration code** — `il2cpp_init` (PRX `0x804ED85D0`) calls into EBOOT code that should trigger registration. Find the exact call site that's missing.
2. **Check if a SharpEmu HLE function returns an error** that causes the registration to be skipped — look for `ORBIS_GEN2_ERROR_*` return values in the IL2CPP init path
3. **Check if a required HLE function is missing** — the registration might depend on a syscall or library function that SharpEmu doesn't implement

The fix is in **`SharpEmu.HLE/`** — either:
- An HLE function that returns an error when it should succeed, causing registration to abort
- A missing HLE function that the registration code depends on

This is NOT fixable by patching the EBOOT or PRX — it requires fixing SharpEmu's HLE layer to properly support the IL2CPP registration chain.
