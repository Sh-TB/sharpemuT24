# EXP-102 — r14 = NULL at Callback Storage — Callback Stored at Address 0

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** `SHARPEMU_SEMA_FAST_PATH=0`, metadata at `Media/Metadata/`, all prior tracers active
**Path:** B (real metadata path)

**Question:** Where is the callback pointer stored (what address does r14 point to at `0x804F88A76: xchg [r14], rax`), and what code should read it to invoke the callback?

**Answer:** `r14 = 0` (NULL). The callback pointer is stored at address 0 — a NULL pointer dereference. The callback is never invoked because it's stored at NULL, not at a valid structure field. Additionally, `r12` (the IL2CPP context pointer loaded from `[0x808923D88]`) is also `0` at this point in the code.

**Confidence:** PROVEN by runtime tracing (INT3 at `0x804F88A76`, r14 captured).

---

## Hypothesis

The callback pointer is stored at a specific address inside an IL2CPP context structure, and finding that address + its readers will reveal the invocation path.

## Test Method

Built `_Exp102CallbackStorageTracer.cs` — INT3 at `0x804F88A76` (the `xchg [r14], rax` instruction). Captures `r14` (storage address), `rax` (callback pointer), `r12` (IL2CPP context), and surrounding memory.

## Runtime Evidence

```
[EXP102-XCHG] *** CALLBACK STORAGE *** r14=0x0000000000000000 rax=0x00007FE77CFC0450
  r12(IL2CPP context)=0x0000000000000000
  r14 region: UNKNOWN
```

**r14 = 0** — the callback storage target is NULL.
**r12 = 0** — the IL2CPP context pointer (`[0x808923D88]`) is also NULL at this point.

The `xchg [r14], rax` attempts to store the callback pointer (rax) at address 0 — a NULL pointer dereference.

## Static Analysis

### How r14 Gets Its Value

From `0x804F889D0` (registration helper):
```asm
0x804F889DF: mov r12, [rip+0x399b3a2]  ; -> 0x808923D88 (IL2CPP context global)
0x804F889E6: mov r14, rdi               ; r14 = first argument (rdi)
...
0x804F88A76: xchg [r14], rax            ; store callback at [r14]
```

From `0x804FA20E0` (registration function):
```asm
0x804FA20EA: mov rbx, rdi               ; save original rdi
0x804FA2119: mov rdi, [rbx + 8]         ; rdi = [original_arg + 8]
0x804FA2127: jmp 0x804F889D0            ; r14 = rdi = [original_arg + 8]
```

So `r14 = [original_arg + 8]`. If `[original_arg + 8] == 0`, then `r14 = 0`.

### Why r12 Is Also NULL

`r12` is loaded from `[0x808923D88]` (the IL2CPP context global). At this point in execution, the context is NULL. This is unexpected — EXP-097 showed `[0x808923D88]` was populated after the `_ThreadPoolWaitCallback` lookup. But the registration path (`0x804FA20E0`) fires AFTER the lookup, and by that time `[0x808923D88]` may have been cleared, or the code path is on a different thread/context.

### The Tracer Crash

After capturing `r14=0`, the tracer attempted to read `[r14]` (memory at address 0), which caused a .NET JIT "Invalid Program" crash (same pattern as EXP-096). The emulator aborted (exit code 134) instead of reaching the normal stall. The `r14=0` finding is valid — it was captured before the crash.

## Conclusion

**The callback is stored at address 0 (NULL).** This is the actual root cause of the ThreadPool deadlock:

1. The registration function `0x804FA20E0` receives an argument whose `[+8]` field is NULL
2. This NULL value becomes `r14` in `0x804F889D0`
3. The callback pointer is stored at `[r14]` = `[0]` = NULL address
4. The callback is never invoked because no code reads from address 0 to find it
5. The ThreadPool work-submission function (`0x804F6EC20`) never receives the callback

### Why Previous Hypothesis Was Wrong

EXP-101 concluded "callback IS stored correctly" based on all PLT stubs returning 0. But EXP-101 didn't check WHERE the callback was stored — it only checked that the `xchg` instruction would execute (no error branch taken). The `xchg` does execute, but it writes to NULL.

### What SharpEmu Is Missing

The registration context structure (passed as `rdi` to `0x804FA20E0`) has a NULL field at `[+8]`. This field should contain a pointer to the callback storage location. On a real PS5, this would be a valid pointer to an IL2CPP internal structure.

The NULL at `[rbx + 8]` likely comes from an uninitialized or incompletely initialized IL2CPP context structure. The structure is allocated but not fully populated — the field at `+8` (which should point to the callback storage) is never set.
