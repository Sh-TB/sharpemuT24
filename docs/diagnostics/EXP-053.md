# EXP-053 — Runtime Tracer for IL2CPP Metadata Registration Walker

## Date: 2026-07-31
## Status: COMPLETE — Wrapper NEVER called on SharpEmu; static table hypothesis disproved

---

## Executive Summary

Implemented a runtime tracer with INT3 at:
- Wrapper `0x800805AE0` (il2cpp_codegen_register candidate)
- Insert `0x800806940` (hash_insert)

Ran Yatzi with `SHARPEMU_SEMA_FAST_PATH=0` and the existing callback stub from
EXP-048. Captured full boot sequence through SIGABRT.

**Key findings:**

1. **Wrapper `0x800805AE0` was NEVER called** (0 hits). The hash table is
   allocated by writer `0x8007F90A0` (1 hit) but never filled. All lookups
   return NULL.

2. **Insert `0x800806940` was NEVER called** (0 hits). Confirms wrapper is
   the only path to fill the hash table.

3. **Static table at `0x1CC0080` is NOT `Il2CppMetadataRegistration`** — it's
   a **string fragment table** for Unity's error message system. The 13,920
   RELATIVE relocations populate pairs of (function_ptr, string_ptr) where
   the strings are fragments like `"es (got start=%i count=%i, mesh has
   %zu indices)"` (substrings of larger error messages).

4. **EXP-039 had a wrong hash table address**: `Exp039_HashTablePtrAddr =
   0x801EE7610` (note double-E). Correct address is `0x801EF7610`. EXP-053
   tracer uses the correct address. The old tracer's "hash_table=0x00FFF00000006090"
   reading was garbage from the wrong address.

5. **Lookup `0x8004BD620` was called once** from `0x8009739BC` (UnityGfxDeviceWorker
   thread), NOT from the init function. The init function's lookup at
   `0x8013EEFE7` was NEVER reached because il2cpp_init crashed before that.

6. **Hash table state at real_init entry**: `hash_table=0x600103DB0` (allocated),
   `entries=0x60053E990`, `mask=0x7FFF8`, all entries = `0xFFFFFFFF` (sentinel).
   **0 populated entries.**

## Task A: Instrumentation Results

### A1: Wrapper `0x800805AE0` — 0 hits

The wrapper was NEVER called during the entire boot. This confirms:
- The wrapper is not called by the writer (different functions)
- The wrapper is not called by il2cpp_init (crashes before reaching it)
- The wrapper is not called by any static initializer (DT_INIT_ARRAY is empty)

### A2: Insert `0x800806940` — 0 hits

Confirms wrapper is the only caller of insert. Since wrapper never runs,
insert never runs, hash table stays empty.

### A3: Lookup `0x8004BD620` — 1 hit (from wrong code path)

The single lookup call came from `0x8009739BC` inside the UnityGfxDeviceWorker
thread (entry `0x800BB06A0`), NOT from the init function. The lookup read
hash key from `[0x801E53108]` (a global), got `hash_input=0`, and crashed
trying to dereference the result.

### A4: Once-init flag `0x801E516F0`

- At tracer install: `once_init_flag=0x00`
- After writer ran: `once_init_flag=0x01` (set by writer)
- Never reset — writer is one-shot

## Task B: Static Table Investigation

### B1: Static table at `0x1CC0080` is NOT Il2CppMetadataRegistration

The 13,920 RELATIVE relocations populate pairs of pointers. The first few
entries point to:
- `0x8003C68F0`, `0x8003C6970` (code addresses in eboot .text)
- `0x8003C6A30`, `0x8003C6AB0` (code addresses)
- ...

The "string pointers" starting at offset +0x4510 (`0x1CC4590`) point to
fragments like:
- `"es (got start=%i count=%i, mesh has %zu indices)"`
- `"X10"`
- `"re format of already created render texture is not supported!"`
- `"_Tier3"`
- `"ase turn SRP Batcher ON to use the BatchRendererGroup API."`

These are **substrings of Unity error messages**, not type/method names.
The table is a **string fragment pool** for Unity's localization system,
NOT `Il2CppMetadataRegistration`.

### B2: EXP-052 hypothesis disproved

EXP-052 claimed the static table was `Il2CppMetadataRegistration` based on
the structure (pairs of function + string pointers). This was WRONG. The
table is a string fragment pool. The actual `Il2CppMetadataRegistration`
table location is still unknown.

### B3: Real `Il2CppMetadataRegistration` location

Still unknown. The wrapper `0x800805AE0` takes a string and inserts it
into the hash table. The string must come from somewhere — either:
1. A different static table we haven't found yet
2. Computed at runtime from PRX metadata
3. Read from `globalgamemanagers.assets` or other Unity asset files

## Task C: Timing Analysis

### C1: Walker timing relative to il2cpp_init

The wrapper was NEVER called, so there's no timing to analyze. However,
the boot sequence shows:

1. Writer called (allocates empty hash table)
2. il2cpp_init called
3. real_init called
4. Call #7 (epilogue, returns immediately)
5. **CRASH** — call #8 would invoke the callback, but the callback stub
   from EXP-048 makes it return 1 immediately
6. After stub returns, control falls through to... something that crashes
7. UnityGfxDeviceWorker thread starts, calls lookup, gets NULL, crashes

### C2: Confirmed: missing walker is the root cause

The wrapper is never called because the **walker function that should call
it is never invoked**. On a real PS5, this walker would:
1. Iterate the real `Il2CppMetadataRegistration` table
2. For each entry, call the wrapper with the type/method name string
3. The wrapper inserts the name→metadata mapping into the hash table

Without the walker, the hash table stays empty, all lookups return NULL,
and il2cpp_init crashes when it tries to use the NULL results.

## Task D: Manual-fill implementation plan

### D1: Cannot implement manual fill yet

The manual fill requires knowing:
1. Where the real `Il2CppMetadataRegistration` table is located
2. What strings to pass to the wrapper
3. The wrapper's exact calling convention (we know `rdi` = string, but
   there may be other required arguments)

Since the static table at `0x1CC0080` is NOT the metadata registration
table, we cannot use it as the source for manual fill.

### D2: Next steps to find the real metadata table

1. **Search PRX (Il2cppUserAssemblies.prx) for the metadata table** —
   The PRX is 74MB and likely contains the IL2CPP metadata. Search for
   patterns of (type_info_ptr, type_name_ptr) pairs.

2. **Trace the callback stub's caller** — The callback at `0x80134FA00`
   is called from real_init call #8. The callback reads metadata. By
   tracing what the callback WOULD read, we can find the metadata table
   location.

3. **Search for `il2cpp_init`'s internal registration call** —
   `il2cpp_init` (in the PRX) likely calls a registration function
   before the callback. Disassemble `real_init` more thoroughly to
   find this call.

4. **Check `globalgamemanagers.assets`** — Unity stores type metadata
   in this file. The loader might parse it and populate the table.

## Next Step (EXP-054)

### Find the real `Il2CppMetadataRegistration` table

1. **Search the PRX** (`Il2cppUserAssemblies.prx`, 74MB) for patterns of
   (type_info_ptr, type_name_ptr) pairs. The PRX has 383,614 relocations —
   many will point to metadata structures.

2. **Trace `real_init` call #8 in detail** — The callback at `0x80134FA00`
   is called from call #8. Disassemble the PRX code around call #8 to see
   what arguments are passed and what metadata structures are accessed.

3. **Search for `il2cpp::vm::MetadataRegistration`** patterns — The PRX
   likely has a global pointer to the metadata registration struct. Search
   for loads from BSS that are passed to functions.

4. **Check if the walker is in the PRX** — The PRX's `real_init` may
   contain the walker call. Disassemble `real_init` more thoroughly,
   looking for loops that call a function with string arguments.

### If real metadata table found

Implement manual fill:
1. Walk the real metadata table's `typeNames[]` array
2. For each name, call the wrapper `0x800805AE0` with the name string
3. The wrapper inserts the name→metadata mapping into the hash table
4. Lookups will then return non-NULL, and il2cpp_init can progress

### Target: BOOT_STAGE_5

Once the hash table is populated:
- Lookups return non-zero
- Init function's metadata globals are set
- il2cpp_init completes successfully
- Unity runtime starts
