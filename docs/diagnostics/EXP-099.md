## Hypothesis

From EXP-098: The registration helper `0x804F889D0` calls `0x804FC33B0` (once-init primitive) and checks the return value:
```asm
0x804F88A00: call 0x804FC33B0
0x804F88A05: mov  ebx, 0x1f
0x804F88A0A: test eax, eax
0x804F88A0C: jne  error_path    ; if eax != 0, skip registration
```

**Hypothesis:** `0x804FC33B0` returns failure (non-zero), causing the registration to be skipped, which prevents the work-submission callback from being stored, which causes the ThreadPool deadlock.

## Test Method

Built `_Exp099OnceInitTracer.cs` with two-stage INT3:
- Stage 1: INT3 at `0x804F88A00` (before call) — capture `rdi` (once_init struct pointer)
- Stage 2: INT3 at `0x804F88A05` (after call returns) — capture `eax` (return value)

Also patched the working path (`0x804FBF799`, call to `0x804FC3750`) for comparison.

## Conclusion

**Hypothesis REJECTED.** The once-init primitive `0x804FC33B0` succeeds (`eax=0`). The registration is NOT skipped. The callback IS registered.

**The registration path works correctly.** The issue is downstream — the registered callback is either never invoked, or an unresolved HLE import (`nid=J3edELK4FvM` at `ret=0x804FC1635`) prevents the IL2CPP runtime from reaching the work-submission stage.

## What Was Rejected

1. "Once-init primitive returns failure" — REJECTED (eax=0, success)
2. "Registration is skipped" — REJECTED (success path taken)

## What SharpEmu Is Missing

The registration succeeds but the deadlock persists. The new lead is:
- **`Import#84004 unresolved: nid=J3edELK4FvM`** — this unresolved import fires right after the registration, from `ret=0x804FC1635`. This is likely a PLT stub that resolves to an HLE function SharpEmu doesn't implement.
- The unresolved import may cause the IL2CPP runtime to skip a critical initialization step (e.g., setting up a timer, registering a GC callback, or configuring the ThreadPool work queue).
