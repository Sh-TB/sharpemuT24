# EXP-089 — Missing Work Submission: Main Thread Enters ThreadPool Without Queuing Work

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** `SHARPEMU_SEMA_FAST_PATH=0`, metadata at `Media/Metadata/`, EXP-085 flag patch active
**Path:** B (real metadata path)

**Question:** What prevents IL2CPP from submitting work to the ThreadPool after `sceKernelAllocateDirectMemory`?

**Answer:** The main thread creates the GC system and thread pool, then **immediately enters the thread pool as a worker** without submitting any work. The IL2CPP runtime's initialization doesn't reach the work submission stage. Classification: **D) Unity/IL2CPP waiting for an event that SharpEmu never generates.**

**Confidence:** PROVEN by log timeline analysis (all HLE calls and semaphore operations have line numbers).

## Classification: D — Unity/IL2CPP Waiting for an Event SharpEmu Never Generates

The main thread:
1. Creates GC system (SuspendSemaphore + ResumeSemaphore)
2. Creates thread pool semaphores (0x85-0x90)
3. Creates GC thread
4. **Immediately enters thread pool as worker** → WaitSema(0x81) → blocks

No work is submitted between steps 3 and 4. On real PS5, the IL2CPP runtime would:
- Register types with the GC
- Queue background initialization tasks to the ThreadPool
- Then the main thread joins the pool to help process tasks

The missing work submission is likely because:
- The GC is not fully operational (GC thread blocks on SuspendSemaphore immediately)
- The IL2CPP runtime may be waiting for a GC acknowledgment before submitting work
- Or a timer/callback/event that triggers work submission is not implemented in SharpEmu

## EXP-058 Tracer Bug Correction

The EXP-058 array_proc tracer reported `count=2454267240`. This was a **tracer bug**: the tracer divides `rsi` by `entry_size (0x38)`, but `rsi` is a pointer (`0x2000002EC0`), not `count * entry_size`. The actual count is `rcx=0x379=889`, which is a reasonable number of IL2CPP type definitions to process.

This correction means EXP-079's "corrupted count" finding was based on a tracer misinterpretation, not actual data corruption. The count was always 889 — the tracer just reported it wrong.

## Fix Direction

The fix requires understanding what event should trigger work submission to the ThreadPool. Candidates:

1. **GC trigger**: The GC thread waits on SuspendSemaphore. On real PS5, the GC is triggered by:
   - Memory allocation pressure (when the managed heap is full)
   - Explicit `GC.Collect()` calls
   - A periodic timer
   
   SharpEmu may not implement the GC trigger mechanism.

2. **IL2CPP runtime callback**: The IL2CPP runtime may register a callback with the OS that fires after system initialization. SharpEmu may not generate this callback.

3. **Timer/event**: A PS5 system timer or event that triggers the IL2CPP runtime to start background work. SharpEmu may not implement this timer.
