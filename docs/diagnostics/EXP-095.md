# EXP-095 — _ThreadPoolWaitCallback Lookup SUCCEEDS (rax=0x6007E64D0) — Deadlock Persists on WaitSema(0xA6)

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** `SHARPEMU_SEMA_FAST_PATH=0`, metadata at `Media/Metadata/`, EXP-085 flag patch active, DT_INIT_ARRAY fix (EXP-092) applied, EXP-095 tracer active
**Path:** B (real metadata path)

**Question:** What are the exact args and return value of the `_ThreadPoolWaitCallback` lookup at runtime, and what does the method table at `[context+0x30]` contain?

**Answer:** The lookup **SUCCEEDED**. `il2cpp_class_get_method_from_name` returned `rax = 0x6007E64D0` (non-NULL guest heap pointer to a valid `MethodInfo` structure). The method table at `[context+0x30]` IS populated and DOES contain `_ThreadPoolWaitCallback`. However, the deadlock **still occurs** — the main thread blocks on `WaitSema(0xA6)` at `0x804F6E9EB` (ThreadPool dispatch), identical to EXP-092. The callback EXISTS but is never INVOKED because no work is submitted to the ThreadPool.

**Confidence:** PROVEN by runtime tracing (two-stage INT3 at call site `0x804F055D6` and return site `0x804F055DB`).

## Key Findings

### 1. The Lookup SUCCEEDED

`rax = 0x6007E64D0` — a non-NULL guest heap pointer. The `MethodInfo` structure at that address contains valid data:
- `+0x00` points back to the `Il2CppClass*` (`0x60070B3A0` — matches `rdi` arg)
- `+0x10`, `+0x18`, `+0x20` are guest heap pointers (likely method name, signature, invoker)
- `+0x28` is a small value (likely method token/flags)

This is a **valid, populated MethodInfo structure**. The lookup found `_ThreadPoolWaitCallback`.

### 2. The Method Table IS Populated

`[context+0x30] = 0x55A9CC8C6090` (non-NULL host pointer). The first 8 entries at that address don't look like simple method pointers (they look like a header/structure, not an array), but the lookup function successfully navigated the structure and found the method. The table IS populated and searchable.

### 3. The Deadlock Persists

After the lookup succeeds, the main thread continues execution, eventually enters the ThreadPool dispatch function (`0x804F6E510`), and blocks on `WaitSema(0xA6)` at `0x804F6E9EB`. This is the **exact same deadlock** as EXP-092:
- Stall handle: `0xA6` (same as EXP-092)
- Stall caller: `0x804F6E9EB` (same ThreadPool dispatch function)
- All 15 threads blocked (main + 13 workers + GC thread)

### 4. Tracer Bug: method_name String Read Failed

The `method_name` was read as `"??p"` instead of `"_ThreadPoolWaitCallback"`. This is because `rdx = 0x6014F9870` is a **guest heap address** (the `0x60...` range), and the tracer's `Exp095ReadCString` function tried to dereference it as a host pointer. SharpEmu's guest heap addresses are NOT identity-mapped to host addresses — only PRX/EBOOT data segment addresses are directly dereferenceable.

The `namespace` string read correctly (`"System.Threading"`) because `rsi = 0x80826CCD3` is in the PRX data segment (identity-mapped). The `method_name` was dynamically allocated on the guest heap by the PRX before the call.

**This tracer bug does NOT affect the key finding** — the return value `rax = 0x6007E64D0` proves the lookup succeeded regardless of whether we could read the method name string.

## Corrections to Prior EXPs

### EXP-090 — "_ThreadPoolWaitCallback Lookup Returns NULL"

**CORRECTED BY EXP-095:** The lookup does NOT return NULL. It returns `0x6007E64D0` (non-NULL). EXP-090's claim was based on the assumption that the hash table at `0x801EF7610` being empty would cause all lookups to fail. EXP-094 proved the lookup doesn't use `0x801EF7610` at all, and EXP-095 now proves the lookup actually SUCCEEDS.

**Root cause of EXP-090's error:** EXP-090 assumed `_ThreadPoolWaitCallback` was missing because:
1. The hash table at `0x801EF7610` was empty (EXP-040)
2. EXP-085's flag patch made `metadata_lookup` return 0 for all queries
3. The ThreadPool had no callback → deadlock

But EXP-094 showed the lookup uses `[0x808923D88]` (not `0x801EF7610`), and EXP-095 shows the lookup returns a valid result. The EXP-085 flag patch does NOT affect the `[0x808923D88]` lookup path.

### EXP-094 — "Method Table Doesn't Contain _ThreadPoolWaitCallback"

**CORRECTED BY EXP-095:** The method table at `[context+0x30]` DOES contain `_ThreadPoolWaitCallback`. The lookup succeeds. EXP-094's hypothesis that "the method table is either incomplete or contains wrong data" was wrong — the table is complete and searchable.

### EXP-088/089 — "No Work Submitted to ThreadPool"

**RE-CONFIRMED BY EXP-095:** The original EXP-088/089 classification was correct — the deadlock is caused by no work being submitted to the ThreadPool. The callback EXISTS (`rax = 0x6007E64D0`) but is never INVOKED because no work items are queued. The main thread enters the pool as a worker and waits for work that never arrives.

EXP-090/091/092/093/094 incorrectly redirected the investigation toward the metadata/hash table. EXP-095 corrects this: the metadata lookup is NOT the problem. The problem is that the IL2CPP runtime doesn't submit work to the ThreadPool after the lookup succeeds.

The main thread creates the GC thread, then enters the ThreadPool and blocks. **No work is submitted between the lookup and the deadlock.**

## Tracer Bug (Minor)

The `Exp095ReadCString` function fails to read guest heap addresses (the `0x60...` range) because they are not identity-mapped to host addresses. Only PRX/EBOOT data segment addresses are directly dereferenceable. To read guest heap strings in future tracers, use `CpuContext.TryReadUInt8()` or the virtual memory interface instead of direct pointer dereference.

This bug does NOT affect the key finding (the return value `rax` was read correctly from the register, not from memory).
