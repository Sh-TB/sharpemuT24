# EXP-110 — Dispatch Is Through [struct+0x08] Not [struct+0x10] — 31 Indirect Call Sites Found

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** Static analysis (byte-pattern search for indirect call instructions)
**Path:** B (real metadata path)

## EXP-110 RESULT

### Hypothesis tested:
The callback dispatch mechanism uses `call [reg+0x10]` (based on EXP-102/103 finding that `[struct+0x10] = 0x804FA1FE0`).

### Finding:
**Hypothesis was WRONG about the offset.** The actual dispatch in `0x804FA1FE0` is:
```asm
0x804FA2002: mov r12, [rbx + 8]    ; load function pointer from +0x08 (NOT +0x10!)
0x804FA2073: call r12               ; call through the loaded pointer
```

The struct layout is:
- `[+0x00]` = callback data (stored by xchg [r14], rax)
- `[+0x08]` = **actual function pointer that gets called** (loaded into r12)
- `[+0x10]` = 0x804FA1FE0 (the callback function address — metadata/registration, not the call target)

### Pattern search results:

**call [reg+0x10]:** 31 sites found (but wrong offset for this dispatch)
**call [reg+0x08]:** 31 sites found (correct offset for this dispatch)

The 31 `call [reg+0x08]` sites are spread across the PRX. None were checked for runtime reachability yet (logs from previous container restart were lost).

### Corrected search direction:
The next step should check whether any of the 31 `call [reg+0x08]` sites are reached at runtime, and whether the value at `[reg+0x08]` matches `0x804FA1FE0` or another registered callback.

### Rejected:
- "Dispatch is through [struct+0x10]" — REJECTED. The actual dispatch is through `[struct+0x08]`.
- EXP-102/103's assumption that `[+0x10]` is the call target — it's metadata, not the dispatch offset.
