## Expected Outcome

Based on EXP-026 evidence, we expect one of the following divergence points:

### Hypothesis 1: SF flag corruption between `test` and `cmovns` (MOST LIKELY)

The critical sequence is:
```
0x804ED9BCC: test eax, eax          ; sets SF based on strcmp result
0x804ED9BCE: lea rcx, [rbx+0x10]    ; does NOT modify flags (Intel SDM)
0x804ED9BD2: cmovns rcx, rbx        ; reads SF
0x804ED9BD6: cmovns r12, rbx        ; reads SF again (must be SAME value)
```

If SharpEmu's `lea` implementation incorrectly modifies SF, the second
`cmovns` would read a wrong SF value, causing the candidate (r12) to be
updated incorrectly. This would result in the resolver always returning 0
(no candidate found) — which matches the observed behavior.

**Detection:** The `test3_sf_preservation.log` file will show SF at each
of these 4 instructions. If SF changes between `test` and the second
`cmovns`, this hypothesis is confirmed.

### Hypothesis 2: strcmp returns wrong value

If SharpEmu's native strcmp returns 0 for all inputs (instead of the
correct negative/zero/positive value), the resolver would always go RIGHT
and never find an exact match.

**Detection:** The `test3_strcmp.log` file will show strcmp's input
strings and the resulting RAX. If RAX is always 0 regardless of input,
this hypothesis is confirmed.

### Hypothesis 3: cmovns always takes (or never takes)

If SharpEmu's `cmovns` always behaves as if SF=0 (always takes) or SF=1
(never takes), the resolver would walk the tree in only one direction
and never find symbols.

**Detection:** The `test1_rflags.log` and `test2_registers.log` will
show whether RBX and RCX change in the expected direction based on SF.

### Hypothesis 4: Memory read returns wrong value

If SharpEmu's memory read of `[rbx+0x20]` (symbol name pointer) or
`[rbx+0x19]` (matched flag) returns wrong values, the resolver would
read garbage data.

**Detection:** The `test3_strcmp.log` will show what strings are passed
to strcmp. If they're garbage or empty, this hypothesis is confirmed.

### Hypothesis 5: Return value corruption (T13)

If the resolver correctly computes RAX=0x804ed8770 inside the guest call,
but the value is lost when returning to the host, the wrapper would see
RAX=0.

**Detection:** The T12/T13 boundary trace logs will show `returnValue`
(the value returned by `TryCallGuestFunction`) vs `cpuContext[Rax]`
(the value in the context after the call). If they differ, this is the bug.
