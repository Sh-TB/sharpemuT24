# EXP-096 — Work Submission Function NEVER Reached — Entire Call Chain Is Dead Code

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** `SHARPEMU_SEMA_FAST_PATH=0`, metadata at `Media/Metadata/`, EXP-085 flag patch active, DT_INIT_ARRAY fix (EXP-092) applied, EXP-095 + EXP-096 tracers active
**Path:** B (real metadata path)

**Question:** What code path should submit work to the ThreadPool after the `_ThreadPoolWaitCallback` lookup, and why doesn't it execute?

**Answer:** **Case A confirmed.** The work-submission function (`0x804F6EC20`, which calls `SignalSema(0xA6)`) is **NEVER reached** at runtime. None of its 3 call sites (`0x804F4571A`, `0x804F9FAAA`, `0x804FA14C8`) are executed. Static analysis proves the entire call chain is dead code — the functions containing these call sites have zero direct callers in the PRX. The work-submission path is only reachable via indirect function pointers that are never set up.

**Confidence:** PROVEN by runtime tracing (INT3 at all 3 call sites, zero hits) + static call-chain analysis.

## Investigation Methodology

Following the EXP-095 methodology (hypothesis → direct runtime test → evidence → static confirmation → accept/reject):

### Hypothesis

The IL2CPP ThreadPool has a work-submission function that calls `SignalSema(0xA6)` to wake workers. This function should be called during IL2CPP initialization to queue background work. The deadlock occurs because this function is never called (Case A), OR it's called but skips submission (Case B), OR it submits but SignalSema fails (Case C).

### Step 1: Static Analysis — Find the Work-Submission Function

From EXP-088: `SignalSema` is called at `0x804F6ECF9` inside function `0x804F6EC20`. Disassembly of `0x804F6EC20` confirms it:
1. Iterates worker entries (loop at `0x804F6EC50..0x804F6EC66`)
2. For each matching worker, performs atomic CAS on `[entry+0x90]` (`0x804F6ECD3: lock cmpxchg`)
3. If CAS succeeds and `esi < 0` (worker needs wake), calls `0x804FC1CE0` (SignalSema) at `0x804F6ECF9`

The `SignalSema` call takes `rdi = [entry+0x88]` (the semaphore handle for that worker).

### Step 2: Find All Callers of 0x804F6EC20

Scanned the entire PRX and EBOOT for `E8 rel32` (call) instructions targeting `0x804F6EC20`:

| Caller Address | Image | Function Containing It |
|----------------|-------|----------------------|
| `0x804F4571A` | PRX | `0x804F456E0` |
| `0x804F9FAAA` | PRX | `0x804F9FA80` |
| `0x804FA14C8` | PRX | `0x804FA1440` |

**3 callers in PRX, 0 in EBOOT.**

### Step 3: Runtime Tracer — INT3 at All 3 Call Sites

Built `_Exp096WorkSubmissionTracer.cs` — patches all 3 call sites with INT3. On each hit, logs:
- Which call site was reached
- Caller RIP, registers (rdi, rsi, rdx, rbx)
- Thread pool context fields ([ctx+0x10], [ctx+0x50], [ctx+0x58], [ctx+0x68], [ctx+0x6c])

### Step 4: Run Emulator

Ran with 120s timeout. Results:
- EXP-095 lookup still succeeded (`rax = 0x6007E64D0` — non-NULL)
- All 3 EXP-096 patches installed successfully
- **ZERO EXP096-WORKSUBMIT-ENTER hits** — none of the 3 call sites were reached
- Same stall: `WaitSema(0xA6)` at `0x804F6E9EB`
- Exit code: 4 (stall)

### Step 5: Static Confirmation — Call Chain Analysis

Found all callers of the 3 containing functions:

| Function | Callers in PRX | Callers in EBOOT |
|----------|---------------|-----------------|
| `0x804F456E0` (contains site #1) | **0** | 0 |
| `0x804F9FA80` (contains site #2) | **1** (at `0x804FA2089`) | 0 |
| `0x804FA1440` (contains site #3) | **0** | 0 |

The single caller `0x804FA2089` is inside function `0x804FA1FE0`. Callers of `0x804FA1FE0`:

| Function | Callers in PRX | Callers in EBOOT |
|----------|---------------|-----------------|
| `0x804FA1FE0` (contains the caller of site #2's function) | **0** | 0 |

**The ENTIRE work-submission call chain is dead code:**

```
Work submission: 0x804F6EC20 (SignalSema(0xA6) caller)
  ← called by 3 sites:
      0x804F4571A in 0x804F456E0  ← 0 callers (DEAD CODE)
      0x804F9FAAA in 0x804F9FA80  ← 1 caller at 0x804FA2089
      0x804FA14C8 in 0x804FA1440  ← 0 callers (DEAD CODE)

  0x804FA2089 is in 0x804FA1FE0  ← 0 callers (DEAD CODE)
```

### Classification: Case A — CONFIRMED

The work-submission function is **NEVER reached**. None of its 3 call sites are executed. The functions containing these call sites have zero direct callers — they are only reachable via indirect function pointers (e.g., C++ virtual methods, .NET delegates, IL2CPP runtime callbacks) that are never set up during SharpEmu's initialization.

## Why the Work-Submission Path Is Dead Code

The functions `0x804F456E0`, `0x804F9FA80`, `0x804FA1440`, and `0x804FA1FE0` have zero direct `call` instructions targeting them. This means they are only callable via:
1. **C++ virtual method tables (vtables)** — the function pointer is stored in a vtable and called indirectly
2. **.NET delegate invocation** — the IL2CPP runtime stores the function pointer in a delegate and calls it via `Invoke()`
3. **IL2CPP runtime callbacks** — the runtime registers these functions as callbacks (e.g., GC callbacks, timer callbacks, type initialization callbacks)
4. **Function pointer globals** — stored at a global address and called via `call [global]`

On a real PS5, one of these indirect registration mechanisms would set up the call chain during IL2CPP initialization. SharpEmu likely doesn't implement the HLE function that performs this registration, so the function pointers are never set, and the work-submission path remains dead code.
