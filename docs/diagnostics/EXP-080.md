## Exact Value Flow

Since `0x92490068` was never observed, there is no value flow to trace. The question "which HLE function produced the bad count" is moot.

However, the A/B test DID reveal a **different corrupted value**:

```
EXP040-STATE      (line 148,021):  hash_table = 0x600103DB0    ← valid heap pointer
EXP041-CALL7-STATE(line 155,960):  hash_table = 0x600103DB0    ← still valid
EXP038-CRASH_FUNC (line 280,197):  hash_table = 0x600103DB0    ← still valid
EXP039-HASH_LOOKUP(line 414,623):  hash_table = 0x00FFF00000006090  ← CORRUPTED
```

The IL2CPP hash table pointer (stored at EBOOT global `0x801EF7610` per EXP058-INIT-STATE) is valid (`0x600103DB0`) during `real_init`/`call#7`/`crash_func`, but becomes corrupted (`0x00FFF00000006090`) by the time `hash_lookup` is called ~134K log lines later.

**Address → register → value → source:**

```
0x8009739B7: call 0x8004BD620        ; hash_lookup(hash_input=0, hash_table=0x00FFF00000006090)
0x8009739BC: mov rdi, [rbx]          ; rbx = IL2CPP type descriptor
  → rdi = *rbx
  → hash_table loaded from a corrupted global/memory location
  → 0x00FFF00000006090 is NOT a valid heap pointer
  → upper bits 0x00FFF look like uninitialized or partially-overwritten memory
```

This corruption pattern is consistent with a SharpEmu HLE bug that writes to the wrong memory offset during IL2CPP metadata registration, partially overwriting the hash_table global.

## Root Cause

**Only if proven.**

### Run A (clean, no NOP) — PROVEN root cause:

Workers crash on NULL `[rbx+0xF8]` calls because the task dispatcher (`0x800AC6080`) is never reached. The dispatcher is never reached because the main thread is stuck in `worker_create` — it creates 13 workers, but each worker immediately enters the dispatch loop, finds `[rbx+0x108] != 0` (byte flag set to 1 at creation), decrements `[rbx+0x70]` to -1, waits on `[rbx+0x68]` (handle 0x5C) which returns immediately (FAST_PATH), then calls `[rbx+0xF8]` which is NULL → SIGSEGV → recovered → loop. After 1,005 such faults, host-side stack corruption causes fatal abort.

**Root cause (Run A):** Workers call NULL function pointers because the dispatcher never assigns task functions. The dispatcher never runs because the main thread never finishes initialization (it crashes first).

### Run B (with NOP) — PROVEN root cause:

The NOP prevents workers from crashing (they signal the wrong sema instead of calling NULL). The main thread progresses to `il2cpp_init` → `real_init` → `call#7` → `hash_lookup`, but at `hash_lookup` the hash_table pointer is corrupted (`0x00FFF00000006090` instead of `0x600103DB0`). The main thread spins in the hash lookup with an invalid table pointer and never progresses to `array_proc` or the dispatcher.

**Root cause (Run B):** The IL2CPP hash table global pointer gets corrupted between `crash_func` (line 280,197) and `hash_lookup` (line 414,623). The corruption is likely caused by a SharpEmu HLE function that writes to the wrong memory offset during IL2CPP metadata registration, partially overwriting the hash_table global at `0x801EF7610`.

### Unified root cause:

**SharpEmu's IL2CPP HLE layer does not correctly maintain the IL2CPP metadata globals.** The hash_table pointer at `0x801EF7610` is either not properly initialized, or gets corrupted by a subsequent HLE call that writes to the wrong offset. This prevents the main thread from completing IL2CPP initialization, which prevents the task dispatcher from running, which prevents workers from receiving task functions, which causes the entire worker pool to stall or crash.

## Permanent Fix Location

**Only if proven.**

The fix must target the **IL2CPP metadata registration HLE layer** in `SharpEmu.HLE/` — specifically the code that maintains the hash_table global at EBOOT `0x801EF7610`.

Two issues need investigation (EXP-081):

1. **hash_table corruption (Run B):** Between `crash_func` (line 280,197) and `hash_lookup` (line 414,623), the hash_table pointer at `0x801EF7610` changes from `0x600103DB0` to `0x00FFF00000006090`. A SharpEmu HLE function is writing to the wrong offset, partially overwriting this global. The most likely culprit is an IL2CPP metadata registration function (`il2cpp_codegen_register`, `il2cpp_metadata_register`, or similar) that computes a wrong store address.

2. **Worker NULL crash (Run A):** Workers call `[rbx+0xF8]` which is NULL because the dispatcher (`0x800AC6080`) never writes a task function. This is downstream of issue #1 — if the IL2CPP metadata were correct, the main thread would complete initialization and call the dispatcher, which would set `[rbx+0xF8]`.

**The fix is NOT:**
- ❌ Re-adding the NOP bypass (masks the symptom, doesn't fix the metadata corruption)
- ❌ Implementing `sceVideoOut`/`sceAgc` (GPU is downstream)
- ❌ Fixing `SHARPEMU_SEMA_FAST_PATH` (semaphore subsystem is correctly implementing what the game asks)
- ❌ Implementing CLEAR as a per-task callback (CLEAR is correctly a destructor)

### Corrected Root Cause (from clean run only)

The real blocker, observable in the clean run without any NOP contamination:

1. `worker_create` (`0x800A9F9A0`) creates 13 worker descriptors, each with `[worker+0xF8] = 0` (NULL task function) and `[worker+0x108] = 0x01` (byte flag: work pending).
2. Each worker enters the dispatch loop (`0x800AA0170`).
3. The dispatch loop checks `[worker+0x108] != 0` → true (it's `0x01`).
4. The dispatch loop decrements `[worker+0x70]` (work count) from 0 to -1.
5. Since old value was ≤ 0, the worker calls `sceKernelWaitSema([worker+0x68], 1)` — the wait sema (handle `0x5C` for worker 0). With `FAST_PATH=1`, this returns immediately.
6. The dispatch loop re-checks `[worker+0x108] != 0` → still true.
7. The dispatch loop calls `[worker+0xF8]` which is NULL → SIGSEGV.
8. SharpEmu recovers from the NULL execute fault, loops back to step 3.
9. After 1,005 such faults, host-side stack corruption causes fatal SIGSEGV.

The task dispatcher (`0x800AC6080`) is the only code that writes `[worker+0xF8]` (task function pointer). It is never reached because the main thread crashes before completing initialization.

### Answer to the Key Question

> Did EXP-080 reveal the real root cause, or did the NOP create an artificial execution path?

**The NOP created an artificial execution path.** EXP-080 did NOT reveal the real root cause — its "hash_table corruption" finding was a false alarm caused by (a) comparing two different memory addresses and (b) observing the value only in the NOP-contaminated run.

The real root cause (from the clean run) is: **workers call NULL `[worker+0xF8]` because the task dispatcher never assigns task functions, and the dispatcher never runs because the main thread crashes first.**

This is a chicken-and-egg problem:
- Workers need the dispatcher to set `[worker+0xF8]`.
- The dispatcher needs the main thread to finish initialization and call `il2cpp_init`.
- The main thread crashes (via worker NULL execute storm) before reaching `il2cpp_init`.

The fix must break this cycle — either by preventing workers from calling NULL `[worker+0xF8]` (so the main thread can progress), or by running the dispatcher earlier (before `il2cpp_init`).
