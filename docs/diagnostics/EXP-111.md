**Question:** Are the UD2 instructions at `0x801832489` and `0x8007F9093` function-entry stubs that fail because patching skips the prologue? Would an ABI-safe trampoline allow execution to continue?

**Answer:** **Hypothesis REJECTED.** Both UD2 instructions are **noreturn markers AFTER calls**, NOT at function entry. The function at `0x801832480` (containing the primary UD2) has a proper prologue (`push rbp; mov rbp, rsp`) that executes BEFORE the call — the prologue is NOT skipped. The UD2 is the compiler's safety net after a call to a noreturn imported function. A trampoline is irrelevant because there is nothing to "continue" to after the UD2 — it's followed by INT3 padding and the next function. Additionally, the function was **never reached** during any emulator run (EXP-092 through EXP-097), and `libSceApt` does not exist anywhere in the codebase.

**Confidence:** PROVEN by static disassembly + call-chain analysis + log search.

## Static Analysis

### Primary UD2: 0x801832489

**Function at 0x801832480 (contains the UD2):**
```asm
0x801832480  push     rbp           ; ← FUNCTION ENTRY (prologue)
0x801832481  mov      rbp, rsp      ; ← prologue continued
0x801832484  call     0x801936B50   ; ← call PLT stub (imported function)
0x801832489  ud2                    ; ← NORETURN MARKER (not function entry!)
0x80183248B  int3                   ; padding
0x80183248C  int3                   ; padding
...
0x801832490  push     rbp           ; ← NEXT function starts here
```

**Key observations:**
1. The UD2 is at offset +9 from function entry, NOT at function entry itself
2. The prologue (`push rbp; mov rbp, rsp`) executes BEFORE the call — it is NOT skipped
3. The `call 0x801936B50` targets a PLT stub: `jmp [rip+0x3e3cca]` → GOT slot at `0x801D1A820`
4. The GOT slot's initial value is `0x1936B56` (lazy binding fallback: `push 0x4f; jmp resolver`)
5. The PLT index is `0x4f` (79) — this is the 79th import in the EBOOT's relocation table
6. After the UD2, there's INT3 padding, then the next function starts at `0x801832490`

**This is a noreturn wrapper pattern:** The function sets up a stack frame, calls an imported function that is supposed to never return (like `abort()`, `exit()`, or a panic handler), and has UD2 as a safety net in case the noreturn function unexpectedly returns.

## What the UD2 Actually Represents

The function at `0x801832480` is a **noreturn wrapper** for an imported function:

```
noreturn_wrapper():
    push rbp              ; set up stack frame
    mov rbp, rsp
    call imported_func    ; call noreturn imported function via PLT
    ud2                   ; safety net — crash if imported_func returns
```

This is a standard compiler pattern for calling `__builtin_unreachable()`, `abort()`, `exit()`, or similar noreturn functions. The UD2 is NOT a bug or a stub — it's intentional compiler-generated code.

The 67 callers of this wrapper are code paths that are supposed to be unreachable (error handlers, assertion failures, panic paths). The fact that none were reached during emulator runs is **correct behavior** — the game didn't trigger any fatal error paths.
