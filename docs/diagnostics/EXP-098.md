**Question:** Why is the IL2CPP ThreadPool initialization path never started? What is the missing caller/initializer?

**Answer:** **EXP-097 CORRECTED.** The registration function `0x804FA20E0` (which registers callback `0x804FA1FE0` via helper `0x804F889D0`) IS REACHED at runtime — it is NOT dead code. Runtime INT3 tracing confirms it fires at line 8492, called from `0x804F527F9` (inside function `0x804F527C0`, called from real_init at `0x804F0590B`). The deadlock persists because the registration helper `0x804F889D0` likely fails — it calls `0x804FC33B0` (a once-init primitive) which may return failure, preventing the callback from being registered.

**Confidence:** PROVEN by runtime tracing (INT3 at `0x804FA20E0` fired with caller `0x804F527F9`).

### How the 7 Working Globals Are Populated (Template Mechanism)

Following the reviewer's advice, I traced how the 7 WORKING function pointer globals get populated:

1. **`0x804F51020`** (once-init, called from real_init at `0x804F04C70`) registers 7 callbacks:
   - Loads function pointers via `lea rdi, [rip+...]`
   - Calls registration helpers: `0x804FBF780`, `0x804FBFC20`, `0x804FB6790`, `0x804FBF9D0`, `0x804FBFA70`, `0x804FC01B0`
   - Each helper stores the function pointer to a different global
   - Example: `0x804FBF780` does `mov [0x808B41900], rbx` (stores `rdi` = function pointer)

2. **`0x804FA20E0`** (called from real_init at `0x804F0590B` via `0x804F527C0`) registers callback `0x804FA1FE0`:
   - Allocates a 0x18-byte struct with (arg1, arg2, arg3)
   - Loads callback function `0x804FA1FE0` via `lea rsi, [rip+...]`
   - Loads once-init guard `[0x808B418D8]` into `rcx`
   - Tail-jumps to `0x804F889D0` (a DIFFERENT registration helper)

### EXP-097 Correction

**EXP-097 claimed:** "Dead-code functions not registered anywhere — self-registering function 0x804FA1FE0 never called"

**CORRECTED BY EXP-098:**
1. `0x804FA1FE0` is NOT self-registering — it's registered BY `0x804FA20E0` (a different function)
2. `0x804FA20E0` IS reached at runtime (caller `0x804F527F9` in `0x804F527C0`, called from real_init)
3. The registration path IS executed — the issue is not "never reached" but "may fail at `0x804F889D0`"

**Golden Rule 8 violation in EXP-097:** I assumed `0x804FA1FE0` was self-registering because the LEA at `0x804FA210F` loads `0x804FA1FE0`. But the LEA is inside function `0x804FA20E0` (a DIFFERENT function), not inside `0x804FA1FE0`. The function boundary was not verified — exactly the mistake Golden Rule 8 warns against.

## What SharpEmu Is Missing

The registration function `0x804FA20E0` IS reached and tail-jumps to `0x804F889D0`. The registration helper `0x804F889D0` calls `0x804FC33B0` (a once-init primitive) and checks its return value. If `0x804FC33B0` returns failure (non-zero), the registration is skipped and the callback is never stored.

**The likely missing piece:** `0x804FC33B0` is probably a `pthread_once`-like function or a C++ `std::call_once` implementation. If SharpEmu doesn't properly implement this primitive (or the HLE function it depends on), it returns failure, and the work-submission callback is never registered.
