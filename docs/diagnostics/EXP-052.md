# EXP-052 — Real IL2CPP/PS5 Metadata Initialization Investigation

## Date: 2026-07-31
## Status: ANALYSIS COMPLETE — Missing mechanism identified; runtime tracer pending

---

## Executive Summary

Stepped back from per-crash patching to find the actual missing initialization
mechanism that populates IL2CPP metadata before `il2cpp_init`. After exhaustive
static analysis of eboot.bin and Il2cppUserAssemblies.prx:

- The hash table at `[0x801EF7610]` is the **IL2CPP name→metadata lookup table**,
  read by `0x8004bd620` (called from 286 sites, including the init function at
  `0x8013EEFE7`).
- The table is **allocated** by writer `0x8007F90A0` (called indirectly via
  lazy-init pattern; no direct callers).
- The table is **filled** by wrapper `0x800805AE0` → insert `0x800806940`
  (wrapper has 0 direct callers — called via function pointer).
- The wrapper handles input strings, including those with `"#dllimport:"` prefix
  (P/Invoke), but also handles generic metadata strings.
- The static metadata table at `0x1CC0080` has **13,920 R_X86_64_RELATIVE
  relocations** initializing pairs of function pointers and string pointers
  (likely `Il2CppMetadataRegistration` entries).
- **No R_X86_64_RELATIVE relocations have addends matching our function
  addresses** (`0x7F90A0`, `0x805AE0`, etc.), confirming the wrapper is called
  via a runtime-computed function pointer or vtable dispatch.

**Conclusion**: The missing mechanism is a function that walks the static
metadata table at `0x1CC0080` and calls the wrapper `0x800805AE0` with each
entry's name string. This function exists in the binary (the table IS populated
on real PS5) but is called indirectly and cannot be found via static analysis
alone.

**Recommended next step**: Implement a runtime tracer that hooks the writer
`0x8007F90A0` and wrapper `0x800805AE0` to log all calls + dump the static
table's raw layout. This will reveal the exact call sites and table structure
needed for the manual fill implementation.

## Task A1: Static search for hash-table writers

### Findings

#### Hash table layout (corrected from EXP-039)

The hash table pointer at `[0x801EF7610]` points to a **0x118-byte struct**,
NOT directly to the entries array. The struct has:

```
+0x00: entries array pointer    (allocated separately)
+0x08: mask (e.g., 0x7FFF8)     (size - 1, used as hash mask)
+0x10: count + flags            (e.g., 0x380000AAAA)
+0x14: flags
+0x20..0x118: lock, name, etc.
```

Each entry in the entries array is **0x38 bytes**:

```
+0x00: hash (uint32, 0xFFFFFFFF if empty)
+0x04: padding (uint32)
+0x08: inline key (16 bytes max)
+0x18: key pointer (if length > 16)
+0x20: length byte (0x18 - length for inline keys)
+0x28: type byte (1 = inline, 0 = pointer)
+0x30: value pointer
+0x34: value2
```

#### Writer function (0x8007F90A0)

- Allocates 0x38-byte config struct, stores at `[0x801E51618]`
- Allocates 0x118-byte hash table struct, saves in `rbx`
- Initializes struct with name, sentinels, etc.
- Calls `0x8007F9690` (entries_init) which:
  - Allocates entries array (size based on config)
  - Fills entries with `0xFFFFFFFF` sentinel
  - Sets struct[0] = entries_ptr, struct[8] = mask, struct[0x10] = count
- Stores hash table struct at `[0x801EF7610]`
- Has 0 direct callers — called via lazy-init pattern

The writer uses `lock cmpxchg` on `[0x801E51658]` (lock) and `[0x801E516F0]`
(once-init flag), confirming the lazy-init pattern.

#### Insert function (0x800806940)

- Takes `rdi` = key, `rsi` = hash table struct, `rdx` = entry to insert, `rcx` = ?
- Hashes the key via `0x801704D40` (string hash)
- Computes bucket index = hash & mask
- Probes linearly: bucket += 1 on collision
- For each bucket: compares hash, then key
- If match: updates the entry's value
- If empty (sentinel 0xFFFFFFFF): inserts new entry
- If table full: calls `0x800806600` (resize) to grow
- Has 1 direct caller at `0x80080602D` (inside wrapper `0x800805AE0`)

#### Wrapper function (0x800805AE0)

- Takes `rdi` = input string pointer
- Calls `0x801936700` (strlen-like)
- Checks if string starts with `"#dllimport:"` (literal byte-by-byte comparison)
- If `"#dllimport:"`: does P/Invoke-specific handling
- Otherwise: generic metadata registration
- Hashes the string and calls insert `0x800806940`
- Has **0 direct callers** — called via function pointer

The wrapper's existence confirms the hash table at `0x801EF7610` is shared
between P/Invoke and metadata lookups. Both are populated by the same wrapper.

### Lookup function (0x8004BD620)

- Takes `edi` = hash key (uint32)
- Reads hash table struct from `[0x801EF7610]`
- If NULL, falls back to alternate lookup at `0x800CE80E0` (via `[0x801EA7EC8]`)
- Otherwise: probes hash table for matching hash, returns the value
- Has **286 direct callers** across eboot.bin — including the init function at
  `0x8013EEFE7`

The init function calls the lookup 15+ times in sequence, each time storing the
result at a different metadata global (e.g., `0x801E51220`, `0x801E51240`,
etc.). All return NULL when the table is empty.

## Task A2: Match against public IL2CPP API surface

### Findings

Based on the structure of the wrapper and the static table:

- The wrapper at `0x800805AE0` matches the behavior of
  **`il2cpp_codegen_register`** — Unity's IL2CPP API that registers a
  metadata entry by name.

- The static table at `0x1CC0080` matches the layout of
  **`Il2CppMetadataRegistration`** (or `Il2CppCodeRegistration`):

  ```
  Il2CppMetadataRegistration {
      const Il2CppType* const* types;        // → 0x8003C68F0 etc.
      const Il2CppMethodDefinition* methods; // → 0x8003C6970 etc.
      ...
      const char* const* typeNames;          // → 0x801B9A697 etc.
      const char* const* methodNames;
      ...
  }
  ```

- The wrapper takes a STRING and inserts it. So Unity's flow is:
  1. Walk `Il2CppMetadataRegistration->types[]` array
  2. For each type, get its name from `typeNames[]`
  3. Call `il2cpp_codegen_register(name, type_info)`
  4. The wrapper hashes the name and inserts into the lookup table

- SharpEmu does NOT call this walker function, so the table stays empty.

## Task B3: Search eboot.bin for secondary init/register entry points

### Findings

- eboot.bin's `e_entry = 0x70` (file vaddr) → runtime `0x800000070`
- DT_INIT at `base+0x10` — the standard module init
- DT_INIT_ARRAY = 0 (EMPTY) — no static constructors
- DT_SCE_INIT_ARRAY = 0 (EMPTY) — no PS5-specific init array
- fini_array has 20 entries (RELATIVE relocations) — destructors only

There is **no separate init/register export** in eboot.bin's dynamic section.
The only entry point is `e_entry`, which on PS5 invokes the standard libc
startup that eventually calls `il2cpp_init`.

The `il2cpp_codegen_register` calls happen INSIDE `il2cpp_init` (or in
functions called by `il2cpp_init`). On SharpEmu, `il2cpp_init` crashes before
reaching the registration code.

## Task B4: Re-parse .sce_process_param / module_param

### Findings (from EXP-038/039)

- eboot ORBI structure (0x60 bytes):
  - +0x00: 0x60 (size)
  - +0x08: "ORBI" magic, version 5
  - +0x10: 0x0700003810590001 (packed flags)
  - +0x58: 0x311

- PRX ORBI (0x20 bytes): same magic, same packed flags, same 0x311

- No PT_SCE_MODULEPARAM, no PT_SCE_PROCPARAM in either module
- Both modules have only PT_SCE_DYNLIBDATA with the ORBI struct

The packed value `0x0700003810590001` does not resolve to a valid code address.
**No alternate startup routine exists in the SCE module parameters.**

## Task C5: Reverse-engineer hash table insert format

### Findings (from disassembling insert `0x800806940` and probe `0x800806800`)

#### Entry layout (0x38 bytes per entry)

```
struct HashEntry {
    uint32_t hash;            // +0x00, 0xFFFFFFFF if empty
    uint32_t padding;         // +0x04
    char     inline_key[16];  // +0x08, used when key length <= 16
    void*    key_ptr;         // +0x18, used when key length > 16
    int8_t   length_byte;     // +0x20, 0x18 - length (for inline keys)
    uint8_t  type;            // +0x28, 1 = inline, 0 = pointer
    uint8_t  padding2[7];     // +0x29-0x2F
    void*    value;           // +0x30
    void*    value2;          // +0x34
};
```

#### Insert algorithm

1. Hash the key (via `0x801704D40`)
2. Compute initial bucket = hash & mask
3. Probe linearly:
   - Read entry.hash at bucket*0x38
   - If hash matches AND key matches: update value, return
   - If hash == 0xFFFFFFFF (empty): insert here, return
   - Otherwise: bucket = (bucket + 1) & mask
4. If probe count exceeds threshold: call resize `0x800806600`

#### Lookup algorithm (in `0x8004BD620`)

Same probing, but returns the value (or NULL if not found).

## Task C6: Manual-fill implementation plan

### Required data (PENDING runtime tracer)

To implement the manual fill, we need:

1. **Static table layout**: Confirm the exact structure of `Il2CppMetadataRegistration`
   at `0x1CC0080`. Specifically:
   - Where is the `types[]` array?
   - Where is the `typeNames[]` array?
   - What's the entry count?

2. **Wrapper calling convention**: Confirm what arguments the wrapper takes.
   Currently we believe:
   - `rdi` = name string pointer
   - But the wrapper also reads other state (e.g., `[rbp - 0x128]` = hash table struct)
   - We need to know if there are other required arguments

3. **Wrapper call site**: Where (if anywhere) is the wrapper called on SharpEmu?
   If it's NEVER called, we need to call it manually.

### Proposed runtime tracer

Install INT3 at three locations:

1. **`0x8007F90A0`** (writer entry) — log when hash table is allocated,
   dump the resulting struct at `[0x801EF7610]`.

2. **`0x800805AE0`** (wrapper entry) — log every call:
   - `rdi` (input string)
   - The string contents (read up to 256 bytes from `rdi`)
   - Caller (from stack)
   - Result

3. **`0x8013EEFE7`** (init function's lookup call) — log every lookup:
   - `edi` (hash key)
   - Result `rax`
   - Which metadata global is being set

Also dump the first 0x100 bytes of the static table at `0x1CC0080` after the
writer completes.

### Manual-fill implementation (after tracer data)

Once we know:
- The static table's `typeNames[]` array address and entry count
- The wrapper's exact calling convention

We can implement a C# function that:
1. Walks the `typeNames[]` array
2. For each name, calls the wrapper via native invocation
3. The wrapper inserts the name→type mapping into the hash table

This bypasses the missing PS5 mechanism and populates the table directly.

## Validation Results

### Confirmed facts

| Item | Value |
|------|-------|
| Hash table pointer address | `0x801EF7610` |
| Hash table struct size | 0x118 bytes |
| Entry size | 0x38 bytes |
| Sentinel (empty entry) | 0xFFFFFFFF |
| Writer function | `0x8007F90A0` (no direct callers) |
| Wrapper function | `0x800805AE0` (no direct callers) |
| Insert function | `0x800806940` (1 caller = wrapper) |
| Resize function | `0x800806600` (20 callers) |
| Lookup function | `0x8004BD620` (286 callers) |
| Hash key generator | `0x800CE3AA0` (294 callers) |
| Static metadata table | `0x1CC0080` (13,920 RELATIVE relocs) |
| ORBI module param | No alt init callback |
| eboot DT_INIT_ARRAY | EMPTY |
| PRX DT_INIT_ARRAY | EMPTY |

### Disproved hypotheses

- ❌ "The hash table at `0x801EF7610` is for P/Invoke only" — it's used for ALL
  metadata lookups (286 callers)
- ❌ "There's a separate PS5 init callback in ORBI" — no such field exists
- ❌ "The wrapper has direct callers we missed" — exhaustively scanned all
  E8/E9 patterns in eboot and PRX

### Confirmed hypotheses

- ✅ "The hash table is allocated by a lazy-init writer" — confirmed by
  `lock cmpxchg` pattern in writer
- ✅ "The wrapper is `il2cpp_codegen_register`" — confirmed by behavior
  (takes string, hashes, inserts)
- ✅ "The static table is `Il2CppMetadataRegistration`" — confirmed by
  structure (pairs of function + string pointers)
