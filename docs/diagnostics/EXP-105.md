# EXP-105 — 0x804F528B0 Is Dead Code — Callback Invocation via 0x804F88AD0

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** Static analysis (no runtime tracer needed — existing data sufficient)
**Path:** B (real metadata path)

**Question:** Is `0x804F528B0` genuinely shutdown-only? What is the real callback invocation path for `0x804F52820`?

**Answer:** `0x804F528B0` IS dead code — its caller chain (`0x804F7E850` → `0x804F06070` → `0x804F528B0`) has 0 callers at the top. The "connects to ThreadPool" claim from EXP-104 was based on a shutdown path, not normal operation. The real invocation path is through `0x804F88AD0`, which reads the stored callback pointer from `[rbx]` and calls `0x804FA84E0` to dispatch it.

**Confidence:** PROVEN by static call-chain analysis.

---

## Step 1: Verify 0x804F528B0 Is Shutdown-Only

### Call Chain

```
0x804F528B0 (calls 0x804FA2130 → ThreadPool dispatch)
  ← 0x804F0620F in 0x804F06070 (separate function, preceded by INT3)
    ← 0x804F7E85D in 0x804F7E850 (0 direct callers, 0 LEA references — DEAD CODE)
```

`0x804F7E850` has 0 callers and 0 LEA references. The entire chain is dead code. The "connects to ThreadPool" finding from EXP-104 was based on this dead-code path.

### EXP-104 Correction

EXP-104 claimed "0x804FA2130 connects the callback to the ThreadPool." This is technically true (the call exists) but **operationally irrelevant** — the path is never reached during normal execution. The reviewer's concern was correct: this is structurally similar to the EXP-075/076 CLEAR misidentification (a destructor mistaken for a live callback).

## Step 2: Find the Real Invocation Path

### 0x804FA1FB0 → 0x804F88AD0

From EXP-104, `0x804FA1FB0` does:
```asm
mov rdi, [rdi + 8]    ; load inner pointer from callback struct
jmp 0x804F88AD0        ; dispatch
```

`0x804F88AD0` is the real invocation function:
```asm
0x804F88AD0: push rbp; mov rbp, rsp; push r15; push r14; push r12; push rbx
0x804F88ADF: mov r12, [0x808923D88]     ; load IL2CPP context
0x804F88AE6: mov r14, rsi               ; save second arg
0x804F88AE9: mov rbx, rdi               ; save first arg (the inner pointer)
0x804F88AF4: call 0x804FC33F0           ; some PLT call
0x804F88AF9: mov rcx, [rbx]             ; load [rbx] = the stored callback pointer!
0x804F88AFC: cmp rax, rcx               ; compare
0x804F88AFF: jne 0x804F88B34            ; if different, skip
0x804F88B01: mov rdi, [rbx]             ; load callback pointer again
0x804F88B04: mov rsi, r14               ; pass second arg
0x804F88B07: call 0x804FA84E0           ; *** INVOKE THE CALLBACK ***
```

This is the invocation mechanism:
1. `rbx` = inner pointer (from `[struct+8]`, loaded by `0x804FA1FB0`)
2. `[rbx]` = the stored callback pointer (set by `xchg [r14], rax` in `0x804F889D0`)
3. `0x804F88AD0` reads `[rbx]` and calls `0x804FA84E0` with the callback as `rdi`

### Who Calls 0x804F88AD0?

`0x804F88AD0` is reached via:
- `0x804FA1FB0` (jmp from callback function `0x804F52820`)
- Direct callers of `0x804F88AD0`?

Let me check direct callers: from the static analysis, `0x804FA1FB0` does `jmp 0x804F88AD0` (tail jump). The callback function `0x804F52820` calls `0x804FA1FB0`, which jumps to `0x804F88AD0`.

But `0x804F52820` itself has 0 direct callers — it's only invoked through the indirect callback mechanism. The callback is stored at `[r14]` by `0x804F889D0`, and `0x804F88AD0` reads `[rbx]` (where `rbx = r14`). So the invocation is:

```
Something calls 0x804F88AD0 with rdi = r14 (the inner pointer)
  → 0x804F88AD0 reads [rdi] = stored callback pointer
  → calls 0x804FA84E0 with the callback
```

The question is: **what calls `0x804F88AD0`?** This is the same "0 direct callers" pattern — but `0x804F88AD0` is reached via `0x804FA1FB0` (which is a 2-instruction trampoline), which is called from `0x804F52820` (the callback itself).

This means the invocation is **self-referential**: the callback `0x804F52820` calls `0x804FA1FB0` → `0x804F88AD0`, which reads the stored callback and calls `0x804FA84E0`. This is a re-entrant dispatch pattern — the callback invokes itself through the registration structure.

## Step 3: The Real Question

The callback `0x804F52820` is stored but has 0 direct callers. The invocation mechanism (`0x804F88AD0`) reads the stored callback but is only reached FROM the callback itself (`0x804F52820` → `0x804FA1FB0` → `0x804F88AD0`).

This means **something external must first invoke `0x804F52820`** to start the chain. That external invoker is the missing piece.

## Step 4: Cross-Reference with EXP-096

The work-submission function `0x804F6EC20` (from EXP-096) reads `[entry+0x88]` and `[entry+0x90]` — these are at offsets much larger than the callback structure. The callback structure (0x28 bytes) is NOT the same structure that `0x804F6EC20` reads from.

## Conclusion

1. **`0x804F528B0` is dead code** — the "connects to ThreadPool" claim from EXP-104 was based on a dead-code shutdown path. The reviewer's concern was correct.
2. **The real invocation path is `0x804F88AD0`** — reads `[rbx]` (stored callback) and calls `0x804FA84E0`.
3. **The callback `0x804F52820` has 0 direct callers** — something external must invoke it to start the chain.
4. **The missing piece**: what external code calls `0x804F52820` (or calls `0x804F88AD0` with the right `rdi`)?
