## Quick Check Results

### Check 1: SHARPEMU_SEMA_FAST_PATH setting

**FACT:** `SHARPEMU_SEMA_FAST_PATH=0` was set (proper blocking mode).

**Evidence:** WaitSema calls show proper blocking behavior:
- 20 WaitSema calls returned READY (semaphore had count available)
- 20 WaitSema calls BLOCKED (semaphore count was 0, thread blocked)
- This is NOT fast-path behavior (fast-path would return immediately always)

### Check 2: Is sceKernelSignalSema ever called?

**FACT:** `sceKernelSignalSema` (NID `4czppHBiriw`) is **NEVER called** — 0 occurrences in the entire 8,768-line log.

**Evidence:**
- `grep -c "4czppHBiriw" /tmp/exp060_logs/baseline_run2.log` = 0
- `grep -c "sceKernelSignalSema" /tmp/exp060_logs/baseline_run2.log` = 0
- The NID never appears in import traces, resolver traces, or any other log line

**PROVEN:** This is a genuine deadlock, not a fast-path artifact. Workers wait, nothing signals.

### Check 3: Is this the same semaphore pattern as EXP-036?

**PARTIALLY:** The mechanism is the same (worker pool waiting for tasks), but the context is different:

- **EXP-036:** Workers spun because `FAST_PATH=1` made WaitSema return immediately. Fix: set `FAST_PATH=0`.
- **EXP-062:** `FAST_PATH=0` is set. Workers properly block. But **nothing calls SignalSema** to wake them.

The difference: In EXP-036, the signaling side existed but workers couldn't wait properly. Here, workers wait properly but the signaling side never fires.

## Root Cause Analysis

### Crash Chain (Rule 003 format)

```
il2cpp_init completes successfully
↓
Unity runtime begins initialization
↓
AssetGarbageCollectorHelper worker threads created (13 threads)
↓
Workers call sceKernelWaitSema (waiting for task assignment)
↓
Main thread creates final worker thread (entry 0x804F88AA0 in PRX)
↓
Main thread also calls sceKernelWaitSema (handle 0x83)
↓
Nothing ever calls sceKernelSignalSema
↓
All threads blocked → 20s stall → process exit
```

### Key Evidence

| Metric | Value |
|--------|-------|
| WaitSema calls | 35 (20 returned, 15 blocked permanently) |
| SignalSema calls | **0** (NEVER called) |
| Blocked threads | 14 (13 AssetGarbageCollectorHelper + 1 main) |
| Semaphore handles waited on | 0x5C, 0x5E, 0x60, 0x62, 0x64, 0x66, 0x68, 0x6A, 0x6C, 0x6E, 0x70, 0x72, 0x74, 0x83 |
| Main thread blocked at | ret=0x804FB5BAF (PRX code, post-il2cpp_init) |
| Worker thread blocked at | ret=0x800AA0207 (eboot code) |
| SignalSema NID | 4czppHBiriw (implemented in SharpEmu, but never called by game) |
| WaitSema NID | Zxa0VhQVTsk (implemented, called 35 times) |

### Why SignalSema is never called

**UNKNOWN** — requires further investigation. Possible causes:

1. **HYPOTHESIS:** The code that should signal runs after an HLE function that returns an error, causing Unity to take an error path that skips signaling
2. **HYPOTHESIS:** A required HLE function (not yet identified) is missing, and its absence prevents the signaling code from executing
3. **HYPOTHESIS:** The Unity runtime initialization sequence has a prerequisite that SharpEmu doesn't satisfy, causing the init to stall before reaching the signaling stage
4. **HYPOTHESIS:** A file I/O operation (e.g., loading a Unity asset bundle) fails silently, and Unity's error handling skips the worker dispatch

## Confirmed Findings

1. **SHARPEMU_SEMA_FAST_PATH=0 is set** — proper blocking mode (not fast-path)
2. **sceKernelSignalSema is NEVER called** — 0 occurrences in entire log
3. **14 threads blocked on sceKernelWaitSema** — genuine deadlock
4. **SignalSema IS implemented in SharpEmu** (NID `4czppHBiriw`, in `KernelSemaphoreCompatExports.cs`)
5. **0 unresolved imports** — all NIDs resolved successfully
6. **IL2CPP init completed successfully** — this is a post-IL2CPP issue
7. **EXP-060 eboot SHA256 confirmed** — `d17fba4a...6d80b6c` (correct Yatzi eboot)

## Disproven Hypotheses

1. ❌ Fast-path is causing the stall — `FAST_PATH=0` is set, proper blocking confirmed
2. ❌ SignalSema is not implemented — it IS implemented, just never called by the game
3. ❌ This is the same issue as EXP-036 — different context (EXP-036 was spin, this is deadlock)
