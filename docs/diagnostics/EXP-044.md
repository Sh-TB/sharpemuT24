# EXP-044 — Investigate Missing PS5 PRX Initialization / module_start Execution

## Date: 2026-07-30
## Status: COMPLETE — INT3 is padding (not module_start), fini_array has 11 entries

---

## Executive Summary

The INT3 at PRX `base+0` is **ELF alignment padding**, NOT a module_start
function. The PRX has `e_entry=0` which points to padding. SharpEmu's
SIGTRAP recovery (treating it as a no-op) is **correct behavior**.

**New finding:** The PRX DT_INIT iterates a **fini_array** with 11 entries
that have RELATIVE relocations. These entries are **non-zero at runtime**
and ARE called by the DT_INIT. However, these PRX functions don't write
to `0x801E9DF28` or `0x801E51240` (both are eboot.bin globals with 0 PRX
references).

The missing pre-init mechanism remains unidentified. The circular
dependency (il2cpp_init needs 0x801E51240, which is set after il2cpp_init)
cannot be resolved without understanding what sets 0x801E51240 on real PS5.

---

## Task 1 — DT_INIT → base+0 INT3 Analysis

### INT3 is ELF padding
- `base+0` has **16 INT3 bytes** (0xCC) in the ELF file
- `e_entry = 0` (points to padding, NOT a function)
- `DT_INIT = 0x10` (first real code at `base+0x10`)
- The INT3 is standard ELF alignment between header and first function

### DT_INIT flag behavior
- Flag at `[0x808923E90]` has RELATIVE relocation (addend `0xA212F0`)
- Runtime value: `0x80D6F62F0` (a data POINTER, not a boolean)
- `cmp [flag], 0` is ALWAYS non-zero → DT_INIT always jumps to `base+0`
- On real PS5: jump to INT3 = breakpoint → kernel skips → returns 0
- On SharpEmu: SIGTRAP → recovered → returns 0
- **Both behaviors are equivalent** — the module_start doesn't exist

### Conclusion
The PRX has **NO module_start function**. `e_entry=0` = padding.
SharpEmu's behavior is correct. The missing pre-init is NOT module_start.

### Fini_array (discovered)
The DT_INIT code iterates a fini_array at `0x8089247D8` backwards.
This array is NOT declared via `DT_FINI_ARRAY` but is hardcoded in the
DT_INIT function. It has **11 entries** with RELATIVE relocations.

## Task 4 — Registration List Population

### Runtime verification
```
[EXP044-FINI_ARRAY] All 16 checked entries are NON-ZERO at runtime
```

SharpEmu correctly applies the RELATIVE relocations for the fini_array.
The DT_INIT calls these 11 functions during PRX module initialization.

### Fini_array function analysis
- All 11 functions are in the PRX code segment
- **None** write to `0x801E9DF28` (registration list head)
- **None** write to `0x801E51240` (metadata global)
- The PRX has **0 references** to any eboot.bin global

### Registration list remains NULL
The fini_array functions don't populate the registration list.
The list at `[0x801E9DF28]` starts as NULL and is populated by
eboot.bin's registration functions during the init function's iterator.

## Task 6 — Hash Table Workaround (not viable)

### Problem
The hash table at `0x801EF7610` has entries initialized to `0xFFFFFFFF`.
To pre-populate it, we need:
1. The hash function (`0x800ce3aa0`) to compute keys
2. The metadata entries from the table at `0x1CC0080`
3. The 12-byte entry format (hash, key, value)

### Assessment
- The metadata table at `0x1CC0080` has 13,905 RELATIVE relocations
- These point to function pointers and string names
- Mapping these to hash table entries requires understanding the
  IL2CPP metadata registration format
- This is too complex for a workaround without reference documentation

## Task 7 — Fix Comparison

### Option A: Correct Fix (implement missing PS5 initialization)
**Description:** Find and implement the PS5 mechanism that sets `0x801E51240`
before il2cpp_init.

**Advantages:**
- Correct behavior matching real PS5
- Works for all IL2CPP games
- No game-specific hacks

**Disadvantages:**
- The mechanism is still unknown
- Requires reverse-engineering PS5 SDK runtime
- May need significant SharpEmu loader changes

### Option B: Workaround (pre-populate metadata)
**Description:** Manually set `0x801E51240` to a valid metadata pointer
before il2cpp_init runs.

**Advantages:**
- Quick to implement
- Can test if the rest of the boot works

**Disadvantages:**
- Don't know the correct value
- Previous attempt (hash table struct) cleared original crash but
  caused new crash at `0x8007E1965`
- Game-specific, not a general fix

### Recommendation
Continue investigating Option A. The key question is: **what sets
`0x801E51240` on a real PS5?** The answer is likely in the PS5 SDK's
runtime initialization code, which runs before the game's init function.

## Task 8 — Downstream Validation

### Current state
```
0x801E51240 = 0x0 (NULL)
crash at 0x80135DE83 (unchanged)
BOOT_STAGE_4 = blocked
```

### New crash at 0x8007E1965 (from EXP-040 workaround)
This crash appeared when `0x801E51240` was set to the hash table struct.
It's a **different metadata dependency** — the hash table struct doesn't
have valid fields at `+0x90`, `+0x98`, `+0xa0`. This confirms that
`0x801E51240` must point to a **real metadata structure**, not just
any non-zero value.

## Key Findings Summary

1. **INT3 at PRX base+0 is ELF padding** — not a module_start function
2. **SharpEmu's SIGTRAP recovery is correct** — matches PS5 behavior
3. **PRX fini_array has 11 entries** with RELATIVE relocations — all called by DT_INIT
4. **Fini_array functions don't write to eboot.bin globals** — PRX has 0 references
5. **The missing pre-init mechanism is still unknown** — not module_start, not fini_array, not relocation
6. **0x801E51240 must point to a real metadata struct** — dummy values cause new crashes
