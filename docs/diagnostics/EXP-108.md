## The Pattern (Reviewer's Point 1)

The reviewer identified that the investigation is recursing through the same "X is registered/exists but nothing invokes it" pattern for the third time:

1. `0x804F52820` (EXP-104/105) — registered, never invoked
2. `0x804FA1FE0` (EXP-106) — registered, never invoked
3. `0x804F88AD0` (EXP-107/108) — 0 direct callers, never reached

This suggests the actual missing piece is NOT any single function call — it's a **class of invocation mechanism** that's absent. The most likely explanation is a **shared dispatcher/scheduler loop** (a "run pending callbacks" pump) that would invoke these callbacks as part of a generic callback list iteration. That pump itself is never entered.

## What This Means

The ThreadPool deadlock is caused by a **missing runtime event/scheduler** that should:
1. Iterate registered callbacks
2. Invoke `0x804F88AD0` (or `0x804FA1FB0`) for each pending callback
3. This would trigger `0x804FA1FE0` → `0x804F9FA80` → `0x804F6EC20` → `SignalSema`

Without this scheduler/dispatcher running, no callbacks are ever invoked, no work is submitted, and the ThreadPool deadlocks.
