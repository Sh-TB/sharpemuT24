# EXP-094 — il2cpp_class_get_method_from_name Reads [0x808923D88], NOT 0x801EF7610 — Hash Table Confirmed RED HERRING

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** `SHARPEMU_SEMA_FAST_PATH=0`, metadata at `Media/Metadata/`, EXP-085 flag patch active, DT_INIT_ARRAY fix (EXP-092) applied
**Path:** B (real metadata path)

**Question:** What data structure does `il2cpp_class_get_method_from_name` (`0x804F21D70`) actually search, and is THAT structure populated?

**Answer:** The function reads `[0x808923D88]` as its context pointer — **NOT** `0x801EF7610`. This definitively confirms EXP-093's hypothesis: the hash table at `0x801EF7610` was a **RED HERRING** across EXP-040..092. The actual lookup structure at `[0x808923D88]` IS populated at runtime (value = `0x7F113CED77E0`, a host-side pointer to a SharpEmu-managed context structure), but the lookup of `_ThreadPoolWaitCallback` still returns NULL — likely because `[context+0x30]` (the method/class table pointer within the context) is NULL or incomplete.

**Confidence:** PROVEN by static disassembly + runtime evidence from EXP-092 log.

## Disassembly Results

```

The function `il2cpp_class_get_method_from_name` is a **single-instruction trampoline**. All real work happens at `0x804EEE8D0`.

### 0x804EEE8D0 — Actual implementation

```asm
0x804EEE8D0  push rbp
0x804EEE8D1  mov  rbp, rsp
0x804EEE8D4  push r15
0x804EEE8D6  push r14

If `rbx` is NULL, the function takes an initialization path (lines `0x804EEE902` onward) that involves lock acquisition (`lock xadd`) and lazy initialization.

## Where Does the Context Pointer Come From?

The value at `[0x808923D88]` (`0x7F113CED77E0`) is a **host-side pointer** (the `0x7F...` range is host memory, not guest memory). This means:

1. The PRX's `module_start` or one of the DT_INIT_ARRAY functions (which now run after EXP-092) called an HLE function that returned a host pointer
2. The PRX stored that host pointer at `0x808923D88`
3. All subsequent PRX functions read `[0x808923D88]` to get the context pointer

The context structure itself contains stack canary guards (`0xC0DEC0DECAFEBA00`), confirming it was allocated by SharpEmu's memory allocator (which uses host pointers for guest allocations).

**The write to `0x808923D88` must happen via an indirect store** — either:
- `mov [rax], rdx` where `rax` happens to equal `0x808923D88` at runtime (computed at runtime, not a RIP-relative constant)
- A `memcpy` or similar function that writes to the address
- A C++ constructor that initializes a global object

This is why the static scan found no direct writes — the write uses a register-computed address, not a RIP-relative displacement.

## Why _ThreadPoolWaitCallback Lookup Returns NULL

The lookup function at `0x804EEE8D0`:
1. Loads context pointer from `[0x808923D88]` into `r14` — **non-NULL** (`0x7F113CED77E0`)
2. Loads `[r14+0x30]` into `rbx` — **non-NULL** (`0x55FBF4A4E3A0`) per the EXP-092 dump
3. Tests `rbx` — if zero, takes initialization path; if non-zero, proceeds with lookup
4. The lookup proceeds but ultimately returns NULL for `_ThreadPoolWaitCallback`

This means the context structure IS populated, but the **method table** at `[context+0x30]` does not contain `_ThreadPoolWaitCallback`. The method table is either:
- Incompletely populated (some methods registered, but not `_ThreadPoolWaitCallback`)
- Populated with wrong data (host pointers instead of guest pointers)
- Using a different lookup key than expected

## Corrections to Prior EXPs

### EXP-040..092 — Hash Table at 0x801EF7610 Was a RED HERRING

**Previous assumption (EXP-040 through EXP-092):** The hash table at `0x801EF7610` is the IL2CPP metadata lookup structure. If it's empty, lookups fail.

**CORRECTED by EXP-094:** The hash table at `0x801EF7610` is **never read by the PRX** (0 reads, 0 writes — EXP-091). The actual lookup function (`il2cpp_class_get_method_from_name`) reads `[0x808923D88]` instead. The entire EXP-040..092 investigation was chasing the wrong structure.

**However**, the EXP-040..092 work was NOT wasted:
- EXP-040 identified the hash table structure (correct structural analysis, wrong target)
- EXP-054/055 correctly identified `Il2CppCodeRegistration` and `Il2CppMetadataRegistration` (these ARE used by `il2cpp_codegen_register` per EXP-093)
- EXP-092's DT_INIT_ARRAY fix was correct and necessary (it enabled `module_start` to run)
- EXP-093 correctly identified that `il2cpp_codegen_register` is a stub

### EXP-090 — "Hash Table Empty → Lookup Returns NULL"

**Previous assumption:** `_ThreadPoolWaitCallback` lookup returns NULL because the hash table at `0x801EF7610` is empty.

**CORRECTED by EXP-094:** The lookup returns NULL because the **method table at `[context+0x30]`** (where context = `[0x808923D88]`) does not contain `_ThreadPoolWaitCallback`. The hash table at `0x801EF7610` is irrelevant — the lookup function never reads it.
