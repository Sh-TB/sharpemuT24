# EXP-104 — Callback Structure Connected to ThreadPool — Invocation Path Is Indirect-Only

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** Static analysis + runtime evidence from EXP-103
**Path:** B (real metadata path)

**Question:** What structure is at `0x20337660`, and what code reads `[struct+0]` or `[struct+0x10]` to invoke the callback?

**Answer:** The callback structure (0x28 bytes, allocated by `0x804F527C0`) is stored at global `0x808B54898`. The callback function `0x804F52820` is registered via `0x804FA20E0` and stored inside the structure. Two functions read the structure: `0x804FA1FB0` (reads `[+8]`, jumps to `0x804F88AD0`) and `0x804FA2130` (reads `[+0x10]`, calls `0x804F6E510` — the ThreadPool dispatch). The callback `0x804F52820` has **0 direct callers** — it's only reachable via the indirect callback mechanism that the registration system sets up.

**Confidence:** PROVEN by static analysis (structure allocation, field layout, reader functions, call chain to ThreadPool dispatch).

## Readers of the Structure

Only 3 reads of global `0x808B54898` exist, all in function `0x804F527C0`:

### Reader 1: `0x804F52834` (in callback function `0x804F52820`)

```asm
0x804F52834: mov rdi, [0x808B54898]  ; load structure
0x804F52849: call 0x804FA1FB0         ; dispatch via structure
```

`0x804FA1FB0` does: `mov rdi, [rdi+8]; jmp 0x804F88AD0` — loads the inner pointer and dispatches.

### Reader 2: `0x804F528D0` (in shutdown function `0x804F528B0`)

```asm
0x804F528D0: mov rdi, [0x808B54898]  ; load structure
0x804F528D7: call 0x804FA2130         ; dispatch via structure
```

`0x804FA2130` does:
```asm
mov rdi, [rdi+0x10]     ; load callback function (0x804FA1FE0)
mov esi, 0xFFFFFFFF     ; arg: -1
mov edx, 1              ; arg: 1
call 0x804F6E510        ; *** CALLS THREADPOOL DISPATCH! ***
```

**This is the connection to the ThreadPool!** `0x804FA2130` reads `[struct+0x10]` (the callback function `0x804FA1FE0`) and calls `0x804F6E510` (the ThreadPool dispatch function from EXP-088).

### Reader 3: `0x804F528DC` (in shutdown, frees the structure)

```asm
0x804F528DC: mov rbx, [0x808B54898]  ; load structure
0x804F528EB: call 0x804FA1AB0         ; some cleanup
0x804F528F3: call 0x804FC2C80         ; free the structure
```

## The Callback Function `0x804F52820`

The callback registered via `0x804FA20E0` is `0x804F52820` (loaded via `lea rsi, [rip+0x38]` at `0x804F527E1`).

**Direct callers of `0x804F52820`: 0** — it's only reachable via the indirect callback mechanism.

The callback function:
1. Calls `0x804F70CD0` — gets some context
2. Calls `0x804F76190` — processes something
3. Loads the structure from `0x808B54898`
4. Calls `0x804FA1FB0` — dispatches via `[struct+8]`
5. Calls `0x804F9FA70` — another operation
6. Checks a flag at `0x808B548A0`
7. Loops or exits

## Cross-Reference with EXP-096

The work-submission function `0x804F6EC20` reads `[entry+0x88]` and `[entry+0x90]` — offsets much larger than the callback structure's fields (+0x00, +0x10, +0x18, +0x20). The callback structure (0x28 bytes) is NOT directly consumed by `0x804F6EC20`.

However, `0x804FA2130` (a reader of the callback structure) calls `0x804F6E510` — the **ThreadPool dispatch function** that contains the `WaitSema(0xA6)` call. This means the callback structure IS connected to the ThreadPool, but through `0x804FA2130`, not directly through `0x804F6EC20`.

## Why the Callback Is Never Invoked

The callback `0x804F52820` has 0 direct callers. It's registered via the indirect callback mechanism, but the code that should INVOKE it (read the stored callback pointer and call it) is itself only reachable indirectly.

The `0x804FA2130` function (which calls ThreadPool dispatch `0x804F6E510`) is called from `0x804F528D7` — inside the shutdown/cleanup path (`0x804F528B0`), NOT during normal operation. During normal operation, the callback `0x804F52820` should be invoked by the registration system's callback dispatch mechanism — but that mechanism appears to be the one set up by `0x804F889D0` (the registration helper), which stores the callback at `[r14]` via `xchg`.

## Conclusion

The callback IS stored correctly at a valid address. The structure IS connected to the ThreadPool (via `0x804FA2130` → `0x804F6E510`). But the callback function `0x804F52820` is never invoked because:
1. It has 0 direct callers
2. The indirect invocation mechanism (whatever reads the stored callback and calls it) is not identified yet
3. The `0x804FA2130` path (which connects to ThreadPool) is in the shutdown path, not the normal operation path
