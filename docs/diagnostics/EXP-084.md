# EXP-084 — Metadata List Flag Bug: Premature Searchable Entries

**Identity:** Yatzi / PPSA17697 / verified
**Configuration:** `SHARPEMU_SEMA_FAST_PATH=0`
**Resumes:** EXP-039/040/041/046 (hash table population thread, abandoned when EXP-061 found wrong dump)

**Question:** What key does hash_lookup search for, and why are the hash table entries empty?

**Answer:** The crash is NOT caused by empty hash table entries. It is caused by **prematurely searchable metadata list entries**. The metadata list at `[0x801EA4E80]` has entries with `flag=0x00` at offset `+0x19`, which causes `metadata_lookup` (`0x800C66B40`) to search them and return a non-zero result. On real PS5, these entries would have `flag!=0` (not searchable), causing the lookup to return 0 and the callback to take a safe code path.

**Confidence:** PROVEN by static analysis (metadata_lookup disassembly showing flag check) + runtime evidence (flag=0x00 in dump, non-zero return value).

## Root Cause

### The metadata list flag at `[entry+0x19]` is 0x00 (searchable) when it should be non-zero (not searchable).

**Evidence:**

1. **metadata_lookup disassembly** (`0x800C66B40`):
   ```
   0x800C66B4F: cmp byte [rdx+0x19], 0   ← check flag
   0x800C66B53: je 0x800C66B58           ← if flag==0, CONTINUE (search)
   0x800C66B55: xor eax, eax             ← if flag!=0, return 0 (NULL)
   0x800C66B57: ret
   ```
   - `flag==0` → lookup searches the list → finds match → returns non-zero
   - `flag!=0` → lookup returns 0 immediately → no crash

2. **Runtime dump** (from `EXP046-META_ENTRIES`):
   ```
   node=0x000000060011BD50 flag=0x00 key1=... key2=... fn=0x0000000801EA5180
   ```
   - `flag=0x00` → entry IS searchable → lookup finds it → returns non-zero

3. **metadata_lookup returns non-zero**:
   ```
   [EXP046-CRASH_PATH_LOOKUP] rax=0x0000000801EC0C78 (metadata lookup result)
   ```
   - On real PS5, this would return 0 (flag!=0 → early exit)

4. **Metadata global is NULL**:
   ```
   [0x801E51240] = 0x0000000000000000
   ```
   - crash_func reads this NULL → `[NULL+0x98]` → SIGSEGV

### Why the flag is 0x00

The registration iterator (`0x800B8D530`) populates the metadata list during the init function's first-time path. It adds entries with `flag=0x00` (searchable). On real PS5, either:
- The entries are added with `flag=0x01` (not searchable) initially, then set to `0x00` after il2cpp_init completes
- OR the entries don't exist yet (list is empty) at this point in the init sequence

On SharpEmu, the entries exist with `flag=0x00` too early, causing the lookup to find them before `0x801E51240` is set.

## Fix Location

**The fix is to set `[metadata_list_entry+0x19] = 1` (non-zero) for all entries before il2cpp_init is called.**

This makes `metadata_lookup` return 0 (matching real PS5 behavior), preventing the callback from calling `crash_func`, allowing `il2cpp_init` to complete, and allowing the hash_lookup at `0x8013EEFE7` to run and set `[0x801E51240]` to a valid value.

### Implementation options:

**Option A (simplest, diagnostic):** In SharpEmu's HLE, after the registration iterator runs but before il2cpp_init, iterate the metadata list at `[0x801EA4E80]` and set `[entry+0x19] = 1` for each entry.

**Option B (most correct):** Find what SharpEmu HLE function causes the registration iterator to add entries with `flag=0x00` instead of `flag=0x01`. The registration iterator at `0x800B8D530` calls registration functions via `[rcx]`. One of these functions may be an HLE stub that should set `flag=0x01` but doesn't.

**Option C (code patch):** Patch `metadata_lookup` at `0x800C66B4F` to always return 0 (NOP the flag check + force `xor eax, eax`). This is a diagnostic patch, not a permanent fix.

### Recommended: Option A first (diagnostic), then Option B for permanent fix.

## Missing Registration Path

The exact missing registration path is:
1. The init function (`0x8013EB6B0`) calls the registration iterator (`0x800B8D530`)
2. The iterator populates the metadata list with `flag=0x00` entries
3. **Something should set `flag=0x01` (non-searchable) before il2cpp_init runs**
4. That "something" is either:
   - A SharpEmu HLE function that initializes the flag (missing)
   - A guest code path that runs between the iterator and il2cpp_init (not reached)
   - The iterator itself should set `flag=0x01` but doesn't (SharpEmu behavior differs from PS5)
