# EXP-081 — Why Worker Task Function Pointers Are NULL

**Identity:** Yatzi / PPSA17697 / verified (SHA256 `d17fba4abc7858495c6f6e207b5c38961eec0c4639b04369f0c7b06866d80b6c` — PASS)

**Question:** Why are worker task function pointers `[worker+0xF8]` NULL in the clean run?

**Answer:** `SHARPEMU_SEMA_FAST_PATH=1` causes `sceKernelWaitSema` to return immediately without blocking, making workers race ahead of the task dispatcher and call `[worker+0xF8]=NULL` before any task is assigned. Setting `SHARPEMU_SEMA_FAST_PATH=0` (proper blocking mode) completely eliminates this crash.

**Confidence:** PROVEN by runtime evidence (FAST_PATH=0 run with 0 NULL executes, il2cpp_init called, Unity job system started).

## Task 1 — Worker Descriptor Layout

From the EXP035-NULL crash dump (worker `0x6006D0FF0`, clean run with FAST_PATH=1):

```
+0x020: 0x6006D0FF0     (self-pointer)
+0x028: 0x800AA0170     (dispatch loop function — [worker+0x28])
+0x060: 0x0E00000000    (byte flags)
+0x068: 0x0D0000005C    (wait_sema handle = 0x5C)
+0x070: 0xFFFFFFFF      (work count = -1, decremented from 0)
+0x0B0: 0x0D0000005D    (signal_sema handle = 0x5D)
+0x0F8: 0x0000000000000000  (task function ptr = NULL ← CRASH CAUSE)
+0x100: 0x0000000000000000  (task arg = NULL)
+0x108: 0x6006D0F01     (byte flag 0x01 = work pending + heap garbage)
```

`worker_create` (`0x800A9F9A0`) initializes the descriptor:
- `[rbx+0xF0]` = 0 (via `mov qword [rbx+0xF0], 0` at `0x800A9FD0F`)
- `[rbx+0xF8]` = 0 (via `mov byte [rbx+0xF8], 0` at `0x800A9FCAE` — **byte only**, upper 7 bytes from zeroed allocation)
- `[rbx+0x100]` = 0 (via `mov qword [rbx+0x100], 0` at `0x800A9FD21`)
- `[rbx+0x108]` = 1 (via `mov byte [rbx+0x108], 1` at `0x800A9FAED` — **byte only**)

The task function pointer `[worker+0xF8]` is **intentionally NULL at creation** — it's supposed to be filled later by the task dispatcher.

## Task 2 — Who Writes `[worker+0xF8]`?

Static analysis found **473 qword writes** to `[reg+0xF8]` across the EBOOT. The only writes in the relevant code paths:

**worker_create (`0x800A9F9A0`):**
- `0x800A9FCAE`: `mov byte [rbx+0xF8], 0` — initializes to 0 (NULL)

**Task dispatcher (`0x800AC6080`):**
- `0x800AC6DB9`: `mov qword [rcx+0xF8], r15` — assigns task function
- `0x800AC7229`: `mov qword [rcx+0xF8], r15` — assigns task function
- `0x800AC7309`: `mov qword [rcx+0xF8], r12` — assigns task function
- `0x800AC7439`: `mov qword [rcx+0xF8], r12` — assigns task function

The dispatcher is the **only** code that assigns a non-NULL value to `[worker+0xF8]`. It is registered at slot `0x801CEEA08` via `R_X86_64_RELATIVE` relocation. No code directly reads this slot — it's called indirectly through a vtable/computed pointer.

## Task 3 — Dispatch Loop Control Flow

The dispatch loop at `0x800AA0170` (called via `[worker+0x28]`):

```
0x800AA019A: cmp byte [rbx+0x108], 0    ; check work-pending flag
0x800AA01A1: je 0x800AA0239             ; if 0 (no work), EXIT
0x800AA01B5: lock xadd [rbx+0x70], -1   ; decrement work count
0x800AA01BC: jle 0x800AA01F7            ; if was ≤0, go to WAIT
0x800AA01BE: cmp byte [rbx+0x108], 0    ; re-check flag
0x800AA01C5: je 0x800AA0239             ; if 0 now, EXIT
0x800AA01C7: mov rdi, [rbx+0x100]       ; load task arg
0x800AA01CE: call [rbx+0xF8]            ; *** CALL TASK FUNCTION ***

WAIT:
0x800AA01F7: mov rdi, [rbx+0x68]        ; wait_sema handle
0x800AA01FB: mov esi, 1
0x800AA0202: call sceKernelWaitSema     ; wait for work
0x800AA0207: cmp byte [rbx+0x108], 0    ; re-check after wait
0x800AA020E: jne 0x800AA01C7            ; if still pending, CALL TASK
0x800AA0210: jmp 0x800AA0239            ; else EXIT
```

The crash sequence with FAST_PATH=1:
1. `worker_create` sets `[0x108]=1` (work pending), `[0x70]=0` (no work items), `[0xF8]=NULL`
2. Worker enters dispatch loop, sees `[0x108]!=0`, decrements `[0x70]` to -1
3. Old `[0x70]` was 0 (≤0) → goes to WAIT
4. `sceKernelWaitSema(0x5C)` → **returns immediately** (FAST_PATH=1)
5. Re-checks `[0x108]!=0` (still 1) → jumps to `call [rbx+0xF8]` = NULL → **SIGSEGV**

On real PS5 hardware, step 4 would **block**, giving the main thread time to call `il2cpp_init` → dispatcher → set `[worker+0xF8]` → `SignalSema(0x5C)` → worker wakes with a real task.

## Task 5 — The Fix

**The fix is to set `SHARPEMU_SEMA_FAST_PATH=0` (or unset it).**

`FAST_PATH=1` was introduced in EXP-063 as a workaround for a deadlock reported in EXP-062. EXP-062 reported that with `FAST_PATH=0`, `SignalSema` was "never called" and all threads deadlocked. However, EXP-062's analysis was incomplete — it did not have the EXP035-NULL tracer or the semaphore lifecycle logging that EXP-080/081 have.

With the current codebase (which includes the EXP-065 heap-allocation fix for signal handler context buffers and all the INT3 diagnostic tracers), `FAST_PATH=0` works correctly:
- Workers block on `WaitSema` (no NULL execute crash)
- Workers signal their `signal_sema` when refcount goes negative (18 `SignalSema` calls observed)
- Main thread progresses through `il2cpp_init` → Unity job system → graphics init
- No deadlock occurs

**No code changes needed.** The fix is purely a configuration change: set `SHARPEMU_SEMA_FAST_PATH=0` instead of `1`.

The NOP bypass from EXP-073 remains **removed** (as of EXP-080). It is not needed and should never be re-added.

## New Crash (separate issue, not EXP-081 scope)

With FAST_PATH=0, the game progresses to a **new crash** at `0x80080684D`:

```
0x80080684D: mov r8d, [r15+rcx]    ; r15 = NULL → Access Violation
```

This is a NULL pointer dereference in Unity's IL2CPP metadata iteration (hash table lookup with a NULL base pointer). It is a **separate issue** from the worker NULL `[rbx+0xF8]` problem and should be investigated in EXP-082.

The crash occurs 100,000+ times (recovery loop) at the same address, eventually causing host-side SIGSEGV. The root cause is likely a missing or incorrect IL2CPP metadata HLE function that should return a non-NULL pointer.

## Root Cause

**`SHARPEMU_SEMA_FAST_PATH=1`** is the root cause of the worker NULL `[rbx+0xF8]` crash.

`FAST_PATH=1` makes `sceKernelWaitSema` return immediately without blocking. This breaks the worker-dispatcher synchronization: workers race ahead of the dispatcher, enter the task-call path with `[worker+0xF8]=NULL`, and crash.

`FAST_PATH=0` (proper blocking mode) restores the correct behavior: workers block on `WaitSema`, the main thread runs `il2cpp_init` → dispatcher → assigns tasks → `SignalSema` → workers wake with real task functions.

---

## Permanent Fix

**Set `SHARPEMU_SEMA_FAST_PATH=0`** (or unset the environment variable).

No source code changes are needed. The `FAST_PATH=1` code path in `KernelSemaphoreCompatExports.cs:108-121` should be considered deprecated — it was a workaround for a deadlock that no longer occurs with the current codebase.

The CLI_RUN_COMMANDS.md documentation should be updated to use `SHARPEMU_SEMA_FAST_PATH=0` instead of `1`.
