## 1. Exact dependency identity — what is `[rbx+0x108]` really?

**PROVEN by static analysis (capstone disassembly of all read/write sites):**

`[rbx+0x108]` is a **single-byte flag** on the worker descriptor, not a tagged pointer.

Evidence:
- Every read site uses `cmp byte ptr [rbx+0x108], 0` (e.g. `0x800AA019A`, `0x800AA01BE`, `0x800AA01EC`, `0x800AA0207`).
- Every write site uses `mov byte ptr [rbx+0x108], <imm8>` (e.g. `0x800A9F834` writes 0, `0x800A9FAED` writes 1).
- The flag's semantics:
  - `0` → "no work pending" — worker exits the dispatch loop
  - `1` → "work pending" — worker continues looping (decrement work count, wait, call task)

**This CORRECTS EXP-076's interpretation** that `[rbx+0x108]` is a tagged pointer to the previous worker descriptor. The "untagged pointer 0x6006D1100" observed in EXP-076 was the **64-bit value** stored at `[rbx+0x108]`, but the worker code only ever reads/writes the **lowest byte**. The upper 56 bits are unrelated stale memory that happens to live there because the field is byte-sized inside a larger struct.

## 2. Exact CLEAR callback — what does `0x800A9F750` actually do?

**PROVEN by static analysis (full disassembly, 0x800A9F750..0x800A9F8DA, 394 bytes):**

CLEAR is a **C++ destructor for the worker collection container**, not a "dependency completion callback".

Annotated control flow:

```
0x800A9F750  push rbp/r15/r14/r13/r12/rbx; sub rsp, 8
0x800A9F75E  r12 = *rdi          ; r12 = container's inner object
0x800A9F761  r14 = rdi            ; r14 = container (saved)
0x800A9F764  if (r12 == 0) goto CLEANUP
0x800A9F76D  r15d = [r14+8]       ; save container's size class for free()
0x800A9F771  rbx = [r12+0x20]     ; rbx = container's "primary" sub-object
0x800A9F776  if (rbx == 0) goto SKIP_PRIMARY
0x800A9F77B  rax = *rbx           ; vtable
0x800A9F77E  rdi = rbx
0x800A9F781  call [rax]           ; VIRTUAL DESTRUCTOR call on primary sub-object
0x800A9F783  rdi = rbx; esi = 0x4f
0x800A9F78B  call 0x8007E2280     ; debug-free(rbx, 0x4f)

SKIP_PRIMARY:
0x800A9F790  [r12+0x20] = 0      ; clear primary sub-object slot
0x800A9F799  rax = &sentinel (0x801C29660)
0x800A9F7A0  rdi = [r12+0x38]    ; another sub-object
0x800A9F7A5  if (rdi == sentinel) skip
0x800A9F7AA  esi = [r12+0x4c]
0x800A9F7AF  call 0x8007E2280     ; debug-free
0x800A9F7B4  rdi = &[r12+0x30]   ; mutex
0x800A9F7B9  call 0x801937610     ; scePthreadMutexDestroy(&mutex)
0x800A9F7BE  if (ret != 0) log_error
0x800A9F7E6  if ([r12+0x10] == 0) goto EXIT_LOOP  ; array length
0x800A9F7F2  r13 = 0              ; loop index

LOOP_TOP (0x800A9F827):
0x800A9F827  rax = [r12]          ; array base
0x800A9F82B  rbx = [rax + r13*8]  ; rbx = array[r13] (worker descriptor)
0x800A9F82F  if (rbx == 0) goto LOOP_NEXT

LOOP_BODY:
0x800A9F834  mov byte [rbx+0x108], 0    ; *** CLEAR DEP FLAG ***
0x800A9F83B  eax = 1
0x800A9F840  lock xadd [rbx+0x70], eax  ; atomic refcount inc
0x800A9F845  if (eax < 0) goto SIGNAL_WAIT_SEMA   ; refcount was negative → worker is waiting
0x800A9F849  if (eax >= 0x1FFFF) goto REF_OVERFLOW

MAIN_PATH:
0x800A9F850  rdi = rbx
0x800A9F853  call 0x800BB0860     ; worker_wake(rbx) — Baselib condition-variable notify

0x800A9F86A  eax = [rbx+0x70]
0x800A9F86D  rdi = [rbx+0x68]    ; wait sema handle
0x800A9F871  call 0x8019377D0     ; sceKernelDeleteSema(wait_sema)  ← deletes the 0x5C handle!
0x800A9F876  if ([rbx+0x60] != 0) goto LOOP_NEXT   ; flag: skip buffer free
0x800A9F87C  rdi = [rbx+0x40]
0x800A9F880  esi = [rbx+0x64]
0x800A9F883  call 0x8007E2280     ; debug-free inline buffer
0x800A9F888  jmp LOOP_NEXT

SIGNAL_WAIT_SEMA (0x800A9F88D):  ; refcount was negative
0x800A9F88D  rdi = [rbx+0x68]    ; wait sema handle (0x5C!)
0x800A9F891  esi = 1
0x800A9F896  call 0x8019377B0    ; sceKernelSignalSema(wait_sema, 1)
                                  ; *** wakes the worker so it can observe the destroy ***
0x800A9F89B  jmp MAIN_PATH

REF_OVERFLOW (0x800A9F89D):
0x800A9F89D  ecx = 0xFFFF
0x800A9F8A2  lock cmpxchg [rbx+0x70], ecx
0x800A9F8A7  if (CAS ok) goto MAIN_PATH
0x800A9F8A9  if (eax <= 0x1FFFE) goto MAIN_PATH
0x800A9F8B0  retry CAS

0x800A9F800  rdi = rbx; esi = 0x4f

0x800A9F80D  rax = [r12]
0x800A9F811  [rax + r13*8] = 0   ; array[r13] = NULL
0x800A9F819  r13++

0x800A9F8C0  call 0x8007E2280    ; debug-free(container_inner, size_class)

CLEANUP (0x800A9F8C5):
0x800A9F8C5  [r14] = 0           ; clear container's back-pointer
0x800A9F8CC  ... pop registers; ret
```

Summary of what CLEAR does:
1. Calls the virtual destructor on the container's primary sub-object
2. Frees various sub-objects
3. Destroys the container's mutex via `scePthreadMutexDestroy`
4. Iterates the worker array, for each worker:
   - Clears `[worker+0x108] = 0` (the dep flag)
   - Increments `[worker+0x70]` (refcount)
   - If refcount was negative → signals `[worker+0x68]` (wait sema — wakes worker so it can see destruction)
   - Calls `0x800BB0860(worker)` (Baselib condition-variable notify)
   - Deletes `[worker+0xB0]` (signal sema)
   - Deletes `[worker+0x68]` (wait sema — the **0x5C handle**)
   - Frees the worker descriptor
5. Calls a finalizer on the container inner object
6. Frees the container inner object
7. Clears the container's back-pointer

**This is a textbook C++ destructor for a "WorkerPool" singleton.** It is NOT invoked when an individual worker completes a task — it is invoked when the entire pool is torn down (typically at process exit, via `__cxa_atexit`).

## 3. Callback registration — where is `0x800A9F750` stored/registered?

**PROVEN by static analysis:**

CLEAR's address is **stored at runtime** at address **`0x801EA3230`** by the static-local initialization function at `0x800A9F210`.

Evidence:
- The init function `0x800A9F210` is a `__cxa_guard_acquire`-style once-init:
  ```
  0x800A9F210  cmp byte [rip + 0x13fa7f9], 0   ; guard byte at 0x801EA4210
  0x800A9F217  je 0x800A9F21A                    ; if 0, run init
  0x800A9F219  ret                                ; else return
  ```
- Inside the init body, at `0x800A9F2FF`:
  ```
  0x800A9F2FF  lea rcx, [rip + 0x44a]   ; rcx = 0x800A9F750 (CLEAR)
  0x800A9F306  mov [rip + 0x13f9923], rcx ; *0x801EA3230 = CLEAR
  ```
- The init function `0x800A9F210` itself is stored at runtime at slot `0x801D1C370` by an `R_X86_64_RELATIVE` relocation (addend `0xA9F210`).
- Slot `0x801D1C370` is in the RW data segment (`vaddr 0x1C80000..0x1D1C450`, flags RW).
- No code in the EBOOT directly LEA/MOV-loads slot `0x801D1C370` — it must be accessed indirectly (via a vtable or function-pointer table whose base is computed at runtime).

**Conclusion:** CLEAR is registered as a destructor via the C++ runtime's `__cxa_atexit` mechanism (or Sony's equivalent). It will fire when the worker-pool singleton is destroyed — typically at process exit. It is NOT a runtime callback that fires per-task.

## 4. Completion trigger — what exact function/event should invoke CLEAR?

**PROVEN by static analysis:**

CLEAR is invoked when the worker-pool singleton is **destroyed**. The triggering event is process exit (via `__cxa_atexit`) or an explicit `delete` on the singleton.

There is **no per-task completion callback** that invokes CLEAR. The previous EXP-075/076 interpretation that CLEAR fires "when the previous worker completes" was wrong — CLEAR fires only during pool teardown.

**The real per-task completion mechanism is the TASK DISPATCHER at `0x800AC6080`**, which:
1. Writes `[worker+0xF8]` (task function pointer)
2. Writes `[worker+0x100]` (task argument)
3. Atomically increments `[worker+0x70]` (work-token count)
4. If the worker was waiting (old `[worker+0x70]` was negative), calls `sceKernelSignalSema([worker+0x68], 1)` — **this is the signal on the 0x5C handle that EXP-078 found missing**.

The dispatcher is registered as a function pointer at slot `0x801CEEA08` (via `R_X86_64_RELATIVE` reloc, addend `0xAC6080`). No code in the EBOOT directly LEA/MOV-loads this slot either — it is accessed indirectly through a scheduler singleton's vtable.

## 6. Why `[rbx+0xF8]` stays NULL

**PROVEN by runtime evidence + static analysis:**

`[worker+0xF8]` is set **only** by the task dispatcher at `0x800AC6080` (specifically at instructions `0x800AC7229`, `0x800AC7309`, `0x800AC7439` — three dispatch loops for different task function variants).

Static proof — dispatcher writes `[worker+0xF8]`:
```
0x800AC7229  mov [rcx + 0xf8], r15      ; r15 = task function pointer
0x800AC7230  mov [rcx + 0x100], rax      ; rax = task argument
0x800AC7237  mov eax, 1
0x800AC723C  lock xadd [rcx + 0x70], eax ; atomic inc work count
0x800AC7241  test eax, eax
0x800AC7243  js 0x800AC7260              ; if was negative, signal wait sema
...
0x800AC7260  mov rdi, [rcx + 0x68]      ; wait sema handle
0x800AC7264  mov esi, 1
0x800AC7269  call sceKernelSignalSema    ; *** THIS signals 0x5C ***
```

Runtime proof — dispatcher never reached (EXP-078 log, 5.7M lines):
- `grep "0x800AC6080\|0x800AC7" /tmp/exp078_logs/run1_sema_trace.log` → **0 matches**
- `grep "sema.signal handle=0x0000005C" /tmp/exp078_logs/run1_sema_trace.log` → **0 matches** (CONFIRMED in EXP-078)
- All 14 even handles (`0x5C, 0x5E, 0x60, ..., 0x72`) have **0 signals** in 5.7M lines

Main-thread RIP timeline (PROVEN by grep of EXP-078 log):
| Log line | Event | RIP / caller |
|----------|-------|--------------|
| 1..8640 | Worker creation begins, semaphores 0x5C..0x5D created | `0x800A9F9A0` (worker_create) |
| 8641..8709 | Main thread `sceKernelWaitSema` on each worker's signal sema (0x5D, 0x5F, ...) | caller `0x800A9FC25` |
| 8710..193289 | Worker spin (NOP-bypassed) — 185K lines of `WaitSema(0x60)/SignalSema(0x61)` | caller `0x800AA0207` |
| 193290 | Main thread calls `il2cpp_init` | caller `0x8013ED05D` (EBOOT) |

**Conclusion:** `[worker+0xF8]` stays NULL because the dispatcher (`0x800AC6080`) is never reached. The dispatcher is never reached because the main thread is stuck in the PRX `array_proc` (`0x804F2B4D0` runtime).

**GPU init is downstream of the PRX stall — not causal, not unrelated.** It is purely a victim of the PRX array_proc never returning.

This **RE-CONFIRMS EXP-077's correction** of EXP-076: GPU init is NOT the blocker. The blocker is upstream, in the PRX.

## 8. Root cause — one precise root cause only

**The main thread is stuck inside the IL2CPP PRX's array processor (`array_proc` at PRX vaddr `0x4F2B4D0`, runtime `0x804F2B4D0`) because the array count it was passed (`0x92490068` ≈ 2.45 billion) is corrupted/uninitialized.** The array_proc never returns, so the main thread never reaches the worker dispatcher at EBOOT `0x800AC6080`, so workers' wait semaphores (handles `0x5C, 0x5E, ..., 0x72`) are never signaled, so workers wait forever.

The "dependency at `[rbx+0x108]`" was a red herring — it's a byte flag set to 1 at worker creation and only cleared by the pool destructor. It is NOT the dependency that needs resolving.

The "CLEAR callback" was also a red herring — it's the pool destructor, not a per-task completion callback.

## 9. Permanent fix location — exact SharpEmu HLE/runtime subsystem

**The fix must target the IL2CPP metadata / PRX initializer path, NOT the semaphore subsystem, NOT the GPU subsystem, NOT the worker pool.**

Specifically, the `array_proc` at PRX `0x4F2B4D0` receives its `count` parameter from upstream IL2CPP initialization. The count `0x92490068` is suspiciously close to a heap-pointer-like value (`0x92000000`-ish), suggesting either:
1. **An uninitialized field in the IL2CPP metadata** that SharpEmu's HLE didn't populate correctly (most likely), or
2. **A stubbed IL2CPP HLE function** that returns garbage instead of the real count.

The most likely SharpEmu subsystem to fix:
- **`SharpEmu.HLE/Il2Cpp/`** — the IL2CPP metadata loader / runtime support. The array processor is iterating what should be the IL2CPP metadata's type/method table. If SharpEmu's HLE doesn't fully populate the metadata blob (e.g., `il2cpp_codegen_register` returns a stub instead of registering real types), the count field stays uninitialized and the array processor spins on garbage.
- A secondary suspect is **`SharpEmu.HLE/Aerolib/Aerolib.cs`** — if any of the IL2CPP imports (`il2cpp_*` NIDs) are returning stubs that should return real values, the metadata could be corrupt.

The fix is NOT:
- ❌ Implement `sceVideoOut` / `sceAgc` (GPU is downstream — fixing this won't unblock the PRX)
- ❌ Fix `SHARPEMU_SEMA_FAST_PATH` (FAST_PATH only matters after the dispatcher is reached, which it never is)
- ❌ Remove the NOP bypass (the bypass is masking the symptom; removing it without fixing the PRX will just crash on NULL call)
- ❌ Implement CLEAR as a per-task callback (CLEAR is correctly a destructor — the design is fine)

## 11. No code fix yet — investigation only

EXP-079 is investigation-only. No code changes were made. The NOP bypass at `0x800AA0207` from EXP-073 remains in source — it should be removed in a future EXP only AFTER the underlying PRX array_proc issue is fixed, otherwise removal will cause workers to crash on NULL `[worker+0xF8]` calls.

The next investigation step (EXP-080, not part of this report) should disassemble the PRX at vaddr `0x4F23431` (runtime `0x804F23431`) to identify where the `count=0x92490068` comes from. The most likely candidates are:
